    Claude Code 教程 10：最佳实践¶

    基于实际使用经验总结的效率指南、避坑手册和高级技巧。帮你从"能用"进阶到"用好"。

    一、任务描述最佳实践¶

    1.1 黄金公式：上下文 + 目标 + 约束¶

    好的任务描述应该包含三个要素：

    [上下文] 当前项目的情况
[目标]  你想让它做什么
[约束]  你希望它遵守的限制

    ❌ 糟糕的描述： 

    修一下这个 bug

    ✅ 好的描述： 

    [上下文] 这是一个 FastAPI 项目，auth.py 负责 JWT 验证
[目标]  修复 /api/users/me 端点返回 401 的问题
[约束]  不要改数据库查询逻辑，只检查 token 解析部分
        写完后运行 pytest tests/test_auth.py 验证

    1.2 明确指定范围¶

    Claude Code 有完整的文件访问权限，但它不知道你关心哪些文件。

    ✅ "只修改 src/auth/ 下的文件"
✅ "查看 config.yaml 和 docker-compose.yml，其他文件不用管"
✅ "在现有的 UserService 类中添加方法，不要创建新文件"

❌ "优化一下认证模块"（范围模糊）

    1.3 分步分解复杂任务¶

    对于大型重构，用分步指令比一句话更有效：

    我想重构这个模块，按以下步骤执行：

1. 先阅读 src/parser.py，列出所有超过 50 行的函数
2. 把这些函数提取到独立的子模块中
3. 确保原有测试全部通过
4. 更新 README 中的模块说明

每一步完成后告诉我，我确认后再继续。

    二、CLAUDE.md 文件最佳实践¶

    2.1 根目录 CLAUDE.md：项目级指南¶

    在项目根目录放置 CLAUDE.md，让它了解你的项目：

    # CLAUDE.md - 项目指南

## 技术栈
- Python 3.12 + FastAPI
- PostgreSQL + SQLAlchemy 2.0
- Redis 用于缓存

## 编码规范
- 函数和变量用 snake_case
- 所有注释使用英语
- 新函数必须包含类型注解

## 项目结构
src/
  ├── api/        # 路由定义
  ├── services/   # 业务逻辑
  ├── models/     # SQLAlchemy 模型
  └── utils/      # 工具函数

## 测试
- 测试文件在 tests/ 目录
- 运行测试：pytest tests/ -v

## 注意事项
- 数据库迁移用 alembic，不要手动改 schema
- API 响应统一用 response.py 中的格式

    2.2 子目录 CLAUDE.md：局部约束¶

    在特定子目录可以放置额外的 CLAUDE.md 覆盖或补充根目录的规则：

    my-project/
├── CLAUDE.md              # 全局规则
├── src/
│   ├── CLAUDE.md          # 仅影响 src/ 下的任务
│   └── ...
└── tests/
    └── CLAUDE.md          # 仅影响 tests/ 下的任务

    2.3 规则文件组织¶

    如果你有多个规则文件，用 .claude/rules/ 目录管理：

    .claude/
└── rules/
    ├── python.md          # Python 编码规范
    ├── git.md             # Git 工作流
    └── testing.md         # 测试规范

    在 CLAUDE.md 中引用它们：

    # 项目指南

## 编码规范
参考 .claude/rules/python.md

## Git 工作流
参考 .claude/rules/git.md

    三、权限与安全最佳实践¶

    3.1 权限模式选择¶

    模式 适用场景 安全性
    default 日常开发 ⭐⭐⭐
    acceptEdits 信任 Claude 的修改 ⭐⭐
    dangerFullAccess 全自动 CI/CD ⭐

    建议： 日常使用 default 模式，让 Claude 在执行危险操作前询问你。

    3.2 用 .clauderules 精确控制¶

    在项目根目录创建 .clauderules 文件，精确控制哪些操作需要审批：

    rules:
  - pattern: "**/*.py"
    permission: edit
  - pattern: "database/migrations/**"
    permission: ask
  - pattern: "**/secrets/**"
    permission: deny

    3.3 敏感文件保护¶

    ✅ 在 .gitignore 中排除敏感文件
✅ 用环境变量而非硬编码密钥
✅ 在 CLAUDE.md 中说明哪些文件不要修改
✅ 定期审查 .claude/settings.json 中的权限配置

    四、高效使用技巧¶

    4.1 利用 Slash 命令¶

    命令 用途
    /compact 清理上下文，节省 token
    /clear 清空对话历史
    /vim 进入 Vim 模式编辑
    /model 切换模型
    /cost 查看当前会话消耗

    4.2 上下文管理¶

    Claude Code 的上下文窗口有限，注意：

    ✅ 开始新任务时用 /compact 压缩上下文
✅ 大型项目先用 /init 让 Claude 理解结构
✅ 不要在一个会话中塞入多个不相关的任务
✅ 用 git diff 查看修改后再决定是否需要回滚

    4.3 批处理与管道¶

    Claude Code 可以处理管道和复杂命令：

    # 在对话中让它执行：
grep -r "TODO" src/ --include="*.py" | head -20

# 或者让它生成并执行脚本：
python scripts/generate_report.py --output report.md

    4.4 用 Hook 自动化常见操作¶

    在 .claude/hooks/ 中配置自动化：

    {
  "onSave": [
    { "run": "black {{file}}" },
    { "run": "ruff check {{file}}" }
  ],
  "preCommand": [
    { "run": "git stash" }
  ]
}

    五、常见陷阱与避坑¶

    5.1 ❌ 过度信任自动生成¶

    Claude Code 可能写出看似正确但逻辑有问题的代码：

    ❌ 直接接受所有修改
✅ 用 git diff 审查每一处改动
✅ 运行测试验证
✅ 对于关键业务逻辑，人工 review 必不可少

    5.2 ❌ 模糊的任务导致错误的方向¶

    ❌ "优化性能"
→ 可能优化了错误的函数，或者引入不必要的复杂度

✅ "profile 一下 /api/search 端点，找到最慢的 3 个函数并优化"
→ 目标明确，结果可验证

    5.3 ❌ 忽略上下文限制¶

    ❌ 在已经 50 轮对话的会话中继续新任务
→ 上下文混乱，Claude 可能基于过时的理解作答

✅ 用 /compact 或直接开新会话

    5.4 ❌ 不写 CLAUDE.md¶

    ❌ 每次会话都重复说明项目结构
✅ 写一次 CLAUDE.md，每次自动生效

    5.5 ❌ 在子代理中浪费资源¶

    ❌ 让子代理做简单的文件读写
✅ 子代理适合：独立任务、并行工作、需要不同模型

💡 判断标准：如果任务 < 30 秒，不需要子代理

    六、与版本控制配合¶

    6.1 Git 工作流¶

    # 1. 开始任务前创建分支
git checkout -b feature/add-auth

# 2. 让 Claude Code 在分支上工作

# 3. 完成后检查
git diff
git status

# 4. 满意后提交
git add -A
git commit -m "feat: add JWT authentication"

# 5. 不满意可以回滚
git checkout -- .
git clean -fd

    6.2 让 Claude 帮你写提交信息¶

    请根据当前 git diff 生成一个符合 Conventional Commits 规范的提交信息。
要求：
- type 要准确（feat/fix/refactor/docs/chore）
- description 不超过 72 字符
- body 列出主要变更

    6.3 交互式 Rebase¶

    帮我整理最近 5 个提交：
1. 把 "fix typo" 和 "fix another typo" squash 到前一个提交
2. 把 "wip" 开头的提交 message 改得专业一点
3. 删除那个空的 commit

    七、团队协作最佳实践¶

    7.1 共享规则文件¶

    .claude/
├── rules/
│   ├── team-coding-style.md    # 团队统一的编码风格
│   ├── review-checklist.md     # Code Review 清单
│   └── release-process.md      # 发布流程
└── settings.json               # 团队共享的默认设置

    把这些文件提交到仓库，团队成员使用 Claude Code 时自动遵守团队规范。

    7.2 CLAUDE.md 模板¶

    # CLAUDE.md

## 项目信息
- **名称：** xxx
- **负责人：** @xxx
- **文档：** https://wiki.xxx

## 开发规范
- 代码风格遵循 [xxx 指南](链接)
- PR 必须包含测试
- 使用 Conventional Commits

## 常用命令
- 启动开发服务器：make dev
- 运行测试：make test
- Lint 检查：make lint

    八、性能与成本优化¶

    8.1 模型选择¶

    模型 适用场景 成本
    Claude Sonnet 日常编码、重构、调试 中等
    Claude Opus 复杂架构设计、深度分析 高
    Claude Haiku 简单问答、代码解释 低

    8.2 省钱技巧¶

    ✅ 用 /compact 压缩上下文再继续对话
✅ 简单问题直接用 /model 切换到便宜模型
✅ 一次性描述清楚需求，避免来回对话浪费 token
✅ 定期 /clear 清空不需要的会话
✅ 使用子代理隔离长任务，避免主会话上下文膨胀

    8.3 监控消耗¶

    # 查看当前会话消耗
/cost

# 查看历史消耗（在设置中）
# Settings → Usage → Cost History

    九、调试技巧¶

    9.1 让 Claude 自己调试¶

    这个测试失败了，请：
1. 分析错误信息
2. 定位问题代码行
3. 解释根本原因
4. 给出修复方案
5. 修复后重新运行测试

    9.2 二分法定位 Bug¶

    请用二分法（git bisect）帮我找到引入这个 bug 的提交：
1. 好的提交：abc1234
2. 坏的提交：def5678
3. 测试命令：pytest tests/test_bug.py

    9.3 日志分析¶

    以下是服务日志的最后 100 行，请分析：
1. 有没有明显的错误？
2. 异常模式是什么？
3. 最可能的原因是什么？

    十、检查清单¶

    任务开始前¶

    • 明确描述任务：上下文 + 目标 + 约束
    • 指定修改范围（文件/目录）
    • 确认当前分支正确
    • 必要时创建新分支

    任务进行中¶

    • 用 /compact 管理上下文
    • 分步验证复杂任务的结果
    • 及时纠正错误的理解

    任务完成后¶

    • 用 git diff 审查所有改动
    • 运行测试套件
    • 运行 lint/format 检查
    • 确认无敏感信息泄露
    • 编写清晰的提交信息
    • 必要时更新文档

    总结¶

    Claude Code 是一个强大的编程助手，但它不是银弹。记住：

    原则 说明
    🎯 明确需求 说清楚你想要什么，以及不想要什么
    🔒 保持审查 永远不要盲目接受所有改动
    📝 善用记忆 CLAUDE.md 是你的项目说明书
    🧪 验证结果 测试、lint、review 一个都不能少
    💰 关注成本 用对模型、管理上下文、定期清理
    🤝 团队共享 把规则提交到仓库，统一团队标准

    一句话总结： 把 Claude Code 当作一个聪明但需要指导的同事，而不是自动驾驶仪。你提供方向和判断，它提供执行和方案。

    最佳实践基于 2026 年 5 月的使用经验总结。随着工具更新和场景变化，建议定期回顾和更新本文档。
