    05 - 进阶主题¶

    事务（Transactions）¶

    Kafka 事务用于实现跨多个 Partition 和 Topic 的原子性写入。

    使用场景¶

    场景：转账
1. 从 account-A 扣款
2. 向 account-B 加款
3. 发送通知消息

要求：要么全部成功，要么全部失败

    事务 Producer¶

    Properties props = new Properties();
props.put("transactional.id", "my-transaction-id");  // 必须设置

KafkaProducer<String, String> producer = new KafkaProducer<>(props);
producer.initTransactions();

try {
    producer.beginTransaction();

    // 写入多个 Topic/Partition
    producer.send(new ProducerRecord<>("account-a", "debit", "100"));
    producer.send(new ProducerRecord<>("account-b", "credit", "100"));
    producer.send(new ProducerRecord<>("notifications", "transfer", "done"));

    producer.commitTransaction();
} catch (Exception e) {
    producer.abortTransaction();  // 回滚
}

    事务隔离级别¶

    Consumer 端配置：

    props.put("isolation.level", "read_committed");  // 只读已提交
// 或
props.put("isolation.level", "read_uncommitted"); // 读所有（默认）
    • read_committed：只看到 commitTransaction() 成功的消息
    • read_uncommitted：看到所有消息，包括事务中的中间状态

    Exactly-Once Semantics（EOS）¶

    At-Least-Once¶

    消息至少被消费一次，可能重复：

    Producer → Broker ✓ → Consumer 处理 ✓ → 提交 offset 失败 ✗
→ Consumer 重启 → 重新消费 → 重复处理

    At-Most-Once¶

    消息最多被消费一次，可能丢失：

    Producer → Broker ✓ → Consumer 提交 offset ✓ → 处理失败 ✗
→ 消息丢失

    Exactly-Once¶

    消息恰好被消费一次：

    实现方式 1：幂等性 Producer - 单 Partition 内去重 - 配置 enable.idempotence=true

    实现方式 2：事务 - 跨 Partition/Topic 原子性 - 配合 isolation.level=read_committed

    实现方式 3：Kafka Streams - 内置 EOS 支持 - 配置 processing.guarantee=exactly_once_v2（需要 broker 2.5+） - 注意：旧版 exactly_once（v1）在 Kafka 3.0 废弃、4.0 已移除，只剩 v2

    补充（Kafka 4.0+）：事务协议升级为 transaction v2（KIP-890，服务端防御）： 每个事务都会 bump producer epoch，防止僵尸 Producer / 延迟到达的请求写入 错误的事务，消除挂起事务（LSO 卡住）等边界问题。broker 端默认启用， 客户端无需感知。

    Kafka Streams¶

    轻量级流处理库，嵌入到 Java 应用中。

    核心概念¶

    Source → Processor → Sink
  ↑          ↓
  └── State Store（状态存储）

    示例：单词计数¶

    Properties props = new Properties();
props.put("application.id", "wordcount-app");
props.put("bootstrap.servers", "broker:9092");
props.put("default.key.serde", Serdes.String().getClass());
props.put("default.value.serde", Serdes.String().getClass());

StreamsBuilder builder = new StreamsBuilder();
KStream<String, String> textLines = builder.stream("input-topic");

KTable<String, Long> wordCounts = textLines
    .flatMapValues(line -> Arrays.asList(line.split(" ")))
    .groupBy((key, word) -> word)
    .count();

wordCounts.toStream().to("output-topic");

KafkaStreams streams = new KafkaStreams(builder.build(), props);
streams.start();

    State Store¶

    // 可查询的状态存储
StoreBuilder<KeyValueStore<String, Integer>> storeBuilder = Stores.keyValueStoreBuilder(
    Stores.persistentKeyValueStore("word-counts"),
    Serdes.String(),
    Serdes.Integer()
);

builder.addStateStore(storeBuilder);

    类型： - Persistent：RocksDB，磁盘存储 - In-Memory：内存存储 - Windowed：时间窗口存储

    窗口操作¶

    // 滚动窗口
windowedBy(TimeWindows.of(Duration.ofMinutes(5)))

// 跳跃窗口
windowedBy(TimeWindows.of(Duration.ofMinutes(5)).advanceBy(Duration.ofMinutes(1)))

// 会话窗口
windowedBy(SessionWindows.with(Duration.ofMinutes(30)))

    静态成员（KIP-345）¶

    Streams 2.3+ 支持静态成员，用的是和 Consumer 相同的 group.instance.id：

    Properties props = new Properties();
props.put(StreamsConfig.APPLICATION_ID_CONFIG, "wordcount-app");
props.put(StreamsConfig.BOOTSTRAP_SERVERS_CONFIG, "broker:9092");
// 静态成员 ID：每个应用实例唯一，K8s 下常用 hostname / Pod 名
props.put(ConsumerConfig.GROUP_INSTANCE_ID_CONFIG, System.getenv("HOSTNAME"));
props.put(ConsumerConfig.SESSION_TIMEOUT_MS_CONFIG, 300000);  // 覆盖滚动升级耗时

    要点：

    • num.stream.threads > 1 时，Streams 会给每个 StreamThread 的 consumer 在 用户配置的 id 后自动追加标识（clientId/线程号），保证同实例多线程不冲突， 所以只需按"实例"粒度配一个
    • 不设置时是动态成员（默认），每次重启都触发 rebalance
    • Streams 2.3+ 默认就是增量 rebalance（StreamsPartitionAssignor），配合静态成员
    • num.standby.replicas=1，滚动升级时实例在 session.timeout 内回来直接拿回 原任务，本地 RocksDB 状态无需从 changelog 重建，基本无中断
    • 注意：新的 Streams group 协议（KIP-1071，4.1+ 早期访问）暂不支持 instance.id

    Kafka Connect¶

    数据集成框架，用于在 Kafka 和其他系统之间移动数据。

    架构¶

    Source System → Source Connector → Kafka → Sink Connector → Sink System
                (Connector + Task)        (Connector + Task)

    常用 Connector¶

    Connector 用途
    JDBC Source 数据库 → Kafka
    JDBC Sink Kafka → 数据库
    Elasticsearch Sink Kafka → ES
    S3 Sink Kafka → S3
    Debezium CDC（Change Data Capture）

    配置示例¶

    {
  "name": "jdbc-source-connector",
  "config": {
    "connector.class": "io.confluent.connect.jdbc.JdbcSourceConnector",
    "connection.url": "jdbc:mysql://localhost:3306/mydb",
    "connection.user": "connect",
    "connection.password": "***",
    "table.include.list": "users",
    "mode": "timestamp",
    "timestamp.column.name": "updated_at",
    "topic.prefix": "db-"
  }
}

    注意：旧版配置名 table.whitelist 已废弃，现在用 table.include.list。

    部署模式¶

    • Standalone：单进程，适合开发
    • Distributed：集群部署，支持容错和扩展
    # Standalone
bin/connect-standalone.sh config/connect-standalone.properties connector.json

# Distributed
bin/connect-distributed.sh config/connect-distributed.properties
curl -X POST -H "Content-Type: application/json" \
  http://localhost:8083/connectors -d @connector.json

    Connect 内置死信队列（DLQ）¶

    Sink Connector 支持把处理失败的消息直接路由到 DLQ topic：

    {
  "errors.tolerance": "all",
  "errors.deadletterqueue.topic.name": "orders-dlq",
  "errors.deadletterqueue.topic.replication.factor": "3",
  "errors.deadletterqueue.context.headers.enable": "true"
}

    静态成员与 Rebalance 优化¶

    Connect 有两层 rebalance 要分开看：

    1. Worker 层（connector/task 分配）

    distributed 模式的 worker 组成自己的 consumer group，2.3+ 默认增量 cooperative rebalance（connect.protocol=compatible）。另有 scheduled.rebalance.max.delay.ms （默认 5 分钟）：worker 离开后在此时间内回来，直接拿回原有任务，不做全量重分配。 所以滚动升级 Connect 集群时，只要 5 分钟内完成重启，任务不会大面积迁移。

    2. Sink task consumer 层

    每个 sink connector 的所有 task 是 connect-<connector-name> 消费组里的 consumer。 Connect 默认不给这些 consumer 设置 group.instance.id（即动态成员），task 重启会触发该消费组的 rebalance。需要时可通过 consumer.override.* 前缀透传 （worker 需设置 connector.client.config.override.policy）：

    {
  "config": {
    "connector.class": "...",
    "consumer.override.group.instance.id": "es-sink-task-0",
    "consumer.override.session.timeout.ms": "300000"
  }
}

    ⚠️ 坑：这个 id 必须每个 task 唯一、且跨重启稳定。connector 的 task 配置由 taskConfigs() 生成后分发——如果所有 task 拿到相同的 id，会抛 FencedInstanceIdException（这是社区里最常见的翻车姿势）。除非 connector 本身 支持按 task 生成唯一 id，否则一般不折腾这层，靠 worker 层的延迟 rebalance 已经 能覆盖大多数滚动升级场景。

    Share Groups（队列语义，KIP-932）¶

    Kafka 4.2 起 GA 的新消费模型，让 Kafka 原生支持队列式竞争消费。

    与 Consumer Group 的核心区别¶

    维度 Consumer Group Share Group
    分配单位 整个 Partition 独占分配给一个 Consumer 按单条记录分发给任意 Consumer
    Consumer 数量 超过 Partition 数则空闲 可以超过 Partition 数，一起干活
    顺序保证 分区内严格有序 不保证顺序（记录级分发）
    确认方式 提交 offset 每条记录单独 ACK（ACCEPT/RELEASE/REJECT/RENEW）
    Rebalance 需要 基本无感知（Broker 端协调记录分发）

    使用场景¶

    • 任务队列：每条消息是独立任务，处理顺序无所谓，只关心吞吐和负载均衡
    • 想同时拥有"日志回溯"和"竞争消费"两种模式

    Java 客户端示例¶

    Properties props = new Properties();
props.put("bootstrap.servers", "broker1:9092");
props.put("group.id", "task-workers");

// 注意：是 KafkaShareConsumer，不是 KafkaConsumer
try (KafkaShareConsumer<String, String> consumer = new KafkaShareConsumer<>(props)) {
    consumer.subscribe(List.of("tasks"));

    while (true) {
        ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(1000));
        for (ConsumerRecord<String, String> record : records) {
            try {
                process(record);
                consumer.acknowledge(record, AcknowledgeType.ACCEPT);   // 处理成功
            } catch (RetriableException e) {
                consumer.acknowledge(record, AcknowledgeType.RELEASE);  // 临时失败，重新投递
            } catch (Exception e) {
                consumer.acknowledge(record, AcknowledgeType.REJECT);   // 永久失败，归档不再投递
            }
        }
        consumer.commitSync();  // 提交 ACK 状态
    }
}
    • 不调用 acknowledge 时，下一次 poll() 隐式确认上一批（implicit ACK）
    • ACK 类型语义：ACCEPT=成功；RELEASE=临时失败，回到 Available 等待重投（累计 delivery count）； REJECT=永久失败，直接归档不再投递
    • 处理时间长可用 AcknowledgeType.RENEW 延长锁，防止被重投（4.2+，KIP-1222）
    • RELEASE 重投次数超过 group.share.delivery.count.limit（默认 5）后记录自动归档（防毒丸消息）

    Schema Registry¶

    管理消息的 Schema（Avro/JSON/Protobuf）。

    为什么需要 Schema？¶

    • 生产者和消费者使用不同的 Schema → 解析失败
    • Schema 演进 → 向后/向前兼容性

    Avro 示例¶

    // Producer
KafkaAvroSerializer serializer = new KafkaAvroSerializer(schemaRegistry);
User user = new User("Alice", 30);
byte[] data = serializer.serialize("users", user);

// Consumer
KafkaAvroDeserializer deserializer = new KafkaAvroDeserializer(schemaRegistry);
User user = (User) deserializer.deserialize("users", data);

    Schema 兼容性¶

    兼容性类型：
- BACKWARD：新 Schema 可以读取旧数据
- FORWARD：旧 Schema 可以读取新数据
- FULL：同时支持 BACKWARD 和 FORWARD

    消息顺序性¶

    Partition 内有序¶

    Producer 发送顺序：msg1, msg2, msg3
Partition 0: [msg1] [msg2] [msg3]  ← 有序

    全局有序（单 Partition）¶

    // 所有消息发到同一个 Partition
producer.send(new ProducerRecord<>("topic", 0, key, value));

    局部有序（相同 Key）¶

    // 相同 key 的消息发到同一个 Partition
producer.send(new ProducerRecord<>("orders", "order-123", "created"));
producer.send(new ProducerRecord<>("orders", "order-123", "paid"));
producer.send(new ProducerRecord<>("orders", "order-123", "shipped"));
// 同一个 order 的消息有序

    消息积压处理¶

    临时方案¶

    1. 增加 Partition（只能加不能减；会触发 rebalance，无需重启 Consumer）
    2. 临时 Consumer：新建一个 Topic，更多 Partition，用临时 Consumer 快速消费

    根本方案¶

    1. 优化处理逻辑：异步处理、批量处理
    2. 增加 Consumer：Consumer 数 = Partition 数
    3. 调优参数： 
      props.put("max.poll.records", 1000);        // 增加每次拉取数量
props.put("fetch.min.bytes", 1048576);      // 1MB，减少请求次数
props.put("fetch.max.wait.ms", 500);        // 减少等待时间

    死信队列（DLQ）¶

    Kafka 本身没有内建 DLQ，需要应用层自己实现（Kafka Connect Sink 有内置支持，见上文）：

    try {
    processMessage(record);
} catch (Exception e) {
    producer.send(new ProducerRecord<>("orders-dlq", record.key(), record.value()));
    log.error("Failed to process, sent to DLQ", e);
}

    Spring Kafka 提供开箱即用的重试 + DLQ（@RetryableTopic），见 07 章。

    注意：Kafka Streams 没有内置 DLQ，需要用 process() + 分支输出自己路由 到错误 topic（社区有相关 KIP 提案但尚未落地）。
