    09 - 面试真题¶

    基础概念¶

    Q1: Kafka 为什么这么快？¶

    答：

    1. 顺序写磁盘：消息追加写入日志文件，顺序写速度接近内存随机写
    2. 零拷贝（sendfile）：消费端使用 sendfile() 系统调用，减少 2 次数据拷贝和上下文切换
    3. Page Cache：利用 OS 页缓存，不自己管理内存
    4. 批量发送：Producer 攒一批消息一起发，减少网络请求
    5. 压缩：支持 gzip/snappy/lz4/zstd，减少网络传输和磁盘占用
    6. 分区并行：多个 Partition 并行处理，提高吞吐

    Q2: Kafka 如何保证消息不丢失？¶

    答：

    Producer 端： - acks=all：等待所有 ISR 副本确认 - retries > 0：失败自动重试 - enable.idempotence=true：幂等性，防止重试导致重复

    Broker 端： - replication.factor >= 3：多副本 - min.insync.replicas >= 2：最少同步副本数 - unclean.leader.election.enable=false：禁止非 ISR 副本当选 Leader

    Consumer 端： - 手动提交 offset：处理完业务逻辑再提交 - enable.auto.commit=false：关闭自动提交

    Q3: Kafka 如何保证消息顺序？¶

    答：

    • Partition 内有序：单个 Partition 内消息严格有序
    • 全局有序：Topic 只有 1 个 Partition（牺牲并行度）
    • 局部有序：相同 Key 的消息路由到同一 Partition
    // 相同 key 的消息有序
producer.send(new ProducerRecord<>("orders", "order-123", "created"));
producer.send(new ProducerRecord<>("orders", "order-123", "paid"));
producer.send(new ProducerRecord<>("orders", "order-123", "shipped"));

    Q4: Kafka 的 Consumer Group 是什么？¶

    答：

    一组 Consumer 共同消费一个 Topic，实现负载均衡：

    • 一个 Partition 只能被组内一个 Consumer 消费
    • Consumer 数 > Partition 数 → 部分 Consumer 空闲
    • Consumer 数 < Partition 数 → 部分 Consumer 消费多个 Partition
    • 不同 Group 独立消费，互不影响

    Q5: Kafka 的 Rebalance 是什么？会触发什么场景？¶

    答：

    Rebalance 是 Consumer Group 内重新分配 Partition 的过程。

    触发条件： 1. 新 Consumer 加入 Group 2. Consumer 离开 Group（正常关闭或崩溃） 3. Topic 的 Partition 数量变化 4. Consumer 心跳超时（session.timeout.ms） 5. Consumer 处理超时（max.poll.interval.ms）

    影响： - 经典协议（Eager）下 Rebalance 期间 Group 停止消费（Stop-The-World） - 需要尽快完成，避免长时间不可用

    Rebalance 会等正在处理的消息处理完吗？ - 不会。Kafka 不等业务处理完，rebalance 信号在下一次 poll() 时送达， 正在处理的那批消息会继续执行完，但期间整个 Group 不再拉取新消息 - 未 commit 的 offset 会因分区被重新分配而重复消费，推荐在 ConsumerRebalanceListener.onPartitionsRevoked() 里 commitSync - Cooperative 协议（2.4+，CooperativeStickyAssignor）/ KIP-848 新协议（4.0+） 是增量式 rebalance，只迁移需要变动的分区，其余消费不受影响

    如何减少 Rebalance 频率？ - 静态成员（KIP-345）：配置 group.instance.id，Consumer 重启在 session.timeout.ms 内回来不触发 rebalance，直接拿回原分区 - 调大 session.timeout.ms / max.poll.interval.ms 避免误判超时 - 使用 KIP-848 新协议，Broker 端增量协调，成员变化不再全局 Stop-The-World

    扩容时 Consumer 挨个启动会频繁 rebalance 吗？ - 会：每个新成员加入触发一轮 rebalance（rebalance 风暴）；但 rebalance 进行中的 join 会折叠进同一轮，启动越集中轮数越少 - group.initial.rebalance.delay.ms（默认 3s）只对新 Group 首次 rebalance 生效 - 静态成员帮不上扩容（新实例是全新身份），根治靠 Cooperative / KIP-848 协议

    架构设计¶

    Q6: Kafka 的副本机制是什么？ISR 是什么？¶

    答：

    • Leader：处理所有读写请求
    • Follower：从 Leader 拉取数据同步
    • ISR（In-Sync Replicas）：与 Leader 保持同步的副本集合

    Follower 落后超过 replica.lag.time.max.ms（默认 30s）会被踢出 ISR。

    Leader 挂掉时，从 ISR 中选新 Leader，保证数据不丢。

    Q7: Kafka 的 Controller 是什么？¶

    答：

    Controller 负责管理集群元数据：Partition 的 Leader 分配、Broker 上下线感知、触发 Rebalance。

    KRaft 模式（Kafka 4.0+ 唯一模式）：Controller 是一个 Raft Quorum（通常 3/5 节点）， 元数据存在内部 topic __cluster_metadata 中，Raft 多数派复制，无单点。

    ZooKeeper 模式（历史，4.0 已移除）：Controller 是某个 Broker，元数据存 ZK， 单点读取后广播给所有 Broker，扩展性差。

    面试加分点：KRaft 去掉了 ZK 依赖、消除 Controller 单点全量同步瓶颈、 元数据用 Raft 保证一致性，官方实测可支撑数百万分区。

    Q8: Kafka 的存储结构是什么？¶

    答：

    每个 Partition 由多个 Segment 文件组成：

    Partition/
├── 00000000000000000000.log        # 消息数据
├── 00000000000000000000.index      # 稀疏索引（offset → 物理位置）
├── 00000000000000000000.timeindex  # 时间戳索引
├── 00000000000000368769.log
└── ...

    查找 offset=368799： 1. 二分查找 .index，找到最大的 <= 368799 的 offset 2. 在 .log 中从该位置顺序扫描

    Q9: Kafka 的零拷贝是什么？¶

    答：

    传统读取（4 次拷贝，4 次上下文切换）： 

    Disk → Kernel Buffer → User Buffer → Socket Buffer → NIC

    零拷贝 sendfile（2 次拷贝，2 次上下文切换）： 

    Disk → Kernel Buffer → NIC

    Kafka Consumer 使用 sendfile() 系统调用，减少数据拷贝和上下文切换。

    Producer¶

    Q10: Kafka 的 ACK 机制是什么？¶

    答：

    acks 含义 延迟 可靠性
    0 不等确认 最低 可能丢
    1 Leader 写入成功 中等 Leader 挂可能丢
    all ISR 所有副本写入成功 最高 不丢

    配合 min.insync.replicas 使用： - acks=all + min.insync.replicas=2：至少 2 个副本写入成功 - ISR 不足时返回 NotEnoughReplicasException

    Q11: Kafka 的幂等性是什么？¶

    答：

    防止 Producer 重试导致消息重复。

    开启 enable.idempotence=true（默认开启）： - 每条消息分配 Producer ID + Sequence Number - Broker 去重，相同 Sequence Number 的消息只接收一次

    Producer PID=1:
  msg1 (seq=0) → Broker 接收 ✓
  msg1 (seq=0) → 重试 → Broker 发现重复，丢弃 ✓
  msg2 (seq=1) → Broker 接收 ✓

    Q12: Kafka 的事务是什么？¶

    答：

    跨多个 Partition 和 Topic 的原子性写入。

    producer.initTransactions();
producer.beginTransaction();
producer.send(new ProducerRecord<>("topic1", "key1", "value1"));
producer.send(new ProducerRecord<>("topic2", "key2", "value2"));
producer.commitTransaction();  // 或 abortTransaction()

    Consumer 端配置 isolation.level=read_committed 只读已提交消息。

    Consumer¶

    Q13: Kafka 的 Offset 管理方式？¶

    答：

    自动提交： 

    props.put("enable.auto.commit", true);
props.put("auto.commit.interval.ms", 5000);
    问题：可能重复消费或丢失消息。

    手动提交： 

    props.put("enable.auto.commit", false);
// 处理完业务逻辑再提交
consumer.commitSync();
    推荐：保证消息至少被处理一次。

    Q14: Kafka 的 auto.offset.reset 是什么？¶

    答：

    新 Consumer Group 第一次消费时，从哪个位置开始：

    值 含义
    earliest 从最早的 offset 开始（消费所有历史数据）
    latest 从最新的 offset 开始（只消费新数据，默认）
    none 没有 offset 就抛异常

    Q15: Kafka 的 Consumer Lag 是什么？怎么处理？¶

    答：

    Consumer Lag = 最新 offset - 已消费 offset，表示消费者延迟。

    处理方案： 1. 增加 Consumer：Consumer 数 = Partition 数 2. 增加 Partition：提高并行度 3. 优化处理逻辑：异步处理、批量处理 4. 调优参数： 

    props.put("max.poll.records", 1000);     // 增加每次拉取数量
props.put("fetch.min.bytes", 1048576);   // 减少请求次数

    高级特性¶

    Q16: Kafka 的 Exactly-Once 如何实现？¶

    答：

    方式 1：幂等性 Producer - 单 Partition 内去重 - enable.idempotence=true

    方式 2：事务 - 跨 Partition/Topic 原子性 - 配合 isolation.level=read_committed

    方式 3：Kafka Streams - 内置 EOS 支持 - processing.guarantee=exactly_once_v2（v1 在 Kafka 4.0 已移除）

    Q17: Kafka 和 RabbitMQ 的区别？¶

    答：

    特性 Kafka RabbitMQ
    吞吐量 百万级 万级
    延迟 ms 级 us 级
    消息保留 持久化，可回溯 消费后删除
    协议 自定义 AMQP
    适用场景 日志、流处理、事件溯源 业务消息、RPC
    路由 Topic + Partition Exchange + Queue

    补充：Kafka 4.2 的 Share Groups（KIP-932）补齐了原生队列语义 （竞争消费、单条 ACK、重投），"Kafka 不适合做任务队列"这个传统说法已经不成立了。

    Q18: Kafka 的 Kafka Streams 是什么？¶

    答：

    轻量级流处理库，嵌入到 Java 应用中：

    KStream<String, String> textLines = builder.stream("input-topic");
KTable<String, Long> wordCounts = textLines
    .flatMapValues(line -> Arrays.asList(line.split(" ")))
    .groupBy((key, word) -> word)
    .count();
wordCounts.toStream().to("output-topic");

    特点： - 无需独立集群 - 支持状态存储（RocksDB） - 支持窗口操作、聚合、Join

    Q19: Kafka 的 Kafka Connect 是什么？¶

    答：

    数据集成框架，用于在 Kafka 和其他系统之间移动数据：

    Source System → Source Connector → Kafka → Sink Connector → Sink System

    常用 Connector： - JDBC Source/Sink：数据库集成 - Elasticsearch Sink：搜索集成 - Debezium：CDC（Change Data Capture）

    Q20: Kafka 的死信队列（DLQ）是什么？¶

    答：

    处理失败的消息放入死信队列，后续人工处理：

    try {
    processMessage(record);
} catch (Exception e) {
    producer.send(new ProducerRecord<>("orders-dlq", record.key(), record.value()));
}

    Kafka Streams 没有内置 DLQ，需要用分支输出自己路由；Kafka Connect Sink 有内置 errors.deadletterqueue.topic.name 配置；Spring Kafka 有 @RetryableTopic。

    运维相关¶

    Q21: Kafka 如何扩缩容？¶

    答：

    增加 Broker： 1. 启动新 Broker 2. 使用 kafka-reassign-partitions.sh 重新分配分区 3. 等待数据迁移完成

    增加 Partition： 

    kafka-topics.sh --alter --topic orders --partitions 6
    注意：只能增加，不能减少；已存在的消息不会重新分配。

    Q22: Kafka 如何监控？¶

    答：

    关键指标： - UnderReplicatedPartitions：副本落后的分区数 - OfflinePartitionsCount：离线分区数量 - ActiveControllerCount：Controller 数量 - ConsumerLag：消费者延迟

    工具： - JMX + Prometheus + Grafana - 开源 UI：AKHQ、Kafbat UI（Yandex 维护的 Kafka Manager 后继）、Conduktor Desktop - 商业：Confluent Control Center

    Q23: Kafka 的磁盘空间不足怎么办？¶

    答：

    # 减少保留时间
log.retention.hours=24

# 减少保留大小
log.retention.bytes=10737418240  # 10GB

    注意：log.cleanup.policy=compact 不是通用解法——它是"按 key 保留最新值"的 另一种数据模型，只适合状态类 topic（如 __consumer_offsets）， 普通日志/事件 topic 不能随意切换。真要长期低成本保留，考虑 Tiered Storage。

    Q24: Kafka 的 Consumer 重复消费怎么办？¶

    答：

    原因： 1. Offset 提交失败 2. Rebalance 导致重复分配 3. Consumer 崩溃，offset 未提交

    解决方案： 1. 幂等性处理（数据库唯一约束） 2. Kafka 事务 3. 业务层去重（Redis 缓存已处理的 message id）

    场景设计题¶

    Q25: 如何保证 Kafka 的高可用？¶

    答：

    1. 多副本：replication.factor >= 3
    2. 多 ISR：min.insync.replicas >= 2
    3. 禁止 Unclean Leader：unclean.leader.election.enable=false
    4. Controller 高可用：KRaft Quorum 3/5 节点（4.0 起 ZooKeeper 已不存在）
    5. 跨机房部署：Broker 分布在不同机房

    Q26: 如何设计一个订单系统，使用 Kafka？¶

    答：

    订单服务 → orders Topic → 多个消费者
                              ├─ 库存服务（扣减库存）
                              ├─ 支付服务（创建支付单）
                              └─ 通知服务（发送短信）

    设计要点： 1. Topic 设计：按业务拆分 Topic（orders、payments、notifications） 2. Partition 策略：按 order_id 分区，保证同一订单的消息有序 3. Consumer Group：每个服务一个 Group，独立消费 4. 幂等性：数据库唯一约束，防止重复处理 5. 事务：跨服务使用 Saga 模式或 TCC

    Q27: 如何处理 Kafka 的消息积压？¶

    答：

    临时方案： 1. 增加 Partition 2. 创建临时 Topic，用临时 Consumer 快速消费

    根本方案： 1. 优化处理逻辑（异步、批量） 2. 增加 Consumer（Consumer 数 = Partition 数） 3. 调优参数： 

    props.put("max.poll.records", 1000);
props.put("fetch.min.bytes", 1048576);

    Q28: 如何设计一个日志收集系统，使用 Kafka？¶

    答：

    应用服务器 → Filebeat/Fluentd → Kafka → Logstash → Elasticsearch → Kibana

    设计要点： 1. Topic 设计：按应用/日志级别拆分 2. 压缩：使用 lz4/zstd 压缩，减少存储 3. 保留策略：log.retention.hours=168（7 天） 4. 批量写入：提高吞吐 5. 监控：Consumer Lag、磁盘使用率

    Q29: 如何实现 Kafka 的跨集群同步？¶

    答：

    MirrorMaker 2（唯一官方方案，MirrorMaker 1 已在 4.0 移除）： 

    A->B.enabled=true
A->B.topics=.*

    Kafka Connect： 使用 MirrorMaker 2 的 Source/Mirror Connector 部署在 Connect 集群中。

    Confluent Replicator / Cluster Linking： 商业方案，功能更全。

    Q30: Kafka 的 Schema Evolution 是什么？¶

    答：

    Schema 演进时保证兼容性：

    兼容性 含义
    BACKWARD 新 Schema 可以读取旧数据
    FORWARD 旧 Schema 可以读取新数据
    FULL 同时支持 BACKWARD 和 FORWARD

    使用 Schema Registry 管理 Schema 版本。

    Kafka 4.x 新特性（高频追问）¶

    Q31: Kafka 4.0 有什么重大变化？¶

    答：

    1. ZooKeeper 彻底移除：只支持 KRaft 模式，4.0 之前必须先完成 ZK→KRaft 迁移
    2. KIP-848 新 Consumer Rebalance 协议：group.protocol=consumer， Broker 端增量协调，去掉 Stop-The-World，官方实测最高 20x 更快
    3. Share Groups 早期访问（KIP-932，队列语义，4.2 GA）
    4. Java 版本要求提高：Broker/工具要求 Java 17+（KIP-1013 移除 Java 11），客户端库要求 Java 11+（KIP-750 移除 Java 8），Scala 2.12 移除
    5. MirrorMaker 1 移除，inter.broker.protocol.version 移除（改用 metadata.version）

    Q32: KIP-848 新 Rebalance 协议是什么？和经典协议的区别？¶

    答：

    Kafka 4.0+ 的新一代 Consumer 组协议，把协调逻辑从客户端整体搬到 Broker 端。

    经典协议：组内选 leader Consumer 计算分配，全员同步、一次到位， 任何成员变化都 Stop-The-World。

    KIP-848：没有 leader，Coordinator（broker）持有全局视图，通过 ConsumerGroupHeartbeat 持续增量调谐（reconcile），成员变化时只有被迁移的 分区短暂交接，其余 Consumer 继续消费。官方实测最高快约 20x。

    对比项 经典协议 KIP-848
    分配计算 客户端 leader Broker 端（服务端 assignor）
    成员变化 全局 Stop-The-World 增量，组不停摆
    判活/心跳 客户端配置 Broker 组级配置
    大 group 易 rebalance 风暴 扩展性好

    要点：

    • 开启：group.protocol=consumer（需 broker 4.0+ / KRaft 模式）
    • 客户端的 session.timeout.ms、heartbeat.interval.ms、 partition.assignment.strategy 改由 broker 端控制，客户端再配会被拒绝
    • 支持滚动迁移：第一个新协议 Consumer 加入时 Coordinator 自动切换整组
    • 4.3 起分阶段弃用经典协议（KIP-1274），新项目建议直接用新协议

    Q33: Tiered Storage（分层存储）是什么？¶

    答：

    KIP-405，Kafka 3.6 Early Access、3.9 GA。把冷数据从 Broker 本地磁盘卸载到远端对象存储（S3 等）：

    • Broker 只保留热数据（local.retention.ms），冷数据透明代理读取
    • 收益：存储成本低、Broker 按计算弹性扩缩、保留期从几天延长到几个月
    • 代价：消费冷数据延迟变高；不支持 compacted topic；单次 fetch 只服务一个远端分区

    Q34: Share Groups 是什么？和 Consumer Groups 的区别？¶

    答：

    KIP-932，Kafka 4.2 GA 的队列式消费模型：

    维度 Consumer Group Share Group
    分配单位 分区独占 单条记录分发
    Consumer 数 ≤ 分区数才有意义 可以超过分区数
    顺序 分区内有序 不保证
    确认 提交 offset 单条 ACCEPT/RELEASE/REJECT
    Rebalance 有 基本无感知

    适合任务队列类负载（消息相互独立、处理顺序无关）。 客户端 API 是 KafkaShareConsumer，运维工具是 kafka-share-groups.sh。

    Q36: 写一个 Kafka Consumer，保证消息不丢失¶

    Properties props = new Properties();
props.put("bootstrap.servers", "broker1:9092");
props.put("group.id", "order-service");
props.put("enable.auto.commit", false);
props.put("auto.offset.reset", "earliest");
props.put("key.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
props.put("value.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");

try (KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props)) {
    consumer.subscribe(Arrays.asList("orders"));

    while (true) {
        ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
        for (ConsumerRecord<String, String> record : records) {
            processOrder(record);   // process business logic first
        }
        if (!records.isEmpty()) {
            consumer.commitSync();  // commit offsets after the whole batch is processed
        }
    }
}

    Q37: 写一个 Kafka 事务 Producer¶

    Properties props = new Properties();
props.put("bootstrap.servers", "broker1:9092");
props.put("transactional.id", "tx-001");
props.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
props.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");

KafkaProducer<String, String> producer = new KafkaProducer<>(props);
producer.initTransactions();

try {
    producer.beginTransaction();
    producer.send(new ProducerRecord<>("topic1", "key1", "value1"));
    producer.send(new ProducerRecord<>("topic2", "key2", "value2"));
    producer.commitTransaction();
} catch (Exception e) {
    producer.abortTransaction();
}
