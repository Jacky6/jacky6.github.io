    02 - 架构设计¶

    整体架构（Kafka 4.x / KRaft 模式）¶

            ┌──────────────────────────────────────────┐
        │        Controller Quorum（Raft）          │
        │   管理集群元数据：Topic/分区/副本/ISR      │
        │   node1(controller) node2  node3         │
        └──────────────┬───────────────────────────┘
                       │ 元数据同步（内部 __cluster_metadata topic）
        ┌──────────────┼──────────────┐
        │              │              │
 ┌──────┴──────┐ ┌────┴──────┐ ┌─────┴─────┐
 │  Broker 0   │ │ Broker 1  │ │ Broker 2  │
 │ Partition 0 │ │ Partition │ │ Partition │
 │ (Leader)    │ │ (Follower)│ │ (Follower)│
 └─────────────┘ └───────────┘ └───────────┘
    • Kafka 4.0 起 ZooKeeper 已被彻底移除，只支持 KRaft 模式

    • Controller 是一个独立的 Raft Quorum（通常 3/5 个节点），可以专职， 也可以和 Broker 合并部署（combined mode，适合小规模）

    • 元数据（Topic、分区、副本、ISR 等）存储在内部 topic __cluster_metadata 中，通过 Raft 复制，不再是"选一个 Controller 存 ZK"

    KRaft vs ZooKeeper 模式（历史对比）¶

    维度 ZooKeeper 模式（≤3.x，已移除） KRaft 模式（3.3+ 生产可用，4.0+ 唯一）
    元数据存储 ZooKeeper Controller Quorum（Raft + 内部 topic）
    元数据一致性 Controller 单点读 ZK，广播给 Broker Raft 多数派复制，线性一致
    故障恢复 Controller 故障要重新选举并全量重建元数据 Quorum 自动选主，增量同步
    扩展性 百万分区级别元数据同步慢 官方实测可支撑数百万分区
    运维 需要额外维护 ZK 集群 少一套组件，部署更简单

    面试常问："KRaft 解决了什么问题？"——核心答案：去掉 ZK 外部依赖、 消除 Controller 单点全量同步的瓶颈、元数据用 Raft 保证一致性。

    存储机制¶

    日志段（Log Segment）¶

    每个 Partition 在磁盘上由多个 Segment 文件组成：

    Partition 0/
├── 00000000000000000000.log      # 第一个 segment，offset 从 0 开始
├── 00000000000000000000.index    # 稀疏索引
├── 00000000000000000000.timeindex # 时间戳索引
├── 00000000000000368769.log      # 第二个 segment
├── 00000000000000368769.index
└── 00000000000000368769.timeindex
    • .log：消息数据
    • .index：offset → 物理位置的映射（稀疏索引）
    • .timeindex：timestamp → offset 的映射

    消息查找过程¶

    查找 offset=368799 的消息：

    1. 二分查找 .index 文件，找到最大的 <= 368799 的 offset
   → 得到物理位置 position
2. 在 .log 文件中从 position 开始顺序扫描
3. 找到 offset=368799 的消息

    为什么用稀疏索引？ 节省内存，同时顺序扫描很快。

    零拷贝（Zero Copy）¶

    传统读取（4 次拷贝，4 次上下文切换）： 

    Disk → Kernel Buffer → User Buffer → Socket Buffer → NIC
       (DMA拷贝)       (CPU拷贝)      (CPU拷贝)      (CPU拷贝)

    零拷贝（sendfile 系统调用，2 次拷贝，2 次上下文切换）： 

    Disk → Kernel Buffer → NIC
       (DMA拷贝)       (DMA拷贝)

    Kafka 消费者读取消息时使用 sendfile()：数据全程由 DMA 搬运， 省去 2 次 CPU 参与的数据拷贝和 2 次上下文切换。

    Tiered Storage（分层存储，KIP-405：3.6 Early Access，3.9 GA）¶

    传统模式下所有数据都保存在 Broker 本地磁盘，保留期受磁盘容量限制。 Tiered Storage 把"冷数据"卸载到远端对象存储（S3/GCS/HDFS/文件系统）：

                     ┌──────────── Broker 本地磁盘 ────────────┐   ┌── 远端存储（S3 等）──┐
Producer ──写入──▶│ 最新数据（热段，可配置 local.retention） │   │ 历史冷段（保留期更长） │
                 └────────────────────────────────────┘   └────────────────────┘
Consumer 读取：热数据走本地；冷数据由 Broker 透明代理从远端拉取

    # Broker 端启用
remote.log.storage.system.enable=true
remote.log.metadata.manager.listener.name=PLAINTEXT
# RemoteStorageManager 实现（Kafka 本身不内置，常用 Aiven 开源插件，支持 S3/文件系统；
# 部分发行版如 Confluent/Red Hat 会随包附带）
remote.log.storage.manager.class.name=io.aiven.kafka.tieredstorage.RemoteStorageManager
remote.log.storage.manager.class.path=/opt/kafka/plugins/tiered-storage/
rsm.config.storage.backend.class=io.aiven.kafka.tieredstorage.storage.s3.S3Storage
rsm.config.storage.s3.bucket.name=kafka-tiered-storage

    # Topic 级：开启分层存储 + 本地/整体保留分离
kafka-configs.sh --bootstrap-server broker1:9092 --alter --topic orders \
  --add-config remote.storage.enable=true,local.retention.ms=86400000
# local.retention.ms：本地磁盘保留多久（热数据）
# retention.ms：整体保留多久（含远端冷数据）

    收益：

    • 存储成本：冷数据放对象存储，Broker 磁盘只留热数据
    • 弹性：Broker 可以按计算需求扩缩，不用为存数据而扩容
    • 更长的可回溯窗口：保留期从"几天"变成"几个月/年"

    注意（官方 Limitations）：

    • 不支持 compacted topic（KIP-1272 在推进中）
    • 单次 fetch 请求只服务一个远端分区，回溯冷数据是吞吐瓶颈
    • 关闭 Broker 级开关前必须先删掉所有启用分层的 topic
    • 消费冷数据延迟更高，fetch 会触发远端拉取

    副本机制¶

    Leader & Follower¶

    每个 Partition 有多个副本（replica），分布在不同的 Broker 上：

    Topic: orders, Partition 0
├── Broker 0: Leader     (处理读写请求)
├── Broker 1: Follower   (从 Leader 拉取数据同步)
└── Broker 2: Follower   (从 Leader 拉取数据同步)
    • Leader：处理所有读写请求
    • Follower：只从 Leader 拉取数据，保持同步
    • 副本集合叫 AR（Assigned Replicas），同步子集叫 ISR

    ISR（In-Sync Replicas）¶

    与 Leader 保持同步的副本集合：

    ISR = {Broker 0, Broker 1, Broker 2}

如果 Broker 2 落后太多（超过 replica.lag.time.max.ms）：
ISR = {Broker 0, Broker 1}   // Broker 2 被踢出

    关键配置：

    • replica.lag.time.max.ms：Follower 落后多久被踢出 ISR（默认 30s）
    • min.insync.replicas：最少同步副本数（配合 acks=all 使用）

    Leader 选举¶

    当 Leader 挂掉：

    1. Controller 从 ISR 中选一个新 Leader（通过 AlterPartition）
    2. 如果 ISR 为空 → 看 unclean.leader.election.enable
    3. true：从非 ISR 中选（可能丢数据）
    4. false：Partition 不可用（保证数据不丢，生产推荐）

    高水位（HW）与 LEO¶

    LEO（Log End Offset）：每个副本下一条要写入的 offset
HW（High Watermark） ：ISR 中所有副本都复制到的最小 LEO
    • Consumer 只能读到 HW 之前的消息（保证读到的一定不丢）
    • Leader 挂了，新 Leader 从 HW 继续，未同步部分被截断（truncation）

    Controller¶

    KRaft 模式（Kafka 4.x 唯一模式）¶

    • Controller 是一个 Raft Quorum（奇数个节点，通常 3 或 5）

    • Active Controller 处理元数据变更（建 Topic、分区重分配、Leader 选举）， 通过 Raft 日志复制给其他 Controller 和所有 Broker

    • Broker 不再需要全量拉取元数据，只订阅增量变更（MetadataVersion 机制）

    • 配置示例：
    # server.properties（KRaft 动态 quorum，4.x 推荐）
process.roles=broker,controller          # 合并模式；生产建议拆分为独立 controller
node.id=1
controller.quorum.bootstrap.servers=host1:9093,host2:9093,host3:9093
controller.listener.names=CONTROLLER
log.dirs=/var/kafka-logs

    # 首次部署生成集群 ID 并格式化（KRaft 必需步骤）
bin/kafka-storage.sh random-uuid
bin/kafka-storage.sh format -t <cluster-uuid> -c config/kraft/server.properties
# （--standalone 用于单节点快速起步，多 controller 用 --initial-controllers，详见 06 章）

    高可用设计总结¶

    机制 作用
    Partition 多副本 数据冗余
    ISR + HW 保证数据一致性，Consumer 只读已同步数据
    Leader 选举 故障自动切换
    Controller Quorum（Raft） 元数据高可用，无单点
    Tiered Storage 冷热分离，长保留低成本
    零拷贝 + 顺序写 高效读写

    写入性能为什么高¶

    1. 顺序写：消息追加到日志文件末尾，磁盘顺序写速度接近内存随机写
    2. Page Cache：利用 OS 页缓存，不自己管理内存
    3. 批量发送：Producer 攒一批消息一起发
    4. 压缩：支持 gzip/snappy/lz4/zstd 压缩
    5. 零拷贝：消费端 sendfile 减少拷贝
    6. 分区并行：多 Partition 分摊负载
