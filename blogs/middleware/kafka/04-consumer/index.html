    04 - 消费者（Consumer）¶

    消费模式¶

    Pull 模式¶

    Kafka Consumer 使用拉取（Pull）模式，主动从 Broker 拉取消息：

    while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> record : records) {
        System.out.printf("offset=%d, key=%s, value=%s%n",
            record.offset(), record.key(), record.value());
    }
}

    为什么不用 Push？

    • Push 模式由 Broker 决定发送速率，Consumer 可能处理不过来
    • Pull 模式由 Consumer 控制节奏，更灵活

    Offset 管理¶

    自动提交（默认）¶

    props.put("enable.auto.commit", true);
props.put("auto.commit.interval.ms", 5000);  // 每 5s 提交一次

    问题：

    • 消息处理完但还没提交 offset → Consumer 挂了 → 重启后重复消费
    • 消息没处理完就提交了 → 丢失消息

    手动提交¶

    props.put("enable.auto.commit", false);

// 同步提交
consumer.commitSync();

// 异步提交
consumer.commitAsync((offsets, exception) -> {
    if (exception != null) {
        System.err.println("Commit failed: " + exception);
    }
});

    推荐做法： 

    while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> record : records) {
        process(record);  // 处理业务逻辑
    }
    consumer.commitSync();  // 处理完再提交
}

    Offset 存储位置¶

    • Kafka 0.9 之前：存在 ZooKeeper
    • Kafka 0.9+：存在 __consumer_offsets Topic（内部 Topic）

    Consumer Group & Rebalance¶

    Rebalance 触发条件¶

    1. 新 Consumer 加入 Group
    2. Consumer 离开 Group（正常关闭或崩溃）
    3. Topic 的 Partition 数量变化
    4. Consumer 心跳超时（session.timeout.ms）
    5. Consumer 处理超时（max.poll.interval.ms）

    Rebalance 过程（经典协议）¶

    1. Coordinator（Group Coordinator，某个 Broker）发起 Rebalance，
   向所有 Consumer 返回 REBALANCE_IN_PROGRESS
2. 所有 Consumer 撤销全部分区（onPartitionsRevoked），发送 JoinGroup 请求
3. Coordinator 选择一个 Consumer 作为 Leader
4. Leader 制定分配方案（Range/RoundRobin/Sticky）
5. Leader 将方案发给 Coordinator（SyncGroup）
6. Coordinator 广播给所有 Consumer
7. 所有 Consumer 按新方案消费（onPartitionsAssigned）

    整个过程中 poll() 被阻塞，Group 内所有 Consumer 停止消费（Stop-The-World）。 超时由 rebalance.timeout.ms（默认 5 分钟）控制：某个 Consumer 在此时间内 没有重新 JoinGroup，会被 Coordinator 直接踢出 Group。

    关键问题：Rebalance 要等所有 Consumer 结束消费吗？¶

    分两层看：

    1. Kafka 层面（协议行为）：不需要等处理完

    • Kafka 从不"等待正在处理的消息处理完"，它只等 Consumer 在 poll() 循环中 响应协调协议。

    • Rebalance 信号是在 Consumer 下一次 poll() 时送达的。此时已拉取到本地 的消息批次还在你的业务代码里处理，Kafka 完全不知情——这部分是普通 Java 代码， 不受任何管控。

    • 所以：正在处理的那批消息不会被暂停或打断，会继续执行完；但处理完之后 Consumer 必须立刻回到 poll() 参与 Rebalance，期间整个 Group 停止拉取新消息。

    2. 业务层面（正确性）：强烈建议处理完并 commit 再进入 rebalance

    • 已拉取但还没 commit offset 的消息，rebalance 后会被重新分配，导致重复消费。
    • 推荐实现：在 ConsumerRebalanceListener.onPartitionsRevoked() 中提交 offset， 保证分区交出去之前进度已持久化：
    consumer.subscribe(topics, new ConsumerRebalanceListener() {
    @Override
    public void onPartitionsRevoked(Collection<TopicPartition> partitions) {
        // Rebalance 前最后的机会：处理完 + 提交，避免重复消费
        consumer.commitSync();
    }

    @Override
    public void onPartitionsAssigned(Collection<TopicPartition> partitions) {
        // 可在此初始化新分区的本地状态
    }
});

    注意：onPartitionsRevoked 是在 poll() 内部被调用的。如果你的业务处理 放在 poll() 之后（标准写法），进入回调时上一批已经处理完了；如果你在 回调里 commit，就能把"处理完"和"提交"串起来。反之，如果一批消息处理 要 10 分钟，rebalance 不会等你，这 10 分钟的工作大概率要重做。

    两种 Rebalance 协议演进¶

    协议 版本 行为
    Eager（经典协议） 0.9+ Rebalance 时所有 Consumer 撤销全部分区，全局 Stop-The-World
    Cooperative 增量 Rebalance（KIP-429） 2.4+ 只迁移真正需要变动的分区，其余 Consumer 继续消费，最多两轮
    新协议（KIP-848，group.protocol=consumer） 4.0+ 完全去掉全局同步屏障，Broker 端增量协调，官方实测最高约 20x 更快，rebalance 期间消费基本不中断

    Cooperative 协议下回答上面的问题就更简单了：绝大多数分区根本不参与 rebalance，持有它们的 Consumer 完全不受影响，只有被迁移分区的那部分 消费会短暂停顿。

    KIP-848 新协议详解（Kafka 4.0+）¶

    KIP-848（新一代 Consumer 组协议）不是对老协议的修补，而是把协调机制从 客户端整体搬到 Broker 端重新设计。类比：从"工人自治"变成"专业项目经理"。

    经典协议：组内选一个 Consumer 当 leader，由它计算分配方案，全员同步、 一次到位——任何成员变化都要所有人停下重新集合（Stop-The-World）。

    KIP-848：没有 leader。Coordinator 就是专职"项目经理"，持有全局视图， 持续增量地把成员往"目标分配"上调谐（reconcile）：

    每个 Consumer 定期发 ConsumerGroupHeartbeat：
  "我当前持有分区 [P0, P1, P2]"
Coordinator：
  1. 更新成员视图
  2. 用服务端 assignor 重新计算目标分配（如 [P0, P3]）
  3. 通过心跳响应通知："请交出 P1/P2，接管 P3"
成员收到后异步执行，其他成员全程无感、继续消费

    关键变化：没有"等所有成员到齐"的环节。新成员加入 → Coordinator 后台 算好新分配，从现有成员手里匀分区给它；成员离开 → 分区回收再分配。 组不停摆，官方实测 rebalance 最高快约 20x。

    解决的痛点对照：

    经典协议的问题 KIP-848 怎么解
    任何成员变化 → 全局 Stop-The-World 完全增量，只有被迁移分区短暂交接
    分配逻辑在客户端（leader 计算） 移到 Broker 端，可插拔 assignor
    判活靠客户端 session.timeout，误判多 判活逻辑在服务端，组级统一配置
    大 group（成百上千 Consumer）协调慢、易 rebalance 风暴 心跳驱动增量协调，大组扩展性质变
    客户端要管心跳线程、rebalance listener 等复杂状态 客户端大幅简化

    配置方式：

    # Consumer 端：开启新协议
group.protocol=consumer
# 可选：选择服务端 assignor（uniform 或 range）
group.remote.assignor=uniform

# ⚠️ 以下配置已改为 broker 端控制，客户端再配会被拒绝：
# session.timeout.ms / heartbeat.interval.ms
# partition.assignment.strategy / rebalance.timeout.ms

    # Broker 端（组级配置，可按组调）
group.consumer.session.timeout.ms=45000        # 默认 45s
group.consumer.heartbeat.interval.ms=5000      # 默认 5s
group.consumer.assignors=uniform,range         # 服务端 assignor，默认 uniform 优先

    客户端侧 assignor 到新协议的映射：RangeAssignor→range， CooperativeStickyAssignor / StickyAssignor / RoundRobinAssignor → uniform。

    迁移与现状：

    • 支持滚动迁移：第一个新协议 Consumer 加入经典组时，Coordinator 自动 切换整组（代理老客户端的 Join/Sync/Heartbeat 请求），可逐台重启升级

    • 需要 KRaft 模式（ZooKeeper 模式没有此能力）

    • 客户端要求：Java client 4.0+；librdkafka 系（confluent-kafka-python 等） 2.10 EA → 2.11 Preview → 2.12 起生产可用；kafka-python / aiokafka 等纯 Python 实现暂不支持

    • 趋势：Kafka 4.3 起分阶段弃用经典协议（KIP-1274），新项目直接用新协议

    • ⚠️ 早期 4.x 小版本存在过新协议相关 bug（如 group 卡在 rebalance 状态）， 上生产前确认 broker 小版本足够新、先在预发环境验证

    静态成员（Static Membership，KIP-345）¶

    减少 rebalance 的另一个重要手段。默认情况下 Consumer 重启 = 新成员加入， 必然触发一次 rebalance；给 Consumer 配置一个稳定身份后就不是了：

    // 每个实例一个固定、组内唯一的 ID
props.put("group.instance.id", "order-service-" + System.getenv("HOSTNAME"));
props.put("session.timeout.ms", 300000);  // 5 分钟，覆盖重启耗时

    工作原理：

    1. Coordinator 记住 group.instance.id → 分区分配的映射
    2. 静态成员关闭时不发送 LeaveGroup，只是停止心跳

    3. 在 session.timeout.ms 内带着相同 instance id 重新加入 → 不触发 rebalance，直接拿回原来的分区继续消费

    4. 超过 session.timeout.ms 没回来 → 被踢出，才触发 rebalance

    典型场景：

    • Kubernetes 滚动发布 / Pod 重启（用 Pod 名做 instance id，天然稳定且唯一）
    • Consumer 本地有重状态（缓存、RocksDB），希望分区分配尽量不动
    • 频繁重启导致 group 反复 rebalance 的"rebalance 风暴"

    注意事项：

    问题 说明
    instance id 冲突 同一 id 被两个实例使用 → 后加入者抛 FencedInstanceIdException
    id 必须稳定 每次重启变化的 id（如随机 UUID）等于没配，还多占一个成员名额
    session.timeout.ms 要够长 应覆盖"重启 + 重新加入"的总耗时，但别长到影响故障检测
    版本 Kafka 2.3+ 引入（KIP-345）
    与新协议的关系 KIP-848 新协议（group.protocol=consumer）同样支持静态成员

    生产建议三件套：CooperativeStickyAssignor（或 KIP-848）+ 静态成员 + 合理的 session.timeout.ms，能把滚动发布期间的消费中断基本消除。 Streams / Connect 中静态成员的用法见 05 章对应小节。

    扩容/缩容会频繁触发 Rebalance 吗？¶

    会——这是经典的"rebalance 风暴"场景，但影响程度取决于协议。

    经典协议下，每个新 Consumer 加入都触发一轮 rebalance：N 台机器挨个启动 ≈ 最多 N 轮 Stop-The-World。不过有两个缓解因素：

    1. Join 会折叠：rebalance 进行中到达的 join 请求会被折叠进同一轮 （Coordinator 在 rebalance.timeout.ms 内收集所有成员的 join）。 机器启动时间越接近，实际轮数越少

    2. group.initial.rebalance.delay.ms（默认 3s，broker 端配置）： 只对新 Group 的第一次 rebalance 生效——Coordinator 先等这段时间 让更多成员加入再分配，适合整组冷启动；对已有 Group 的扩容无效

    静态成员帮不上扩容的忙：新机器是全新身份（新的或没有 instance id）， 加入必然触发 rebalance。静态成员解决的是"同一身份重启回来"，不是"新成员加入"。

    缓解手段（按效果排序）：

    手段 效果
    KIP-848 新协议（4.0+） 新成员加入不再全局停顿，Coordinator 后台增量协调，扩容基本无感
    Cooperative 增量 rebalance 每轮仍发生，但只迁移必要分区，其余 Consumer 继续消费
    新机器尽量集中启动 join 折叠进更少的轮次
    新 Group 调大 group.initial.rebalance.delay.ms 冷启动一轮到位

    ⚠️ Consumer 数已超过 Partition 数时，再扩容只会多出空闲成员，还白白触发 rebalance——先加分区再加机器。

    缩容同理：优雅关闭的 Consumer 触发一轮 rebalance；"下线后分区先不动、等原实例 回来"靠的是静态成员 + 足够长的 session.timeout.ms，属于重启场景，不是永久下线。

    分配策略¶

    客户端默认配置是 [RangeAssignor, CooperativeStickyAssignor] 列表： 组内所有 Consumer 都 ≥ 2.4 时自动使用 CooperativeStickyAssignor（增量 rebalance）， 有老客户端混跑时回落到 Range。下面逐个介绍。

    Range（最经典，多 Topic 时可能不均）¶

    按 Partition 范围分配：

    Topic: t0 (P0, P1, P2, P3)
Consumer: C0, C1

C0: P0, P1
C1: P2, P3

    问题：多个 Topic 时可能导致某个 Consumer 负载不均。

    RoundRobin¶

    轮询分配：

    Topic: t0 (P0, P1, P2, P3)
Consumer: C0, C1

C0: P0, P2
C1: P1, P3

    Sticky（0.11+，KIP-54）¶

    尽量保持原有分配，减少 Rebalance 时的变动：

    Rebalance 前:
C0: P0, P1
C1: P2, P3

C0 挂了，Rebalance 后:
C1: P0, P1, P2, P3  (尽量保持 C1 原有的 P2, P3)

    注意区分两个容易混的概念： - StickyAssignor（0.11+）：分配结果 sticky，但 rebalance 仍是 Eager（Stop-The-World） - CooperativeStickyAssignor（2.4+，KIP-429）：sticky + 增量 rebalance，生产环境推荐

    props.put("partition.assignment.strategy",
    "org.apache.kafka.clients.consumer.CooperativeStickyAssignor");

    从 Eager 迁到 Cooperative 需要滚动升级（新旧客户端混跑时先同时配置两种策略）， 不能一把全切，否则会触发异常。

    消息处理超时¶

    props.put("max.poll.records", 500);         // 一次 poll 最大记录数
props.put("max.poll.interval.ms", 300000);  // 两次 poll 最大间隔

    如果处理时间超过 max.poll.interval.ms：

    • Consumer 被踢出 Group
    • 触发 Rebalance
    • 消息被重新消费

    解决方案：

    • 减小 max.poll.records
    • 增大 max.poll.interval.ms
    • 异步处理（但要小心 offset 提交顺序）

    代码示例¶

    Properties props = new Properties();
props.put("bootstrap.servers", "broker1:9092,broker2:9092");
props.put("group.id", "order-service");
props.put("key.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
props.put("value.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
props.put("enable.auto.commit", false);
props.put("auto.offset.reset", "earliest");  // 新 Group 从哪开始

try (KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props)) {
    consumer.subscribe(Arrays.asList("orders"));

    while (true) {
        ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
        for (ConsumerRecord<String, String> record : records) {
            processOrder(record);
        }
        consumer.commitSync();
    }
}

    auto.offset.reset¶

    新 Consumer Group 第一次消费时，从哪个位置开始？

    值 含义
    earliest 从最早的 offset 开始（消费所有历史数据）
    latest 从最新的 offset 开始（只消费新数据，默认）
    none 没有 offset 就抛异常

    常见配置速查¶

    配置 默认值 说明
    group.id - Consumer Group ID
    enable.auto.commit true 自动提交 offset
    auto.commit.interval.ms 5000 自动提交间隔
    auto.offset.reset latest 新 Group 起始位置
    max.poll.records 500 一次 poll 最大记录数
    max.poll.interval.ms 300000 两次 poll 最大间隔
    session.timeout.ms 45000 心跳超时（Kafka 3.0 起默认 45s，旧版 10s）
    heartbeat.interval.ms 3000 心跳间隔
    rebalance.timeout.ms 300000 单个 Consumer 参与 Rebalance（重新 Join）的超时
    group.instance.id null 静态成员 ID（KIP-345），设置后重启不触发 rebalance，组内必须唯一
    partition.assignment.strategy [RangeAssignor, CooperativeStickyAssignor] 客户端默认列表：全员 2.4+ 时组内实际生效 Sticky+Cooperative；老客户端混跑时回落到 Range
    group.protocol classic Kafka 4.0+ 可设 consumer 启用新 Rebalance 协议（KIP-848）

    新协议（KIP-848）下的 broker 端组级配置（开启 group.protocol=consumer 时生效）：

    配置（broker 端） 默认值 说明
    group.consumer.session.timeout.ms 45000 判活超时（替代客户端 session.timeout.ms）
    group.consumer.heartbeat.interval.ms 5000 心跳间隔
    group.consumer.assignors [uniform, range] 服务端 assignor，客户端可用 group.remote.assignor 选择
