    12_并发编程原理¶

    前置：已学完 01_多线程基础、07_并发工具类详解、08_原子类、10_ThreadLocal。本篇汇总并发面试重灾区：synchronized 原理、JMM、AQS、锁、线程池原理与高频陷阱。 基于 JDK 17（注意：偏向锁自 JDK 15 起默认禁用）。

    本篇总览： - ⭐ synchronized 本质是对象头的 Monitor（monitorenter/monitorexit），锁升级是"无竞争优化" - ⭐ JMM 解决可见性/有序性：volatile 靠内存屏障 + happens-before 规则 - ⭐ AQS 是并发包的基石：state + CLH 队列，ReentrantLock/Semaphore/CountDownLatch 都基于它 - ⭐ 线程池七参数 + 四种拒绝策略 + 执行流程，面试必考 - ⚠️ 三大陷阱：双重检查锁缺 volatile、ThreadLocal 内存泄漏、死锁四条件

    2. synchronized 原理深挖 ⭐⭐⭐⭐¶

    知识点： - ⭐ synchronized 编译后是 monitorenter/monitorexit 指令，本质是对象头里的 Monitor 锁 - ⭐ 对象头 Mark Word 存锁状态；锁升级：无锁 → 偏向 → 轻量级（CAS）→ 重量级（OS mutex） - ⚠️ JDK 15+ 偏向锁默认禁用（-XX:+UseBiasedLocking 需显式开启）

    2.1 Monitor 与对象头¶

    每个 Java 对象头里都有一个 Mark Word（64 位 JVM 占 8 字节）：

┌──────────────────────────────────────────────┐
│ Mark Word（8 字节）                            │
│   无锁：   hashCode + 分代年龄 + 锁标志 01     │
│   偏向锁： 线程 ID + epoch + 锁标志 01（1）    │
│   轻量级： 指向栈中锁记录的指针 + 锁标志 00     │
│   重量级： 指向 Monitor 的指针 + 锁标志 10     │
└──────────────────────────────────────────────┘

    // synchronized 编译后的字节码（javap -c 可见）：
public void syncMethod() {
    synchronized (this) {
        // monitorenter        ← 进入：获取对象监视器
        // ...业务代码...
        // monitorexit         ← 退出：释放（正常/异常路径各一份）
    }
}

    Monitor 三个关键区： - Owner：当前持锁线程 - EntryList：等待获取锁的线程（阻塞） - WaitSet：调用 wait() 后等待的线程（notify 唤醒后回 EntryList 竞争）

    2.2 锁升级过程 ⭐¶

    无锁 → 偏向锁 → 轻量级锁 → 重量级锁（单向升级，不降级）

① 偏向锁：只有一个线程访问时，Mark Word 记下线程 ID，
   下次进入不用任何同步操作（但 JDK 15+ 默认禁用）
② 轻量级锁：出现第二个线程竞争，用 CAS 把 Mark Word
   换到线程栈的 Lock Record——无竞争时避免内核态切换
③ 重量级锁：CAS 失败（真实竞争），膨胀为 Monitor，
   未获锁线程进 EntryList 阻塞（涉及内核态切换，慢）

    ⚠️ 面试常问"锁能降级吗"：HotSpot 实际不降级（GC 时会回收锁记录，但运行中不会重量级→轻量级）。答"单向升级"最稳。

    2.3 synchronized 三种用法¶

    public class SyncDemo {
    private final Object lock = new Object();

    public void method() {
        synchronized (lock) { }        // ① 锁指定对象
    }

    public synchronized void m2() { }  // ② 锁 this（实例方法）

    public static synchronized void m3() { }  // ③ 锁 Class 对象（静态方法）
}

    ⚠️ 经典坑：①锁的是 lock 对象，②锁的是 this，③锁的是 SyncDemo.class——三把锁互不相干，同时用会以为互斥其实没互斥。

    3. JMM 与 happens-before ⭐⭐⭐⭐¶

    知识点： - ⭐ JMM 解决三大问题：原子性（synchronized/CAS）、可见性（volatile）、有序性（happens-before） - ⭐ volatile 两语义：可见性（写立即刷主内存）+ 禁止指令重排（内存屏障） - ⚠️ volatile 不保证原子性（i++ 不是原子的，用 AtomicInteger）

    3.1 JMM 内存模型¶

    线程A 工作内存（CPU 缓存/寄存器）      线程B 工作内存
    │   x=1（改了没刷回）                  │  x=0（读到旧值）
    └──────────► 主内存（x）◄──────────────┘

可见性问题：线程A 的修改，线程B 不一定看得到
有序性问题：编译器/CPU 会重排指令，单线程无影响，多线程出错

    3.2 volatile 原理¶

    写 volatile 变量：
    StoreStore 屏障 → 写操作 → StoreLoad 屏障（强制刷主内存）

读 volatile 变量：
    读操作 → LoadLoad/LoadStore 屏障（强制从主内存读）

效果：
✅ 可见性：写后立即对其他线程可见
✅ 有序性：屏障禁止前后的指令重排
❌ 原子性：count++（读-改-写三步）仍然不安全

    3.3 happens-before 八大规则 ⭐¶

    ① 程序次序：同一线程内，代码按顺序执行
② 监视器锁：unlock 先于后续对同一锁的 lock
③ volatile：写先于后续对该变量的读
④ 线程启动：Thread.start() 先于子线程的任何操作
⑤ 线程终止：子线程的所有操作先于其他线程检测到它终止
⑥ 线程中断：interrupt() 先于被中断线程检测到中断
⑦ 对象终结：构造函数先于 finalize()
⑧ 传递性：A hb B，B hb C，则 A hb C

    💡 happens-before 不是说"A 物理时间在 B 之前"，而是"A 的结果对 B 可见"——这是面试加分答法。

    3.4 经典案例：双重检查锁（DCL）¶

    public class Singleton {
    // ⚠️ 必须加 volatile！
    private static volatile Singleton instance;

    public static Singleton getInstance() {
        if (instance == null) {                    // 第一次检查（无锁）
            synchronized (Singleton.class) {
                if (instance == null) {            // 第二次检查（有锁）
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}

    为什么必须 volatile？ new Singleton() 不是原子的，分三步：

    ① 分配内存
② 初始化对象
③ 把引用指向内存

    指令重排可能变成 ①→③→②：线程A 执行到 ③ 时（引用非 null 但对象未初始化），线程B 第一次检查发现 instance != null 直接拿去用——拿到半初始化对象。volatile 禁止 ②③ 重排。

    4. AQS 原理 ⭐⭐⭐⭐¶

    知识点： - ⭐ AQS（AbstractQueuedSynchronizer）= state（int 状态）+ CLH 变体双向队列（等待线程排队） - ⭐ ReentrantLock、Semaphore、CountDownLatch、ReentrantReadWriteLock 都基于 AQS - 独占模式（ReentrantLock）vs 共享模式（Semaphore/CountDownLatch）

    4.1 AQS 结构¶

    AbstractQueuedSynchronizer：

state（volatile int）—— 同步状态
  ReentrantLock：0=无人持锁，>0=重入次数
  Semaphore：剩余许可数
  CountDownLatch：剩余计数

CLH 队列（双向链表）：
  head ⇄ Node(线程A) ⇄ Node(线程B) ⇄ tail
         等待获锁/获许可的线程在这里排队（park 阻塞）

    4.2 以 ReentrantLock 为例¶

    lock() 流程（非公平锁）：
① CAS(state, 0→1)：成功 → 直接获锁（插队，所以叫非公平）
② 失败 → 检查是否重入（当前线程已持锁 → state+1）
③ 还不行 → 包装成 Node 进队列尾部，park() 阻塞
④ 前驱释放后，unpark 被唤醒，重新竞争

unlock() 流程：
① state-1；减到 0 时真正释放
② unpark 队列里下一个等待线程

    公平 vs 非公平：

    对比 非公平锁（默认） 公平锁
    获锁策略 新线程先 CAS 插队 必须排队
    吞吐量 ✅ 高（少线程切换） 较低
    饥饿 ⚠️ 可能 ✅ 不会
    用法 new ReentrantLock() new ReentrantLock(true)

    4.3 手写极简互斥锁（理解 AQS）¶

    import java.util.concurrent.locks.AbstractQueuedSynchronizer;

/** 基于 AQS 的不可重入互斥锁（教学用） */
public class SimpleLock {
    private final Sync sync = new Sync();

    static class Sync extends AbstractQueuedSynchronizer {
        // 尝试获锁：state 0→1 成功
        protected boolean tryAcquire(int arg) {
            return compareAndSetState(0, 1);
        }
        // 尝试释放：state 1→0
        protected boolean tryRelease(int arg) {
            setState(0);
            return true;
        }
    }

    public void lock() { sync.acquire(1); }      // 失败自动排队阻塞
    public void unlock() { sync.release(1); }    // 唤醒下一个
}

    💡 看懂这段就懂了并发包一半：CountDownLatch 只需把 tryAcquire 改成"state==0 才成功"、tryRelease 改成"state-1"。

    5. 锁分类与选择 ⭐⭐⭐¶

    锁类型 代表 特点 适用场景
    乐观锁 CAS/AtomicInteger 无阻塞，冲突重试 读多写少、竞争轻
    悲观锁 synchronized/ReentrantLock 先加锁再操作 写多、竞争激烈
    可重入锁 ReentrantLock/synchronized 同线程可重复获锁 递归调用防死锁
    读写锁 ReentrantReadWriteLock 读读并发，读写/写写互斥 读远多于写
    自旋锁 CAS 循环 忙等不切换线程 锁持有时间极短
    分段思想 ConcurrentHashMap（JDK7） 降低锁粒度 高并发容器 
    // 读写锁实战：缓存（读多写少）
private final ReadWriteLock rwLock = new ReentrantReadWriteLock();
private final Map<String, Object> cache = new HashMap<>();

public Object get(String key) {
    rwLock.readLock().lock();          // 多个读并发
    try { return cache.get(key); }
    finally { rwLock.readLock().unlock(); }
}

public void put(String key, Object val) {
    rwLock.writeLock().lock();         // 写时独占
    try { cache.put(key, val); }
    finally { rwLock.writeLock().unlock(); }
}

    选择口诀： 1. 能用原子类/并发容器就不用锁 2. 必须用锁：临界区短选 synchronized（JIT 优化好），要超时/中断/公平选 ReentrantLock 3. 读多写少上读写锁 4. 锁对象要 private final，别锁 String 常量/Integer 缓存

    6. 线程池原理 ⭐⭐⭐⭐¶

    知识点： - ⭐ 七参数：corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler - ⭐ 执行顺序：核心线程 → 队列 → 最大线程 → 拒绝策略 - ⚠️ 不要用 Executors 创建（队列无界/线程数无上限 → OOM）

    6.1 执行流程（必背）¶

    提交任务
  │
  ├─① 核心线程数未满 → 创建核心线程执行
  │
  ├─② 核心满 → 任务入队列排队
  │
  ├─③ 队列满 → 创建非核心线程（直到 maximumPoolSize）
  │
  └─④ 都满了 → 执行拒绝策略

    6.2 四种拒绝策略¶

    策略 行为 适用
    AbortPolicy（默认） 抛 RejectedExecutionException 快速失败，上层感知
    CallerRunsPolicy ⭐ 调用者线程自己跑 降速不丢任务
    DiscardPolicy 静默丢弃 可丢弃任务
    DiscardOldestPolicy 丢队头再提交 只要新任务

    6.3 参数怎么定¶

    CPU 密集型：线程数 ≈ CPU 核数 + 1（多了只是切换开销）
IO 密集型：线程数 ≈ 核数 × 2（或 核数 × (1 + IO等待时间/CPU时间)）

队列选择：
- LinkedBlockingQueue（有界！指定容量）：吞吐优先
- ArrayBlockingQueue：有界，公平可选
- SynchronousQueue：不存任务，直接交接（CachedThreadPool 用）

    // 生产标准写法
ExecutorService pool = new ThreadPoolExecutor(
    8, 16, 60L, TimeUnit.SECONDS,        // 核心/最大/存活
    new LinkedBlockingQueue<>(1000),      // 有界队列
    new ThreadFactoryBuilder().setNameFormat("biz-%d").build(),
    new ThreadPoolExecutor.CallerRunsPolicy()  // 拒绝不丢任务
);

    ⚠️ Executors.newFixedThreadPool 用无界队列、newCachedThreadPool 线程数无上限——都是 OOM 隐患，这是强制用 ThreadPoolExecutor 的根本原因。

    7. 高频并发陷阱 ⭐⭐⭐¶

    7.1 死锁四条件与排查¶

    四个必要条件（破坏任一即可避免）：
① 互斥 ② 持有并等待 ③ 不可剥夺 ④ 循环等待

排查：jstack <pid> 直接输出 "Found one Java-level deadlock"
预防：多资源加锁保持固定顺序（破坏循环等待）

    7.2 ThreadLocal 内存泄漏（回顾）¶

    ThreadLocalMap 的 Entry 用弱引用指向 key，但 value 是强引用：
线程池复用线程 → Thread 不死 → value 一直存在 → 泄漏
规则：用完必须 remove()，放 finally 里

    7.3 其他易错点¶

    ❌ HashMap 多线程 put → 数据丢失/死循环（JDK7 头插法），用 ConcurrentHashMap
❌ SimpleDateFormat 共享 → 解析错乱，用 DateTimeFormatter
❌ i++ 用 volatile → 仍非原子，用 AtomicInteger
❌ 锁 String 常量 → 全局互斥（常量池同一个对象）
❌ 先 notify 后 wait 的顺序错误 → 永久等待

    8. 高频面试题¶

    Q1：synchronized 和 ReentrantLock 的区别？

    都是可重入锁。区别：①实现层面——synchronized 是 JVM 内置（monitorenter/字节码），ReentrantLock 是 JDK 类（AQS）；②功能——ReentrantLock 支持公平锁、可中断获锁（lockInterruptibly）、超时尝试（tryLock）、多条件变量（Condition）；③释放——synchronized 自动，ReentrantLock 必须 finally 手动 unlock。临界区短优先 synchronized，需要高级特性用 ReentrantLock。

    Q2：volatile 能保证线程安全吗？

    不能完全保证。它保证可见性和禁止重排，但不保证原子性——count++ 这种读-改-写复合操作仍不安全，要用 AtomicInteger 或锁。经典应用是 DCL 单例中防止 new 的指令重排。

    Q3：说说 AQS 原理？

    AQS 用一个 volatile int state 表示同步状态，加一个 CLH 变体的双向队列管理等待线程。获锁失败的线程包装成 Node 入队并 park 阻塞；释放时更新 state 并 unpark 队首后继。独占模式（ReentrantLock）和共享模式（Semaphore/CountDownLatch）分别重写 tryAcquire/tryAcquireShared。

    Q4：线程池的执行流程？参数怎么配？

    流程：核心线程 → 队列 → 非核心线程 → 拒绝策略。参数：CPU 密集 ≈ 核数+1，IO 密集 ≈ 2×核数；队列必须有界；拒绝策略按业务选（不能丢任务用 CallerRuns）。禁用 Executors 工厂方法，因为队列/线程数无界会 OOM。

    Q5：DCL 单例为什么要加 volatile？

    new 分三步：分配内存 → 初始化 → 赋引用。无 volatile 时后两步可能重排，别的线程可能拿到非 null 但未初始化的对象。volatile 禁止重排并保证可见性。

    Q6：Java 怎么实现原子操作？

    两条路：锁（synchronized/ReentrantLock，悲观）和 CAS（AtomicInteger/LongAdder，乐观）。CAS 靠 CPU 的 cmpxchg 指令 + 自旋，注意 ABA 问题（AtomicStampedReference 加版本号）、自旋开销（LongAdder 分段累加缓解）。

    参考答案¶

    // ========== 练习 1：锁对象辨析 ==========
// a.m1() 锁的是实例 a 的 this；b.m2() 锁的是实例 b 的 this
// → 两把不同的锁，不互斥，可并发执行
// a.m1() 锁 this（a 实例），SyncDemo.m3() 锁 SyncDemo.class
// → 还是两把不同的锁，也不互斥！
// 想让实例方法和静态方法互斥，必须显式锁同一个对象：
//   synchronized (SyncDemo.class) { ... } 两边都用它

// ========== 练习 2：happens-before ==========
// 有 volatile：写 x hb 读 x（规则③），B 一定读到 1，且能
//   看到写 x 之前的所有操作（传递性⑧）
// 无 volatile：不保证！B 可能读到旧值（可见性问题），
//   即使最终读到 1，也不保证看到之前的相关写入

// ========== 练习 3：OneShotLatch ==========
import java.util.concurrent.locks.AbstractQueuedSynchronizer;

public class OneShotLatch {
    private final Sync sync = new Sync();

    static class Sync extends AbstractQueuedSynchronizer {
        // 共享获锁：门开（state=1）才成功
        protected int tryAcquireShared(int arg) {
            return getState() == 1 ? 1 : -1;
        }
        // 共享释放：开门（0→1），只开一次
        protected boolean tryReleaseShared(int arg) {
            setState(1);
            return true;
        }
    }

    public void await() { sync.acquireShared(1); }   // 门关则排队
    public void signal() { sync.releaseShared(1); }  // 开门 + 唤醒全部
}

    10. 本章小结¶

    核心知识点： - ✅ synchronized = 对象头 Monitor；锁升级：偏向→轻量级（CAS）→重量级 - ✅ JMM 三大问题：原子性/可见性/有序性；volatile 保证前两者不保证原子性 - ✅ happens-before 是"可见性承诺"，不是物理时间先后 - ✅ AQS = state + CLH 队列；独占/共享两种模式撑起半个并发包 - ✅ 线程池流程：核心→队列→最大→拒绝；参数按 CPU/IO 密集定 - ✅ DCL 必须加 volatile；ThreadLocal 必须 remove

    最佳实践： 1. 优先无锁方案：原子类 > 并发容器 > 锁 2. 锁粒度要小，锁对象要 private final 3. 线程池显式用 ThreadPoolExecutor，队列有界、线程命名 4. 多锁场景固定加锁顺序，破坏死锁的循环等待条件 5. volatile 只用于一写多读的标志位，计数用 AtomicInteger
