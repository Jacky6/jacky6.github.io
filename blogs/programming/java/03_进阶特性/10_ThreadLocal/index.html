    1. ThreadLocal 概述¶

    知识点：

    • ⭐ ThreadLocal 为每个线程提供独立变量副本，线程隔离，天然免锁
    • 与锁互补：锁解决"共享数据互斥"，ThreadLocal 解决"每人一份数据"
    • 典型场景：数据库连接绑定、Web 请求用户上下文、链路追踪 traceId、SimpleDateFormat 包装

    1.1 什么是 ThreadLocal¶

    ThreadLocal 为每个线程提供独立的变量副本，实现线程隔离：每个线程访问的都是自己私有的那份数据，天然线程安全，无需加锁。

    ThreadLocal<String> tl = new ThreadLocal<>();

new Thread(() -> {
    tl.set("线程A的数据");
    System.out.println(tl.get());  // 线程A的数据
}).start();

new Thread(() -> {
    System.out.println(tl.get());  // null（B 线程看到的是自己的副本，不受 A 影响）
}).start();

    一句话：锁（synchronized/ReentrantLock）解决的是"多线程共享数据时的互斥"，ThreadLocal 解决的是"让每个线程拥有自己的数据"。

    1.2 典型使用场景¶

    场景 说明
    数据库连接/Session 每个线程绑定自己的 Connection（Spring 事务就是这么做的）
    用户上下文 Web 请求中保存当前登录用户，全链路随取随用
    日期格式化器 SimpleDateFormat 非线程安全，每线程一份
    链路追踪 ID traceId 贯穿一次请求的所有日志 
    // 经典场景：SimpleDateFormat 线程不安全
// ❌ 共享一个实例，多线程 format 会出错
// ✅ 每个线程一份
private static final ThreadLocal<SimpleDateFormat> DATE_FORMAT =
    ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

String s = DATE_FORMAT.get().format(new Date());

    2. 基本使用¶

    知识点：

    • 核心三方法：set / get / remove；withInitial(Supplier) 提供初始值
    • ⚠️ 线程池场景用完必须 remove，否则线程复用导致数据串号/内存泄漏
    • Web 框架通常在拦截器入口 set、出口 clear

    2.1 常用方法¶

    ThreadLocal<Integer> tl = new ThreadLocal<>();

tl.set(100);                  // 设置当前线程的值
Integer v = tl.get();         // 获取当前线程的值
tl.remove();                  // 删除当前线程的值（重要！防内存泄漏）

// 带初始值的写法（推荐）：get 时如果没 set 过，自动调用 initialValue()
ThreadLocal<Integer> withInit = ThreadLocal.withInitial(() -> 0);

    2.2 实战：Web 请求的用户上下文¶

    // 1. 上下文持有者
public class UserContext {
    private static final ThreadLocal<User> HOLDER = new ThreadLocal<>();

    public static void set(User user) { HOLDER.set(user); }
    public static User get()          { return HOLDER.get(); }
    public static void clear()        { HOLDER.remove(); }
}

// 2. 拦截器：请求进入时 set，请求结束时 clear
public class LoginInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse resp, Object handler) {
        User user = parseToken(req);   // 从 token 解析用户
        if (user != null) {
            UserContext.set(user);
        }
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest req, HttpServletResponse resp,
                                Object handler, Exception ex) {
        UserContext.clear();  // ⭐ 必须清理，否则线程池复用线程时会"串数据"
    }
}

// 3. 业务代码中随取随用，无需层层传参
public Order createOrder(OrderDTO dto) {
    Long userId = UserContext.get().getId();
    // ...
}

    3. 底层原理 ⭐⭐⭐⭐¶

    知识点：

    • ⭐ 数据不存在 ThreadLocal 里，而是存在每个 Thread 的 threadLocals（ThreadLocalMap） 里，key 是 ThreadLocal 实例
    • ⭐ Entry 的 key 是弱引用、value 是强引用——key 被 GC 后 value 残留 → 内存泄漏根因
    • ThreadLocalMap 用开放地址法解决冲突，hashCode 用黄金分割数 0x61c88647 递增

    3.1 存储结构¶

    关键认知：数据不是存在 ThreadLocal 对象里，而是存在每个 Thread 对象里。

    每个 Thread 对象内部：
class Thread {
    ThreadLocal.ThreadLocalMap threadLocals = null;  // 真正存数据的地方
}

ThreadLocalMap 的结构（简化）：
┌──────────────────────────────────────────┐
│ Entry[] table（哈希表）                    │
│  ┌─────────┬─────────┬─────────┐         │
│  │ Entry   │ Entry   │ Entry   │ ...     │
│  └─────────┴─────────┴─────────┘         │
│  Entry 继承 WeakReference<ThreadLocal<?>> │
│  Entry.key   = ThreadLocal 对象（弱引用）  │
│  Entry.value = 存的值（强引用）            │
└──────────────────────────────────────────┘

    调用关系：

    tl.set(value);
// 实际执行：
Thread t = Thread.currentThread();          // 拿到当前线程
ThreadLocalMap map = t.threadLocals;        // 拿线程内部的 Map
map.set(this, value);                       // key = 这个 ThreadLocal 对象

tl.get();
// 实际执行：拿当前线程的 Map，用 this 作 key 查出 value

    为什么这样设计？

    • 每个线程有自己的 Map，存取时不存在竞争，天然线程安全
    • 一个线程可以用多个 ThreadLocal，都以 ThreadLocal 实例为 key 存在同一个 Map 里

    3.2 ThreadLocalMap 的哈希冲突：开放地址法¶

    ThreadLocalMap 没有用链表解决冲突，而是开放地址法（线性探测）：

    // 定位：i = key.threadLocalHashCode & (len - 1)
// 冲突时：i = nextIndex(i, len)，向后找下一个空位

    原因：

    • ThreadLocalMap 通常元素不多，开放地址法内存更紧凑（不需要 Node 对象）
    • ThreadLocal 的 hashCode 用黄金分割数 0x61c88647 累加生成，分布非常均匀，冲突概率低
    // ThreadLocal 源码
private static final int HASH_INCREMENT = 0x61c88647;
private static AtomicInteger nextHashCode = new AtomicInteger();
// 每个 ThreadLocal 实例的 hashCode = 上一个 + 0x61c88647（模 2^32）

    3.3 内存泄漏问题 ⭐⭐⭐⭐（必问）¶

    先看引用链：

    线程栈
  └─ Thread 对象
       └─ ThreadLocalMap
            └─ Entry[]
                 ├─ key ──弱引用──→ ThreadLocal 对象 ←──强引用── 外部变量（如 static 字段）
                 └─ value ──强引用──→ 存储的对象

    泄漏是怎么发生的：

    1. Entry 的 key 是弱引用：当外部对 ThreadLocal 的强引用消失（如方法结束、局部变量置空），GC 会回收 ThreadLocal 对象 → key 变成 null
    2. 但 value 是强引用，且 Entry 挂在 Thread 的 Map 上
    3. 如果线程长期存活（线程池里的线程就是），这个 key=null、value 非 null 的 Entry 永远无法被访问到，也永远不被回收 → 内存泄漏

    为什么 key 要设计成弱引用？ 如果 key 是强引用，ThreadLocal 对象被置空后，Entry 仍然强引用着它，连 key 都回收不了，泄漏更彻底。弱引用至少让 key 能被回收，给 ThreadLocalMap 的自清理（get/set 时会顺手清理 key=null 的 Entry）留了机会。

    正确做法：用完必须 remove！

    try {
    threadLocal.set(context);
    // 业务逻辑
} finally {
    threadLocal.remove();  // ⭐ 强制清理，不依赖弱引用的自清理
}

    记忆口诀："弱引用防泄漏只是缓解，remove 才是根治；线程池场景必须 remove"。

    3.4 ThreadLocal 与线程池：数据污染¶

    线程池的线程是复用的。若任务结束没 remove，下一个任务复用同一线程时，get() 会拿到上一个任务残留的数据——轻则逻辑错误，重则用户数据串号（A 用户看到了 B 的信息）。这就是 2.2 节拦截器里 afterCompletion 必须 clear 的原因。

    4. InheritableThreadLocal 与线程传递¶

    知识点：

    • ⭐ InheritableThreadLocal 只在 new Thread() 那一刻把父线程值拷贝给子线程
    • ⚠️ 线程池的线程是提前创建复用的 → InheritableThreadLocal 失效
    • 跨线程池传递上下文用阿里的 TransmittableThreadLocal（TTL）

    4.1 父子线程传递¶

    普通 ThreadLocal 的值不会传给子线程。InheritableThreadLocal 可以在创建子线程时把父线程的值拷贝过去：

    ThreadLocal<String> tl = new InheritableThreadLocal<>();
tl.set("父线程的值");

new Thread(() -> {
    System.out.println(tl.get());  // 父线程的值（创建时拷贝）
}).start();

    4.2 线程池场景的失效与 TransmittableThreadLocal¶

    InheritableThreadLocal 只在 new Thread() 那一刻拷贝。线程池的线程是复用的、早就创建好了，提交任务时不会重新拷贝 → 失效。

    阿里开源的 TransmittableThreadLocal（TTL） 解决了这个问题：在任务提交/执行时捕获并恢复上下文，是线程池 + 链路追踪（traceId 透传）场景的标准方案。

    // TTL 用法（依赖 com.alibaba:transmittable-thread-local）
TransmittableThreadLocal<String> ttl = new TransmittableThreadLocal<>();
ttl.set("trace-123");

// 用 TtlRunnable 包装任务，或 TtlExecutors 包装线程池
ExecutorService pool = TtlExecutors.getTtlExecutorService(rawPool);
pool.submit(() -> System.out.println(ttl.get()));  // trace-123 ✅

    5. 源码中的设计思想（进阶）¶

    知识点：

    • ThreadLocalMap 挂在 Thread 上而非反过来：线程销毁时整个 Map 随线程一起回收，干净
    • get/set/remove 时会顺手清理 key=null 的 Entry（expungeStaleEntry）——但只是缓解，根治靠显式 remove

    5.1 为什么 ThreadLocalMap 是 Thread 的成员而不是反过来？¶

    如果"一个 ThreadLocal 持有一个 Map"：

    • Thread 对象作为 key 需要弱引用管理，更复杂
    • 线程销毁时清理麻烦

    现在的设计（Map 挂在 Thread 上）：线程销毁时，整个 Map 跟着回收，干净利落。

    5.2 get/set 时的自清理¶

    ThreadLocalMap 在 get/set/remove 时会探测性地清理一部分 key=null 的 Entry（expungeStaleEntry），这是弱引用设计的配套机制——但它是"顺手的"，不能替代显式 remove。

    6. JDK 21+：ScopedValue（了解）¶

    虚拟线程时代，每个虚拟线程都带一个 ThreadLocalMap 成本太高，且 ThreadLocal 的可变性、无界生命周期不利于并发编程。JDK 21 引入了 ScopedValue（预览特性，JEP 446）：

    // 不可变、作用域结束自动释放、可被结构化并发继承
static final ScopedValue<User> CURRENT_USER = ScopedValue.newInstance();

ScopedValue.where(CURRENT_USER, user).run(() -> {
    // 作用域内任何调用链都能读到
    User u = CURRENT_USER.get();
});
// 作用域结束自动释放，无需手动 remove

    目前仍是预览 API，生产代码继续用 ThreadLocal + remove 即可，但面试可以提一句这个演进方向。

    7. 常见面试题¶

    Q1：ThreadLocal 的原理？ 每个 Thread 内部有一个 ThreadLocalMap，以 ThreadLocal 实例为 key 存储值。get/set 操作的都是当前线程自己的 Map，所以线程隔离、无需加锁。

    Q2：ThreadLocal 为什么会内存泄漏？怎么避免？ Entry 的 key 是 ThreadLocal 的弱引用，key 被 GC 后变成 null，但 value 是强引用且挂在线程上；线程长期存活（线程池）时这个 Entry 无法回收。避免：用完在 finally 中 remove。

    Q3：为什么 key 是弱引用？ 让不再使用的 ThreadLocal 对象能被 GC 回收（强引用则完全回收不了），并给 ThreadLocalMap 的自清理机制留机会。但弱引用只是缓解，根治靠 remove。

    Q4：ThreadLocal 在线程池中要注意什么？ 线程复用会导致：① 上个任务的数据残留（数据污染）；② 内存泄漏。必须在 finally 中 remove。需要跨线程池传递上下文时用 TransmittableThreadLocal。

    Q5：InheritableThreadLocal 能解决线程池的上下文传递吗？ 不能。它只在 new Thread() 时拷贝一次，线程池的线程是提前创建复用的。要用 TTL（TransmittableThreadLocal）。

    Q6：ThreadLocalMap 怎么解决哈希冲突？ 开放地址法（线性探测），不是链表。因为元素少、hashCode 用黄金分割数递增分布均匀。

    8. 练习题¶

    练习 1（基本使用）：创建一个 ThreadLocal，在两个线程中分别 set 不同值，验证互不影响。

    练习 2（SimpleDateFormat）：用 ThreadLocal 包装 SimpleDateFormat，写一个线程安全的 format(Date) 工具方法。

    练习 3（用户上下文）：实现 UserContext 类（set/get/clear），写一个模拟"请求进入 set → 业务读取 → 请求结束 clear"的完整流程，并用线程池连续执行两个任务，验证不 remove 时会发生数据污染（第二个任务 get 到第一个的数据）。

    参考答案¶

    import java.text.SimpleDateFormat;
import java.util.Date;
import java.util.concurrent.*;

public class ThreadLocalExercises {

    public static void main(String[] args) throws Exception {
        // 练习 1：线程隔离验证
        ThreadLocal<Integer> tl = new ThreadLocal<>();
        new Thread(() -> {
            tl.set(1);
            System.out.println("线程1: " + tl.get());  // 1
        }).start();
        new Thread(() -> {
            tl.set(2);
            System.out.println("线程2: " + tl.get());  // 2
        }).start();
        // 各线程读写自己的副本，互不干扰

        // 练习 2：线程安全的日期格式化
        System.out.println(DateUtil.format(new Date()));

        // 练习 3：数据污染演示
        ThreadLocal<String> context = new ThreadLocal<>();
        ExecutorService pool = Executors.newFixedThreadPool(1);  // 单线程池，必然复用
        pool.submit(() -> context.set("用户A"));
        Thread.sleep(100);
        pool.submit(() -> {
            // 没有 remove，复用同一线程 → 读到上一个任务残留的"用户A"
            System.out.println("本任务读到：" + context.get());  // 用户A（污染！）
        });
        Thread.sleep(100);
        pool.shutdown();
        // 正确做法：每个任务 finally { context.remove(); }
    }

    // 练习 2
    static class DateUtil {
        private static final ThreadLocal<SimpleDateFormat> FMT =
            ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd HH:mm:ss"));

        public static String format(Date date) {
            return FMT.get().format(date);
        }
    }
}

    9. 本章小结¶

    核心知识点¶

    ✅ 定位：线程隔离方案，每线程独立副本，无锁线程安全
    ✅ 原理：数据存在 Thread.threadLocals（ThreadLocalMap）里，key 是 ThreadLocal 实例
    ✅ 冲突解决：开放地址法 + 黄金分割 hashCode
    ✅ 内存泄漏：key 弱引用 / value 强引用 + 线程长期存活 → 必须 remove
    ✅ 传递：InheritableThreadLocal（父子线程）、TransmittableThreadLocal（线程池）
    ✅ 演进：JDK 21 ScopedValue（预览）面向虚拟线程

    最佳实践¶

    1. ThreadLocal 尽量声明为 private static final
    2. 用完必须 remove（finally 中），尤其是线程池场景
    3. Web 框架中在拦截器/过滤器的出口统一清理
    4. 需要跨线程池传递上下文时引入 TransmittableThreadLocal
    5. 优先 ThreadLocal.withInitial() 提供初始值，避免 get 到 null
