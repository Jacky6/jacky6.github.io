    05_Java 编码规范¶

    参考《阿里巴巴 Java 开发手册（泰山版）》、Google Java Style、Clean Code 整理 规则分级：【强制】必须遵守 | 【推荐】应该遵守 | 【参考】视场景决定

    一、命名规范¶

    1.1 通用规则¶

    • 【强制】代码中的命名均不能以下划线或美元符号开始或结束
    • 【强制】代码中的命名均不能使用拼音命名（国际通用的除外，如 alibaba、taobao）
    • 【强制】类名使用 UpperCamelCase；方法名、参数名、成员变量、局部变量统一使用 lowerCamelCase
    • 【强制】常量命名全部大写，单词间用下划线隔开：MAX_RETRY_COUNT
    • 【强制】抽象类命名使用 Abstract 或 Base 开头；异常类命名以 Exception 结尾；测试类以被测目标类名 + Test 结尾
    • 【强制】包名统一使用小写，点分隔符之间有且仅有一个自然语义的英语单词，包名统一使用单数形式
    • 【推荐】杜绝完全不规范的缩写，避免望文不知义

    1.2 命名对照表¶

    类型          风格               示例
─────────────────────────────────────────────────────
包名          全小写单数          com.company.project.user
类名          UpperCamelCase     UserService, OrderController
方法名        lowerCamelCase     getUserById(), calculateTotal()
局部变量      lowerCamelCase     userName, orderList
常量          UPPER_SNAKE_CASE   MAX_POOL_SIZE, DEFAULT_TIMEOUT
布尔变量      禁止 is 前缀*      success, deleted, active
接口          不加 I 前缀        PaymentService（实现类加 Impl）
枚举类        带 Enum 后缀       OrderStatusEnum
POJO 布尔     禁止 is 前缀       private Boolean deleted;

    *注：POJO 类中布尔类型变量加 is 前缀，序列化时部分框架会解析出错。

    1.3 领域模型命名¶

    数据对象：xxxDO（与数据库表一一对应）
数据传输：xxxDTO（远程调用对象）
展示对象：xxxVO（通常是 Web 向模板渲染层返回）
查询对象：xxxQuery（数据查询对象，封装超过 2 个参数时用）

    二、常量与变量¶

    • 【强制】不允许任何魔法值（未经预先定义的常量）直接出现在代码中
    • 【强制】long 或 Long 赋值时，数值后使用大写 L，小写 l 易和数字 1 混淆
    • 【强制】常量按功能归类到不同常量类，不建一个 Consts 类维护所有常量
    • 【强制】变量必须在定义时赋初值（或确保使用前已赋值），编译器不会帮你检查未初始化的局部变量所有路径
    • 【推荐】不要使用一个类的对象去访问静态变量或静态方法，直接用类名访问
    • 【推荐】接口中的常量不要加 public static final 修饰（冗余）
    // 反例：魔法值
if (user.getType() == 2) { ... }

// 正例：常量定义
public static final int USER_TYPE_VIP = 2;
if (user.getType() == USER_TYPE_VIP) { ... }

// 更优：用枚举
if (user.getType() == UserTypeEnum.VIP) { ... }

    三、代码格式¶

    • 【强制】如果大括号内为空，则简洁地写成 {} 即可；非空时左大括号前不换行，左大括号后换行，右大括号前换行
    • 【强制】左小括号与右边相邻字符之间不出现空格；右小括号与左边相邻字符之间不出现空格
    • 【强制】任何二目、三目运算符的左右两边都需要加一个空格
    • 【强制】单行字符数限制不超过 120 个，超出需要换行，换行时第二行相对第一行缩进 4 个空格
    • 【强制】方法参数在定义和传入时，多个参数逗号后面必须加空格
    • 【强制】IDE 的 text file encoding 设置为 UTF-8；不同逻辑、不同语义、不同业务的代码之间插入一个空行分隔
    • 【推荐】单个方法总行数不超过 80 行（不含注释、空行）
    • 【推荐】单行注释使用 //，且单独一行放在所注释代码的上一行
    // 正例
int result = a + b * (c - d) / 2;

// 反例：运算符两侧无空格
int result = a+b*(c-d)/2;

    四、OOP 规约¶

    • 【强制】避免通过一个类的对象引用访问此类的静态变量或静态方法
    • 【强制】所有的覆写方法，必须加 @Override 注解
    • 【强制】相同参数类型、相同业务含义，才可以使用 Java 的可变参数，避免使用 Object...（可变参数必须放置在参数列表的最后）
    • 【强制】外部正在调用的接口，不允许修改方法签名，可以用 @Deprecated 注解 + 说明新接口
    • 【强制】Object 的 equals 方法容易抛空指针异常，应使用常量或确定有值的对象来调用："test".equals(obj)
    • 【强制】所有整型包装类对象之间值的比较，全部使用 equals 方法（== 比较的是引用）
    • 【强制】任何货币金额，均以最小货币单位且整型存储；浮点数之间等值判断用 BigDecimal
    • 【强制】定义数据对象、类成员变量时，不要使用 BigDecimal 默认构造（用 BigDecimal("0.1") 或 BigDecimal.valueOf(0.1)）
    • 【强制】POJO 类必须写 toString（或依赖 Lombok @Data），便于调试
    • 【强制】构造方法里禁止加入任何业务逻辑，如需初始化用 init 方法
    • 【强制】类内方法定义的顺序：公有方法 > 保护方法 > 私有方法（被调用方法紧跟调用方法之后）
    • 【推荐】类内方法行数不超过 80 行；方法参数不超过 5 个，超过则封装为对象
    • 【推荐】final 可以声明类、成员变量、方法、以及本地变量，适当使用：不允许被继承的类、不允许修改的对象引用、不允许被覆写的方法
    // 反例：整型包装类用 == 比较
Integer a = 128, b = 128;
if (a == b) { ... }  // false！-128~127 之外是不同对象

// 正例
if (a.equals(b)) { ... }

// 反例：BigDecimal 精度丢失
new BigDecimal(0.1)  // 0.1000000000000000055511151231257827021181583404541015625

// 正例
BigDecimal.valueOf(0.1)  // 0.1

    五、集合处理¶

    • 【强制】关于 hashCode 和 equals：只要覆写 equals，就必须覆写 hashCode；Set 存储的对象必须覆写；作为 Map 的 key 必须覆写
    • 【强制】ArrayList 的 subList 结果不可强转成 ArrayList（返回的是视图）
    • 【强制】使用集合转数组时使用 toArray(T[] array)，传入类型一致长度为 0 的空数组
    • 【强制】使用工具类 Arrays.asList() 转换时，不要使用其修改方法（add/remove/clear 会抛 UnsupportedOperationException）
    • 【强制】不要在 foreach 循环里进行元素的 remove/add 操作。remove 请使用 Iterator，并发操作需要对 Iterator 对象加锁
    • 【强制】使用 entrySet 遍历 Map 类集合 KV，而不是先 keySet 取 key 再取 value（多一次 HashMap 查找）
    • 【强制】Map 类集合 K/V 能不能存储 null 值，必须注意（HashMap 可以，ConcurrentHashMap 不可以）
    • 【强制】集合初始化时，指定集合初始值大小：new HashMap<>(expectedSize / 0.75 + 1) 或用 Maps.newHashMapWithExpectedSize()
    • 【强制】使用 Collections.unmodifiableMap/List/Set 创建不可变集合时，如果原集合可变，修改原集合会破坏不可变性
    • 【推荐】使用 isEmpty() 方法检查集合是否为空，而不是 size() == 0
    // 反例：foreach 中 remove
for (String item : list) {
    if (condition) {
        list.remove(item);  // ConcurrentModificationException
    }
}

// 正例 1：Iterator
Iterator<String> it = list.iterator();
while (it.hasNext()) {
    if (condition) {
        it.remove();
    }
}

// 正例 2：removeIf（JDK 8+）
list.removeIf(item -> condition);

// 正例：指定初始容量
Map<String, String> map = new HashMap<>(16);

    六、并发处理¶

    • 【强制】获取单例对象需要保证线程安全，其中的方法也要保证线程安全
    • 【强制】创建线程或线程池时请指定有意义的线程名称，方便出错时回溯： 
      new ThreadFactoryBuilder().setNameFormat("order-process-%d").build()
    • 【强制】线程资源必须通过线程池提供，不允许在应用中自行显式创建线程
    • 【强制】线程池不允许使用 Executors 去创建，而是通过 ThreadPoolExecutor 的方式（FixedThreadPool/SingleThreadPool 队列无界可能 OOM；CachedThreadPool 允许创建线程数可能 OOM）
    • 【强制】SimpleDateFormat 是线程不安全的类，不要定义为 static 变量。推荐用 DateTimeFormatter（JDK 8+）
    • 【强制】必须回收自定义的 ThreadLocal 变量，尤其在线程池场景下，线程被复用时可能导致业务逻辑出错或内存泄漏： 
      try {
    threadLocal.set(value);
    // business logic
} finally {
    threadLocal.remove();
}
    • 【强制】高并发时，同步调用应该去考量锁的性能损耗。能用无锁数据结构，就不要用锁；能锁区块，就不要锁整个方法体；能用对象锁，就不要用类锁
    • 【强制】对多个资源、数据库表、对象同时加锁时，需要保持一致的加锁顺序，否则可能造成死锁
    • 【强制】在使用尝试机制来获取锁的方式中，进入业务代码块之前，必须先判断当前线程是否持有锁
    • 【强制】多线程并行处理定时任务时，Timer 运行多个 TimeTask 时，只要其中一个没有捕获抛出的异常，其它任务便会自动终止。推荐 ScheduledExecutorService
    • 【强制】volatile 解决多线程内存不可见问题。对于一写多读可以解决，多写场景无法解决（要用原子类或锁）
    • 【强制】HashMap 在容量不够进行 resize 时由于高并发可能出现死链，导致 CPU 飙升，使用 ConcurrentHashMap
    • 【推荐】使用 CountDownLatch 进行异步转同步操作，每个线程退出前必须调用 countDown 方法，且 countDown 放在 finally 中
    • 【推荐】避免 Random 实例被多线程使用，虽然共享该实例是线程安全的，但会因竞争同一 seed 导致性能下降。JDK 7+ 使用 ThreadLocalRandom
    // 反例：Executors 创建线程池
ExecutorService pool = Executors.newFixedThreadPool(10);  // 队列无界，可能 OOM

// 正例：ThreadPoolExecutor 显式指定参数
ExecutorService pool = new ThreadPoolExecutor(
    10,                                  // corePoolSize
    20,                                  // maximumPoolSize
    60L, TimeUnit.SECONDS,               // keepAliveTime
    new LinkedBlockingQueue<>(1000),     // 有界队列
    new ThreadFactoryBuilder().setNameFormat("order-%d").build(),
    new ThreadPoolExecutor.CallerRunsPolicy()  // 拒绝策略
);

// 反例：static SimpleDateFormat
private static SimpleDateFormat sdf = new SimpleDateFormat("yyyy-MM-dd");  // 线程不安全！

// 正例：DateTimeFormatter（不可变，线程安全）
private static final DateTimeFormatter FMT = DateTimeFormatter.ofPattern("yyyy-MM-dd");

    七、控制语句¶

    • 【强制】switch 中每个 case 要么 break/return 要么注释说明继续执行到哪一个 case。必须包含 default 语句
    • 【强制】switch 括号内的变量类型为 String 且此变量为外部参数，必须先进行 null 判断（否则 NPE）
    • 【强制】if/else/for/while/do 语句中必须使用大括号，即使只有一行
    • 【强制】三目运算符 condition ? a : b，注意类型自动转换导致的 NPE（a 或 b 为包装类型且另一边是基本类型时会拆箱）
    • 【强制】在超过三层嵌套的判断语句中，请使用卫语句、策略模式、状态模式进行重构
    • 【推荐】表达异常的分支时，少用 if-else 方式，优先使用卫语句： 
      // 卫语句：先处理异常分支，提前 return
public void process(User user) {
    if (user == null) return;
    if (!user.isActive()) return;
    // 正常逻辑
}
    • 【推荐】除常用方法（如 getXxx/isXxx）外，不要在条件判断中执行复杂语句，将复杂逻辑结果赋值给一个有意义的布尔变量
    • 【推荐】不要在表达式中插入赋值语句（容易看成 ==）

    八、异常处理¶

    • 【强制】Java 类库中定义的可以通过预检查方式规避的 RuntimeException 不应该通过 catch 处理，如 NullPointerException、IndexOutOfBoundsException
    • 【强制】异常捕获后不要用来做流程控制、条件控制
    • 【强制】catch 时请分清稳定代码和非稳定代码，对大段代码进行 try-catch 是不负责任的表现
    • 【强制】捕获异常是为了处理它，不要捕获了却什么都不处理而抛弃之。如果不想处理，请将该异常抛给它的调用者。最外层的业务使用者必须处理异常，将其转化为用户可以理解的内容
    • 【强制】事务场景中，抛出异常被 catch 后，如果需要回滚，一定要手动回滚事务
    • 【强制】finally 块必须对资源对象、流对象进行关闭，推荐 try-with-resources。不要在 finally 中使用 return
    • 【强制】不要在 finally 块中使用 throw（会覆盖 try 块中的异常）
    • 【强制】捕获异常与抛出异常必须完全匹配，或捕获异常是抛出异常的父类
    • 【强制】方法的返回值可以为 null，不强制返回空集合或空对象，但必须添加注释充分说明什么情况下会返回 null
    • 【强制】定义时区分 unchecked（RuntimeException）和 checked（Exception）异常，对于可恢复的条件使用 checked
    • 【强制】避免出现重复的代码（Don't Repeat Yourself），即 DRY 原则
    • 【推荐】防止 NPE 是调用者的责任。即使是 RPC 返回、数据库查询、集合元素取出，都需要做 NPE 判断
    • 【推荐】使用 Optional 表达"可能为空"的返回值（参数中慎用）
    • 【推荐】自定义异常体系：业务异常继承 RuntimeException，系统异常单独分类
    // 正例：try-with-resources
try (BufferedReader br = new BufferedReader(new FileReader(path))) {
    return br.readLine();
}  // 自动关闭，异常时也能关闭

// 反例：吞异常
try {
    doSomething();
} catch (Exception e) {
    // 什么都不做  ← 绝对禁止
}

// 正例：记录 + 上抛或处理
try {
    doSomething();
} catch (BusinessException e) {
    log.error("业务处理失败, orderId={}", orderId, e);
    throw e;
}

// 反例：抛异常不带上下文
throw new RuntimeException("error");

// 正例：带上下文信息 + 原始异常
throw new RuntimeException("订单创建失败, orderId=" + orderId, e);

    九、日志规约¶

    • 【强制】应用中不可直接使用日志系统（Log4j、Logback）中的 API，而应依赖使用日志框架（SLF4J）中的 API： 
      import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
private static final Logger logger = LoggerFactory.getLogger(XxxClass.class);
    • 【强制】日志文件至少保存 15 天
    • 【强制】对 DEBUG/INFO 级别的日志输出，必须进行日志级别的开关判断或使用占位符： 
      // 反例：字符串拼接（即使不输出也会执行拼接）
logger.debug("result: " + user.toString());

// 正例：占位符
logger.debug("result: {}", user);

// 正例：级别判断
if (logger.isDebugEnabled()) {
    logger.debug("result: {}", buildExpensiveString());
}
    • 【强制】避免重复打印日志，浪费磁盘空间。设置 additivity=false
    • 【强制】异常信息应该包括两类信息：案发现场信息和异常堆栈信息： 
      logger.error("操作失败, orderId={}, userId={}", orderId, userId, e);
    • 【强制】生产环境禁止直接使用 System.out 或 System.err
    • 【推荐】谨慎地记录日志。生产环境禁止输出 DEBUG 日志；有选择地输出 INFO 日志
    • 【推荐】使用日志框架输出日志，不要使用 e.printStackTrace()

    十、MySQL 规约（简版）¶

    建表规约¶

    • 【强制】表达是否概念的字段，必须使用 is_xxx 的方式命名，数据类型是 unsigned tinyint（1 是 / 0 否）
    • 【强制】表名、字段名必须使用小写字母或数字，禁止以数字开头，禁止两个下划线中间只出现数字
    • 【强制】表必备三字段：id（bigint unsigned 主键自增）、gmt_create（datetime）、gmt_modified（datetime）
    • 【强制】小数类型为 decimal，禁止使用 float 和 double
    • 【强制】如果存储的字符串长度几乎相等，使用 char 定长
    • 【强制】varchar 是可变长字符串，不预先分配存储空间，长度不要超过 5000（超过用 text 并独立建表）
    • 【强制】单表行数超过 500 万行或者单表容量超过 2GB，才推荐进行分库分表
    • 【推荐】表的命名最好是业务名称_表的作用，如 trade_order
    • 【推荐】库名与应用名称尽量一致

    索引规约¶

    • 【强制】业务上具有唯一特性的字段，即使是多个字段的组合，也必须建成唯一索引
    • 【强制】超过三个表禁止 join。需要 join 的字段，数据类型保持绝对一致；多表关联查询时，保证被关联的字段需要有索引
    • 【强制】在 varchar 字段上建立索引时，必须指定索引长度（区分度 > 0.7）
    • 【强制】页面搜索严禁左模糊或者全模糊，如果需要请用搜索引擎
    • 【推荐】建立组合索引，区分度最高的在最左边
    • 【推荐】防止因字段类型不同造成的隐式转换，导致索引失效
    • 【推荐】建组合索引时，区分度最高的字段放在最左边；组合索引的字段数量不超过 5 个

    SQL 语句¶

    • 【强制】不要使用 count(列名) 或 count(常量) 来替代 count(*)。count(*) 是 SQL92 定义的标准统计行数的语法
    • 【强制】使用 ISNULL() 来判断是否为 NULL 值（NULL 与任何值的直接比较都为 NULL）
    • 【强制】在代码中写分页查询逻辑时，若 count 为 0 应直接返回，避免执行后面的分页语句
    • 【强制】不得使用外键与级联，一切外键概念必须在应用层解决
    • 【强制】禁止使用存储过程
    • 【强制】数据订正（特别是删除或修改记录操作）时，要先 select，避免出现误删除，确认无误才能执行
    • 【强制】in 操作能避免则避免，若实在避免不了，需要仔细评估 in 后边的集合元素数量，控制在 1000 个之内
    • 【推荐】in 子查询改成 join；exists 改成 join
    • 【推荐】不要使用 select *，明确写出需要的列

    分层规约¶

    • 【强制】分层领域模型转换规则：DO ↔ DTO ↔ VO，禁止跨层传递（如 DO 直接返回给前端）
    • 【强制】Controller 层只做参数校验和结果封装，业务逻辑放 Service
    • 【强制】Service 层是核心业务逻辑所在，事务在此层控制
    • 【强制】DAO 层只负责数据访问，不包含业务逻辑
    • 【强制】二方库依赖：版本号命名方式为主版本号.次版本号.修订号；主版本号不兼容修改时 +1
    • 【推荐】单个类的成员数量不超过 30 个；单个方法不超过 80 行；单个文件不超过 2000 行
    • 【推荐】工具类命名以 Utils/Helper 结尾，放在 common.util 包下，且构造方法设为 private

    十二、单元测试¶

    • 【强制】好的单元测试必须遵守 AIR 原则：
    • Automatic（自动化）
    • Independent（独立性，测试间不能互相调用）
    • Repeatable（可重复，不受外界影响）
    • 【强制】单元测试应该是全自动执行的，并且非交互式的。禁止使用 System.out 来进行人肉验证，必须使用 assert 来验证
    • 【强制】单元测试代码必须写在 src/test/java 目录下，不允许写在业务代码目录下
    • 【强制】单元测试要符合 BCDE 原则：
    • Border：边界值测试（循环边界、特殊数值、空值）
    • Correct：正确的输入，并得到预期的结果
    • Design：与设计文档相结合，来写单元测试
    • Error：强制错误信息输入（非法数据、异常流程），业务代码要能正确处理
    • 【推荐】单元测试的基本目标：语句覆盖率达到 70%；核心模块的语句覆盖率和分支覆盖率都要达到 100%
    • 【推荐】使用 JUnit 5 + Mockito，mock 外部依赖（数据库、RPC、MQ）
    // JUnit 5 + Mockito 示例
@ExtendWith(MockitoExtension.class)
class OrderServiceTest {

    @Mock
    private OrderRepository orderRepository;

    @InjectMocks
    private OrderService orderService;

    @Test
    @DisplayName("创建订单：库存充足时成功创建")
    void createOrder_withStock_success() {
        // Given
        when(orderRepository.save(any(Order.class)))
            .thenReturn(new Order(1L));

        // When
        Order result = orderService.createOrder("item-001", 2);

        // Then
        assertNotNull(result);
        assertEquals(1L, result.getId());
        verify(orderRepository).save(any(Order.class));
    }

    @Test
    @DisplayName("创建订单：库存不足时抛出异常")
    void createOrder_noStock_throwsException() {
        assertThrows(InsufficientStockException.class,
            () -> orderService.createOrder("item-404", 1));
    }
}

    十三、安全规约¶

    • 【强制】隶属于用户个人的页面或者功能必须进行权限控制校验（防止水平越权、垂直越权）
    • 【强制】用户敏感数据禁止直接展示，必须对展示数据进行脱敏（手机号 131****0000）
    • 【强制】用户输入的 SQL 参数严格使用参数绑定或者 METADATA 字段值限定，防止 SQL 注入
    • 【强制】用户请求传入的任何参数必须做有效性验证
    • 【强制】禁止向 HTML 页面输出未经安全过滤或未正确转义的用户数据（XSS）
    • 【强制】表单、AJAX 提交必须执行 CSRF 安全验证
    • 【强制】URL 外部重定向传入的目标地址必须执行白名单过滤
    • 【推荐】发贴、评论、发送即时消息等用户生成内容的场景必须实现防刷（数量限制、疲劳度控制、验证码）
    • 【推荐】密码、密钥等敏感信息禁止出现在日志中；配置文件中的敏感信息要加密
    // 反例：SQL 拼接（注入风险）
String sql = "SELECT * FROM user WHERE name = '" + name + "'";

// 正例：参数绑定
String sql = "SELECT * FROM user WHERE name = ?";
psmt.setString(1, name);

// 反例：明文日志打印密码
logger.info("user login: {}", user);  // toString 含密码

// 正例：脱敏
logger.info("user login: userId={}", user.getId());

    面试题速记¶

    Q: 为什么强制用 ThreadPoolExecutor 而不是 Executors？

    FixedThreadPool 和 SingleThreadPool 用的无界队列 LinkedBlockingQueue，任务堆积会 OOM；CachedThreadPool 和 ScheduledThreadPool 允许创建 Integer.MAX_VALUE 个线程，也可能 OOM。ThreadPoolExecutor 可以显式控制核心参数和拒绝策略。

    Q: 为什么 SimpleDateFormat 线程不安全？

    它内部维护 Calendar 对象，多线程共享实例时，format/parse 会并发修改 Calendar 状态，导致结果错乱。解决方案：1) ThreadLocal 包装；2) 用线程安全的 DateTimeFormatter（JDK 8+）。

    Q: POJO 布尔字段为什么不能加 is 前缀？

    部分序列化框架（如某些 RPC 框架）解析 getter 方法 isDeleted 时，会映射成字段 deleted 而不是 isDeleted，导致属性丢失。

    Q: HashMap 为什么高并发下危险？

    JDK 7 的 HashMap 扩容时头插法，多线程并发 resize 可能形成环形链表，get 时死循环，CPU 飙到 100%。JDK 8 改成尾插法解决了死循环，但并发写入仍会丢数据。并发场景用 ConcurrentHashMap。

    Q: foreach 中 remove 为什么抛 ConcurrentModificationException？

    foreach 底层用 Iterator，遍历时修改集合会改变 modCount，下次 next() 检查 fail-fast 机制抛异常。正确做法：Iterator.remove() 或 JDK 8 的 removeIf()。

list.removeIf(item -> cond(item));

List<Item> toRemove = list.stream().filter(this::cond).toList();

    十七、本章小结¶

    核心知识点： - ✅ 命名：类大驼峰、方法变量小驼峰、常量全大写下划线、POJO 布尔禁 is 前缀 - ✅ 拒绝魔法值：常量归类管理，业务状态用枚举 - ✅ OOP：@Override 必加、包装类用 equals、金额用 BigDecimal - ✅ 集合：foreach 中删除用 Iterator、Map 遍历用 entrySet、指定初始容量 - ✅ 并发：ThreadPoolExecutor 显式创建、ThreadLocal 必须 remove、SimpleDateFormat 换 DateTimeFormatter - ✅ 异常：不吞异常、try-with-resources、事务场景注意手动回滚 - ✅ 日志：SLF4J 占位符、异常带上下文 - ✅ MySQL：表必备三字段、索引三原则、禁 select * - ✅ 安全：参数绑定防注入、脱敏、防越权
