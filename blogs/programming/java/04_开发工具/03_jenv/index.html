    03_jenv¶

    多 JDK 版本管理器：一条命令切换全局/目录/会话级 Java 版本 本章全部命令与输出在 Ubuntu 24.04 + jenv 0.6.0 + JDK 17.0.20 / 21.0.12 实机验证

    1. jenv 概述¶

    知识点清单：

    知识点 一句话结论 重要度
    jenv 是什么 Java 版本管理器（rbenv 的 Java 版），只管切换、不管安装 ⭐⭐
    解决什么问题 一台机器多 JDK 共存，按项目/目录/会话切换 ⭐⭐
    三级版本设置 global < local < shell，优先级从低到高 ⭐⭐⭐
    shim 机制 java 命令被 ~/.jenv/shims/java 拦截，按当前版本转发 ⭐⭐⭐
    export 插件 让 jenv 接管 JAVA_HOME（默认不设！） ⭐⭐⭐
    JAVA_HOME 滞后坑 export 插件靠 PROMPT_COMMAND 更新，切换后不会立刻生效 ⭐⭐⭐⭐
    maven/gradle 插件 把 jenv options 的 JVM 参数注入 MAVEN_OPTS/GRADLE_OPTS ⭐⭐

    1.1 什么是 jenv¶

    jenv 是从 rbenv（Ruby 版本管理器）移植来的 Java 环境管理工具，提供两个核心能力：

    1. 切换 java 命令版本：全局、当前目录、当前 shell 三个粒度；
    2. 管理 JAVA_HOME（需启用 export 插件）：让 Maven/Gradle 等依赖 JAVA_HOME 的工具跟随切换。

    ⚠️ jenv 不安装 Java。JDK 要用平台包管理器装（macOS 用 brew，Linux 用 apt/yum，或手动下载解压），jenv 只负责"登记 + 切换"。

    1.2 解决什么问题¶

    典型场景——一台机器同时维护多个项目：

    老项目 A：必须 JDK 8（依赖的框架不支持更高版本）
中间件 B：JDK 17 LTS
新项目 C：JDK 21（用虚拟线程）

    没有版本管理器时，切版本要么改 JAVA_HOME + PATH（每开一个终端都要重来），要么 update-alternatives（全局生效，切了影响所有项目）。jenv 的做法：

    cd ~/work/项目A && java -version   # 自动 1.8（目录里有 .java-version）
cd ~/work/项目C && java -version   # 自动 21

    cd 进目录自动切版本，配置文件 .java-version 可以提交 git，团队成员开箱即用。

    1.3 jenv vs SDKMAN vs update-alternatives¶

    对比项 jenv SDKMAN update-alternatives（Linux）
    安装 JDK ❌ 不管 ✅ 一条命令装（sdk install java） ❌ 用 apt 装
    版本粒度 global/local/shell 三级 global + 当前 shell 仅全局
    目录级自动切换 ✅ .java-version ✅ .sdkmanrc ❌
    管理范围 仅 Java JVM 全家桶（Java/Gradle/Maven/Kotlin/Scala…） 仅系统级命令
    机制 shim 拦截命令 改 PATH/JAVA_HOME 符号链接投票
    平台 macOS/Linux macOS/Linux/WSL Linux

    选型建议：只需要切 JDK 版本 → jenv（轻、专注、目录级切换成熟）；还想让工具链（Gradle/Maven 本体版本）也统一管理 → SDKMAN。两者都能用 .xxx-version/.sdkmanrc 文件做目录级锁定，思路一致。

    2. 安装与初始化¶

    知识点：

    • ⭐ macOS 用 brew，Linux 用 git clone；装完必须在 shell 配置里 eval "$(jenv init -)"
    • ⚠️ 忘了 eval 初始化是"command not found"的第一原因
    • jenv doctor 一条命令自检安装状态

    2.1 安装¶

    # macOS（Homebrew）
brew install jenv

# macOS（MacPorts）
sudo port install jenv

# Linux / 手动安装（任何平台通用）
git clone https://github.com/jenv/jenv.git ~/.jenv

    2.2 shell 初始化（关键步骤）¶

    把 jenv 的 bin 加入 PATH，并让每个新 shell 执行 jenv init -：

    # bash：写入 ~/.bash_profile（Ubuntu 上常是 ~/.bashrc，看你系统实际加载哪个）
echo 'export PATH="$HOME/.jenv/bin:$PATH"' >> ~/.bash_profile
echo 'eval "$(jenv init -)"' >> ~/.bash_profile

# zsh：写入 ~/.zshrc
echo 'export PATH="$HOME/.jenv/bin:$PATH"' >> ~/.zshrc
echo 'eval "$(jenv init -)"' >> ~/.zshrc

    然后重启 shell（或 exec $SHELL -l）。

    jenv init - 做了什么：输出一段 shell 脚本，把 ~/.jenv/shims 插到 PATH 最前、注册 cd 钩子（用于 local 版本感知）、启用补全。每次开新 shell 都要执行这段，所以写进 rc 文件。

    2.3 自检：jenv doctor¶

    $ jenv doctor
[OK]    No JAVA_HOME set
[ERROR] Java binary in path is not in the jenv shims.
[ERROR] Please check your path, or try using `jenv add /path/to/java/home`.
        PATH : /home/user/.jenv/libexec:/home/user/.jenv/shims:/home/user/.jenv/bin:/usr/local/bin:/usr/bin:...
[OK]    Jenv is correctly loaded

    （以上为刚装好、还没 add 任何 JDK 时的真实输出。）三行含义：

    • No JAVA_HOME set：还没启用 export 插件，属正常（第 6 节处理）；
    • Java binary in path is not in the jenv shims：PATH 里的 java 还是系统的，没被 jenv 接管——jenv add 之后自动解决；
    • Jenv is correctly loaded：init 生效了，安装本身没问题。

    ⚠️ 易错点：[ERROR] 不一定代表装坏了——新装未 add JDK 时这两行 ERROR 是预期状态，看最后一行 [OK] Jenv is correctly loaded 判断安装是否成功。

    3. 注册 JDK：jenv add¶

    知识点：

    • ⭐ jenv add <JDK_HOME路径>：路径是 JDK 根目录（bin 的上一级），不是 bin 本身
    • ⭐ 一次 add 自动生成多个别名（17 / 17.0 / 17.0.20 / openjdk64-17.0.20），方便不同精度引用
    • versions/ 下全是指向真实 JDK 的软链接，jenv 不复制文件

    3.1 找到 JDK 安装路径¶

    # macOS：系统工具直接给出当前 JDK 路径
/usr/libexec/java_home                 # 最新版
/usr/libexec/java_home -v 17           # 指定大版本
ls /Library/Java/JavaVirtualMachines/  # 所有已装 JDK

# Linux（apt 安装）：统一在这个目录
ls /usr/lib/jvm/
# java-17-openjdk-amd64  java-21-openjdk-amd64 ...

# 通用：从 java 命令反查
readlink -f $(which java)              # /usr/lib/jvm/java-17-openjdk-amd64/bin/java → 去掉 /bin/java

    3.2 add 与别名生成（实测）¶

    $ jenv add /usr/lib/jvm/java-17-openjdk-amd64
openjdk64-17.0.20 added
17.0.20 added
17.0 added
17 added

$ jenv add /usr/lib/jvm/java-21-openjdk-amd64
openjdk64-21.0.12 added
21.0.12 added
21.0 added
21 added

$ jenv versions
* system (set by /home/user/.jenv/version)
  17
  17.0
  17.0.20
  21
  21.0
  21.0.12
  openjdk64-17.0.20
  openjdk64-21.0.12

    jenv 解析 java -version 输出，自动生成 4 个别名：完整版本号、次版本号、大版本号、架构前缀名。同一 JDK 的多个别名指向同一个软链接：

    $ ls -la ~/.jenv/versions/
17    -> /usr/lib/jvm/java-17-openjdk-amd64
17.0  -> /usr/lib/jvm/java-17-openjdk-amd64
17.0.20 -> /usr/lib/jvm/java-17-openjdk-amd64
21    -> /usr/lib/jvm/java-21-openjdk-amd64
...

    别名精度的意义：jenv local 17 表示"17 系都行"（实际解析到已注册的 17.x），jenv local 17.0.20 锁死具体版本。团队协作锁具体版本更稳，个人开发用大版本号更省事。

    💡 macOS 用 brew 装的 openjdk 需要先按 brew 提示 symlink 到 /Library/Java/JavaVirtualMachines/，再 jenv add /Library/Java/JavaVirtualMachines/openjdk.jdk/Contents/Home。注意 macOS 的 JDK 根目录多一层 Contents/Home。

    3.3 移除¶

    jenv remove 21.0.12     # 只删 jenv 的登记（软链接），不动真实 JDK 文件
# 实测输出：JDK 21.0.12 removed

    ⚠️ remove 只解除注册；真实 JDK 要用包管理器卸载（apt remove openjdk-21-jdk / brew uninstall openjdk@21）。

    4. 三级版本切换 ⭐¶

    知识点：

    • ⭐ 优先级：shell（JENV_VERSION 环境变量）> local（.java-version 文件）> global（~/.jenv/version）
    • ⭐ jenv local 在当前目录写 .java-version 文件，cd 进来自动生效，可提交 git
    • ⭐ jenv version 显示当前生效版本及其来源——排查"为什么是这个版本"就靠它
    • 0.6.0 新增 jenv with：不改任何设置，单次执行用指定版本

    4.1 global：全局默认¶

    jenv global 17.0.20        # 写入 ~/.jenv/version
jenv global                # 查看
jenv global --unset        # 取消（回落到 system）

    4.2 local：目录级（最常用）¶

    cd ~/work/项目C
jenv local 21.0.12         # 在当前目录生成 .java-version 文件
cat .java-version          # 21.0.12
jenv local --unset         # 删除该文件

    cd 进任何包含 .java-version 的目录（或其子目录），版本自动切换——这是 jenv 的核心价值。把 .java-version 提交到 git，队友 clone 后只要装了对应 JDK 并 add 过，进目录即自动用对版本。

    4.3 shell：会话级（临时）¶

    jenv shell 17.0.20         # 只对当前 shell 生效（设 JENV_VERSION 环境变量）
jenv shell --unset         # 取消（等价 unset JENV_VERSION）

    用途：当前终端临时用另一个版本跑几条命令，不想动 global/local。

    4.4 优先级实测¶

    三级同时设置时，高优先级覆盖低优先级：

    # 场景：global=17，项目目录 local=21
$ jenv global 17.0.20
$ cd ~/proj21                # 目录里有 .java-version=21.0.12
$ jenv version
21.0.12 (set by /home/user/proj21/.java-version)     # local 赢 global
$ java -version
openjdk version "21.0.12" 2026-07-21

$ jenv shell 17.0.20         # 再设 shell 级
$ jenv version
17.0.20 (set by JENV_VERSION environment variable)   # shell 赢 local
$ java -version
openjdk version "17.0.20" 2026-07-21

$ jenv shell --unset         # 撤销 shell 级
$ jenv version
21.0.12 (set by /home/user/proj21/.java-version)     # 回落到 local

    注意 jenv version 输出自带来源说明（set by 哪个文件/环境变量），排查版本问题第一步永远是它。

    4.5 with：单次执行（0.6.0+）¶

    $ jenv with 17.0.20 java -version
openjdk version "17.0.20" 2026-07-21
$ java -version               # 当前环境不受影响
openjdk version "21.0.12" 2026-07-21

    适合"就用别的版本跑这一条命令"，比 jenv shell 设了再 unset 干净。

    5. shim 机制原理 ⭐¶

    知识点：

    • ⭐ which java 指向 ~/.jenv/shims/java（假命令），真实 java 由 shim 按当前版本转发
    • shim 对 java 某文件.java 会按文件所在目录找 .java-version（单文件运行也能目录级切换）
    • 装了新 JDK 的可执行文件后跑 jenv rehash 重建 shims

    5.1 shim 拦截¶

    $ which java
/home/user/.jenv/shims/java          # 不是真实 java！
$ jenv which java
/home/user/.jenv/versions/21.0.12/bin/java   # 真实路径（经软链接）
$ jenv javahome
/home/user/.jenv/versions/21.0.12    # 当前版本对应的 JDK 根目录

    ~/.jenv/shims/java 是个 bash 脚本（实测节选）：

    #!/usr/bin/env bash
program="${0##*/}"
# 对 java 命令的特殊处理：扫描参数里的文件路径，
# 若命中真实存在的文件，把 JENV_DIR 设为该文件所在目录
# —— 于是 `java /path/to/Foo.java` 会按 Foo.java 所在目录的 .java-version 选版本
export JENV_ROOT="/home/user/.jenv"
exec /home/user/.jenv/bin/jenv exec "java" "$@"

    5.2 执行链路¶

    你敲 java -version
 → PATH 命中 ~/.jenv/shims/java（init 把 shims 放 PATH 最前）
 → shim 脚本 exec jenv exec java ...
 → jenv exec 依次确定版本：JENV_VERSION（shell）→ JENV_DIR 向上找 .java-version（local）→ ~/.jenv/version（global）→ system
 → 用该版本的真实 java 执行

    这条链解释了前面所有行为：三级优先级就是 jenv exec 的查找顺序；shim 的 JENV_DIR 特判让"运行某个目录下的 .java 文件"也遵守那个目录的版本锁定。

    5.3 rehash¶

    shims 目录里每个可执行文件（java/javac/jar/jshell…）都是 add 时生成的。手动往 JDK 里装了新工具、或 shims 行为异常时：

    jenv rehash    # 重建全部 shims

    辅助命令：

    jenv whence javac   # 哪些已注册版本包含 javac（实测输出：17 17.0 17.0.20 21 ...）
jenv commands       # 列出所有 jenv 子命令

    ⚠️ IDE 不走 shim：IntelliJ IDEA 的 Project SDK、VS Code 的 Java 运行时都在 IDE 里单独配置，与 jenv 无关。jenv 只管终端里的 java 命令和 JAVA_HOME。

    6. export 插件与 JAVA_HOME ⭐¶

    知识点：

    • ⭐ jenv 默认只切 java 命令、不设 JAVA_HOME；Maven/Gradle 认 JAVA_HOME，必须启用 export 插件
    • ⭐ export 插件通过 PROMPT_COMMAND 钩子更新 JAVA_HOME——不是切换瞬间生效（实测大坑）
    • macOS 可用 jenv macos-javahome 给 GUI 应用设 JAVA_HOME

    6.1 启用 export 插件¶

    jenv enable-plugin export
# export plugin activated
exec $SHELL -l          # 重启 shell 生效

    启用后每次 shell 提示符渲染前，钩子把 JAVA_HOME（JDK 存在时还有 JDK_HOME）设为 jenv javahome 的结果：

    # 插件源码（~/.jenv/plugins/export/etc/jenv.d/...，实测节选）
_jenv_export_hook() {
  export JAVA_HOME="$(jenv javahome 2>/dev/null)"
  if [ -e "$JAVA_HOME/bin/javac" ]; then
    export JDK_HOME="$JAVA_HOME"
  fi
}
PROMPT_COMMAND="_jenv_export_hook;$PROMPT_COMMAND"

    6.2 ⚠️ JAVA_HOME 滞后（实测复现的坑）¶

    钩子挂在 PROMPT_COMMAND（bash 每次显示提示符前执行），所以：

    $ jenv local 21.0.12         # 当前 global=17
$ java -version              # ✅ 立刻是 21（shim 实时解析，不依赖 JAVA_HOME）
openjdk version "21.0.12" 2026-07-21
$ echo $JAVA_HOME            # ❌ 还是 17！
/home/user/.jenv/versions/17.0.20
$ （按一下回车，让提示符重新渲染）
$ echo $JAVA_HOME            # ✅ 现在才更新
/home/user/.jenv/versions/21.0.12

    交互式终端里这只是"晚一个提示符"，cd + 下一条命令时已刷新，基本无感。但两种场景会真踩坑：

    1. 同一行连着执行：jenv local 21 && mvn package —— mvn 拿到的 JAVA_HOME 还是旧版本（java 命令已是新版本，工具行为分裂）；
    2. 非交互脚本/CI：PROMPT_COMMAND 根本不执行，JAVA_HOME 永远是初始值。

    解法：

    # 脚本/CI 里不要依赖 export 插件，显式设置：
export JAVA_HOME=$(jenv javahome)
mvn package

# 或者用 jenv exec 包一层（在正确的版本环境里执行）：
jenv exec mvn package

    6.3 macOS GUI 应用¶

    GUI 启动的应用（双击的 IDEA、终端之外的工具）不读 shell 配置：

    jenv macos-javahome    # 生成系统级 JAVA_HOME 配置（只跟随 global 版本，不随 local/shell 变）

    7. maven/gradle 插件与 JVM 参数¶

    知识点：

    • ⭐ jenv local-options -Xmx512m 把 JVM 参数写进目录级 .java-options 文件
    • maven/gradle 插件在执行 mvn/gradle 时把 jenv options 注入 MAVEN_OPTS/GRADLE_OPTS
    • ⚠️ 环境里已有 MAVEN_OPTS 时 jenv 不覆盖，只打印提示

    7.1 插件一览¶

    jenv enable-plugin maven    # mvn/mvnDebug 注入 MAVEN_OPTS
jenv enable-plugin gradle   # gradle 注入 GRADLE_OPTS
jenv plugins                # 查看可用插件：ant export gradle lein maven sbt ...
jenv disable-plugin maven   # 停用

    7.2 JVM 参数（options）¶

    与版本三级设置对称，JVM 参数也有三级（global-options / local-options / shell-options）：

    cd ~/proj
jenv local-options -Xmx512m      # 写入当前目录 .java-options 文件
jenv options                     # -Xmx512m
jenv options-origin              # /home/user/proj/.java-options（参数来源）

    7.3 注入实测¶

    启用 maven 插件后，在 local=21.0.12、local-options=-Xmx512m 的目录执行 mvn（实测）：

    $ mvn -v 时环境实际拿到：
JAVA_HOME=/home/user/.jenv/versions/21.0.12   ← 跟随 jenv 当前版本
MAVEN_OPTS=-Xmx512m                            ← 来自 .java-options

    插件注入规则（源码实测）：JENV_OPTIONS（即 jenv options 的值）只在 MAVEN_OPTS 未设置时注入；已设置则打印 MAVEN_OPTS is set and not overridden by jenv 并保留原值。想让 jenv 的 options 生效，别在 shell 配置里写死 MAVEN_OPTS。

    💡 注意 MAVEN_OPTS 影响的是 Maven 进程本身的 JVM 参数（编译内存等）；要控制"用哪个 JDK 编译产物字节码"，用 pom.xml 的 maven.compiler.release（见 Maven 章），两者是不同层面的事。

    8. 实战：多版本项目共存¶

    8.1 完整工作流¶

    # ① 一次性：装好各版本 JDK 并全部注册
sudo apt install openjdk-17-jdk openjdk-21-jdk     # Linux
jenv add /usr/lib/jvm/java-17-openjdk-amd64
jenv add /usr/lib/jvm/java-21-openjdk-amd64
jenv global 17.0.20                                 # 全局默认用 LTS 17
jenv enable-plugin export && exec $SHELL -l         # 接管 JAVA_HOME

# ② 每个项目：进目录锁版本（.java-version 提交 git）
cd ~/work/legacy-app && jenv local 17.0.20
cd ~/work/new-app    && jenv local 21.0.12

# ③ 日常：cd 进项目即自动切，验证三连
jenv version      # 当前版本 + 来源
java -version     # 实际 java
echo $JAVA_HOME   # 构建工具看到的（记得滞后问题）

# ④ 临时借用其他版本
jenv with 21.0.12 jshell        # 单次用 21 进 jshell

    8.2 .java-version 与 git¶

    git add .java-version        # ✅ 提交：团队统一版本
echo ".java-options" >> .gitignore   # JVM 参数偏个人化，通常不提交（团队约定则提交）

    ⚠️ 队友机器上必须先 jenv add 过对应版本，否则 cd 进目录报 jenv: version '21.0.12' is not installed（实测）——报错信息明确，装好 add 即可。

    8.3 CI 场景¶

    CI 容器通常只有一个 JDK，jenv 价值不大；但如果 runner 多版本共存：

    # CI 脚本里显式指定，不依赖 PROMPT_COMMAND（见 6.2）
jenv shell 17.0.20
export JAVA_HOME=$(jenv javahome)
./mvnw verify

    9. 常见坑汇总 ⚠️¶

    1. 忘装/忘 add：jenv 不装 JDK；装完 JDK 还要 jenv add，否则 jenv versions 里只有 system。
    2. JAVA_HOME 没接管：默认不启用 export 插件，echo $JAVA_HOME 为空或旧值，Maven/Gradle 用的 JDK 和 java -version 不一致 → jenv enable-plugin export + 重启 shell。
    3. JAVA_HOME 滞后（6.2 详述）：切换后同一行命令、非交互脚本里 JAVA_HOME 是旧值 → 脚本里 export JAVA_HOME=$(jenv javahome)。
    4. .zshrc/.bashrc 写错文件：init 两行必须写进实际被加载的 rc 文件；macOS 终端默认 zsh（.zshrc），Ubuntu 图形终端 bash 交互 shell 读 .bashrc（.bash_profile 只有登录 shell 读）。
    5. PATH 顺序被破坏：后续装的软件把自己插到 PATH 最前（shims 之后），java 又变回系统的 → jenv doctor 检查 PATH 里 shims 位置。
    6. IDE 与终端版本不一致：IDEA/VS Code 用自己配置的 JDK，不走 shim → IDE 里单独设 Project SDK。
    7. macOS JDK 路径少一层：macOS 的 JDK 根是 .../xxx.jdk/Contents/Home，add 时别指到 .jdk 就停。
    8. remove ≠ 卸载：jenv remove 只解除注册，真实文件还在；反之 apt/brew 卸载 JDK 后记得 jenv remove 清掉失效登记。

    10. 高频面试题¶

    Q1：jenv 的原理是什么？

    shim 拦截 + 三级版本文件。jenv init 把 ~/.jenv/shims 置于 PATH 最前，shims 下每个可执行文件是转发脚本，经 jenv exec 按 shell（JENV_VERSION）→ local（.java-version，向上查找）→ global（~/.jenv/version）的优先级确定版本后调用真实二进制；versions/ 目录全是指向真实 JDK 的软链接。

    Q2：jenv local 之后 JAVA_HOME 为什么没变？

    jenv 默认不设 JAVA_HOME，需启用 export 插件；且该插件通过 PROMPT_COMMAND 钩子在每次提示符渲染前更新 JAVA_HOME，切换命令执行的瞬间不更新。交互式终端下一次提示符即刷新；脚本里应显式 export JAVA_HOME=$(jenv javahome)。java 命令本身走 shim 实时解析，不受此影响。

    Q3：jenv 和 SDKMAN 怎么选？

    jenv 只做 Java 版本切换（不装 JDK），三级粒度 + .java-version 目录锁定，轻；SDKMAN 能安装并管理整个 JVM 生态（Java/Gradle/Maven/Kotlin…）版本，用 .sdkmanrc 做目录锁定。只管 JDK 用 jenv，工具链全托管用 SDKMAN。

    Q4：为什么 jenv add 一个 JDK 会出现 4 个版本号？

    jenv 解析该 JDK 的 java -version 输出，自动生成完整版本（17.0.20）、次版本（17.0）、大版本（17）、架构名（openjdk64-17.0.20）四个别名，全部软链到同一目录，方便按不同精度引用；锁具体版本用完整号，日常用大版本号。

    11. 练习题¶

    1. 安装注册：Linux 上从 git 安装 jenv，注册系统已有的 JDK 17，设为 global 默认，用 jenv doctor 与 jenv versions 验证。
    2. 三级切换：建两个目录分别 jenv local 到不同版本，验证 cd 切换、jenv shell 覆盖 local、--unset 回落，并说出每步 jenv version 显示的来源。
    3. 排查 JAVA_HOME：写一个脚本，在 jenv local 切换版本的同一行紧接着打印 $JAVA_HOME，复现滞后问题，并给出脚本内的正确写法。
    4. 思考：jenv local 21.0.12 后执行 java /other/proj/Hello.java（Hello.java 所在目录有自己的 .java-version=17），用哪个版本跑？为什么？

    参考答案¶

    练习 2 关键输出（实测）：
  cd dir21 && jenv version → 21.0.12 (set by .../dir21/.java-version)
  jenv shell 17.0.20       → 17.0.20 (set by JENV_VERSION environment variable)
  jenv shell --unset       → 21.0.12 (set by .../dir21/.java-version)

练习 3：
  jenv local 21.0.12 && echo $JAVA_HOME   # 打印旧版本路径（钩子未触发）
  正确：export JAVA_HOME=$(jenv javahome) 后再用，或 jenv exec 包一层。

练习 4：
  用 17。shim 脚本对 java 命令有特判：扫描参数中的文件路径，命中真实文件时把
  JENV_DIR 设为该文件所在目录（/other/proj），版本解析优先该目录的 .java-version
  ——运行"别处的源文件"时按源文件目录锁定的版本执行（5.1 节 shim 源码）。

    12. 本章小结¶

    主题 核心要点
    定位 只切换不安装；JDK 用包管理器装，jenv add 登记
    三级切换 shell(JENV_VERSION) > local(.java-version) > global(~/.jenv/version)；jenv version 自带来源
    shim PATH 最前的假命令 → jenv exec 按优先级解析 → 真实 JDK；rehash 重建
    JAVA_HOME 必须 enable-plugin export；PROMPT_COMMAND 钩子更新，有滞后坑；脚本里 export JAVA_HOME=$(jenv javahome)
    options local-options 写 .java-options；maven/gradle 插件注入 MAVEN_OPTS/GRADLE_OPTS（已有值不覆盖）
    协作 .java-version 提交 git；IDE 不走 shim 需单独配

    最佳实践：

    1. global 设 LTS 版本兜底，每个项目根 jenv local 锁版本并提交 git
    2. 启用 export 插件，但脚本/CI 里一律显式 export JAVA_HOME=$(jenv javahome)
    3. 排查版本问题三连：jenv version（来源）→ java -version（实际）→ echo $JAVA_HOME（工具视角）
    4. jenv doctor 是安装问题的第一诊断命令
