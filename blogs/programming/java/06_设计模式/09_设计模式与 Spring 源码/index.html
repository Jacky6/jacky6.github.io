    09_设计模式与 Spring 源码¶

    前置：已学完本篇 01-08 八个模式。本篇是设计模式篇的收官章：把八个模式映射到 Spring 源码的真实落点——面试经典题"Spring 里用到了哪些设计模式"的专项突破。

    本篇总览： - ⭐ 八大模式在 Spring 中全部能找到真实用例，且都是面试高频追问点 - ⭐ 最常考三问：BeanFactory 是什么工厂？AOP 用的什么代理？Bean 怎么实现单例？ - ⭐ 学完源码映射，才算真正"理解"了模式——能说出"在哪用、为什么用"

    1. 为什么用 Spring 源码学模式¶

    学模式的三个层次：
① 会写：手写单例、手写工厂（01-08 章已覆盖）
② 会认：在框架代码里认出模式（本章目标）
③ 会用：自己写业务时主动套用（面试加分项）

Spring 是最好的教材：它 20 年打磨，几乎每个经典模式都
被用在刀刃上，而且带着"为什么这么用"的完整上下文。

    2. 工厂模式：BeanFactory 与 FactoryBean ⭐⭐⭐⭐¶

    落点：BeanFactory、ApplicationContext、FactoryBean 接口

    // Spring 本身就是个"大工厂"：你传类/名字，它给你对象
BeanFactory factory = new AnnotationConfigApplicationContext(AppConfig.class);
UserService us = factory.getBean(UserService.class);   // 工厂方法
UserService us2 = factory.getBean("userService", UserService.class);

// FactoryBean：让用户自定义"复杂对象的创建逻辑"
public class ConnectionFactoryBean implements FactoryBean<Connection> {
    @Override
    public Connection getObject() throws Exception {
        return DriverManager.getConnection(url);   // 复杂创建过程封装在这
    }
    @Override
    public Class<?> getObjectType() { return Connection.class; }
}
// MyBatis 的 SqlSessionFactoryBean、Dubbo 的引用代理都是这个套路

    追问：BeanFactory 是简单工厂、工厂方法还是抽象工厂？

    严格说都不是标准形态——它更接近"注册表 + 工厂方法"的混合体：Bean 定义（BeanDefinition）先注册进容器，getBean 按名字/类型取。面试答"IOC 容器本身是对象工厂，getBean 相当于工厂方法"即可。

    3. 单例模式：Bean 作用域 ⭐⭐⭐⭐¶

    落点：DefaultSingletonBeanRegistry.singletonObjects（一级缓存）

    // Spring 的单例不是经典懒汉/饿汉，而是"容器级注册表单例"：
// DefaultSingletonBeanRegistry 中：
Map<String, Object> singletonObjects = new ConcurrentHashMap<>(256);

// getSingleton 简化逻辑：
public Object getSingleton(String beanName) {
    Object obj = singletonObjects.get(beanName);   // 先查缓存
    if (obj == null) {
        obj = createBean(beanName);                // 没有才创建
        singletonObjects.put(beanName, obj);       // 放入缓存
    }
    return obj;
}

    对比经典实现：

    维度 经典单例 Spring 单例
    实现方式 私有构造 + 静态实例 容器缓存（Map）
    实例数量 硬编码一个 每个 beanName 一个（可注册多个不同单例）
    创建时机 类加载/首次调用 容器启动时预实例化
    优势 简单 统一管理生命周期、可替换为 prototype

    ⚠️ Spring 单例只保证"同一容器内同一 beanName 唯一"——两个 ApplicationContext 会有两个实例。

    4. 代理模式：AOP 的灵魂 ⭐⭐⭐⭐¶

    落点：AbstractAutoProxyCreator（生成代理）、JdkDynamicAopProxy、CglibAopProxy

    // AOP 代理生成的简化流程（postProcessAfterInitialization 阶段）：
public Object postProcessAfterInitialization(Object bean, String name) {
    if (bean 需要增强) {                    // 有匹配的切面
        return createProxy(bean);          // 返回代理对象替代原对象
    }
    return bean;
}

// JDK 代理核心（JdkDynamicAopProxy.invoke）：
public Object invoke(Object proxy, Method method, Object[] args) {
    // ① 执行前置通知链
    applyBeforeAdvice();
    // ② 反射调用目标方法
    Object result = method.invoke(target, args);
    // ③ 执行后置/返回通知链
    applyAfterAdvice();
    return result;
}

    面试追问： - 有接口用 JDK 动态代理、无接口用 CGLIB（SpringBoot 2.x 起默认全 CGLIB） - 自调用失效：this.method() 绕过代理 → 注入自己或拆类（见 08 章） - @Transactional 失效 8 大场景的根源全是"代理没生效"

    5. 模板方法：父类定骨架，子类填细节 ⭐⭐⭐¶

    落点：JdbcTemplate、RestTemplate、AbstractApplicationContext.refresh()

    // JdbcTemplate：把"连接→执行→处理结果→关闭"的骨架固定，
// 变化的部分（SQL 和结果映射）交给回调
public <T> T queryForObject(String sql, RowMapper<T> mapper) {
    return execute(connection -> {           // 骨架在 execute 里
        PreparedStatement ps = connection.prepareStatement(sql);
        ResultSet rs = ps.executeQuery();
        return mapper.mapRow(rs, 0);         // 变化点：怎么映射
    });
}

// 更纯粹的模板方法：容器刷新
// AbstractApplicationContext.refresh() 定义了 13 步固定流程，
// 其中 onRefresh()、postProcessBeanFactory() 是钩子，
// 子类（如 ServletWebServerApplicationContext）覆写创建 Web 服务器

    识别特征：抽象类里有 final 方法定流程 + 抽象/钩子方法留给子类。

    6. 观察者模式：Spring 事件机制 ⭐⭐⭐¶

    落点：ApplicationEventPublisher（发布者）、@EventListener（订阅者）

    // 发布（相当于 notifyObservers）
publisher.publishEvent(new OrderCreatedEvent(this, order));

// 订阅（相当于 addObserver，但用注解声明）
@EventListener
public void onOrder(OrderCreatedEvent e) { ... }

// 底层：ApplicationEventMulticaster 维护"事件类型 → 监听器"映射，
// 发布时遍历匹配的监听器逐个调用（默认同步，@Async 异步）

    进阶：@TransactionalEventListener(phase = AFTER_COMMIT)——事务提交后才通知，避免"事务回滚了短信却发出去了"。

    7. 策略模式：同一接口，多种实现 ⭐⭐⭐¶

    落点：HandlerMapping、HandlerAdapter、Resource 接口

    // HandlerMapping 是个"策略族"：不同策略用不同方式找处理器
RequestMappingHandlerMapping   // 策略1：按 @RequestMapping 注解找
BeanNameUrlHandlerMapping      // 策略2：按 Bean 名 = URL 找
SimpleUrlHandlerMapping        // 策略3：显式配置 URL → Handler

// DispatcherServlet 遍历所有 HandlerMapping 策略，
// 谁返回 Handler 就用谁——运行时切换策略，零 if-else

    // Resource 接口：统一的资源访问策略
Resource r1 = new ClassPathResource("app.yml");  // 策略：classpath
Resource r2 = new FileSystemResource("/tmp/a");  // 策略：文件系统
Resource r3 = new UrlResource("https://...");    // 策略：URL
// 调用方只面向 Resource 接口，不关心底层来源

    8. 适配器模式：接口转换 ⭐⭐⭐¶

    落点：HandlerAdapter（名字就叫 Adapter）、AdvisorAdapter

    // 问题：Controller 写法五花八门（@RequestMapping 方法、
//       HttpRequestHandler、老式 Controller 接口）
// 解法：每种写法配一个 Adapter，统一转成"执行并返回结果"

// DispatcherServlet 里：
HandlerAdapter adapter = getHandlerAdapter(handler);
ModelAndView mv = adapter.handle(request, response, handler);
// 不管 handler 是哪种类型，Adapter 都适配成统一的调用方式

    识别特征：类名/参数带 Adapter、把不兼容的接口转成统一接口。

    9. 装饰器与建造者 ⭐⭐¶

    装饰器落点：HttpServletRequestWrapper、BeanWrapper

    // 内容缓存：包一层就能重复读请求体（原本流只能读一次）
ContentCachingRequestWrapper wrapped =
    new ContentCachingRequestWrapper(request);
// 不改原对象，动态加功能——标准装饰器

    建造者落点：UriComponentsBuilder、BeanDefinitionBuilder、RequestEntity

    // 链式构建复杂对象
URI uri = UriComponentsBuilder.fromHttpUrl("https://api.example.com")
        .path("/users/{id}")
        .queryParam("detail", "full")
        .buildAndExpand(42)
        .toUri();

    10. 速查表：模式 → Spring 落点 ⭐⭐⭐⭐¶

    模式          Spring 中的代表                    面试追问点
─────────────────────────────────────────────────────────────
工厂          BeanFactory / FactoryBean          FactoryBean vs Bean 本身
单例          singletonObjects 一级缓存           三级缓存解决循环依赖
代理          JdkDynamicAopProxy / CglibAopProxy 自调用失效、代理选择
模板方法      JdbcTemplate / refresh()           骨架固定 + 钩子
观察者        ApplicationEvent / @EventListener   同步默认、事务事件

适配器        HandlerAdapter / AdvisorAdapter    统一异构接口
装饰器        HttpServletRequestWrapper          动态增强不改原类
建造者        UriComponentsBuilder               链式构建复杂对象

    11. 高频面试题¶

    Q1：Spring 里用到了哪些设计模式？举几个例子。

    八大类都有：①工厂——BeanFactory/FactoryBean；②单例——Bean 默认单例，一级缓存管理；③代理——AOP 的 JDK 动态代理/CGLIB；④模板方法——JdbcTemplate、容器 refresh 流程；⑤观察者——Spring 事件机制；⑥策略——HandlerMapping 多种路由策略；⑦适配器——HandlerAdapter 适配不同 Controller 写法；⑧装饰器——RequestWrapper。

    Q2：FactoryBean 和普通 Bean 的区别？

    普通 Bean 就是容器管理的对象本身；FactoryBean 是"能生产对象的 Bean"——getBean 拿到的是它 getObject() 的产物，想拿 FactoryBean 本身要加 & 前缀（getBean("&factory")）。MyBatis 的 SqlSessionFactory、Dubbo 远程引用都是它实现的。

    Q3：Spring 的单例和经典单例模式有什么区别？

    经典单例靠私有构造 + 静态变量保证全局唯一；Spring 靠容器的 ConcurrentHashMap 缓存（singletonObjects）按 beanName 保证唯一，且支持多单例、生命周期管理、作用域切换。本质是"注册表模式的单例"。

    Q4：DispatcherServlet 里体现了哪些模式？

    ①前端控制器本身是调度中心；②策略——多种 HandlerMapping 找处理器；③适配器——HandlerAdapter 统一调用；④模板方法——doDispatch 骨架固定；⑤责任链——拦截器链。一个类串起五种模式，是面试亮点答法。

    Q5：为什么 Spring 用模板方法封装 JDBC？

    JDBC 样板代码（获取连接、创建语句、异常转换、关闭资源）每次都一样且容易漏写；JdbcTemplate 用模板方法固定这些步骤，把 SQL 和结果映射作为回调传入——消除重复、强制资源释放、统一异常转换（SQLException → DataAccessException）。

    12. 练习题¶

    1. 源码走读：打开 JdbcTemplate 源码，找出模板方法的"骨架方法"和"回调接口"分别是什么；再找 RestTemplate 验证同样的套路。
    2. 手写映射：用观察者模式写一个"订单事件"：定义 OrderEvent，写一个发布者（持监听器列表）和两个监听器（发短信、加积分），跑通发布流程；然后对照 Spring 事件机制说出对应关系。
    3. 策略改造：写一段按"支付方式"分支的 if-else 代码（支付宝/微信/银行卡），用策略模式 + Map 注册表重构，体会"新增支付方式不改原有代码"。
    4. 思考题：为什么 Spring 不强制你用单例（可以 @Scope("prototype")）？这和经典单例模式"全局唯一"的设计意图冲突吗？

    参考答案¶

    // ========== 练习 2：手写订单事件（观察者模式） ==========
// 事件
class OrderEvent {
    final String orderId;
    OrderEvent(String orderId) { this.orderId = orderId; }
}

// 监听器接口
interface OrderListener {
    void onOrder(OrderEvent event);
}

// 发布者（对应 Spring 的 ApplicationEventPublisher）
class OrderPublisher {
    private final List<OrderListener> listeners = new ArrayList<>();

    void subscribe(OrderListener l) { listeners.add(l); }

    void publish(OrderEvent event) {
        listeners.forEach(l -> l.onOrder(event));   // 逐个通知
    }
}

// 两个监听器
OrderListener sms = e -> System.out.println("发短信：" + e.orderId);
OrderListener point = e -> System.out.println("加积分：" + e.orderId);

// 运行
OrderPublisher publisher = new OrderPublisher();
publisher.subscribe(sms);
publisher.subscribe(point);
publisher.publish(new OrderEvent("ORD-001"));
// 对应关系：subscribe ↔ @EventListener 注册
//           publish  ↔ publisher.publishEvent()
//           listeners ↔ ApplicationEventMulticaster 的映射表

// ========== 练习 3：策略模式重构支付 ==========
// 重构前（if-else，新增方式要改原代码）：
// if ("alipay".equals(type)) {...} else if ("wechat".equals(type)) {...}

// 重构后：
interface PayStrategy {
    void pay(BigDecimal amount);
}

@Component("alipay")
class AlipayStrategy implements PayStrategy {
    public void pay(BigDecimal amount) { System.out.println("支付宝支付 " + amount); }
}

@Component("wechat")
class WechatStrategy implements PayStrategy {
    public void pay(BigDecimal amount) { System.out.println("微信支付 " + amount); }
}

@Service
class PayService {
    // Spring 自动把所有 PayStrategy 按 Bean 名注入 Map
    private final Map<String, PayStrategy> strategies;

    PayService(Map<String, PayStrategy> strategies) {
        this.strategies = strategies;
    }

    void pay(String type, BigDecimal amount) {
        PayStrategy s = strategies.get(type);       // 查表，零 if-else
        if (s == null) throw new IllegalArgumentException("不支持：" + type);
        s.pay(amount);
    }
}
// 新增支付方式 = 加一个 @Component 实现类，PayService 一行不改

// ========== 练习 4：思考题答案 ==========
// 不冲突。经典单例解决的是"技术上必须唯一"（如配置管理器）；
// Spring 单例是"默认最合理的生命周期选择"——无状态 Service/Dao
// 没必要每请求新建。有状态对象（如购物车）用 prototype 才是对的。
// Spring 把"是否单例"变成可配置项，是比经典模式更工程化的设计。

    13. 本章小结¶

    核心知识点： - ✅ 工厂：BeanFactory 是 IOC 容器，FactoryBean 生产复杂对象 - ✅ 单例：一级缓存按 beanName 管理，不是经典饿汉/懒汉 - ✅ 代理：AOP = JDK/CGLIB 动态代理，自调用失效是最高频追问 - ✅ 模板方法：JdbcTemplate/refresh()，骨架 + 钩子 - ✅ 观察者：事件机制，@EventListener + 事务事件 - ✅ 策略/适配器：HandlerMapping 找、HandlerAdapter 调 - ✅ 装饰器/建造者：RequestWrapper、UriComponentsBuilder

    最佳实践： 1. 答"Spring 用了什么模式"时，每个模式配一个具体类名，别说空话 2. DispatcherServlet 串讲五种模式是加分项 3. 业务代码里主动用策略消灭 if-else、用模板方法消灭样板代码
