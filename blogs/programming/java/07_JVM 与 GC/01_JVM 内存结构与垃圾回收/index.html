    01_JVM 内存结构与垃圾回收¶

    1. 概述¶

    Java"一次编写，到处运行"的功臣是 JVM（Java Virtual Machine）：屏蔽系统差异、自动管理内存——你只管 new，回收交给 GC（垃圾回收）。

    ⭐ 理解 JVM 内存结构与 GC，才能解释线上 OOM、做性能调优、答好高频面试题。

    JVM / JRE / JDK 三者关系¶

    🏠 类比：JDK 是整栋房子，JRE 是能住的客厅+厨房，JVM 是地基。

    ┌────────────────────────────────────────────┐
│ JDK：开发工具包（javac/jar/jdb/jps...）      │
│ ┌────────────────────────────────────┐     │
│ │ JRE：运行环境（JVM + 核心类库）       │     │
│ │ ┌────────────────────────────┐     │     │
│ │ │ JVM：类加载+数据区+执行引擎   │     │     │
│ │ └────────────────────────────┘     │     │
│ └────────────────────────────────────┘     │
└────────────────────────────────────────────┘
            JDK ⊃ JRE ⊃ JVM

    ⚠️ JDK 9 起官方不再单独发行 JRE（可用 jlink 定制最小运行时）。

    2. JVM 整体架构与类加载¶

    知识点：

    • ⭐ 类加载三阶段：加载→链接（验证/准备/解析）→初始化
    • ⭐ 双亲委派模型：加载请求先逐级委托给父加载器，防止核心类被篡改
    • 打破双亲：SPI（线程上下文类加载器）、Tomcat 隔离 Web 应用
    .java --javac--> .class 字节码
   → ① 类加载子系统（加载/链接/初始化）
   → ② 运行时数据区（堆、栈、方法区...）
   → ③ 执行引擎（解释器 + JIT 编译器 + GC）

    2.1 类加载三阶段¶

    阶段 做什么
    加载 读入字节流，生成 Class 对象
    链接 验证合法性 → 准备（静态变量赋零值）→ 解析（符号引用转直接引用）
    初始化 执行 <clinit>()，静态变量真正赋值

    2.2 双亲委派模型 ⭐¶

    收到加载请求先委派给父加载器，父加载器搞不定才自己加载：

       Bootstrap ClassLoader      加载 java.lang.* 核心类（C++ 实现）
        ▲ 委派向上 / 加载失败向下
   Extension ClassLoader      加载 jre/lib/ext（JDK 9+ 更名 Platform）
        ▲
   Application ClassLoader    加载 classpath（你的业务代码）
        ▲
   自定义 ClassLoader          打破双亲委派的常见入口

    ✅ 好处：安全（自己写的 java.lang.String 永远不会被加载）+ 唯一（类只加载一次）。

    ❌ 何时打破？Tomcat 等容器要让不同应用加载各自版本的同名类——自定义 ClassLoader 重写 loadClass()，优先自己加载：

    public class MyClassLoader extends ClassLoader {
    @Override
    protected Class<?> loadClass(String name, boolean resolve)
            throws ClassNotFoundException {
        Class<?> c = findLoadedClass(name);      // 1. 已加载过直接返回
        if (c == null) {
            try {
                c = findClass(name);             // 2. 优先自己加载（打破点）
            } catch (ClassNotFoundException e) {
                c = super.loadClass(name, resolve); // 3. 不行再委派给父
            }
        }
        return c;
    }
}

    3. 运行时数据区（内存结构）¶

    知识点：

    • ⭐ 五大区域：堆（对象，GC 主战场）、虚拟机栈（线程私有，栈帧）、方法区/元空间（类元信息）、程序计数器、本地方法栈
    • ⭐ JDK 8 起永久代被元空间取代（用本地内存），不再受 -XX:MaxPermSize 限制
    • 栈帧 = 局部变量表 + 操作数栈 + 动态链接 + 返回地址

    🏢 类比：堆是公共会议室（全员共享），虚拟机栈是员工私人工位，程序计数器是便签本（记"干到第几步"）。

    ┌──────────── JVM 运行时数据区 ────────────┐
│  线程私有              线程共享            │
│  ┌──────────────┐  ┌──────────────────┐ │
│  │ 程序计数器(不OOM)│  │ 堆 Heap           │ │
│  ├──────────────┤  │  新生代 Eden:S0:S1 │ │
│  │ 虚拟机栈(栈帧)  │  │   = 8:1:1         │ │
│  ├──────────────┤  │  老年代 (新:老=1:2) │ │
│  │ 本地方法栈      │  ├──────────────────┤ │
│  └──────────────┘  │ 方法区(JDK 8+ =    │ │
│                    │  元空间, 本地内存)   │ │
│                    └──────────────────┘ │
└──────────────────────────────────────────┘

    3.1 五大区域速查 ⭐¶

    区域 私有/共享 存放内容 异常
    程序计数器 私有 当前字节码行号 ✅ 唯一不会 OOM
    虚拟机栈 私有 栈帧（局部变量表、操作数栈、返回地址） StackOverflowError / OOM
    本地方法栈 私有 native 方法调用 StackOverflowError / OOM
    堆 共享 几乎所有对象实例 OutOfMemoryError: Java heap space
    方法区 共享 类元数据、常量池、静态变量 OutOfMemoryError: Metaspace

    3.2 方法区：永久代 → 元空间 ⭐¶

    对比 永久代 PermGen（JDK ≤ 7） 元空间 Metaspace（JDK ≥ 8）
    位置 堆内 本地内存（Native Memory）
    限制 -XX:MaxPermSize，易 OOM 默认只受物理内存限制
    字符串常量池 永久代 JDK 7 起已移入堆

    ✅ 为什么替换：永久代大小难估，动态类（反射/CGLIB/JSP）极易 PermGen space OOM；元空间弹性更大，也为 HotSpot 与 JRockit 合并铺路。

    3.3 虚拟机栈与栈帧¶

    每次方法调用创建一个栈帧压栈，返回则弹栈：

    ┌────────────────────┐ 栈顶
│ 栈帧: methodC() ←当前│  局部变量表 + 操作数栈 + 动态链接 + 返回地址
├────────────────────┤
│ 栈帧: methodB()     │
├────────────────────┤
│ 栈帧: methodA()     │
└────────────────────┘ 栈底

    🍽️ 类比：栈帧像摞盘子，最后放的最先取——递归太深就是"盘子摞太高"，抛 StackOverflowError。

    4. 对象的一生与 GC 触发¶

    知识点：

    • 对象分配在堆的新生代（Eden），Eden 满触发 Minor GC
    • ⭐ 晋升机制：年龄达到阈值（默认 15）进老年代；大对象直接进老年代
    • 老年代满触发 Major/Full GC（STW 更长，要尽量避免）
    new → ① Eden 分配 → Eden 满触发 Minor GC
    → ② 存活复制到 Survivor（S0/S1 来回），年龄 +1
    → ③ 年龄 ≥ 15（-XX:MaxTenuringThreshold）晋升老年代
    → ④ 老年代满 → Major / Full GC

    补充：大对象直接进老年代（-XX:PretenureSizeThreshold）；Survivor 放不下的也提前晋升。

    GC 类型 回收范围 触发条件
    Minor GC 新生代 Eden 满
    Major GC 老年代 老年代空间不足
    Full GC 整堆 + 方法区 ① 老年代不足 ② 元空间不足 ③ System.gc()（仅建议）④ 晋升空间担保失败 ⑤ CMS 并发失败

    ⚠️ Full GC 伴随 STW（Stop The World），频率高就是性能事故。

    5. 垃圾判定与四种引用¶

    知识点：

    • ⭐ 可达性分析判死活（GC Roots 出发不可达即可回收），不用引用计数（无法解决循环引用）
    • ⭐ 四种引用：强（不回收）→ 软（内存不足才回收，缓存用）→ 弱（下次 GC 回收，ThreadLocal key）→ 虚（跟踪回收）

    5.1 引用计数 vs 可达性分析¶

    方案 原理 优缺点
    引用计数 计数归零即回收 ✅ 简单 ❌ 无法解决循环引用
    可达性分析 从 GC Roots 出发，不可达即垃圾 ✅ 主流方案，解决循环引用 
    GC Roots ─→ A ─→ B   ✅ 可达，存活
       ╳    C ⇄ D    ❌ 不可达即垃圾（哪怕互相引用）

    GC Roots 有哪些（面试高频）：① 虚拟机栈局部变量引用的对象 ② 静态变量引用的对象 ③ 常量引用的对象 ④ JNI 引用的对象 ⑤ synchronized 持有的对象、JVM 内部引用等。

    5.2 四种引用 ⭐¶

    类型 回收时机 用途
    强 Strong 永不回收（引用在就不回收） 普通 new
    软 Soft OOM 前才回收 内存敏感缓存
    弱 Weak 下次 GC 就回收 WeakHashMap、ThreadLocal key
    虚 Phantom 拿不到对象，配合 ReferenceQueue 跟踪回收 堆外内存管理 
    import java.lang.ref.SoftReference;
import java.lang.ref.WeakReference;

public class ReferenceDemo {
    public static void main(String[] args) {
        // 软引用：内存不足才回收，适合缓存
        SoftReference<byte[]> soft = new SoftReference<>(new byte[1024 * 1024]);
        System.gc();
        System.out.println("GC 后软引用：" + soft.get()); // 内存充足，仍存活

        // 弱引用：一发生 GC 就回收
        WeakReference<String> weak = new WeakReference<>(new String("弱引用"));
        System.gc();
        System.out.println("GC 后弱引用：" + weak.get()); // null
    }
}

    6. GC 算法¶

    知识点：

    • ⭐ 三算法：标记-清除（碎片）、标记-复制（浪费空间，新生代用）、标记-整理（老年代用）
    • 复制算法适合存活率低的区域——新生代对象朝生夕死，正是其用武之地

    6.1 标记-清除¶

    ┌─┬▓┬─┬▓┬▓┬─┐      ┌─┬ ┬─┬ ┬ ┬─┐
│A│▓│B│▓│▓│C│  →   │A│ │B│ │ │C│  清除后留下碎片
└─┴─┴─┴─┴─┴─┘      └─┴ ┴─┴ ┴ ┴─┘
    ✅ 优点 ❌ 缺点
    简单，不移动对象 内存碎片，大对象难分配

    6.2 标记-复制¶

    From ─存活复制→ To
┌─┬▓┬─┬▓┬─┐   →   ┌─┬─┬─┬ ┬ ┐
│A│▓│B│▓│C│       │A│B│C│ │ │  规整无碎片
└─┴─┴─┴─┴─┘       └─┴─┴─┴ ┴ ┘
    ✅ 优点 ❌ 缺点
    无碎片，分配快 浪费一半空间；存活率高时复制开销大

    ➡️ 适合新生代（存活率低）。HotSpot 用 Eden + 双 Survivor（8:1:1）把浪费降到 10%。

    6.3 标记-整理¶

    ┌─┬▓┬─┬▓┬▓┬─┐   →   ┌─┬─┬─┬ ┬ ┬ ┐
│A│▓│B│▓│▓│C│       │A│B│C│ │ │ │  存活向一端移动
└─┴─┴─┴─┴─┴─┘       └─┴─┴─┴ ┴ ┴ ┘
    ✅ 优点 ❌ 缺点
    无碎片、不浪费空间 移动对象需 STW

    ➡️ 适合老年代（存活率高）。

    7. GC 收集器¶

    知识点：

    • ⭐ 演进线：Serial/ParNew/Parallel（吞吐量优先）→ CMS（低停顿，已废弃）→ G1（分 Region，JDK 9+ 默认）→ ZGC（超低停顿）
    • ⭐ G1：堆分 Region，可预测停顿时间，优先回收垃圾最多的区域
    • 选型口诀：吞吐优先 Parallel，延迟敏感 G1/ZGC

    7.1 一览表 ⭐¶

    收集器 分代 算法 特点
    Serial / Serial Old 新/老 复制 / 标记-整理 单线程，客户端模式
    ParNew 新生代 复制 Serial 多线程版，配 CMS
    Parallel Scavenge / Old 新/老 复制 / 标记-整理 重吞吐量，JDK 8 默认
    CMS 老年代 标记-清除 低停顿；JDK 9 废弃、JDK 14 移除
    G1 整堆 Region 复制 + 标记-整理 JDK 9 起默认，可预测停顿
    ZGC 整堆 染色指针 + 读屏障 停顿通常 <1ms；JDK 11 实验、JDK 15 转正

    📌 版本事实：JDK 8 默认 Parallel；JDK 9 默认 G1（JEP 248）；ZGC/Shenandoah 于 JDK 15 转正（JEP 377）。

    7.2 重点：G1 的 Region 模型 ⭐¶

    G1 把堆切成约 2048 个 Region（1~32MB），每个 Region 动态扮演 Eden / Survivor / Old / Humongous 角色——逻辑分代、物理不分代：

    ┌──┬──┬──┬──┬──┬──┬──┬──┐
│ E│ O│ S│ H│ E│ O│ O│ E│  E=Eden O=Old S=Survivor H=大对象
├──┼──┼──┼──┼──┼──┼──┼──┤
│ O│ E│ O│ E│ H│ S│ E│ O│  角色随 GC 动态变化
└──┴──┴──┴──┴──┴──┴──┴──┘
    • 优先回收垃圾最多的 Region（Garbage First 得名）
    • Mixed GC = 全部新生代 + 部分高收益老年代 Region
    • -XX:MaxGCPauseMillis（默认 200ms）设定目标停顿
    • ✅ 适合大堆（6GB+）与低延迟场景

    8. 常用 JVM 参数¶

    参数 含义 示例
    -Xms 堆初始大小 -Xms2g
    -Xmx 堆最大值（⭐常与 -Xms 相同，避免扩缩容抖动） -Xmx4g
    -Xmn 新生代大小 -Xmn1g
    -Xss 线程栈大小（默认 512K~1M） -Xss512k
    -XX:MetaspaceSize 元空间初始阈值 256m
    -XX:MaxMetaspaceSize 元空间上限（默认无限） 512m
    -XX:NewRatio 老年代:新生代 2
    -XX:SurvivorRatio Eden:Survivor 8
    -XX:MaxTenuringThreshold 晋升年龄阈值 15
    -XX:+UseG1GC 使用 G1 —
    -XX:+PrintGCDetails GC 详情（JDK 9+ 用 -Xlog:gc*） 配 -Xloggc:gc.log
    -XX:+HeapDumpOnOutOfMemoryError OOM 自动导堆快照 排查泄漏必备 
    java -Xms2g -Xmx2g -XX:MetaspaceSize=256m -XX:+UseG1GC \
     -XX:+PrintGCDetails -XX:+HeapDumpOnOutOfMemoryError \
     -XX:HeapDumpPath=/tmp/dump.hprof -jar app.jar

    9. 内存问题排查实战¶

    知识点：

    • ⭐ 排查工具链：jstat 看 GC 频率、jmap 导出堆 dump、jstack 看线程栈、MAT/jhat 分析 dump
    • 两类典型事故：StackOverflowError（递归过深，-Xss 调栈）、OutOfMemoryError（堆不够，-Xmx 调大或查泄漏）
    • 加 -XX:+HeapDumpOnOutOfMemoryError 让 OOM 时自动留证据

    9.1 复现 StackOverflowError（运行参数：-Xss256k）¶

    public class StackOverflowDemo {
    private static int depth = 0;

    public static void recurse() {
        depth++;    // 每次调用压一个栈帧
        recurse();  // 无限递归，永不弹栈
    }

    public static void main(String[] args) {
        try {
            recurse();
        } catch (StackOverflowError e) {
            System.out.println("栈溢出！递归深度 = " + depth);
        }
    }
}

    9.2 复现 OutOfMemoryError（运行参数：-Xmx32m -XX:+HeapDumpOnOutOfMemoryError）¶

    import java.util.ArrayList;
import java.util.List;

public class OOMDemo {
    static class BigObject {
        private final byte[] data = new byte[1024 * 1024]; // 每个约 1MB
    }

    public static void main(String[] args) {
        List<BigObject> list = new ArrayList<>();
        while (true) {
            list.add(new BigObject()); // 只进不出，强引用一直持有
        }
        // java.lang.OutOfMemoryError: Java heap space
    }
}

    ⚠️ 泄漏 vs 溢出：泄漏是对象用不到却回收不掉（集合只进不出、监听器不注销）；溢出是内存真不够用。泄漏是因，溢出是果。

    9.3 排查工具速查¶

    工具 用途 常用命令
    jps 找 Java 进程 jps -l
    jstat GC 统计 jstat -gc <pid> 1000
    jmap 导出堆快照 jmap -dump:format=b,file=heap.hprof <pid>
    jstack 线程快照（查死锁/CPU 高） jstack <pid>
    jconsole / jvisualvm 图形化监控 直接启动连接进程

    套路：jps 找进程 → jstat 看 GC 频率 → jmap 导快照 → MAT/VisualVM 找大对象 → 定位泄漏。

    10. 高频面试题 ⭐¶

    Q1：什么是双亲委派？为什么需要？ A：加载请求逐级委派给父加载器，父搞不定才自己加载。保证核心类不被篡改（安全）、类只加载一次（唯一）。Tomcat 重写 loadClass() 优先自加载来打破它。

    Q2：堆和栈的区别？ A：栈线程私有，存局部变量和方法帧，随方法进出，空间小速度快；堆线程共享，存对象实例，由 GC 管理。递归过深 → StackOverflowError（栈）；对象太多 → OOM（堆）。

    Q3：什么时候触发 Full GC？ A：老年代不足、元空间不足、System.gc()、晋升担保失败、CMS 并发失败。会 STW，线上频繁触发要立即排查。

    Q4：内存泄漏和溢出的区别？ A：泄漏（Leak）是对象无用但被 GC Roots 可达无法回收；溢出（OOM）是空间确实不足。泄漏积累会引发溢出。

    Q5：为什么 JDK 8 用元空间替换永久代？ A：永久代大小难估，动态类场景易 OOM；元空间用本地内存更弹性；简化 Full GC；为 HotSpot 与 JRockit 合并铺路。

    11. 练习题¶

    练习 1：写一个必然抛 StackOverflowError 的程序并解释原因。 练习 2：写一个必然抛 OutOfMemoryError: Java heap space 的程序并解释原因。 练习 3：用 -Xmx32m -XX:+PrintGCDetails 运行练习 2，观察 GC 日志：Minor GC 出现几次？Full GC 后为什么还是崩了？

    📖 参考答案（先自己写再看！） **练习 1**：见 9.1。每次递归压入新栈帧且不返回，超过 `-Xss` 允许的深度即 StackOverflowError。 **练习 2**：见 9.2。强引用链一直可达，GC 无法回收，堆被撑满后 OOM。 **练习 3**：日志中多次 Minor GC，对象晋升后老年代也满，触发 Full GC；但 list 持有全部对象，Full GC 后堆占用几乎不变，再次分配即 OOM——这正是"泄漏引发溢出"的活教材。
