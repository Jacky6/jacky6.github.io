    03_JVM 调优与 GC 实战¶

    前置知识：01_JVM 内存结构与垃圾回收（内存结构、GC 算法、收集器一览）。本章定位是调优与线上实战：GC 日志怎么读、G1/ZGC 怎么调、CPU 飙高/内存泄漏/死锁/OOM 怎么查。

    给 C++/Python 背景的你：C++ 里 new/delete 自己管内存，Python 靠引用计数加分代 GC；Java 把回收完全交给 JVM，代价是——出问题时要会读 GC 日志、会用 JVM 工具链。本章全部基于 JDK 17 统一日志框架。

    2. GC 日志解读实战¶

    调优第一步永远是看日志。JDK 9+ 的统一日志框架（Unified Logging）用一个 -Xlog 开关搞定所有输出，JDK 8 的 -XX:+PrintGCDetails 早已废弃，面试别再提旧格式。

    2.1 -Xlog:gc* 配置¶

    # 生产环境推荐写法：GC 全量日志 + 按大小滚动，不怕撑爆磁盘
java -Xlog:gc*:file=gc-%t.log:time,uptime,level,tags:filecount=10,filesize=50M \
     -jar app.jar

    语法拆解 -Xlog:<选择器>:<输出>:<装饰器>:<输出选项>：

    片段 含义
    gc* tag 选择器：gc 及所有子 tag（gc,heap / gc,phases / gc,age…）
    file=gc-%t.log 输出到文件，%t 是启动时间戳，重启不覆盖
    time,uptime,level,tags 装饰器：墙上时间、启动耗时、级别、tag
    filecount=10,filesize=50M 滚动策略：最多 10 个 50MB 文件

    ⚠️ 只要摘要可写 -Xlog:gc（不带星号），但排查问题时 gc* 的信息量才够。

    2.2 日志字段含义¶

    一条典型的 G1 Young GC 日志：

    [2026-08-22T10:15:32.123+0800][12.345s][8848][info][gc] GC(42) Pause Young (Normal) (G1 Evacuation Pause) 120M->48M(512M) 5.321ms
└──────── 墙上时间 ────────┘└启动耗时┘└pid┘└级别┘└tag┘└编号┘└──────────── 停顿原因 ────────────────┘└─前->后(堆上限)─┘└停顿时长┘

    三个数字 120M->48M(512M) 是速读核心：回收前堆占用 → 回收后堆占用（堆上限）。回收后降不下来 = 有存活对象撑着，可能是正常缓存，也可能是泄漏。

    并发标记周期的日志长这样（两行 STW 很短即健康）：

    [3.500s][info][gc] GC(17) Concurrent Mark Cycle
[3.518s][info][gc] GC(17) Pause Remark  150M->150M(256M) 1.234ms
[3.530s][info][gc] GC(17) Pause Cleanup 151M->151M(256M) 0.234ms

    2.3 从日志看触发原因 ⭐¶

    日志关键字 GC 类型 常见触发原因
    Pause Young (Normal) (G1 Evacuation Pause) Young GC Eden Region 用满（最常见，正常）
    Pause Young (Concurrent Start) (G1 Humongous Allocation) 并发标记起点 大对象（≥半个 Region）分配且堆占用高
    Pause Young (Mixed) Mixed GC 并发标记完成后，回收老年代高垃圾比例 Region
    Pause Full (G1 Compaction Pause) Full GC Mixed 追不上分配 / 疏散失败
    Pause Full (Metadata GC Threshold) Full GC 元空间不足触发 
    正常节奏：Young GC ─(堆到 IHOP)─▶ 并发标记 ─▶ Mixed GC ─▶ 回到 Young GC
危险信号：Mixed 后老年代仍快速涨 ─▶ Full GC ─▶ 堆降不下来 ─▶ 反复 Full GC ≈ 泄漏

    ✅ 读日志口诀：看类型定方向，看前后差值定严重程度，看频率定紧急度。

    3. G1 调优实战¶

    G1 是 JDK 9+ 的默认收集器。设计哲学：你给停顿目标，它自己决定每次回收哪些 Region——调优思路与老收集器完全不同。

    3.1 关键参数¶

    参数 默认值 作用
    -XX:MaxGCPauseMillis 200 期望最大停顿（软目标），决定每次回收的 Region 数
    -XX:G1HeapRegionSize 堆/2048 Region 大小（1~32MB，2 的幂）；对象 ≥ 半个 Region 即大对象
    -XX:InitiatingHeapOccupancyPercent 45 IHOP：堆占用达此比例启动并发标记
    -XX:ParallelGCThreads 按 CPU 核数 STW 阶段并行线程数
    -XX:ConcGCThreads ≈并行数/4 并发标记线程数
    -XX:G1ReservePercent 10 保留堆比例，防疏散失败

    3.2 调优思路 ⭐¶

    ① 给足堆（-Xms=-Xmx 避免运行时扩缩抖动）并打开 GC 日志
② 压测出基线：Young GC 频率/停顿、Mixed 是否及时、有无 Full GC
③ 一次只改一个参数 → 压测 → 对比日志，循环迭代
    • 停顿不达标：MaxGCPauseMillis 适度调小（如 200→100）；⚠️ 调太小会牺牲吞吐、增加 GC 频率；
    • Mixed 来得太晚引发 Full GC：IHOP 从 45 降到 40/35，让并发标记提前；
    • 大对象频繁出现：调大 Region（如 16M→32M），让大数组走普通分配而非 Humongous；
    • 并发标记拖太久占 CPU：微调 ConcGCThreads。

    3.3 常见误区 ❌¶

    • ❌ 用 -Xmn/NewRatio 固定新生代——G1 靠自适应调整分代完成停顿目标，手动固定反而拖后腿；
    • ❌ MaxGCPauseMillis 设 10ms——G1 不是 ZGC，做不到；要极低延迟请换收集器；
    • ❌ 一次改五六个参数——出问题无法归因；
    • ❌ 不看日志直接抄"网上最佳参数"——参数与堆大小、对象生命周期强相关，没有通用值。

    4. ZGC 简介¶

    ZGC（JDK 15 转正）目标：停顿 ≤1ms，且不随堆大小增长——TB 级堆也一样。JDK 16 起实际做到亚毫秒。

    4.1 着色指针与读屏障 ⭐¶

    传统 GC 要在 STW 里标记和移动对象；ZGC 把状态信息塞进指针本身：

    64 位指针：[ 元数据位 Marked0/Marked1/Remapped/Finalizable ][──── 42 位地址（4TB）────]
    • 着色指针（Colored Pointers）：对象标记状态直接写在指针高位 bit，标记对象只需改指针颜色，不用改对象头；
    • 读屏障（Load Barrier）：每次从堆读引用时插一小段检查代码，发现指针"颜色不对"（对象已被并发移动）就顺手修正——把移动对象的开销摊到应用线程的每次读取上；
    • 于是对象标记、移动全程与应用并发，STW 只剩根扫描等常数级工作 → 停顿 <1ms 且与堆大小无关。

    4.2 G1 vs ZGC¶

    维度 G1 ZGC（JDK 17）
    停顿目标 几十~几百 ms（软目标） ≤1ms，与堆大小无关
    舒适堆规模 几 GB~几十 GB 可达 TB 级
    屏障 写屏障 读屏障，吞吐约降 5%~15%
    分代 分代 不分代（分代 ZGC 是 JDK 21 的事）
    启用 JDK 9+ 默认 需显式 -XX:+UseZGC

    4.3 适用场景与 JDK 17 参数¶

    ✅ 适合：大堆 + 低延迟（金融撮合、实时计算、网关）。⚠️ 不适合：吞吐优先的批处理、小堆服务（G1 足够，没必要吃读屏障开销）。

    # SoftMaxHeapSize 是软上限：ZGC 会优先把堆压到 12g，最多用到 16g
java -XX:+UseZGC -Xmx16g -Xms16g -XX:SoftMaxHeapSize=12g \
     -Xlog:gc*:file=gc-%t.log -jar app.jar

    5. 线上问题排查完整流程¶

    5.1 CPU 飙高：top -Hp + jstack 三步法 ⭐¶

    top                            # ① 找到吃 CPU 的 java 进程，记下 pid
top -Hp 8848                   # ② 看进程内哪个线程吃 CPU，记下线程号 tid
printf '%x\n' 8877             # ③ tid 转 16 进制 → 22ad（jstack 里 nid 是 16 进制）
jstack 8848 > stack.txt        # ④ 导出线程栈，搜 nid=0x22ad 看栈顶在干嘛

    栈顶是死循环？正则回溯？还是名为 GC Thread#0 的 GC 线程——若是后者，CPU 其实烧在 GC 上，转查 GC 日志。

    5.2 内存泄漏：jmap 导出 + MAT 分析支配树¶

    jmap -histo:live 8848 | head -20                 # 先看哪类对象占得多
jmap -dump:live,format=b,file=heap.hprof 8848    # 导出堆快照

    用 Eclipse MAT 打开 hprof，三板斧：

    1. Leak Suspects 报告：直接给出疑似泄漏点；
    2. Dominator Tree（支配树）：按"支配的内存量"排序，揪出最大对象；
    3. Path to GC Roots → exclude weak/soft：看它为什么没被回收。泄漏 = 不该活着的对象被一条意外的强引用链拽住（典型：static Map 当缓存只进不出、ThreadLocal 没 remove、监听器没注销）。

    ⚠️ dump 会 STW 数秒~数十秒，生产环境先在负载均衡上摘流量。

    5.3 死锁：jstack 定位¶

    jstack 8848 | grep -A 25 'deadlock'

    输出会直接给出 Found one Java-level deadlock:，列出两个线程各持哪把锁、又在等哪把锁——照栈统一加锁顺序即可。

    5.4 频繁 Full GC¶

    jstat -gcutil 8848 1000 10    # 每秒输出各区占用、GC 次数与累计耗时

    再对照 GC 日志找触发原因：

    日志线索 根因方向 处置
    Full GC 后老年代几乎不降 内存泄漏 走 5.2 流程
    (G1 Humongous Allocation) 反复出现 大对象（大数组/大报文） 拆小对象或调大 Region
    (Metadata GC Threshold) 元空间不足 加大 MaxMetaspaceSize，查动态类生成
    Evacuation Failure 堆太满/预留不足 加堆或加 G1ReservePercent

    6. 常见 OOM 案例与解决¶

    报错 原因 解决
    Java heap space 堆不够：泄漏或 -Xmx 太小 dump+MAT 找泄漏；确属容量问题再加堆
    Metaspace 类元数据爆：CGLIB/反射狂生成类、热部署类加载器泄漏 -XX:MaxMetaspaceSize=512m，查动态代理与重复部署
    Direct buffer memory 堆外直接内存耗尽（NIO/Netty 的 allocateDirect） -XX:MaxDirectMemorySize；直接内存靠 GC 触发 Cleaner 回收，检查是否被长期持有
    GC overhead limit exceeded GC 占 >98% 时间却回收 <2% 堆 本质多为泄漏，按泄漏排查，别只加堆

    ✅ 统一保险参数：-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dumps——OOM 时自动留现场，事后慢慢分析。

    7. 调优方法论 ⭐¶

    定目标 ──▶ 建监控 ──▶ 测基线 ──▶ 单变量改动 ──▶ 压测验证 ──▶ 对照目标
  │            │
  P99 停顿?    GC 日志 + jstat + 指标大盘
  吞吐?        （没有监控的调优 = 玄学）
    1. 先定目标再动手：要 P99 停顿、吞吐还是内存占用？目标不同，参数方向相反；
    2. 监控指标先行：GC 频率/耗时、各区占用、Full GC 次数——没有基线数据就没有调优；
    3. ❌ 不要盲目调参：多数服务用默认 G1 加合理的 -Xmx 就够；先改代码（对象生命周期、缓存淘汰策略），再改 JVM；
    4. 一次只改一个变量，压测对比；上线灰度观察一天再全量。

    8. 高频面试题 ⭐¶

    Q1：你们线上用什么收集器？怎么调优的？

    JDK 17 默认 G1；-Xms=-Xmx=4g，MaxGCPauseMillis 默认 200ms 起步，开 -Xlog:gc* 滚动日志；监控 P99 停顿与 Full GC 次数；只有日志显示 Mixed 追不上分配时才下调 IHOP。答出"基于日志和监控调优"的过程，而不是背参数表。

    Q2：Full GC 频繁怎么排查？

    jstat 确认频率 → GC 日志看触发原因与回收效果 → Full GC 后老年代降不下来就 dump + MAT 支配树找泄漏；Humongous/Metadata Threshold 等各有对应处置（见 5.4）。

    Q3：IHOP 是什么？怎么调？

    启动并发标记的堆占用阈值，默认 45%。Mixed 前总出现 Full GC → 调低让标记提前；并发标记太频繁浪费 CPU → 调高。JDK 17 默认开自适应 IHOP，日志里可观察它的学习值。

    Q4：ZGC 为什么能做到 <1ms？

    着色指针把标记状态放指针高位，读屏障在读取时并发修正被移动的引用，标记/移动全程与应用并发；STW 只剩根扫描等常数级工作，与堆大小无关。

    Q5：线上 CPU 100% 怎么排查？

    top 找进程 → top -Hp 找线程 → tid 转 16 进制 → jstack 搜 nid 看栈顶；若是 GC 线程占 CPU，转查 GC 日志与堆占用。

    Q6：GC overhead limit exceeded 和 heap space 有什么区别？

    都是堆不够用。前者是"GC 拼命跑也回收不动"（>98% 时间回收 <2%），几乎必然是泄漏；后者是分配时直接没空间。排查路径相同：dump + 支配树。

    9. 练习题¶

    1. 写出生产环境开启 GC 日志滚动输出的完整 -Xlog 参数，并说明每段含义。

    2. 日志连续出现 Pause Full (G1 Compaction Pause) 490M->470M(512M)，给出你的排查步骤（至少三步）。

    3. 服务每运行 2 天就 Metaspace OOM，重启即恢复。列出两个最可能的根因与验证手段。

    4. 业务要求 P99 GC 停顿 <10ms、堆 32GB，G1 和 ZGC 选哪个？说明理由与关键参数。

    参考答案¶

    1. -Xlog:gc*:file=gc-%t.log:time,uptime,level,tags:filecount=10,filesize=50M
   gc*=收集 gc 及子 tag 的全量日志；file=输出文件（%t 时间戳防覆盖）；
   time,uptime,level,tags=装饰器；filecount/filesize=滚动 10 个 50MB 文件。

2. ① 490M->470M：Full GC 后堆几乎不降，存活对象接近堆上限，高度疑似泄漏；
   ② 摘流量后 jmap -dump:live,format=b,file=heap.hprof <pid> 导出堆快照；
   ③ MAT Dominator Tree 找最大对象，Path to GC Roots 找强引用链；
   ④ 定位代码（常见：static Map 缓存无淘汰、ThreadLocal 未 remove），
   修复后压测并观察 GC 日志验证。

3. ① 动态生成类失控：CGLIB/反射/Groovy 每次调用都生成新 Class——
   用 -Xlog:class+load 观察类数量是否持续增长；
   ② 热部署类加载器泄漏：旧 ClassLoader 被静态引用无法卸载——
   MAT 里搜已停应用的类仍存活。临时把 -XX:MaxMetaspaceSize 调大只是
   延后崩溃，必须修根因。

4. 选 ZGC。32GB 堆下 G1 的 Mixed/Full GC 很难稳定压进 10ms，
   而 ZGC 停顿与堆大小无关（≤1ms）。关键参数：
   -XX:+UseZGC -Xms32g -Xmx32g -XX:SoftMaxHeapSize=28g -Xlog:gc*。
   代价：读屏障带来约 5%~15% 吞吐损失，需压测确认业务可接受。

    10. 本章小结¶

    主题 核心要点
    GC 日志 -Xlog:gc* 统一日志；读类型、读前后差值、读频率
    G1 调优 给停顿目标不给具体方案；忌固定新生代；单变量迭代
    ZGC 着色指针+读屏障，停顿<1ms 与堆无关；大堆低延迟首选
    排查三板斧 top -Hp+jstack 查 CPU；jmap+MAT 查泄漏；jstack 查死锁
    OOM 四种典型报错各有根因；HeapDumpOnOutOfMemoryError 必开
    方法论 目标→监控→基线→单变量→压测；先改代码再改参数
