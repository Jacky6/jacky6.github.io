    05_Spring MVC 进阶¶

    前置：已学完 02_Spring MVC 基础篇。本篇基于 JDK 17 + Spring Boot 3.x（jakarta.* 命名空间），覆盖六大进阶主题：WebMvcConfigurer、HttpMessageConverter 与 Jackson 定制、RESTful 设计规范、统一异常处理深化（RFC 7807）、拦截器实战、参数解析器扩展。

    本篇总览：

    • ⭐ WebMvcConfigurer 是定制 Spring MVC 默认行为的正规入口（SpringBoot 下不要加 @EnableWebMvc）
    • ⭐ Jackson 定制三档：spring.jackson.* 属性 < Jackson2ObjectMapperBuilderCustomizer < 自定义 ObjectMapper Bean
    • ⭐ RESTful = 资源建模 + HTTP 方法语义 + 状态码规范 + 版本控制 + 幂等性
    • ⭐ 异常三件套：ErrorCode 枚举 + BusinessException（保留异常链）+ @RestControllerAdvice（可选 ProblemDetail）
    • ⭐ 拦截器三实战：登录态 / 接口耗时 / 防重复提交；ThreadLocal 必须在 afterCompletion 中 remove
    • ⭐ HandlerMethodArgumentResolver 让 @LoginUser 直接把当前用户注入 Controller 参数

    1. WebMvcConfigurer 全接口方法详解¶

    知识点：

    • ⭐ WebMvcConfigurer 是 Spring 提供的回调接口：Spring MVC 初始化时回调它的方法，让你往默认配置里"加料"
    • ⭐ SpringBoot 下写法：@Configuration 类实现该接口，重写哪个方法就定制哪块，其余保持 Boot 自动配置
    • ⭐ 可以有多个实现类，全部生效（内部用组合器合并调用），冲突时可用 @Order 控制顺序
    • ⚠️ SpringBoot 中千万不要加 @EnableWebMvc——它会让 Boot 的 WebMvc 自动配置整体失效（见 1.3）

    1.2 configureMessageConverters vs extendMessageConverters（⭐高频）¶

    两者都操作 List<HttpMessageConverter<?>>，但语义完全不同：

    • configureMessageConverters(list)：回调结束后，只要 list 非空，Spring 就不再添加任何默认转换器。相当于"推倒重来"，你必须自己把 Jackson、String、Form 等全部加回去，否则连 JSON 都返回不了。
    • extendMessageConverters(list)：默认转换器已经全部加好才回调，你只做增删或调顺序。
    @Configuration
public class WebMvcConfig implements WebMvcConfigurer {

    /** 方式一：微调（推荐）——默认转换器都在，只改 Jackson 那一个 */
    @Override
    public void extendMessageConverters(List<HttpMessageConverter<?>> converters) {
        for (HttpMessageConverter<?> converter : converters) {
            if (converter instanceof MappingJackson2HttpMessageConverter jackson) {
                // 例如：把默认的 Jackson 转换器挪到第一位，优先处理
                converters.remove(jackson);
                converters.add(0, jackson);
                break;
            }
        }
    }

    /** 方式二：完全替换（慎用）——加了任何元素后，Boot 默认转换器全部不再注册 */
    /*
    @Override
    public void configureMessageConverters(List<HttpMessageConverter<?>> converters) {
        ObjectMapper om = new ObjectMapper();
        converters.add(new MappingJackson2HttpMessageConverter(om)); // 必须自己加
        converters.add(new StringHttpMessageConverter(StandardCharsets.UTF_8));
        // 漏加哪个，哪种响应就 406/不支持
    }
    */
}

    ⚠️ 99% 的场景用 extendMessageConverters 或直接定制 ObjectMapper（第 2 节），不要用 configureMessageConverters。

    1.3 各核心方法逐个详解¶

    ① addInterceptors——注册拦截器

    @Configuration
public class WebMvcConfig implements WebMvcConfigurer {

    private final LoginInterceptor loginInterceptor; // 拦截器做成 Bean，可注入 Service

    public WebMvcConfig(LoginInterceptor loginInterceptor) {
        this.loginInterceptor = loginInterceptor;
    }

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(loginInterceptor)
                .addPathPatterns("/api/**")                    // 拦截范围（Ant 风格）
                .excludePathPatterns("/api/auth/login",        // 登录接口放行
                                     "/api/auth/register",
                                     "/error")
                .order(1);                                     // 数字越小越先执行
    }
}

    ② addCorsMappings——全局跨域

    @Override
public void addCorsMappings(CorsRegistry registry) {
    registry.addMapping("/api/**")                              // 生效路径
            .allowedOriginPatterns("https://*.example.com")     // ⭐ 用 patterns，别用 "*" + 允许 Cookie
            .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
            .allowedHeaders("*")
            .allowCredentials(true)                             // 允许携带 Cookie/Authorization
            .maxAge(3600);                                      // 预检请求缓存 1 小时
}

    ⚠️ allowCredentials(true) 时不能用 allowedOrigins("*")，启动直接报错；必须用 allowedOriginPatterns 或写明确域名。

    ③ addResourceHandlers——静态资源映射

    @Override
public void addResourceHandlers(ResourceHandlerRegistry registry) {
    // 把 /files/** 映射到服务器本地磁盘目录（上传文件的访问入口）
    registry.addResourceHandler("/files/**")
            .addResourceLocations("file:/data/upload/")        // 注意 file: 前缀和结尾斜杠
            .setCachePeriod(86400);                            // 浏览器缓存 1 天

    // classpath 资源 + 版本化文件名场景
    registry.addResourceHandler("/webjars/**")
            .addResourceLocations("classpath:/META-INF/resources/webjars/");
}

    💡 Boot 默认已映射 classpath:/static/、/public/ 等；此方法主要用于外部目录或改缓存策略。

    ④ addFormatters——类型转换与格式化

    @RequestParam、@PathVariable 的字符串 → 目标类型转换在这里扩展：

    @Override
public void addFormatters(FormatterRegistry registry) {
    // Converter：String → LocalDate，支持 "2026-08-22"
    registry.addConverter(String.class, LocalDate.class,
            source -> LocalDate.parse(source, DateTimeFormatter.ofPattern("yyyy-MM-dd")));

    // Formatter：带格式的双向转换（parse + print）
    registry.addFormatter(new Formatter<BigDecimal>() {
        @Override
        public BigDecimal parse(String text, Locale locale) {
            return new BigDecimal(text.replace(",", ""));      // "1,234.56" → 1234.56
        }
        @Override
        public String print(BigDecimal object, Locale locale) {
            return object.toPlainString();
        }
    });
}

    💡 只给某个字段定制日期格式时，优先用字段上的 @DateTimeFormat(pattern="...")，不必全局注册。

    ⑤ configurePathMatch——路径匹配与统一前缀

    @Override
public void configurePathMatch(PathMatchConfigurer configurer) {
    // 给所有标注 @ApiV1 的 Controller 自动加前缀 /api/v1（版本控制利器，见第 3.4 节）
    configurer.addPathPrefix("/api/v1",
            c -> c.isAnnotationPresent(ApiV1.class));
}

    ⚠️ SpringBoot 3.2（Spring 6.1）起尾斜杠不再等价：/api/users/ 和 /api/users 是两个路径，前者 404。旧项目迁移时这是常见故障点。

    1.4 常见坑¶

    1. ⚠️ SpringBoot 下加了 @EnableWebMvc：WebMvcAutoConfiguration 上有条件 @ConditionalOnMissingBean(WebMvcConfigurationSupport.class)，而 @EnableWebMvc 会导入 DelegatingWebMvcConfiguration（它继承 WebMvcConfigurationSupport），导致 Boot 自动配置整体失效——spring.mvc.*、spring.jackson.* 属性全部不再生效。Boot 3.x 中正确姿势只有：实现 WebMvcConfigurer。
    2. ⚠️ 在 configureMessageConverters 里加了元素：默认转换器全部不注册，接口突然返回不了 JSON/String，报 406 或找不到转换器。
    3. ⚠️ 拦截器直接 new 出来：registry.addInterceptor(new LoginInterceptor()) 里的拦截器不是 Bean，内部 @Autowired 全是 null。要么注入 Bean，要么在配置类里手动传依赖。
    4. ⚠️ 拦截器 /api/** 把静态资源也拦了：/files/** 这类资源路径要么不放在拦截范围内，要么 excludePathPatterns 放行。
    5. ⚠️ 尾斜杠：Boot 3.2+ 中 /users/ ≠ /users，前端拼接 URL 多一个斜杠就是 404。
    6. ⚠️ 多个配置类覆盖：多个 WebMvcConfigurer 不是后者覆盖前者，而是全部执行（组合模式）；同名配置叠加可能产生意外效果，建议项目里只留一个总配置类。

    2. HttpMessageConverter 详解与 Jackson 定制¶

    知识点：

    • ⭐ HttpMessageConverter 是"HTTP 报文 ↔ Java 对象"的双向转换器接口；@RequestBody 反序列化、@ResponseBody 序列化都靠它
    • ⭐ 选择规则：按注册顺序遍历，第一个 canRead/canWrite 匹配的就生效——顺序即优先级
    • ⭐ SpringBoot 默认注册约 10 个转换器，JSON 场景用的是 MappingJackson2HttpMessageConverter（内部持有一个 ObjectMapper）
    • ⭐ Jackson 定制三档由浅入深：spring.jackson.* 属性 → Jackson2ObjectMapperBuilderCustomizer → 自定义 ObjectMapper Bean

    2.1 接口本质与默认转换器¶

    // org.springframework.http.converter.HttpMessageConverter（简化）
public interface HttpMessageConverter<T> {
    boolean canRead(Class<?> clazz, MediaType mediaType);   // 能否把报文读成 clazz
    T read(Class<? extends T> clazz, HttpInputMessage input) throws IOException;
    boolean canWrite(Class<?> clazz, MediaType mediaType);  // 能否把 clazz 写成报文
    void write(T t, MediaType contentType, HttpOutputMessage output) throws IOException;
    List<MediaType> getSupportedMediaTypes();
}

    SpringBoot 默认注册顺序（WebMvcAutoConfiguration，只列常用的）：

    顺序 转换器 处理
    1 ByteArrayHttpMessageConverter byte[]
    2 StringHttpMessageConverter String（text/plain）
    3 ResourceHttpMessageConverter Resource（文件流）
    5 FormHttpMessageConverter 表单 MultiValueMap
    7 MappingJackson2HttpMessageConverter ⭐ JSON（application/json）

    💡 Content-Type: application/json 的请求体 → 排到 Jackson 转换器；text/plain 的字符串 → 排到 String 转换器。Content-Type 不对就 415，本质是没有任何转换器 canRead。

    2.2 日期格式（LocalDateTime 序列化为 "yyyy-MM-dd HH:mm:ss"）¶

    spring.jackson.date-format 只对 java.util.Date 生效，对 Java 8 时间（LocalDateTime 等）无效。正确做法是注册自定义序列化器：

    @Configuration
public class JacksonConfig {

    private static final DateTimeFormatter DATE_TIME_FMT =
            DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");
    private static final DateTimeFormatter DATE_FMT =
            DateTimeFormatter.ofPattern("yyyy-MM-dd");
    private static final DateTimeFormatter TIME_FMT =
            DateTimeFormatter.ofPattern("HH:mm:ss");

    @Bean
    public Jackson2ObjectMapperBuilderCustomizer jacksonCustomizer() {
        return builder -> {
            builder.simpleDateFormat("yyyy-MM-dd HH:mm:ss");      // 针对 java.util.Date
            builder.timeZone(TimeZone.getTimeZone("Asia/Shanghai"));
            builder.serializers(
                new LocalDateTimeSerializer(DATE_TIME_FMT),       // ⭐ java.time 三件套
                new LocalDateSerializer(DATE_FMT),
                new LocalTimeSerializer(TIME_FMT));
            builder.deserializers(
                new LocalDateTimeDeserializer(DATE_TIME_FMT),
                new LocalDateDeserializer(DATE_FMT),
                new LocalTimeDeserializer(TIME_FMT));
        };
    }
}

    // 验证用的 DTO
public class OrderVO {
    private Long id;
    private LocalDateTime createTime;   // 输出 "2026-08-22 14:30:00"
    private LocalDate shipDate;         // 输出 "2026-08-22"
    // 省略 getter/setter
}

    💡 只改个别字段时，用字段级注解更轻：@JsonFormat(pattern = "yyyy-MM-dd HH:mm:ss", timezone = "GMT+8")。

    2.3 Long 精度丢失（雪花 ID 必踩坑）¶

    原因：JavaScript 的 Number 是 IEEE 754 双精度浮点，安全整数上限 2^53 - 1 = 9007199254740991（16 位）。雪花算法生成的 ID 是 18~19 位，前端 JSON.parse 后末尾几位变成 0。

    解法：把 Long 序列化成字符串。两种粒度：

    // 方案 A：字段级（精准，推荐新项目用）
public class OrderVO {
    @JsonSerialize(using = ToStringSerializer.class)   // 输出 "1958833990022942720"
    private Long id;
}

// 方案 B：全局（老项目一把梭，加到 2.2 的 customizer 里）
builder.serializerByType(Long.class, ToStringSerializer.instance);
builder.serializerByType(Long.TYPE, ToStringSerializer.instance);

    ⚠️ 全局方案会让所有 Long 字段（含 total、pageSize 等）都变成字符串，前端取值时要注意类型；新接口建议字段级 @JsonSerialize。反序列化不受影响——Jackson 能把 "123" 自动转回 Long。

    2.4 null 处理¶

    // ① 全局：序列化时忽略所有 null 字段
spring.jackson.default-property-inclusion=non_null   # application.yml

// ② 类级：只对该类生效
@JsonInclude(JsonInclude.Include.NON_NULL)
public class UserVO { ... }

// ③ 字段级
@JsonInclude(JsonInclude.Include.NON_EMPTY)          // null、""、空集合都不输出
private List<String> tags;

    反序列化方向：JSON 里的 null 赋给 包装类型（Long/Integer）没问题，赋给基本类型（long/int）会抛异常。DTO 一律用包装类型即可避免。

    2.5 常用 Jackson 注解¶

    @JsonIgnoreProperties(ignoreUnknown = true)   // ⭐ 类级：JSON 多了未知字段不报错（前后端版本兼容必备）
public class UserDTO {

    @JsonProperty("user_name")                // 改名：Java 驼峰 ↔ JSON 下划线
    private String userName;

    @JsonIgnore                               // 序列化、反序列化都忽略（如密码）
    private String password;

    @JsonProperty(access = JsonProperty.Access.WRITE_ONLY)  // 只接收不回显（入参有、出参无）
    private String idCard;

    @JsonAlias({"phone", "mobile"})           // 反序列化时多个别名都认（序列化仍用本名）
    private String phoneNumber;

    @JsonFormat(pattern = "yyyy-MM-dd HH:mm:ss", timezone = "GMT+8")
    private LocalDateTime updateTime;

    // getter/setter 略
}
    注解 作用 典型场景
    @JsonProperty 改 JSON 字段名 / 控制读写方向 对接下划线风格第三方 API
    @JsonIgnore 双向忽略 密码、内部状态
    @JsonIgnoreProperties 类级忽略 / 容忍未知字段 版本兼容
    @JsonAlias 反序列化别名 字段改名过渡期
    @JsonFormat 日期/数字格式 单字段日期格式
    @JsonSerialize/@JsonDeserialize 指定自定义（反）序列化器 Long→String、脱敏
    @JsonInclude 控制 null/空值输出 精简响应

    2.6 自定义 ObjectMapper Bean（完全接管）¶

    当你需要完全控制 ObjectMapper 时，直接定义 Bean。注意：这会整体替换 Boot 自动配置的那个，spring.jackson.* 属性将全部失效，所有配置必须手写：

    @Configuration
public class JacksonConfig {

    @Bean
    @Primary
    public ObjectMapper objectMapper() {
        ObjectMapper om = new ObjectMapper();

        // ① 序列化行为
        om.setSerializationInclusion(JsonInclude.Include.NON_NULL);     // 忽略 null
        om.configure(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS, false); // 日期不用时间戳
        om.configure(SerializationFeature.FAIL_ON_EMPTY_BEANS, false);  // 空对象不报错

        // ② 反序列化行为
        om.configure(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES, false); // 容忍未知字段 ⭐
        om.configure(DeserializationFeature.ACCEPT_EMPTY_STRING_AS_NULL_OBJECT, true);

        // ③ Java 8 时间模块（自定义 Bean 后必须手动注册！Boot 不再帮你）
        JavaTimeModule timeModule = new JavaTimeModule();
        DateTimeFormatter fmt = DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");
        timeModule.addSerializer(LocalDateTime.class, new LocalDateTimeSerializer(fmt));
        timeModule.addDeserializer(LocalDateTime.class, new LocalDateTimeDeserializer(fmt));
        om.registerModule(timeModule);

        // ④ Long → String 防精度丢失
        SimpleModule longModule = new SimpleModule();
        longModule.addSerializer(Long.class, ToStringSerializer.instance);
        longModule.addSerializer(Long.TYPE, ToStringSerializer.instance);
        om.registerModule(longModule);

        om.setTimeZone(TimeZone.getTimeZone("Asia/Shanghai"));
        return om;
    }
}

    ⚠️ 三档配置的优先级：自定义 ObjectMapper Bean > Jackson2ObjectMapperBuilderCustomizer > spring.jackson.* 属性。一旦定义了 ObjectMapper Bean，前两档全部失效——这是最常见的"配置了但没生效"事故。

    💡 推荐次序：能用属性解决就用属性；需要写代码定制就用 Jackson2ObjectMapperBuilderCustomizer（可与 Boot 默认行为叠加，支持多个）；只有要彻底接管才写 ObjectMapper Bean。

    2.7 常见坑¶

    1. ⚠️ spring.jackson.date-format 对 LocalDateTime 无效：它只管 java.util.Date；java.time 要注册（反）序列化器或字段 @JsonFormat。
    2. ⚠️ 自定义 ObjectMapper Bean 后忘了注册 JavaTimeModule：LocalDateTime 直接序列化报错或变成时间戳数组。Boot 的 builder 会自动注册 jsr310 模块，你的 new ObjectMapper() 不会。
    3. ⚠️ Long 精度丢失只在浏览器出现：后端日志里 ID 是对的，前端拿到就错了——排查方向别搞反。
    4. ⚠️ 全局 ToStringSerializer 会让分页 total 等也变字符串，前端 total + 1 变字符串拼接。
    5. ⚠️ DTO 缺无参构造或 setter：Jackson 默认反序列化需要无参构造 + setter（或 @JsonCreator + @JsonProperty 参数标注，或 jackson-module-parameter-names 配合 -parameters 编译参数）。用 record 做 DTO 时需确认模块支持。
    6. ⚠️ 415/406：请求没带 Content-Type: application/json → 415；Accept 头与可用转换器不匹配 → 406。curl 测试记得 -H "Content-Type: application/json"。
    7. ⚠️ 用 configureMessageConverters 加转换器导致默认全丢（1.2 节）：JSON、String 响应全挂，优先 extendMessageConverters。

    3. RESTful API 设计规范¶

    知识点：

    • ⭐ REST = 以"资源"为中心建模：URL 定位资源，HTTP 方法表达动作，状态码表达结果
    • ⭐ URL 用名词复数、层级表达从属关系；动作用方法不用动词
    • ⭐ 版本控制放 URL 前缀（/api/v1）最直观；幂等性靠方法语义 + 幂等键
    • ⚠️ REST 不是教条：查询条件复杂时 POST /search 这类"RPC 风"接口完全可接受

    3.2 HTTP 方法语义¶

    方法 语义 幂等 安全 请求体 典型响应
    GET 读取资源 ✅ ✅（不改服务端状态） 无 200
    POST 新增 / 触发处理 ❌ ❌ 有 201 + Location
    PUT 全量替换资源 ✅ ❌ 有 200
    PATCH 局部修改 ❌（可实现幂等） ❌ 有 200
    DELETE 删除资源 ✅ ❌ 无 204

    幂等：同一请求执行 1 次与 N 次，服务端状态一致。GET/PUT/DELETE 天然幂等，POST 不幂等（重复提交会重复创建）。

    PUT vs PATCH 的关键区别：PUT 是"整体替换"——没传的字段应被置空/重置；PATCH 只改传了的字段。很多团队用 PATCH 语义实现"全量更新"，面试时说清区别即可。

    // POST 新增：成功返回 201 + Location 头指向新资源（REST 正统做法）
@PostMapping
public ResponseEntity<UserVO> create(@Valid @RequestBody UserCreateDTO dto) {
    UserVO vo = userService.save(dto);
    URI location = URI.create("/api/v1/users/" + vo.getId());
    return ResponseEntity.created(location).body(vo);   // 201 Created
}

// DELETE：成功返回 204 No Content（无响应体）
@DeleteMapping("/{id}")
public ResponseEntity<Void> delete(@PathVariable Long id) {
    userService.delete(id);
    return ResponseEntity.noContent().build();          // 204
}

    💡 国内团队普遍用"200 + Result 包装"代替 201/204，两种风格都合理，团队内保持一致比"正统"更重要。

    3.3 状态码规范¶

    状态码 含义 何时用
    200 OK 成功 查询/修改成功
    201 Created 创建成功 POST 新增，带 Location
    204 No Content 成功但无响应体 DELETE 成功
    400 Bad Request 参数错误 @Valid 校验失败、格式错
    401 Unauthorized 未认证（你是谁？） Token 缺失/过期
    403 Forbidden 未授权（认识你但没权限） 普通用户访问管理员接口
    404 Not Found 资源不存在 ID 查不到
    405 Method Not Allowed 方法不支持 对只读接口发 DELETE
    409 Conflict 状态冲突 重复创建、库存不足、乐观锁冲突
    415 Unsupported Media Type Content-Type 不支持 发 JSON 但没写 Content-Type
    429 Too Many Requests 限流 触发限流
    500 Internal Server Error 服务端异常 未捕获异常兜底

    ⚠️ 401 vs 403 是高频面试题：401 = 没带证件（未认证），403 = 带了证件但没权限（未授权）。

    3.4 版本控制（/api/v1）¶

    三种主流方案：

    方案 示例 优点 缺点
    URL 路径（推荐） /api/v1/users 直观、缓存友好、易路由 URL 变化
    请求头 Accept: application/vnd.api.v1+json URL 稳定 调试不直观
    查询参数 /users?version=1 简单 易被忽略、缓存难

    Spring MVC 实现 URL 版本控制的两种方式：

    3.5 幂等性实战¶

    为什么重要：网络重试、用户连点"提交"、MQ 重复消费都会导致请求重放。非幂等接口（POST 下单/支付）必须防重。

    // ① 乐观锁更新：带版本号，天然幂等（重复提交只有第一次成功）
@PutMapping("/{id}")
public Result<Void> update(@PathVariable Long id, @Valid @RequestBody UserUpdateDTO dto) {
    int rows = userMapper.updateWithVersion(id, dto, dto.getVersion()); // UPDATE ... WHERE id=? AND version=?
    if (rows == 0) throw new BizException(ErrorCode.CONFLICT, "数据已被他人修改，请刷新重试"); // 409
    return Result.ok();
}

// ② 幂等键（Idempotency-Key）：客户端生成唯一键，服务端去重（支付/下单标配）
@PostMapping("/orders")
public Result<OrderVO> createOrder(
        @RequestHeader("Idempotency-Key") String idempotencyKey,   // 客户端传 UUID
        @Valid @RequestBody OrderCreateDTO dto) {
    // setIfAbsent = Redis SETNX：同一个 key 第二次进来返回 false
    boolean firstTime = redisTemplate.opsForValue()
            .setIfAbsent("idem:order:" + idempotencyKey, "1", Duration.ofMinutes(10));
    if (!firstTime) {
        // 重复请求：返回第一次的结果（或 409），绝不重复创建
        OrderVO cached = orderService.findByIdempotencyKey(idempotencyKey);
        return cached != null ? Result.ok(cached) : Result.error(409, "请勿重复提交");
    }
    OrderVO vo = orderService.create(dto, idempotencyKey);
    return Result.ok(vo);
}

    3.6 常见坑¶

    1. ⚠️ URL 里带动词：/api/getUserInfo、/api/deleteOrder——这是 RPC 风格不是 REST，面试会被追问。
    2. ⚠️ GET 带请求体：HTTP 规范不禁止但几乎所有客户端/网关都不支持，查询参数一律走 query string。
    3. ⚠️ 404 与 403 混用：有些团队对"无权限资源"返回 404 防止信息泄露（不暴露资源存在性），这是有意设计；但普通 CRUD 查不到就是 404。
    4. ⚠️ POST 重复提交没防护：按钮连点创建两条订单。前端防抖 + 后端幂等键双保险。
    5. ⚠️ 把 HTTP 状态码当业务码用：业务失败（余额不足）返回 200 + code=40001 是国内主流；若选 4xx 表达业务错误，注意网关/监控会把 4xx 当故障告警。两种风格选一种，别混用。
    6. ⚠️ 版本号放代码里散落各处：用 @ApiV1 + configurePathMatch 或配置类常量统一管理。

    4. 统一异常处理深化¶

    知识点：

    • ⭐ 业务异常码设计：模块 + 类型 + 序号 的枚举（如 USER_40001），业务码与 HTTP 状态码解耦
    • ⭐ 异常链：自定义异常必须支持 cause 传递，throw new BizException(..., e)，否则排查断链
    • ⭐ Spring 6 / Boot 3 原生支持 RFC 7807 ProblemDetail：ResponseEntityExceptionHandler 基类 + spring.mvc.problemdetails.enabled=true
    • ⚠️ 兜底 Exception 处理器必须打日志（带 traceId 更佳），且绝不向前端暴露堆栈

    4.1 业务异常码设计¶

    设计原则：

    • 用枚举集中管理，禁止代码里散落魔法数字
    • 编码规则示例：模块(2位) + 错误类型(1位) + 序号(2位)，或直接分段数字（10001 用户模块、20001 订单模块）
    • 每个错误码配一个面向用户的 message（可直接展示）和可选的面向开发的 detail
    • HTTP 状态码与业务码分离：HTTP 码给基础设施看（网关/监控），业务码给前端展示
    /** 错误码枚举：集中定义，一码一义 */
@Getter
public enum ErrorCode {
    // 通用：1 开头
    SUCCESS(0, "成功"),
    INTERNAL_ERROR(10000, "系统繁忙，请稍后重试"),
    PARAM_INVALID(10001, "参数校验失败"),
    UNAUTHORIZED(10401, "未登录或登录已过期"),
    FORBIDDEN(10403, "无权限访问"),
    NOT_FOUND(10404, "资源不存在"),

    // 用户模块：2 开头
    USER_NOT_FOUND(20404, "用户不存在"),
    USER_PASSWORD_WRONG(20001, "用户名或密码错误"),
    USER_DISABLED(20002, "账号已被禁用"),

    // 订单模块：3 开头
    ORDER_NOT_FOUND(30404, "订单不存在"),
    ORDER_STOCK_NOT_ENOUGH(30001, "库存不足"),
    ORDER_STATUS_CONFLICT(30002, "订单状态不允许该操作");

    private final int code;
    private final String message;

    ErrorCode(int code, String message) {
        this.code = code;
        this.message = message;
    }
}

    4.2 业务异常类与异常链¶

    异常链：底层异常（SQLException、第三方 SDK 异常）包装成业务异常时，必须把原异常作为 cause 传入，日志才能打出完整调用栈；new BizException(msg) 丢掉 cause 是排查事故的第一大源头。

    /** 业务异常：RuntimeException，无需 throws 声明；携带错误码并保留异常链 */
public class BizException extends RuntimeException {
    private final int code;

    public BizException(ErrorCode errorCode) {
        super(errorCode.getMessage());
        this.code = errorCode.getCode();
    }

    /** ⭐ 带 cause：保留底层异常栈，日志可追因 */
    public BizException(ErrorCode errorCode, Throwable cause) {
        super(errorCode.getMessage(), cause);
        this.code = errorCode.getCode();
    }

    /** 需要动态消息时（消息来自枚举模板 + 参数） */
    public BizException(int code, String message) {
        super(message);
        this.code = code;
    }

    public int getCode() { return code; }
}

    4.3 全局异常处理器（Result 风格）¶

    @Slf4j
@RestControllerAdvice   // = @ControllerAdvice + @ResponseBody，可加 basePackages 限定范围
public class GlobalExceptionHandler {

    /** 业务异常：按码返回，WARN 级（预期内，不告警） */
    @ExceptionHandler(BizException.class)
    public ResponseEntity<Result<Void>> handleBiz(BizException ex) {
        log.warn("业务异常: code={}, msg={}", ex.getCode(), ex.getMessage());
        int httpStatus = mapHttpStatus(ex.getCode());
        return ResponseEntity.status(httpStatus).body(Result.error(ex.getCode(), ex.getMessage()));
    }

    /** @Valid 校验 @RequestBody 失败 */
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<Result<Void>> handleValid(MethodArgumentNotValidException ex) {
        String msg = ex.getBindingResult().getFieldErrors().stream()
                .map(e -> e.getField() + ": " + e.getDefaultMessage())
                .collect(Collectors.joining("; "));
        return ResponseEntity.badRequest().body(Result.error(ErrorCode.PARAM_INVALID.getCode(), msg));
    }

    /** @Validated 校验单个方法参数失败（@RequestParam/@PathVariable） */
    @ExceptionHandler(ConstraintViolationException.class)
    public ResponseEntity<Result<Void>> handleConstraint(ConstraintViolationException ex) {
        return ResponseEntity.badRequest()
                .body(Result.error(ErrorCode.PARAM_INVALID.getCode(), ex.getMessage()));
    }

    /** 请求体格式错误（JSON 解析失败） */
    @ExceptionHandler(HttpMessageNotReadableException.class)
    public ResponseEntity<Result<Void>> handleNotReadable(HttpMessageNotReadableException ex) {
        return ResponseEntity.badRequest().body(Result.error(10001, "请求体格式错误"));
    }

    /** 404：@RestController 路径不存在（需配 spring.mvc.throw-exception-if-no-handler-found=true 等，见坑 4） */
    @ExceptionHandler(NoHandlerFoundException.class)
    public ResponseEntity<Result<Void>> handle404(NoHandlerFoundException ex) {
        return ResponseEntity.status(404)
                .body(Result.error(ErrorCode.NOT_FOUND.getCode(), "接口不存在"));
    }

    /** 兜底：ERROR 级 + 完整堆栈，前端只看到通用话术 */
    @ExceptionHandler(Exception.class)
    public ResponseEntity<Result<Void>> handleOther(Exception ex) {
        log.error("未预期异常", ex);                    // ⭐ 必须打，且带堆栈
        return ResponseEntity.status(500)
                .body(Result.error(ErrorCode.INTERNAL_ERROR.getCode(), "系统繁忙，请稍后重试"));
    }

    /** 业务码 → HTTP 状态码映射 */
    private int mapHttpStatus(int code) {
        if (code == 10401) return 401;
        if (code == 10403) return 403;
        if (code == 10404 || code % 10000 == 404) return 404;
        if (code == 10001) return 400;
        return 200;   // 国内风格：业务错误也返回 200，前端看 code 字段
    }
}

    4.4 ProblemDetail 与 RFC 7807（Spring 6 新标准）¶

    RFC 7807 定义了标准化的错误响应格式 application/problem+json：

    {
  "type": "https://example.com/problems/stock-not-enough",
  "title": "库存不足",
  "status": 409,
  "detail": "SKU 1001 库存仅剩 3 件",
  "instance": "/api/v1/orders"
}

    Spring 6 的支持：ProblemDetail 类 + ResponseEntityExceptionHandler 基类（Boot 3 中它已把 Spring 内部异常转成 ProblemDetail）。

    /** 继承 ResponseEntityExceptionHandler，获得对 15+ 种 Spring 内部异常的 ProblemDetail 处理 */
@Slf4j
@RestControllerAdvice
public class ProblemDetailAdvice extends ResponseEntityExceptionHandler {

    /** 业务异常 → ProblemDetail */
    @ExceptionHandler(BizException.class)
    public ProblemDetail handleBiz(BizException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, ex.getMessage());
        pd.setTitle("业务处理失败");
        pd.setType(URI.create("https://example.com/problems/biz-error"));
        pd.setProperty("code", ex.getCode());        // ⭐ 扩展属性：放业务码
        pd.setProperty("timestamp", Instant.now());
        return pd;
    }

    /** 覆盖基类对 @Valid 失败的处理，补充字段级错误明细 */
    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(
            MethodArgumentNotValidException ex, HttpHeaders headers,
            HttpStatusCode status, WebRequest request) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "参数校验失败");
        List<Map<String, String>> errors = ex.getBindingResult().getFieldErrors().stream()
                .map(fe -> Map.of("field", fe.getField(), "message", String.valueOf(fe.getDefaultMessage())))
                .toList();
        pd.setProperty("errors", errors);
        return ResponseEntity.badRequest().body(pd);
    }

    /** 兜底 */
    @ExceptionHandler(Exception.class)
    public ProblemDetail handleOther(Exception ex) {
        log.error("未预期异常", ex);
        return ProblemDetail.forStatusAndDetail(HttpStatus.INTERNAL_SERVER_ERROR, "系统繁忙");
    }
}

    开启 Spring 内部异常自动转 ProblemDetail：

    spring:
  mvc:
    problemdetails:
      enabled: true   # Boot 3：Spring 内部异常（404/405 等）自动返回 problem+json

    Result 风格 vs ProblemDetail 怎么选：

    维度 Result<T> 包装 ProblemDetail (RFC 7807)
    成功响应 统一包一层 只规范错误响应，成功响应自由
    适用 国内前后端分离主流 对外开放 API、遵循国际标准
    迁移成本 — 前端需适配 problem+json

    💡 二者可共存：正常接口返回 Result，@ExceptionHandler 返回 ProblemDetail——但项目里统一选一种。

    4.5 常见坑¶

    1. ⚠️ 异常链丢失：catch (Exception e) { throw new BizException("出错了"); }——底层堆栈没了，线上只能靠猜。永远 throw new BizException(code, msg, e) 或至少先 log.error("...", e)。
    2. ⚠️ 兜底处理器不打日志：@ExceptionHandler(Exception.class) 里只 return 不 log，异常被静默吞掉，监控曲线一片祥和。
    3. ⚠️ 异常处理器里再抛异常：处理器方法内部出错会直接 500 且日志难看，处理器代码要尽量简单、防御式。
    4. ⚠️ 404 不走 @ExceptionHandler：默认 NoHandlerFoundException 不抛出（直接走 /error），要捕获需配 spring.mvc.throw-exception-if-no-handler-found=true 并关闭静态资源默认映射（Boot 3.2+ 行为有变化，实测为准）。
    5. ⚠️ @ControllerAdvice 作用范围：默认管所有 Controller；多模块项目可用 @RestControllerAdvice(basePackages = "com.xxx.module1") 或 @Order 控制优先级——两个 advice 都能处理同一异常时，@Order 小的赢。
    6. ⚠️ 把堆栈/SQL 信息返给前端：ex.getMessage() 直接回显可能泄露表名、SQL。业务异常消息走枚举，兜底用固定话术。
    7. ⚠️ ProblemDetail 与 Result 混用：同一接口有时 {code, data} 有时 problem+json，前端没法统一处理。

    5. 拦截器实战¶

    知识点：

    • ⭐ 三方法执行顺序：preHandle（true 才继续）→ Controller → postHandle → afterCompletion；preHandle=false 时只有更早的拦截器的 afterCompletion 会执行
    • ⭐ 用户态在拦截器存 ThreadLocal，afterCompletion 必须 remove（Tomcat 线程复用导致数据串号/内存泄漏）
    • ⭐ 防重复提交：自定义注解 + 拦截器 + Redis SETNX 是标准实现
    • ⚠️ 耗时统计放 afterCompletion 而不是 postHandle——postHandle 不含视图渲染/异常场景，异常时不会执行

    执行顺序速记（多拦截器时是"栈式"）：

    请求 → A.pre → B.pre → Controller → B.post → A.post → A.after → B.after → 响应
        （false 短路点）                        （异常时 post 跳过，after 仍执行）

    5.1 实战一：登录态拦截器（ThreadLocal 保存当前用户）¶

    /** 当前登录用户（简化版，实际项目含 userId/username/角色等） */
public record LoginUserVO(Long userId, String username) {}

    /** 用户上下文：ThreadLocal 存取 + 强制清理 */
public final class UserContext {
    private static final ThreadLocal<LoginUserVO> HOLDER = new ThreadLocal<>();

    public static void set(LoginUserVO user) { HOLDER.set(user); }

    /** ⭐ 需要登录态时调用，未登录直接抛 401 业务异常 */
    public static LoginUserVO require() {
        LoginUserVO user = HOLDER.get();
        if (user == null) throw new BizException(ErrorCode.UNAUTHORIZED);
        return user;
    }

    /** 可选场景：允许未登录（如游客浏览） */
    public static LoginUserVO get() { return HOLDER.get(); }

    public static void clear() { HOLDER.remove(); }   // ⭐ 必须调用
}

    /** 登录态拦截器：校验 Token → 查用户 → 放入 ThreadLocal */
@Slf4j
@Component
public class LoginInterceptor implements HandlerInterceptor {

    private final UserService userService;

    public LoginInterceptor(UserService userService) {
        this.userService = userService;
    }

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response,
                             Object handler) {
        String token = request.getHeader("Authorization");
        if (token == null || !token.startsWith("Bearer ")) {
            writeUnauthorized(response);
            return false;                                  // 短路，不再往后走
        }
        try {
            // 实际项目：JWT 解析 / 查 Redis 会话，这里简化为查库
            LoginUserVO user = userService.resolveByToken(token.substring(7));
            if (user == null) {
                writeUnauthorized(response);
                return false;
            }
            UserContext.set(user);                         // ⭐ 存入 ThreadLocal
            return true;
        } catch (Exception e) {
            log.error("登录态校验异常", e);
            writeUnauthorized(response);
            return false;
        }
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response,
                                Object handler, Exception ex) {
        UserContext.clear();                               // ⭐⭐⭐ 无论如何都要清理
    }

    private void writeUnauthorized(HttpServletResponse response) {
        response.setStatus(401);
        response.setContentType("application/json;charset=UTF-8");
        try {
            response.getWriter().write(
                    "{\"code\":10401,\"message\":\"未登录或登录已过期\"}");
        } catch (IOException e) {
            log.error("写 401 响应失败", e);
        }
    }
}

    💡 拦截器里 return false 时不走 @ExceptionHandler（Controller 还没执行），所以这里手动写响应体；或者抛异常配合 HandlerExceptionResolver 转发。

    5.2 实战二：接口耗时统计拦截器¶

    /** 耗时统计：preHandle 记开始时间，afterCompletion 输出（覆盖异常场景） */
@Slf4j
@Component
public class ApiTimingInterceptor implements HandlerInterceptor {

    private static final String ATTR_START = "api_start_time";
    private static final long SLOW_THRESHOLD_MS = 1000;   // 慢接口阈值

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response,
                             Object handler) {
        request.setAttribute(ATTR_START, System.currentTimeMillis());
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response,
                                Object handler, Exception ex) {
        Object start = request.getAttribute(ATTR_START);
        if (!(start instanceof Long startMs)) return;
        long cost = System.currentTimeMillis() - startMs;

        String handlerName = (handler instanceof HandlerMethod hm)
                ? hm.getBeanType().getSimpleName() + "#" + hm.getMethod().getName()
                : handler.toString();

        // ⭐ 慢接口用 WARN 级别，方便日志系统配告警
        if (cost > SLOW_THRESHOLD_MS) {
            log.warn("慢接口 {} {} -> {} 耗时 {}ms", request.getMethod(),
                    request.getRequestURI(), handlerName, cost);
        } else if (log.isDebugEnabled()) {
            log.debug("{} {} -> {} 耗时 {}ms", request.getMethod(),
                    request.getRequestURI(), handlerName, cost);
        }
    }
}

    ⚠️ 为什么不用 postHandle？① Controller 抛异常时 postHandle 不执行，耗时日志就丢了；② 返回视图时 postHandle 在渲染前执行，统计不全。afterCompletion 一定执行（只要对应 preHandle 返回了 true），是唯一正确位置。

    💡 开始时间用 request.setAttribute 而非 ThreadLocal：请求属性随请求生灭，无泄漏风险；此处也不需要跨方法传递。

    5.3 实战三：防重复提交（注解 + 拦截器 + Redis）¶

    第一步：定义注解

    /** 标注在 Controller 方法上即开启防重 */
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface NoRepeatSubmit {
    /** 锁定时长（秒），默认 3 秒内不能重复提交 */
    int interval() default 3;
}

    第二步：拦截器实现（Redis SETNX）

    @Component
public class NoRepeatSubmitInterceptor implements HandlerInterceptor {

    // import org.springframework.util.DigestUtils;
    // import java.nio.charset.StandardCharsets;
    private final StringRedisTemplate redisTemplate;

    public NoRepeatSubmitInterceptor(StringRedisTemplate redisTemplate) {
        this.redisTemplate = redisTemplate;
    }

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response,
                             Object handler) throws Exception {
        // ① 不是 HandlerMethod（静态资源等）直接放行
        if (!(handler instanceof HandlerMethod hm)) return true;

        // ② 方法上没注解直接放行
        NoRepeatSubmit annotation = hm.getMethodAnnotation(NoRepeatSubmit.class);
        if (annotation == null) return true;

        // ③ 构造防重 key：用户 + 接口 + 参数指纹
        String key = buildKey(request, hm);

        // ④ SETNX：第一次设置成功才放行；已存在说明重复提交
        Boolean firstTime = redisTemplate.opsForValue()
                .setIfAbsent(key, "1", Duration.ofSeconds(annotation.interval()));
        if (Boolean.TRUE.equals(firstTime)) return true;

        // ⑤ 重复提交：直接返回业务错误（也可抛 BizException 交异常处理器）
        response.setStatus(429);
        response.setContentType("application/json;charset=UTF-8");
        response.getWriter().write("{\"code\":42901,\"message\":\"操作过于频繁，请稍后再试\"}");
        return false;
    }

    private String buildKey(HttpServletRequest request, HandlerMethod hm) {
        String userPart = UserContext.get() != null
                ? String.valueOf(UserContext.get().userId())
                : request.getRemoteAddr();                    // 未登录用 IP
        String methodPart = hm.getBeanType().getSimpleName() + "#" + hm.getMethod().getName();
        // 参数指纹：防止"同一接口不同参数"误伤（如不同商品下单）
        // 用 Spring 自带的 DigestUtils，避免额外引 commons-codec
        String raw = request.getQueryString() == null ? "" : request.getQueryString();
        String paramFingerprint = DigestUtils.md5DigestAsHex(raw.getBytes(StandardCharsets.UTF_8));
        return "no-repeat:" + userPart + ":" + methodPart + ":" + paramFingerprint;
    }
}

    第三步：注册 + 使用

public class WebMvcConfig implements WebMvcConfigurer {
    private final LoginInterceptor loginInterceptor;
    private final ApiTimingInterceptor apiTimingInterceptor;

                        ApiTimingInterceptor apiTimingInterceptor,

    5.4 常见坑¶

    1. ⚠️ ThreadLocal 不清理：Tomcat 线程池复用线程，上一个请求的用户残留给下一个请求——数据串号是最严重的生产事故。afterCompletion 里必须 UserContext.clear()，且 preHandle 里 set 之前所有 return false 路径都要确认没有 set。
    2. ⚠️ preHandle 返回 false 后写了重定向又返回 true 等混乱逻辑：短路就短路，响应已写出时不要再 return true。
    3. ⚠️ 拦截器里抛异常期望 @ExceptionHandler 处理：preHandle 抛异常会走异常处理链，但 return false 不会——两种短路方式选一种，行为不同。
    4. ⚠️ 耗时统计用 postHandle：异常场景丢日志（见 5.2 说明）。
    5. ⚠️ 防重 key 只按"用户+接口"：用户 3 秒内给两个不同商品下单被误拦。key 里要带参数指纹；反之，幂等场景（同一笔订单重试）又希望命中同一个 key——两者设计目标相反，别混用。
    6. ⚠️ 拦截器顺序：防重依赖登录态（需要 userId）就必须排在登录拦截器之后（order 更大）。
    7. ⚠️ 拦截器不是 Filter：它拦不到 /error 转发、静态资源（除非匹配路径）；请求体（RequestBody）在拦截器里读了就没了（流只能读一次），需要读请求体做签名校验时要用 Filter + 包装 request 缓存流。

    6. 参数解析器扩展（HandlerMethodArgumentResolver）¶

    知识点：

    • ⭐ HandlerMethodArgumentResolver 决定"某个 Controller 参数怎么被赋值"；内置解析器处理 @PathVariable、@RequestBody 等，自定义解析器处理你自己的约定
    • ⭐ 两方法契约：supportsParameter（认不认这个参数）+ resolveArgument（怎么取值）
    • ⭐ 经典案例：@LoginUser LoginUserVO user 直接注入当前登录用户，Controller 不再碰 ThreadLocal/HttpServletRequest
    • ⚠️ 自定义解析器优先级低于内置解析器；参数类型/注解必须足够独特，避免与内置规则冲突

    6.1 解析器接口与执行时机¶

    public interface HandlerMethodArgumentResolver {
    /** 是否支持该参数（按注解/类型判断），返回 true 则用本解析器 */
    boolean supportsParameter(MethodParameter parameter);

    /** 真正解析出参数值 */
    Object resolveArgument(MethodParameter parameter, ModelAndViewContainer mavContainer,
                           NativeWebRequest webRequest, WebDataBinderFactory binderFactory)
            throws Exception;
}

    执行时机：HandlerAdapter 调用 Controller 方法前，对每个参数依次问已注册的解析器"你支持吗"，第一个说支持的负责赋值。

    6.2 完整实现：@LoginUser 注入当前用户¶

    第一步：定义注解

    /** 标注在 Controller 参数上，自动注入当前登录用户 */
@Target(ElementType.PARAMETER)
@Retention(RetentionPolicy.RUNTIME)
public @interface LoginUser {
    /** 是否必须登录；false 时游客访问该参数为 null */
    boolean required() default true;
}

    第二步：实现解析器

    /** 从 ThreadLocal（登录拦截器已放入）取当前用户注入参数 */
@Component
public class LoginUserArgumentResolver implements HandlerMethodArgumentResolver {

    @Override
    public boolean supportsParameter(MethodParameter parameter) {
        // 认：带 @LoginUser 注解、且类型是 LoginUserVO 的参数
        return parameter.hasParameterAnnotation(LoginUser.class)
                && LoginUserVO.class.isAssignableFrom(parameter.getParameterType());
    }

    @Override
    public Object resolveArgument(MethodParameter parameter, ModelAndViewContainer mavContainer,
                                  NativeWebRequest webRequest, WebDataBinderFactory binderFactory) {
        LoginUser annotation = parameter.getParameterAnnotation(LoginUser.class);
        LoginUserVO user = UserContext.get();               // 拦截器已写入
        if (user == null && annotation != null && annotation.required()) {
            // 走到这说明登录拦截器没拦住（接口没在拦截范围内）——兜底抛 401
            throw new BizException(ErrorCode.UNAUTHORIZED);
        }
        return user;   // required=false 且未登录时返回 null
    }
}

    第三步：注册（回到第 1 节的 WebMvcConfigurer）

    public WebMvcConfig(LoginUserArgumentResolver loginUserArgumentResolver) {
        this.loginUserArgumentResolver = loginUserArgumentResolver;

    @Override

    6.3 进阶：解析器里做更多事¶

    解析器不只是取 ThreadLocal，任何"从请求中提取并转换"的逻辑都可以放这里。示例：从 Header 解析分页对象：

    @Target(ElementType.PARAMETER)
@Retention(RetentionPolicy.RUNTIME)
public @interface PageParam {}

@Component
public class PageParamResolver implements HandlerMethodArgumentResolver {

    @Override
    public boolean supportsParameter(MethodParameter parameter) {
        return parameter.hasParameterAnnotation(PageParam.class)
                && PageRequest.class == parameter.getParameterType();
    }

    @Override
    public Object resolveArgument(MethodParameter parameter, ModelAndViewContainer mavContainer,
                                  NativeWebRequest webRequest, WebDataBinderFactory binderFactory) {
        HttpServletRequest request = webRequest.getNativeRequest(HttpServletRequest.class);
        int page = Integer.parseInt(Optional.ofNullable(request.getParameter("page")).orElse("1"));
        int size = Integer.parseInt(Optional.ofNullable(request.getParameter("size")).orElse("10"));
        if (size > 100) size = 100;          // 防止恶意大分页拖垮数据库
        if (page < 1) page = 1;
        return new PageRequest(page, size);
    }
}

// 用法：public Result<Page<UserVO>> list(@PageParam PageRequest page) { ... }

    6.4 常见坑¶

    1. ⚠️ 忘了注册：解析器写了但不加进 addArgumentResolvers，参数永远是 null（对象类型参数不报错，只是 null）——比 404 更隐蔽。
    2. ⚠️ 类型与注解不匹配：supportsParameter 里同时校验注解和类型，只校验注解时别人用了同名注解就撞车。
    3. ⚠️ 自定义解析器与内置冲突：自定义的排在内置之后，若你的参数类型恰好被内置解析器认领（比如 HttpServletRequest），自定义的根本没机会执行。
    4. ⚠️ 解析器里查库不缓存：每个请求每个 @LoginUser 参数都查一次数据库；登录拦截器里查一次放 ThreadLocal，解析器只取，是标准分工。
    5. ⚠️ 单元测试：Controller 依赖 @LoginUser 注入，用 MockMvc 测试时需注册解析器并预置 UserContext，或用 @WebMvcTest + mock UserContext。
    6. ⚠️ 与 @Valid 配合：解析器返回的对象若要触发校验，需配合 @Valid 且解析器内部要调用 binderFactory 创建 binder 并 validate——简单场景直接在解析器里手动校验更省事。

    7. 高频面试题¶

    Q1：WebMvcConfigurer 和 @EnableWebMvc 的区别？为什么 Boot 下不能加 @EnableWebMvc？

    WebMvcConfigurer 是回调接口，在保留 Boot 自动配置的前提下做增量定制；@EnableWebMvc 导入 DelegatingWebMvcConfiguration（继承 WebMvcConfigurationSupport），会触发 @ConditionalOnMissingBean(WebMvcConfigurationSupport) 条件，使 WebMvcAutoConfiguration 整体失效，spring.mvc./spring.jackson. 属性全部失灵。

    Q2：configureMessageConverters 和 extendMessageConverters 的区别？

    前者一旦添加了元素，Spring 就不再注册默认转换器（替换模式）；后者在默认转换器全部注册后才回调，只做增删调整（微调模式）。生产一律用 extend。

    Q3：Long 类型 ID 传给前端精度丢失怎么解决？

    JS Number 安全上限 2^53-1，雪花 ID 18~19 位超限。用 @JsonSerialize(using = ToStringSerializer.class) 字段级转字符串，或全局注册 ToStringSerializer；反方向不受影响。

    Q4：自定义 @LoginUser 参数注入的原理？

    登录拦截器在 preHandle 校验 Token 并把用户存入 ThreadLocal；自定义 HandlerMethodArgumentResolver 在 supportsParameter 中匹配 @LoginUser 注解，在 resolveArgument 中从 ThreadLocal 取值返回；afterCompletion 中清理 ThreadLocal 防止线程复用串数据。本质：拦截器负责"认证 + 存"，解析器负责"取 + 注入"。

    Q5：防重复提交怎么实现？

    自定义注解 @NoRepeatSubmit + HandlerInterceptor：以"用户 + 接口 + 参数指纹"为 key，用 Redis SETNX 设置短过期锁，设置成功放行，失败说明重复提交直接拒绝。它和幂等键的区别：防重是拒绝重复请求，幂等是重复请求返回同一结果。

    Q6：拦截器和过滤器的区别？（进阶版）

    层级：Filter（Servlet 规范）在 DispatcherServlet 之前，拦截所有请求；Interceptor 只能拦到 Controller 的请求。能力：拦截器是 Spring Bean 可注入、能拿到 HandlerMethod 知道目标方法、有 afterCompletion 做清理。读请求体：拦截器里读 body 会消耗流，需要读体做校验时用 Filter + ContentCachingRequestWrapper。

    8. 本章小结¶

    核心知识点¶

    ✅ WebMvcConfigurer：增量定制入口，禁 @EnableWebMvc；configure 替换 / extend 微调 ✅ Jackson：三档定制（属性 < Customizer < ObjectMapper Bean）；LocalDateTime 格式化、Long→String、null 忽略、@JsonProperty/@JsonIgnore ✅ RESTful：名词复数 + 方法语义 + 状态码 + /api/v1 版本 + 幂等键 ✅ 异常处理：ErrorCode 枚举 + 异常链（带 cause）+ @RestControllerAdvice + ProblemDetail(RFC 7807) ✅ 拦截器实战：登录态（ThreadLocal 必清理）、耗时统计（afterCompletion）、防重复提交（注解 + Redis SETNX） ✅ 参数解析器：@LoginUser 注入 = supportsParameter 认参数 + resolveArgument 取 ThreadLocal

    最佳实践¶

    1. 全项目只有一个 WebMvcConfig 总配置类，拦截器按 order 排序
    2. Jackson 定制优先 Jackson2ObjectMapperBuilderCustomizer，不要随手 new ObjectMapper
    3. 业务异常必须带异常链，兜底处理器必须打日志
    4. 登录态 = 拦截器认证存 ThreadLocal + 解析器注入 + afterCompletion 清理，三件套缺一不可
    5. 写操作接口默认考虑幂等：乐观锁（更新）或幂等键（创建）
