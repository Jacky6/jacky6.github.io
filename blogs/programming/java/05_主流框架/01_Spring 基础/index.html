    01_Spring 基础¶

    1. Spring 概述¶

    知识点：

    • ⭐ Spring = IOC 容器 + AOP 框架，Java 企业开发事实标准
    • 核心价值：解耦（对象创建交给容器）、横切逻辑复用（AOP）
    • Spring 5 模块化：Core（IOC/AOP）、Data Access、Web MVC、Test 等

    1.1 什么是 Spring¶

    Spring 是 Java 企业级开发的事实标准框架，由 Rod Johnson 于 2004 年正式发布（其思想源自他 2002 年的著作《Expert One-on-One J2EE Design and Development》）。

    解决的核心痛点：EJB 时代企业开发代码臃肿、组件耦合严重、测试困难。Spring 用 IOC + AOP 两板斧简化了这一切。

    核心特性：

    • ✅ IOC（控制反转）：对象创建和依赖关系交给容器管理
    • ✅ AOP（面向切面编程）：日志、事务、权限等横切逻辑与业务解耦
    • ✅ 声明式事务：一个注解管理事务
    • ✅ 生态整合：Spring MVC、Spring Data、Spring Security、SpringBoot……

    1.2 版本演进¶

    版本 发布 关键变化
    Spring 1.0 2004 IOC + AOP 奠基
    Spring 2.5 2007 注解驱动（@Component、@Autowired）
    Spring 3.0 2009 Java 配置类（@Configuration）、SpEL
    Spring 4.0 2013 Java 8 支持、SpringBoot 诞生（1.0）
    Spring 5.0 2017 响应式编程 WebFlux，最低 JDK 8
    Spring 6.0 2022 最低 JDK 17，Jakarta EE 9+（包名 javax. → jakarta.）

    ⚠️ 面试常问：Spring 5 → 6 的最大变化是 Jakarta EE 迁移（javax.servlet → jakarta.servlet），SpringBoot 3 同步切换，老项目升级时这是最大的坑。

    2. IOC 控制反转¶

    知识点：

    • ⭐ IOC（控制反转）：对象的创建/组装权从代码 new 反转到容器
    • DI（依赖注入）是 IOC 的实现手段：构造器注入（推荐）、setter 注入、字段注入
    • 容器：BeanFactory（懒加载基础容器）、ApplicationContext（企业级，预加载+事件+国际化）

    2.1 什么是 IOC¶

    IOC（Inversion of Control）控制反转：对象的创建权和依赖关系的组装权，从代码里反转给容器。

    DI（Dependency Injection）依赖注入：IOC 的具体实现手段。

    传统方式：我需要什么，我自己 new
  UserService → new UserDaoImpl()        ← 强耦合，换实现要改代码

IOC 方式：我需要什么，容器给我
  UserService ← 容器注入 UserDao 实现    ← 面向接口，实现可替换

    // ❌ 传统方式：自己创建依赖
public class UserService {
    private UserDao userDao = new UserDaoImpl();  // 写死了实现
}

// ✅ IOC 方式：依赖由外部注入
public class UserService {
    private final UserDao userDao;

    public UserService(UserDao userDao) {   // 构造方法注入（推荐）
        this.userDao = userDao;
    }
}

    IOC 的好处：

    • ✅ 解耦：面向接口编程，替换实现不改业务代码
    • ✅ 可测试：单元测试可以注入 Mock 对象
    • ✅ 统一生命周期：单例、初始化、销毁都由容器管理

    2.2 两种容器¶

    容器 说明
    BeanFactory 最基础的容器，懒加载（getBean 时才创建）
    ApplicationContext BeanFactory 的超集，启动即创建单例，支持事件、国际化、资源访问 ⭐ 推荐 
    // Java 配置类方式创建容器（现代写法）
ApplicationContext context =
    new AnnotationConfigApplicationContext(AppConfig.class);

// XML 方式（老项目常见）
ApplicationContext context =
    new ClassPathXmlApplicationContext("applicationContext.xml");

// 获取 Bean
UserService userService = context.getBean(UserService.class);

    3. Bean 管理¶

    知识点：

    • ⭐ Bean = 由 Spring 容器创建、装配依赖、管理生命周期的对象（容器里的"公民"）
    • ⭐ 声明 Bean 三方式：组件扫描注解（@Component 家族）、@Bean 方法、XML（老项目）
    • ⭐ 注入三方式对比：构造器注入（不可变、必填依赖）> setter > 字段注入
    • 作用域：singleton（默认单例）、prototype（每次新建）、request/session（Web）

    3.1 什么是 Bean ⭐¶

    一句话定义：

    Bean 是由 Spring 容器创建、装配依赖、管理生命周期的 Java 对象。

    和你自己 new 的对象对比：

    普通对象：
    UserService us = new UserService(new UserDaoImpl());
    // 你自己 new、自己装依赖、自己管销毁

Spring Bean：
    @Service
    public class UserServiceImpl { ... }
    // 容器负责：实例化 → 注入依赖 → 初始化 → 提供使用 → 销毁
    // 你只需要 @Autowired 拿来用

    容器管三件事：

    职责 说明
    创建 按你的声明（注解/@Bean 方法）实例化对象
    装配 把它依赖的其他 Bean（如 UserDao）注入进来（DI）
    生命周期 默认全局单例、初始化回调（@PostConstruct）、销毁回调（@PreDestroy）

    两个容易混淆的概念：

    概念 含义 语境
    JavaBean 编码规范：无参构造 + 私有属性 + getter/setter 纯 Java 编码约定，和技术无关
    Spring Bean 容器管理的对象实例 面试说"Bean"默认指这个

    ⚠️ 面试别说混：JavaBean 只是写代码的规范（像 POJO 风格），Spring Bean 是运行在容器里的对象—— 一个 Spring Bean 不必符合 JavaBean 规范（构造器注入的类可以没有 setter）。

    Bean 在容器里的"蓝图"——BeanDefinition：

    你写的声明（@Service / @Bean 方法）
        ↓ 容器启动时扫描解析
BeanDefinition（元数据：类名、作用域、依赖关系、初始化方法...）
        ↓ 容器按蓝图创建
Bean 实例（放入单例缓存 / 按需新建）

    容器内部维护 beanName → BeanDefinition 和 beanName → Bean 实例 两张表， context.getBean("userService") 本质就是查表。

    3.2 声明 Bean 的三种方式¶

    方式一：XML 配置（老项目）

    <beans>
    <bean id="userDao" class="com.example.UserDaoImpl"/>

    <bean id="userService" class="com.example.UserServiceImpl">
        <constructor-arg ref="userDao"/>        <!-- 构造注入 -->
        <property name="timeout" value="3000"/> <!-- setter 注入基本值 -->
    </bean>
</beans>

    方式二：注解 + 组件扫描（最常用）

    @Component   // 通用组件
public class UserDaoImpl implements UserDao { }

@Service     // 业务层（语义化的 @Component）
public class UserServiceImpl implements UserService {
    @Autowired
    private UserDao userDao;
}

@Controller  // Web 层     @Repository  // 数据访问层

    四个注解功能完全相同，只是语义分层不同。

    方式三：Java 配置类（推荐，SpringBoot 默认）

    @Configuration                 // 标记为配置类（本身也是 Bean）
@ComponentScan("com.example")  // 组件扫描
public class AppConfig {

    @Bean                      // 方法返回值注册为 Bean
    public DataSource dataSource() {
        HikariDataSource ds = new HikariDataSource();
        ds.setJdbcUrl("jdbc:mysql://localhost:3306/test");
        return ds;
    }
}

    @Bean 适合注册第三方库的类（你无法在源码上加 @Component），@Component 适合注册自己写的类。

    3.3 依赖注入详解 ⭐⭐⭐¶

    @Autowired vs @Resource vs @Qualifier：

    注解 来源 注入规则
    @Autowired Spring 先按类型；找到多个再按名称
    @Resource JSR-250（jakarta.annotation） 先按名称；找不到再按类型
    @Qualifier Spring 配合 @Autowired 指定 Bean 名称

    @Autowired 完整匹配流程（面试追问"怎么找到该注入哪个"就答这个）：

    @Autowired 字段/参数，目标类型 T
        ↓
① 按类型查找：容器里所有 T 类型（含子类/实现类）的 Bean
        ↓
   找到 0 个 ──→ ❌ NoSuchBeanDefinitionException（除非 required=false）
   找到 1 个 ──→ ✅ 直接注入
   找到多个 ──→ 进入消歧流程 ↓
② 有 @Primary 标记的？──→ ✅ 注入它
        ↓ 没有
③ 有 @Qualifier("名字")？──→ ✅ 按名字注入
        ↓ 没有
④ 字段名/参数名 == 某个 beanName？──→ ✅ 按名字注入
        ↓ 还不匹配
   ❌ NoUniqueBeanDefinitionException

    四种使用位置：

    @Service
public class DemoService {

    // ① 字段注入（不推荐：无法 final、难单测）
    @Autowired
    private UserDao userDao;

    // ② setter 注入（可选依赖可用）
    @Autowired(required = false)
    public void setCache(CacheService cache) { this.cache = cache; }

    // ③ 构造器注入（推荐：可 final、保证非空）
    // Spring 4.3+ 单构造器可省略 @Autowired
    @Autowired
    public DemoService(UserDao userDao) { ... }

    // ④ 任意方法参数注入（少用，配置类 @Bean 方法常见）
    public void refresh(@Autowired DataSource ds) { ... }
}

    多实现冲突的三种解法：

    // 接口有两个实现
@Component
public class SmsMessageService implements MessageService { }

@Component
public class EmailMessageService implements MessageService { }

// ❌ 直接注入：两个候选，抛 NoUniqueBeanDefinitionException
@Autowired
private MessageService messageService;

// ✅ 方案 1：@Qualifier 指定名称
@Autowired
@Qualifier("emailMessageService")
private MessageService messageService;

// ✅ 方案 2：@Primary 标记首选实现
@Component
@Primary
public class SmsMessageService implements MessageService { }

// ✅ 方案 3：变量名与 Bean 名一致（按名称回退匹配）
@Autowired
private MessageService smsMessageService;

    可选依赖：依赖不存在也不报错：

    // 方式 1：required = false
@Autowired(required = false)
private SmsService smsService;   // 容器没有 SmsService 时为 null，不报错

// 方式 2：Optional（Java 8+，语义更明确，推荐）
@Autowired
private Optional<SmsService> smsService;
smsService.ifPresent(sms -> sms.send(...));

    集合注入：一次收下所有实现 ⭐⭐⭐⭐：

    // 场景：多种支付策略，想全部拿到按类型分发
@Component public class AlipayStrategy implements PayStrategy { }
@Component public class WechatStrategy implements PayStrategy { }
@Component public class UnionPayStrategy implements PayStrategy { }

@Service
public class PayService {

    // 注入 List：收下所有 PayStrategy 实现
    @Autowired
    private List<PayStrategy> strategies;

    // 注入 Map：key 是 beanName，value 是实例（策略模式标准玩法）
    @Autowired
    private Map<String, PayStrategy> strategyMap;

    public void pay(String type, BigDecimal amount) {
        PayStrategy strategy = strategyMap.get(type);   // 查表分发，零 if-else
        if (strategy == null) throw new IllegalArgumentException("不支持：" + type);
        strategy.pay(amount);
    }
}

    💡 这是"策略模式 + Spring"的标准组合：新增支付方式只需加一个 @Component 实现类， 分发代码一行不改。完整实战见 04_策略模式。 注意：集合里的顺序可以用 @Order / Ordered 接口控制。

    3.4 三种注入方式对比 ⭐¶

    "三种注入方式"指把依赖对象塞进 Bean 的三种途径：

    // ① 字段注入：直接标在字段上（最常见，但不推荐 ❌）
@Service
public class FieldInjectService {
    @Autowired
    private UserService userService;
}

// ② Setter 注入：通过 setter 方法（适合可选依赖）
@Service
public class SetterInjectService {
    private UserService userService;

    @Autowired
    public void setUserService(UserService userService) {
        this.userService = userService;
    }
}

// ③ 构造器注入：通过构造器传入（推荐 ⭐）
@Service
public class ConstructorInjectService {
    private final UserService userService;   // 可声明 final

    public ConstructorInjectService(UserService userService) {
        this.userService = userService;
    }
}

    对比：

    注入方式 优点 缺点 推荐度
    构造器注入 依赖可 final（不可变）、保证非空、便于单测 参数多时冗长 ⭐⭐⭐⭐
    Setter 注入 适合可选依赖、可重新注入 依赖可能未初始化就被使用 ⭐⭐⭐
    字段注入 最简洁，一行搞定 无法 final、难以单测、隐藏依赖 ❌ 不推荐

    为什么推荐构造器注入：

    1. final 不可变——依赖创建后不会变，天然线程安全
    2. 保证非空——构造完成依赖必就绪，不会"用着用着 NPE"
    3. 好单测——new OrderService(mockUserService) 直接用，不需要容器
    4. 暴露依赖膨胀——构造器参数超过 5 个，说明类职责太重该重构；字段注入加一行毫无痛感，依赖越积越多
    // 推荐写法：构造器注入（Spring 4.3+ 单构造器可省略 @Autowired）
@Service
public class OrderService {
    private final UserService userService;       // final 保证不可变
    private final ProductService productService;

    public OrderService(UserService userService, ProductService productService) {
        this.userService = userService;
        this.productService = productService;
    }
}

    💡 Spring 4.3+ 类只有一个构造器时可省略 @Autowired，容器自动用它注入—— 这就是为什么现在很多代码看不到 @Autowired 但依赖照样注入了。

    面试一句话：

    "构造器注入必填依赖，可 final 且保证非空；setter 注入可选依赖；字段注入简洁但隐藏依赖、难测试，Spring 官方和 SonarLint 都不推荐。"

    字段注入一时爽，重构火葬场。

    3.5 其他常用注解¶

    @Scope("prototype")  // 作用域（见第 5 节）
@Lazy                // 懒加载：首次 getBean/注入时才创建
public class HeavyBean { }

// 生命周期回调
@Component
public class CacheBean {
    @PostConstruct      // 初始化后执行（依赖注入完成后）
    public void init() { /* 加载缓存 */ }

    @PreDestroy         // 容器关闭前执行
    public void cleanup() { /* 释放资源 */ }
}

    4. Bean 生命周期 ⭐⭐⭐⭐¶

    知识点：

    • ⭐ 四阶段：实例化 → 属性填充 → 初始化（各种 Aware/BeanPostProcessor/InitializingBean/init-method）→ 使用 → 销毁
    • ⭐ BeanPostProcessor 是扩展点：AOP 代理就是在初始化后置处理器里生成的
    • 面试答题骨架：实例化→注入→Aware 回调→前置处理→初始化→后置处理→使用→销毁

    面试必问。一个 Bean 从创建到销毁的完整过程：

    ① 实例化（反射调用构造器，得到"空壳"对象）
        ↓
② 属性填充（依赖注入：@Autowired 等）
        ↓
③ Aware 回调（注入容器基础设施）
   BeanNameAware → BeanFactoryAware → ApplicationContextAware
        ↓
④ BeanPostProcessor.postProcessBeforeInitialization（初始化前增强）
   （@PostConstruct 就在此阶段执行）
        ↓
⑤ 初始化：InitializingBean.afterPropertiesSet() → 自定义 init-method
        ↓
⑥ BeanPostProcessor.postProcessAfterInitialization（初始化后增强）
   ⭐ AOP 代理对象就是在这里生成的！
        ↓
⑦ Bean 就绪，投入使用
        ↓
⑧ 容器关闭：@PreDestroy → DisposableBean.destroy() → destroy-method

    代码验证：

    @Component
public class LifecycleBean implements BeanNameAware, InitializingBean, DisposableBean {

    public LifecycleBean() {
        System.out.println("1. 构造器：实例化");
    }

    @Autowired
    public void setOtherBean(OtherBean other) {
        System.out.println("2. 属性填充：依赖注入");
    }

    @Override
    public void setBeanName(String name) {
        System.out.println("3. Aware 回调：" + name);
    }

    @PostConstruct
    public void postConstruct() {
        System.out.println("4. @PostConstruct（初始化前增强阶段）");
    }

    @Override
    public void afterPropertiesSet() {
        System.out.println("5. InitializingBean.afterPropertiesSet");
    }

    public void customInit() {
        System.out.println("5b. 自定义 init-method");
    }

    @PreDestroy
    public void preDestroy() {
        System.out.println("8a. @PreDestroy");
    }

    @Override
    public void destroy() {
        System.out.println("8b. DisposableBean.destroy");
    }
}

    为什么要理解生命周期：

    • AOP 代理在⑥生成 → 解释为什么注入的是代理对象而不是原始对象
    • @PostConstruct 在依赖注入之后 → 可以安全使用注入的依赖做初始化
    • 三级缓存解决循环依赖（下一节）依赖①②之间的间隙

    5. Bean 作用域¶

    作用域 说明 场景
    singleton（默认） 容器中唯一实例 无状态 Bean（Service/Dao）
    prototype 每次获取创建新实例 有状态 Bean
    request 每个 HTTP 请求一个 Web 环境
    session 每个会话一个 Web 环境 
    @Component
@Scope("prototype")
public class ShoppingCart { }

    ⚠️ 经典陷阱：singleton 注入 prototype

    @Service   // 单例，只创建一次
public class OrderService {
    @Autowired
    private ShoppingCart cart;   // ❌ cart 也只会被注入一次！
    // 之后每次调用拿到的都是同一个 cart，prototype 失效
}

    解决方案：

    // 方案 1：@Lookup 每次调用方法获取新实例
@Service
public abstract class OrderService {
    @Lookup
    protected abstract ShoppingCart createCart();
}

// 方案 2：注入 ObjectFactory / Provider
@Autowired
private ObjectProvider<ShoppingCart> cartProvider;

public void checkout() {
    ShoppingCart cart = cartProvider.getObject();  // 每次都是新实例
}

    6. 循环依赖与三级缓存 ⭐⭐⭐⭐¶

    知识点：

    • ⭐ 循环依赖：A 依赖 B，B 又依赖 A；Spring 用三级缓存解决单例 setter/字段注入的循环
    • ⭐ 三级缓存分工：singletonObjects（成品）→ earlySingletonObjects（早期半成品）→ singletonFactories（ObjectFactory，生成代理）
    • ⚠️ 构造器注入的循环依赖无法解决（实例化就需要对方）；prototype 也不解决

    Spring 面试最高频问题之一。

    6.1 什么是循环依赖¶

    @Service
public class A {
    @Autowired private B b;   // A 依赖 B
}

@Service
public class B {
    @Autowired private A a;   // B 依赖 A
}

    创建 A 需要先有 B，创建 B 又需要先有 A——死锁了？Spring 用三级缓存解决它。

    6.2 三级缓存¶

    DefaultSingletonBeanRegistry 中的三个 Map：

一级缓存 singletonObjects        ← 成品 Bean（完全初始化）
二级缓存 earlySingletonObjects   ← 早期 Bean（已实例化，未完成属性填充，可能是代理）
三级缓存 singletonFactories      ← ObjectFactory（能生产早期引用的工厂）

    解决过程（A、B 互相字段注入）：

    ① 创建 A：实例化 A（空壳）→ 把 A 的 ObjectFactory 放入三级缓存
② A 填充属性，发现依赖 B → 去创建 B
③ 创建 B：实例化 B → B 填充属性，发现依赖 A
④ B 从三级缓存拿到 A 的 ObjectFactory → 生成 A 的早期引用
   （如果 A 需要 AOP 代理，这里提前生成代理对象）
   → 早期引用升级到二级缓存，三级缓存移除
⑤ B 拿到 A 的早期引用，完成初始化 → 放入一级缓存
⑥ 回到 A，注入完整的 B → A 完成初始化 → 放入一级缓存

    6.3 三个经典追问¶

    Q：哪些循环依赖 Spring 解决不了？

    场景 能否解决 原因
    单例 + 字段/setter 注入 ✅ 能 三级缓存生效
    构造器注入 ❌ 不能 实例化就要依赖，没机会放缓存
    prototype 作用域 ❌ 不能 不缓存，每次都新建
    @Async 标注的 Bean（某些版本） ⚠️ 有坑 代理生成时机特殊

    Q：为什么需要三级，两级不行吗？

    两级缓存也能解决普通循环依赖。第三级的意义在于 AOP：正常情况下代理对象在初始化后（生命周期⑥）才创建；但如果发生循环依赖，别的 Bean 需要提前拿到 A 的引用——此时必须给"代理后的 A"而不是原始 A。三级缓存的 ObjectFactory（getEarlyBeanReference）保证：如果需要代理就提前生成，且全局只生成一次，避免最终一级缓存里的对象和提前暴露的引用不一致。

    Q：构造器循环依赖怎么办？

    • 重构设计消除循环依赖（最优解）
    • 其中一方改用 setter/字段注入
    • @Lazy 延迟注入：public A(@Lazy B b)

    7. AOP 面向切面¶

    知识点：

    • ⭐ AOP = 把横切逻辑（日志/事务/权限）从业务代码抽出来统一织入
    • 五要素：切面（Aspect）、切点（Pointcut）、通知（Advice：before/after/around 等）、连接点、织入
    • ⭐ 代理机制：接口用 JDK 动态代理，无接口用 CGLIB 子类代理（SpringBoot 默认 CGLIB）
    • ⚠️ 自调用失效：同类内部方法互调不经过代理，AOP 不生效

    7.1 什么是 AOP¶

    AOP（Aspect Oriented Programming）把横切关注点（日志、事务、权限）从业务代码中抽离出来，统一维护。

    // ❌ 没有 AOP：每个方法都重复日志代码
public void createOrder() {
    long start = System.currentTimeMillis();
    log.info("开始");
    // ... 真正的业务逻辑（只有这几行）
    log.info("结束，耗时 " + (System.currentTimeMillis() - start));
}

    核心概念：

    概念 说明
    Aspect 切面 横切关注点的模块化（一个类）
    Joinpoint 连接点 程序执行的点（Spring 中 = 方法执行）
    Pointcut 切点 用表达式筛选哪些连接点要被切
    Advice 通知 切面在连接点执行的动作
    Weaving 织入 把切面应用到目标对象的过程

    7.2 五种通知¶

    @Aspect
@Component
public class LogAspect {

    // 复用切点表达式
    @Pointcut("execution(* com.example.service.*.*(..))")
    public void serviceLayer() {}

    @Before("serviceLayer()")
    public void before(JoinPoint jp) {
        System.out.println("方法执行前：" + jp.getSignature().getName());
    }

    @After("serviceLayer()")
    public void after(JoinPoint jp) {
        System.out.println("方法执行后（无论是否异常）");
    }

    @AfterReturning(pointcut = "serviceLayer()", returning = "result")
    public void afterReturning(Object result) {
        System.out.println("正常返回：" + result);
    }

    @AfterThrowing(pointcut = "serviceLayer()", throwing = "ex")
    public void afterThrowing(Exception ex) {
        System.out.println("抛出异常：" + ex.getMessage());
    }

    @Around("serviceLayer()")
    public Object around(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.currentTimeMillis();
        Object result = pjp.proceed();   // 执行目标方法
        System.out.println("耗时：" + (System.currentTimeMillis() - start) + "ms");
        return result;
    }
}

    执行顺序（正常情况）：@Around 前 → @Before → 目标方法 → @AfterReturning → @After → @Around 后

    7.3 切点表达式¶

    execution(修饰符? 返回类型 包名.类名.方法名(参数))

execution(* com.example.service.*.*(..))
//        │ │              │ │  │  └─ 任意参数
//        │ │              │ │  └─ 任意方法名
//        │ │              │ └─ service 包下任意类
//        │ │              └─ 包名（.. 表示含子包）
//        │ └─ 返回类型（* 任意）
//        └─ 修饰符（可省略）

// 其他常用指示符
within(com.example.controller..*)          // 包内所有方法
@annotation(org.springframework.transaction.annotation.Transactional)  // 标注某注解的方法
args(java.lang.String)                     // 参数类型匹配

    7.4 代理机制：JDK 动态代理 vs CGLIB ⭐⭐⭐¶

    Spring AOP 的本质是动态代理：容器注入的不是原始对象，而是代理对象。

    对比项 JDK 动态代理 CGLIB
    要求 目标必须实现接口 无需接口，生成目标类的子类
    原理 基于接口，反射调用 基于继承，字节码增强
    限制 没接口就不能用 final 类/方法无法代理
    速度 创建快、调用稍慢 创建慢、调用快 
    // Spring 的选择策略（原生 Spring Framework）：
// 有接口 → JDK 动态代理；无接口 → CGLIB
//
// ⚠️ SpringBoot 2.x 起默认 spring.aop.proxy-target-class=true
//    即统一用 CGLIB，避免"注入实现类时报类型不匹配"的经典坑

    7.5 AOP 自调用失效 ⭐⭐⭐⭐¶

    面试必问的坑：同一个类内部方法互调，切面不生效。

    @Service
public class UserService {

    @Transactional
    public void methodA() {
        // ...
    }

    public void methodB() {
        this.methodA();   // ❌ 事务不生效！
    }
}

    原因：AOP 基于代理对象工作。外部调用 userService.methodA() 走的是代理对象 → 切面生效；而 this.methodA() 的 this 是原始对象，绕过了代理。

    外部调用：  调用方 → 代理对象.methodA() → 切面 → 原始对象.methodA() ✅
内部调用：  methodB → this.methodA()（原始对象直调）❌

    解决方案：

    // 方案 1：注入自己（推荐）
@Service
public class UserService {
    @Autowired
    @Lazy
    private UserService self;   // 注入的是代理对象

    public void methodB() {
        self.methodA();   // ✅ 走代理，切面生效
    }
}

// 方案 2：从容器获取
ApplicationContext context;
context.getBean(UserService.class).methodA();

// 方案 3：拆分到两个类（最干净的设计）

    事务失效的第一大原因也是它——见第 8.4 节。

    7.6 代理字段陷阱：别访问 Bean 的字段 ⭐⭐⭐¶

    和自调用同源的坑：代理只转发方法调用，不转发字段访问。

    CGLIB 代理是目标类的子类，容器注入的是代理实例——它内部持有一个真实目标对象，方法调用被拦截后转发过去；但代理实例自己的字段副本从未被初始化（代理由 Objenesis 绕过构造器创建）。

    @Service
public class ConfigService {
    public String appName = "my-app";   // public 字段

    @Transactional                      // ← 该类被 CGLIB 代理
    public void doSomething() { }
}

@Autowired ConfigService config;
System.out.println(config.appName);    // ⚠️ null！读到的是代理实例上未初始化的字段副本

    代理对象（子类）──持有──→ 真实目标对象（字段有值）
  方法调用 → 拦截转发给目标 ✅
  字段访问 → 直接读代理自己的副本（未初始化）❌

    规避规则： 1. 字段一律 private + getter/setter，通过方法访问（方法会被正确转发） 2. 被代理的 Bean（有 @Transactional/@Async/切面）尤其严禁直连字段 3. @Autowired 注入本身不受影响——反射作用于真实对象，注入 private 字段照常工作

    💡 "为什么 public 字段读出来是 null"这类灵异 bug，先怀疑代理字段陷阱。

    8. 事务管理¶

    知识点：

    • ⭐ 声明式事务 @Transactional：基于 AOP 代理，方法前后自动 begin/commit/rollback
    • 传播行为常用：REQUIRED（默认，有则加入无则新建）、REQUIRES_NEW（总是新开）
    • ⭐ 失效 8 场景必背：自调用、非 public、异常被吞、抛出受检异常未声明 rollbackFor、多线程、非 Spring 管理对象等

    8.1 声明式事务¶

    @Service
public class AccountService {

    // 默认配置：传播 REQUIRED、隔离级别跟随数据库、
    //          只对 RuntimeException/Error 回滚
    @Transactional
    public void transfer(Long from, Long to, BigDecimal amount) {
        accountDao.decrease(from, amount);
        accountDao.increase(to, amount);   // 任何一步抛运行时异常 → 整体回滚
    }

    // 生产环境推荐写法：显式 rollbackFor
    @Transactional(rollbackFor = Exception.class)
    public void riskyBusiness() throws IOException {
        // 受检异常也会回滚
    }
}

    8.2 事务属性¶

    @Transactional(
    isolation = Isolation.REPEATABLE_READ,     // 隔离级别
    propagation = Propagation.REQUIRED,        // 传播行为
    timeout = 30,                              // 超时秒数
    readOnly = false,                          // 只读（查询优化）
    rollbackFor = Exception.class,             // 哪些异常回滚
    noRollbackFor = BusinessException.class    // 哪些异常不回滚
)

    隔离级别（解决并发问题）：

    级别 脏读 不可重复读 幻读
    READ_UNCOMMITTED ⚠️ 可能 ⚠️ ⚠️
    READ_COMMITTED ✅ 防止 ⚠️ ⚠️
    REPEATABLE_READ（MySQL 默认） ✅ ✅ ⚠️（InnoDB 靠间隙锁基本解决）
    SERIALIZABLE ✅ ✅ ✅

    8.3 传播行为¶

    传播行为 说明
    REQUIRED（默认） 有事务则加入，无则新建
    REQUIRES_NEW 无论如何新建事务，挂起当前事务
    NESTED 有事务则开嵌套事务（savepoint），无则同 REQUIRED
    SUPPORTS 有则加入，无则非事务执行
    NOT_SUPPORTED 非事务执行，挂起当前事务
    MANDATORY 必须在事务中，否则抛异常
    NEVER 必须非事务，否则抛异常 
    // 经典用法：操作日志即使失败也不影响主业务
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void writeAuditLog(String action) {
    // 独立事务：主事务回滚不影响日志，日志失败也不拖累主事务
}

    8.4 事务失效的 8 大场景 ⭐⭐⭐⭐¶

    面试必问，逐个记牢：

    # 场景 原因 解决
    1 自调用 this 调用绕过代理 注入自己/拆类（见 7.5）
    2 方法非 public Spring 默认只代理 public 方法 改为 public
    3 异常被吞掉 catch 后没抛出，事务管理器感知不到 捕获后手动回滚或重新抛出
    4 抛受检异常 默认只回滚 RuntimeException/Error rollbackFor = Exception.class
    5 rollbackFor 配错 抛的异常不在回滚范围内 检查异常继承关系
    6 数据库引擎不支持 如 MySQL MyISAM 改用 InnoDB
    7 类没被 Spring 管理 不是 Bean，没有代理 加 @Service 等注解
    8 多线程调用 新线程不在同一事务上下文 事务内避免开线程写库 
    // 场景 3 示例：最常见的错误
@Transactional
public void pay() {
    try {
        accountDao.decrease(userId, amount);
        notifyService.send();
    } catch (Exception e) {
        log.error("支付失败", e);   // ❌ 异常被吞，扣了钱不回滚！
    }
}

    9. Spring 事件机制¶

    知识点：

    • Spring 事件 = 观察者模式实现：ApplicationEventPublisher 发布，@EventListener 监听
    • 默认同步执行（在发布线程），@Async 可异步
    • 典型用途：注册成功发邮件/送积分等解耦场景

    基于观察者模式的组件间解耦通信（发布-订阅）。

    // 1. 定义事件
public class OrderCreatedEvent extends ApplicationEvent {
    private final Order order;
    public OrderCreatedEvent(Object source, Order order) {
        super(source);
        this.order = order;
    }
    public Order getOrder() { return order; }
}

// 2. 发布事件
@Service
public class OrderService {
    @Autowired
    private ApplicationEventPublisher publisher;

    public void createOrder(Order order) {
        orderDao.save(order);
        publisher.publishEvent(new OrderCreatedEvent(this, order));
    }
}

// 3. 监听事件
@Component
public class OrderEventListener {

    @EventListener
    public void onOrderCreated(OrderCreatedEvent event) {
        System.out.println("发短信通知：" + event.getOrder().getPhone());
    }

    @Async              // 异步执行（需 @EnableAsync）
    @EventListener
    public void sendEmail(OrderCreatedEvent event) {
        System.out.println("发送邮件");
    }

    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void afterCommit(OrderCreatedEvent event) {
        // ⭐ 事务提交成功后才执行——避免事务回滚了却发了通知
        System.out.println("推送消息");
    }
}

    事件机制是"订单创建后要做 N 件事"这类需求的标准解法：下单逻辑不用关心积分、通知、库存各自怎么做。

    // DAO 层
@Repository
public class UserDaoImpl implements UserDao {
    @Autowired
    private JdbcTemplate jdbcTemplate;

    @Override
    public void insert(User user) {
        jdbcTemplate.update(
            "INSERT INTO users (name, email) VALUES (?, ?)",
            user.getName(), user.getEmail());
    }
}

// Service 层
@Service
public class UserServiceImpl implements UserService {
    private final UserDao userDao;

    public UserServiceImpl(UserDao userDao) {
        this.userDao = userDao;
    }

    @Transactional(rollbackFor = Exception.class)
    @Override
    public void register(User user) {
        userDao.insert(user);
        // 后续步骤抛异常 → insert 一起回滚
    }
}

// Controller 层
@RestController

    public UserController(UserService userService) {
        this.userService = userService;
    }

    @PostMapping
    public ResponseEntity<?> create(@RequestBody User user) {
        userService.register(user);
        return ResponseEntity.ok().build();
    }
}

    11. 常见面试题¶

    Q1：BeanFactory 和 ApplicationContext 的区别？

    BeanFactory 是最基础的容器，懒加载；ApplicationContext 是超集，启动时预实例化单例，额外支持事件发布、国际化、资源加载、AOP 集成。生产环境都用 ApplicationContext。

    Q2：@Autowired 和 @Resource 的区别？

    @Autowired 是 Spring 的，先按类型后按名称；@Resource 是 Jakarta/JSR-250 标准注解，先按名称后按类型。多实现场景下 @Resource(name=...) 语义更直接。

    Q3：Spring 如何解决循环依赖？为什么是三级缓存？

    见第 6 节。三级缓存的 ObjectFactory 负责按需生成早期引用（含 AOP 代理），保证提前暴露的引用和最终 Bean 一致。构造器注入和 prototype 无法解决。

    Q4：Spring AOP 和 AspectJ 的区别？

    Spring AOP 是运行时动态代理，只支持方法级切入，无需特殊编译器；AspectJ 是编译期/加载期字节码织入，功能完整（字段、构造器都能切）但需要专门工具。Spring 项目默认用 Spring AOP。

    Q5：@Transactional 什么时候失效？

    见 8.4 八大场景：自调用、非 public、异常被吞、受检异常未配 rollbackFor、引擎不支持事务、类不是 Bean、多线程等。

    Q6：什么是 Spring Bean？和 JavaBean 有什么区别？

    Spring Bean 是由容器创建、装配依赖、管理生命周期的对象；容器启动时把声明（注解/@Bean 方法）解析成 BeanDefinition 元数据，再按蓝图实例化并放入缓存。JavaBean 只是编码规范（无参构造 + getter/setter），和技术无关——一个 Spring Bean 不必符合 JavaBean 规范（构造器注入的类可以没有 setter）。

    Q7：@Autowired 注入 List/Map 是什么机制？有什么用途？

    注入 List<T> 会收下容器中所有 T 类型的 Bean；注入 Map<String, T> 的 key 是 beanName、value 是实例。典型用途是策略模式：每种策略一个 @Component 实现，注入 Map 后按类型查表分发，新增策略不用改分发代码（配合 @Order 可控顺序）。

    Q8：@Autowired 找不到匹配或匹配多个时分别抛什么异常？怎么解决？

    找不到：NoSuchBeanDefinitionException（可用 required=false 或 Optional 变可选）；找到多个：按 @Primary → @Qualifier → 字段名回退消歧，都失败抛 NoUniqueBeanDefinitionException。

    Q9：Bean 可以有 public 字段吗？为什么被代理的 Bean 访问字段会读到 null？

    技术上可以但不应该：①违反封装规范；②CGLIB 代理只转发方法调用不转发字段访问——代理实例自己的字段副本未初始化（Objenesis 绕过构造器创建），直接读字段拿到的是 null 而非真实值；③数据绑定依赖 getter/setter。字段一律 private，通过方法访问。

// ========== 练习 2：AOP 性能监控 ==========
@Aspect
@Component
public class PerformanceAspect {

    // 环绕通知：记录 service 包下所有方法的执行耗时
    @Around("execution(* com.example.service.*.*(..))")
    public Object recordTime(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.currentTimeMillis();          // 记录开始时间
        Object result = pjp.proceed();                    // 执行目标方法
        long cost = System.currentTimeMillis() - start;   // 计算耗时
        System.out.println(pjp.getSignature().getName() + " 耗时：" + cost + " ms");
        return result;
    }
}

    13. 本章小结¶

    核心知识点¶

    ✅ IOC/DI：控制反转、三种注入方式、@Autowired/@Resource/@Qualifier
    ✅ Bean 生命周期：实例化 → 注入 → Aware → 初始化 → 销毁
    ✅ 作用域：singleton/prototype，singleton 注入 prototype 的陷阱
    ✅ 三级缓存：循环依赖的解决机制与边界
    ✅ AOP：五种通知、切点表达式、JDK/CGLIB 代理、自调用失效
    ✅ 事务：传播行为、隔离级别、8 大失效场景
    ✅ 事件机制：发布-订阅解耦

    最佳实践¶

    1. 构造方法注入：依赖明确、便于测试
    2. @Transactional(rollbackFor = Exception.class)：显式声明回滚范围
    3. 事务放在 Service 层：边界清晰
    4. 避免自调用：需要时注入自己或拆分类
    5. 理解代理机制：注入的是代理对象，不是原始对象
