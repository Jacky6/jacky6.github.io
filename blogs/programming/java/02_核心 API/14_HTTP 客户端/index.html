    1. HTTP 客户端演进与选型¶

    知识点：

    • Java 生态 HTTP 客户端四代演进：HttpURLConnection（JDK 1.0）→ Apache HttpClient → OkHttp → java.net.http（JDK 11 转正）
    • ⭐ 选型结论：无第三方依赖需求用 java.net.http；需要拦截器、精细连接管理、Android 场景用 OkHttp
    • ⚠️ HttpURLConnection 同步阻塞、API 反人类、不支持 HTTP/2，新代码不要再用
    客户端 出现时间 特点 现状
    HttpURLConnection JDK 1.0 标准库自带，同步阻塞，API 繁琐 能用但别用 ⚠️
    Apache HttpClient 4.x/5.x 2007+ 功能全、连接池成熟，配置重 维护中，存量项目多
    OkHttp 2013 Square 出品，拦截器链、HTTP/2、Android 事实标准 活跃（5.x）⭐
    java.net.http.HttpClient JDK 11 标准库，同步+异步，HTTP/2，Builder API 新项目推荐 ⭐ 
    // ❌ HttpURLConnection：老代码里还常见，认识即可
java.net.URL url = java.net.URI.create("https://api.github.com").toURL();
java.net.HttpURLConnection conn = (java.net.HttpURLConnection) url.openConnection();
conn.setRequestMethod("GET");
conn.setConnectTimeout(3000);
conn.setReadTimeout(5000);
int code = conn.getResponseCode();   // 手动读流、手动关流、手动处理错误流...
conn.disconnect();

    2. java.net.http 快速开始（JDK 11+）¶

    知识点：

    • 三件套：HttpClient（连接与配置载体）、HttpRequest（不可变，可复发）、HttpResponse
    • ⭐ HttpClient 是重量级且线程安全的对象，全局复用一个实例，千万别每个请求 new 一个
    • BodyHandlers 决定响应体怎么收：ofString()、ofByteArray()、ofFile()、ofInputStream()
    • 同步 send() 阻塞当前线程；异步 sendAsync() 返回 CompletableFuture（第 5 节展开）
    import java.net.URI;
import java.net.http.*;
import java.time.Duration;

public class JdkHttpDemo {
    // 全局单例：内部维护线程池和连接，创建成本高
    private static final HttpClient CLIENT = HttpClient.newBuilder()
            .connectTimeout(Duration.ofSeconds(3))      // 建连超时
            .followRedirects(HttpClient.Redirect.NORMAL) // 自动跟随重定向
            .build();

    public static void main(String[] args) throws Exception {
        // GET
        HttpRequest get = HttpRequest.newBuilder()
                .uri(URI.create("https://api.github.com/users/octocat"))
                .header("Accept", "application/vnd.github+json")
                .timeout(Duration.ofSeconds(5))          // 请求级超时
                .GET()
                .build();
        HttpResponse<String> resp = CLIENT.send(get, HttpResponse.BodyHandlers.ofString());
        System.out.println(resp.statusCode());   // 200
        System.out.println(resp.headers().firstValue("Content-Type"));
        System.out.println(resp.body().substring(0, 100));

        // POST JSON（生产用 Jackson/Gson 序列化，这里手写演示）
        String json = "{\"title\":\"New Post\",\"body\":\"Content\"}";
        HttpRequest post = HttpRequest.newBuilder()
                .uri(URI.create("https://jsonplaceholder.typicode.com/posts"))
                .header("Content-Type", "application/json")
                .POST(HttpRequest.BodyPublishers.ofString(json))
                .timeout(Duration.ofSeconds(5))
                .build();
        HttpResponse<String> postResp = CLIENT.send(post, HttpResponse.BodyHandlers.ofString());
        System.out.println(postResp.statusCode());   // 201
    }
}

    本章示例用 https://api.github.com 等公共接口；若要离线练习，可以用 JDK 自带的 com.sun.net.httpserver.HttpServer 在本地起一个测试服务器（练习 4 给了完整代码）。

    3. ⭐ 超时配置（生产级重点）¶

    知识点：

    • ⭐⭐ 面试重点：JDK HttpClient 的 timeout() 只覆盖到响应头接收为止（JDK ≤25 实测），响应体读取不受限——下载大文件时 timeout 不会生效！JDK 26 起才扩展为覆盖响应体
    • connectTimeout（client 级）：TCP 建连超时，超时抛 HttpConnectTimeoutException
    • timeout()（request 级）：等待响应头超时，超时抛 HttpTimeoutException
    • ⚠️ 两个都不设 = 默认无限等待，下游一卡死你的线程就永久阻塞——生产必须全设
    • 对比 Python requests：timeout=(connect, read) 元组里的 read 是"两次收到数据的最大间隔"，Java 这边没有直接对应物，OkHttp 的 readTimeout 才是

    3.1 JDK HttpClient 超时实测¶

    // 实测：服务端立即返回响应头，但 2 秒后才写响应体
// request.timeout(500ms) 并不会中断——body 照样读完，总耗时 2 秒+
HttpRequest req = HttpRequest.newBuilder()
        .uri(URI.create("http://localhost:18080/slowbody"))
        .timeout(Duration.ofMillis(500))
        .GET().build();
HttpResponse<String> r = CLIENT.send(req, HttpResponse.BodyHandlers.ofString());
// JDK 17 实测：status=200, 总耗时 2006ms —— timeout 没管住 body！

// 而响应头慢的场景，timeout 正常生效：
// 服务端 2 秒后才发响应头 → 500ms 时抛 HttpTimeoutException: request timed out

    结论：调用返回大响应体或流式传输的接口时，JDK HttpClient 要靠 BodyHandlers.ofInputStream() 自己控制读取节奏，或换 OkHttp（readTimeout 覆盖 body）。

    3.2 OkHttp 四级超时对比 ⭐¶

    超时 默认值（5.5.0 实测） 覆盖阶段
    connectTimeout 10s TCP 建连 + TLS 握手
    readTimeout 10s 两次收到数据的最大间隔（含响应体读取）
    writeTimeout 10s 两次写出请求体数据的最大间隔
    callTimeout 0（不限） 整个调用的总时长上限（含 body） 
    OkHttpClient client = new OkHttpClient.Builder()
        .connectTimeout(Duration.ofSeconds(3))   // 建连
        .readTimeout(Duration.ofSeconds(10))     // 读（覆盖慢响应体！）
        .writeTimeout(Duration.ofSeconds(10))    // 写
        .callTimeout(Duration.ofSeconds(30))     // 总时限兜底
        .build();

// 实测对比：同样的"响应头立即返回、body 延迟 2 秒"场景
// readTimeout(500ms) → 551ms 抛 SocketTimeoutException ✅（JDK HttpClient 不会）
// callTimeout(500ms) → 501ms 抛 timeout，覆盖整个调用 ✅

    3.3 生产建议超时值¶

    场景 connect read 总时限
    内部微服务 API 1-3s 3-5s 10s
    第三方 API 3-5s 10-15s 30s
    文件下载 5s 30s+（按文件大小） 不设或设大

    ⚠️ 超时值要和下游的 SLA 对齐：你的 read 超时比下游处理时间还短，重试只会雪上加霜。

    4. ⭐ 并发与连接复用¶

    知识点：

    • ⭐⭐ 客户端复用 = 连接复用：HTTP/1.1 keep-alive 连接池、HTTP/2 一条连接多路复用（实测默认协商出 HTTP/2）
    • sendAsync() 返回 CompletableFuture：扇出多个请求并发执行，比串行快 N 倍（实测 3 个 2 秒请求并发只要 2 秒）
    • 实测数据：单个 HttpClient 实例扛 100 并发请求仅 104ms（本地服务器）——复用是免费的性能提升
    • OkHttp 侧对应 Dispatcher（默认 maxRequests=64、每 host maxRequestsPerHost=5）+ ConnectionPool（默认 5 个空闲连接、5 分钟不活跃回收）
    // sendAsync：并发请求三个接口，总耗时 ≈ 最慢的那个，而不是三者之和
HttpRequest r1 = HttpRequest.newBuilder(URI.create("https://api.github.com/users/octocat")).GET().build();
HttpRequest r2 = HttpRequest.newBuilder(URI.create("https://api.github.com/users/torvalds")).GET().build();
HttpRequest r3 = HttpRequest.newBuilder(URI.create("https://api.github.com/zen")).GET().build();

CompletableFuture<HttpResponse<String>> f1 =
        CLIENT.sendAsync(r1, HttpResponse.BodyHandlers.ofString());
CompletableFuture<HttpResponse<String>> f2 =
        CLIENT.sendAsync(r2, HttpResponse.BodyHandlers.ofString());
CompletableFuture<HttpResponse<String>> f3 =
        CLIENT.sendAsync(r3, HttpResponse.BodyHandlers.ofString());

// 等所有完成，收集结果（更多 CompletableFuture 用法见 03_进阶特性/09_CompletableFuture.md）
CompletableFuture.allOf(f1, f2, f3).join();
System.out.println(f1.get().statusCode() + " " + f2.get().statusCode() + " " + f3.get().statusCode());

// 超时兜底：join 可能无限等，生产用 orTimeout
CompletableFuture<String> safe = CLIENT.sendAsync(r1, HttpResponse.BodyHandlers.ofString())
        .thenApply(HttpResponse::body)
        .orTimeout(5, TimeUnit.SECONDS);   // JDK 9+

    // OkHttp 并发：enqueue 异步回调，Dispatcher 控制并发上限
OkHttpClient client = new OkHttpClient.Builder()
        .dispatcher(new Dispatcher(Executors.newFixedThreadPool(20)))  // 自定义线程池
        .build();
// 默认 Dispatcher：最多 64 个并发请求，单个 host 最多 5 个（实测默认值）
// 打同一个下游接口时，maxRequestsPerHost=5 常常是瓶颈，按需调大：
client.dispatcher().setMaxRequestsPerHost(20);

    HTTP/2 多路复用：对支持 HTTP/2 的服务端（实测 repo1.maven.org 协商成功）， 一条 TCP 连接上并行多个请求流，没有 HTTP/1.1 的队头阻塞，连接池只需一条连接。 java.net.http 默认 Version.HTTP_2，服务端不支持自动降级 HTTP/1.1。

    Java 21+ 还可以用虚拟线程跑同步代码获得并发能力（见 03_进阶特性/11_Java9-21 新特性.md）： HttpClient.newBuilder().executor(Executors.newVirtualThreadPerTaskExecutor())。

    5. ⭐ 重试策略（生产级重点）¶

    知识点：

    • ⭐⭐ 面试重点：只重试幂等请求——GET/PUT/DELETE 可重试；POST 重试必须配合幂等键，否则可能重复下单/扣款
    • 重试条件：连接失败、超时、502/503/504（网关/过载类）；4xx 是客户端错误，重试无用
    • ⭐ 指数退避 + 抖动：第 n 次等待 base × 2^n + random，避免所有客户端同一时刻重试打垮下游（重试风暴）
    • OkHttp 的 retryOnConnectionFailure=true（默认）只重试连接级失败（如连接池里的死连接），不会重试 5xx——状态码重试要自己写
    • 成熟方案：Resilience4j 的 Retry 模块（生产推荐，还带熔断/限流全家桶）

    5.1 手写重试 + 指数退避¶

    import java.io.IOException;
import java.net.http.*;
import java.util.Set;
import java.util.concurrent.ThreadLocalRandom;

public class HttpRetry {
    private static final Set<Integer> RETRYABLE_STATUS = Set.of(502, 503, 504);
    private static final int MAX_ATTEMPTS = 3;
    private static final long BASE_DELAY_MS = 200;

    public static HttpResponse<String> sendWithRetry(HttpClient client, HttpRequest req)
            throws IOException, InterruptedException {
        IOException lastError = null;
        for (int attempt = 0; attempt < MAX_ATTEMPTS; attempt++) {
            if (attempt > 0) {
                // 指数退避 + 抖动：200ms, 400ms, 800ms... + 随机抖动
                long delay = BASE_DELAY_MS * (1L << (attempt - 1))
                        + ThreadLocalRandom.current().nextLong(0, 100);
                Thread.sleep(delay);
            }
            try {
                HttpResponse<String> resp = client.send(req, HttpResponse.BodyHandlers.ofString());
                if (!RETRYABLE_STATUS.contains(resp.statusCode())) {
                    return resp;   // 成功或不可重试的状态码，直接返回
                }
                System.out.println("第 " + (attempt + 1) + " 次收到 " + resp.statusCode() + "，准备重试");
            } catch (IOException e) {
                lastError = e;   // 连接失败/超时，重试
            }
        }
        throw lastError != null ? lastError : new IOException("重试用尽");
    }
}
// ⚠️ 前提：req 必须是幂等请求（GET/PUT/DELETE）。HttpRequest 不可变，同一对象可安全重发

    5.2 OkHttp 拦截器重试（实测）¶

    OkHttpClient retrying = new OkHttpClient.Builder()
        .addInterceptor(chain -> {
            int maxAttempts = 3;
            for (int i = 0; ; i++) {
                Response resp = chain.proceed(chain.request());
                if (resp.code() < 500 || i == maxAttempts - 1) {
                    return resp;          // 非 5xx 或重试用尽
                }
                resp.close();             // 重试前必须关闭旧 Response！
                try {
                    Thread.sleep(100L << i);   // 100ms, 200ms, 400ms
                } catch (InterruptedException ignored) {}
            }
        })
        .build();
// 实测：服务端前 2 次返回 503，第 3 次 200 → 客户端最终拿到 200，共耗时 323ms

    5.3 Resilience4j（生产推荐）¶

    <!-- pom.xml：Resilience4j 2.4.0（重试 + 熔断 + 限流全家桶） -->
<dependency>
    <groupId>io.github.resilience4j</groupId>
    <artifactId>resilience4j-retry</artifactId>
    <version>2.4.0</version>
</dependency>

    import io.github.resilience4j.core.IntervalFunction;
import io.github.resilience4j.retry.Retry;
import io.github.resilience4j.retry.RetryConfig;
import java.time.Duration;

RetryConfig config = RetryConfig.custom()
        .maxAttempts(4)                                    // 总尝试次数（含首次）
        .waitDuration(Duration.ofMillis(200))              // 固定间隔
        // 或指数退避：初始 100ms，倍率 2.0 → 100/200/400ms
        .intervalFunction(IntervalFunction.ofExponentialBackoff(100, 2.0))
        .retryExceptions(java.io.IOException.class)        // 只对这些异常重试
        .retryOnResult(r -> ((HttpResponse<?>) r).statusCode() == 503)  // 状态码也算重试条件
        .build();

Retry retry = Retry.of("userApi", config);

// 装饰任意调用（实测：前 2 次抛异常，第 3 次成功，总耗时 409ms）
HttpResponse<String> resp = retry.executeCheckedSupplier(
        () -> CLIENT.send(request, HttpResponse.BodyHandlers.ofString()));

    6. OkHttp 主线：生产级配置¶

    知识点：

    • ⭐ Maven 项目依赖要写 okhttp-jvm：OkHttp 5.x 是 Kotlin Multiplatform 项目，okhttp 这个 artifact 在 Maven 里是空包（官方 README 明确说明）
    • Response.body() 只能消费一次，且必须关闭（try-with-resources），否则连接泄漏
    • 拦截器链是 OkHttp 的灵魂：日志、UA、鉴权、埋点都挂拦截器，业务代码零侵入
    • OkHttpClient 也是全局单例复用（和 JDK HttpClient 同理）
    <!-- pom.xml：注意是 okhttp-jvm 不是 okhttp -->
<dependency>
    <groupId>com.squareup.okhttp3</groupId>
    <artifactId>okhttp-jvm</artifactId>
    <version>5.5.0</version>
</dependency>

    import okhttp3.*;
import java.time.Duration;

public class OkHttpDemo {
    private static final OkHttpClient CLIENT = new OkHttpClient.Builder()
            .connectTimeout(Duration.ofSeconds(3))
            .readTimeout(Duration.ofSeconds(10))
            .writeTimeout(Duration.ofSeconds(10))
            .callTimeout(Duration.ofSeconds(30))
            .connectionPool(new ConnectionPool(20, 5, java.util.concurrent.TimeUnit.MINUTES)) // 20 空闲连接
            .retryOnConnectionFailure(true)   // 默认 true：连接级失败自动重试
            .addInterceptor(chain -> chain.proceed(chain.request().newBuilder()
                    .header("User-Agent", "MyApp/1.0")    // 统一 UA
                    .build()))
            .build();

    public static void main(String[] args) throws Exception {
        // GET：try-with-resources 确保 Response 关闭（不关 = 连接泄漏 ⚠️）
        Request get = new Request.Builder()
                .url("https://api.github.com/users/octocat")
                .header("Accept", "application/vnd.github+json")
                .build();
        try (Response resp = CLIENT.newCall(get).execute()) {
            if (!resp.isSuccessful()) {
                System.out.println("HTTP 错误: " + resp.code());
                return;
            }
            System.out.println(resp.body().string());   // body() 只能读一次
        }

        // POST JSON
        MediaType JSON = MediaType.get("application/json; charset=utf-8");
        Request post = new Request.Builder()
                .url("https://jsonplaceholder.typicode.com/posts")
                .post(RequestBody.create("{\"title\":\"hi\",\"body\":\"test\"}", JSON))
                .build();
        try (Response resp = CLIENT.newCall(post).execute()) {
            System.out.println(resp.code());   // 201
        }
    }
}

    7. 生产配置检查清单¶

    知识点：

    • 上线前逐项自查：超时、重试、连接池、UA、异常处理、监控
    • ⭐ 面试重点：能说清"一次 HTTP 调用在生产上要配哪些参数、为什么"
    检查项 要求 不做的后果
    建连超时 1-5s 下游 DNS/网络故障时线程挂死
    读超时 按下游 SLA 慢响应拖垮线程池
    总时限兜底 callTimeout / orTimeout 大 body 传输无上限
    客户端复用 全局单例 每请求建连，端口耗尽、延迟飙升
    重试 幂等 + 指数退避 + 上限 重试风暴打垮下游
    User-Agent 表明身份 被 WAF/网关拒绝
    异常分类 超时/连接/业务分开处理 告警混乱、无法定位
    监控埋点 耗时、状态码、成功率 故障时无数据可查
    Response 关闭 try-with-resources（OkHttp） 连接池泄漏

    8. Spring 生态：RestClient 深入 ⭐⭐⭐¶

    知识点：

    • ⭐ RestClient（Spring Framework 6.1 / Boot 3.2 引入）：同步流式 API，RestTemplate 的官方接班人
    • ⭐ RestTemplate 自 5.0 进入维护模式，Spring Framework 7.0 起正式标记废弃，新项目不要再选
    • ⭐ 流式 API：builder 构建客户端 → get()/post() 发起 → uri/header/body 组装 → retrieve() 处理响应
    • 错误处理用 onStatus，横切逻辑用 requestInterceptor，底层可换 OkHttp/Apache HttpClient 5
    • 声明式接口调用（HTTP Interface）见 06_SpringBoot 进阶 5.2 节

    8.1 Spring HTTP 客户端演进与选型¶

    演进路线：
RestTemplate（2009，命令式，已废弃 ⚠️）
    ↓
RestClient（2023，Spring 6.1，同步流式，推荐 ⭐）
    ↓（响应式场景）
WebClient（Spring 5+，异步，需要 reactor 依赖）
    ↓（声明式接口）
HTTP Interface（Spring 6.0+，接口+注解，底层就是 RestClient）
    客户端 模型 现状 使用场景
    RestTemplate 同步命令式 ❌ 7.0 废弃，仅维护 老项目存量代码
    RestClient ⭐ 同步流式 ✅ 官方推荐 Spring Boot 同步调用首选
    WebClient 异步响应式 ✅ 维护中 响应式栈 / 高并发扇出
    HTTP Interface 声明式接口 ✅ 推荐 微服务间调用（类 Feign 体验）

    8.2 RestClient 快速开始：流式 API¶

    @Configuration
public class RestClientConfig {

    // ⭐ RestClient 是线程安全的，注册为单例 Bean 全局复用
    @Bean
    public RestClient restClient() {
        return RestClient.builder()
                .baseUrl("https://api.github.com")
                .defaultHeader("User-Agent", "MyApp/1.0")   // 默认头
                .build();
    }
}

@RestController
public class GitHubController {
    private final RestClient restClient;   // 构造器注入

    public GitHubController(RestClient restClient) {
        this.restClient = restClient;
    }

    // GET + 路径变量 + 反序列化为对象
    @GetMapping("/users/{user}")
    public Map<String, Object> getUser(@PathVariable String user) {
        return restClient.get()
                .uri("/users/{user}", user)                 // 路径模板
                .accept(MediaType.APPLICATION_JSON)
                .retrieve()
                .body(new ParameterizedTypeReference<Map<String, Object>>() {});
    }

    // POST + JSON 请求体 + 拿完整响应（状态码/响应头）
    public ResponseEntity<Map<String, Object>> createIssue(String title) {
        return restClient.post()
                .uri("/repos/{owner}/{repo}/issues", "jacky6", "demo")
                .contentType(MediaType.APPLICATION_JSON)
                .body(Map.of("title", title, "body", "created by RestClient"))
                .retrieve()
                .toEntity(new ParameterizedTypeReference<Map<String, Object>>() {});
        // toEntity() 返回 ResponseEntity：能拿到状态码和响应头
        // body() 只返回反序列化后的对象
    }
}

    流式 API 记忆链：

    restClient.get()/post()/put()/delete()    ← HTTP 方法
    .uri(...)                              ← 路径 + 变量
    .header(...) / .accept(...) / .contentType(...)  ← 请求头
    .body(...)                             ← 请求体（post/put）
    .retrieve()                            ← 发起请求，拿响应
        .body(Class / TypeReference)       ← 反序列化为对象
        .toEntity(...)                     ← 完整 ResponseEntity
    .exchange((req, res) -> ...)           ← 最底层：完全自己处理

    ⚠️ 泛型返回类型（Map<String, Object>、List<User>）必须用 ParameterizedTypeReference，和 Jackson 的 TypeReference 同理（防泛型擦除，见 11_JSON 4.1 节）。

    8.3 错误处理：onStatus ⭐¶

    retrieve() 默认遇到 4xx/5xx 抛 HttpClientErrorException/HttpServerErrorException。 更精细的控制用 onStatus：

    String result = restClient.get()
        .uri("/api/users/{id}", 42)
        .retrieve()
        // ① 匹配状态码，自定义处理（返回的值作为响应体，不再抛异常）
        .onStatus(HttpStatusCode::is4xxClientError, (request, response) -> {
            // 读响应体拿服务端错误信息
            String detail = new String(response.getBody().readAllBytes(),
                    StandardCharsets.UTF_8);
            throw new BizException(400, "用户服务返回错误: " + detail);
        })
        // ② 只对特定状态码兜底
        .onStatus(s -> s.value() == 503, (request, response) -> {
            throw new BizException(503, "用户服务不可用，稍后重试");
        })
        .body(String.class);

    默认行为与自定义的优先级：
没有 onStatus → 4xx/5xx 自动抛 RestClientResponseException
有 onStatus   → 匹配到的状态码走你的回调，未匹配的不抛异常（⚠️ 注意这点，
                和默认行为不同！必要时最后补一个 is5xxServerError 兜底）

    8.4 拦截器：日志、鉴权、重试 ⭐¶

    ClientHttpRequestInterceptor 相当于 OkHttp 的拦截器，横切逻辑集中管理：

    // ① 日志拦截器：记录每次调用的方法、URI、状态码、耗时
public class LogInterceptor implements ClientHttpRequestInterceptor {
    private static final Logger log = LoggerFactory.getLogger(LogInterceptor.class);

    @Override
    public ClientHttpResponse intercept(HttpRequest request, byte[] body,
            ClientHttpRequestExecution execution) throws IOException {
        long start = System.currentTimeMillis();
        ClientHttpResponse response = execution.execute(request, body);  // 放行
        log.info("HTTP {} {} -> {} ({}ms)",
                request.getMethod(), request.getURI(),
                response.getStatusCode().value(),
                System.currentTimeMillis() - start);
        return response;
    }
}

// ② 鉴权拦截器：统一注入 Token
public class AuthInterceptor implements ClientHttpRequestInterceptor {
    private final Supplier<String> tokenSupplier;   // 从登录态/配置取

    public AuthInterceptor(Supplier<String> tokenSupplier) {
        this.tokenSupplier = tokenSupplier;
    }

    @Override
    public ClientHttpResponse intercept(HttpRequest request, byte[] body,
            ClientHttpRequestExecution execution) throws IOException {
        request.getHeaders().setBearerAuth(tokenSupplier.get());
        return execution.execute(request, body);
    }
}

// 注册到 RestClient（顺序即执行顺序）
RestClient client = RestClient.builder()
        .baseUrl("https://internal.example.com")
        .requestInterceptor(new LogInterceptor())
        .requestInterceptor(new AuthInterceptor(() -> tokenService.getToken()))
        .build();

    💡 重试也可以在拦截器里实现（包裹 execution.execute 加重试循环），但生产建议交给 Resilience4j（见第 5 章），职责更清晰。

    8.5 生产配置：超时与底层替换 ⭐⭐¶

    RestClient 的超时、连接池配置都在底层 ClientHttpRequestFactory 上——这正是本章 3-4 章通用原则的落点。

    // 方案 1：JDK HttpClient 作为底层（零额外依赖，JDK 11+）
@Bean
public RestClient restClient(RestClient.Builder builder) {
    java.net.http.HttpClient jdkClient = java.net.http.HttpClient.newBuilder()
            .connectTimeout(Duration.ofSeconds(3))        // 建连超时
            .build();
    return builder
            .baseUrl("https://api.github.com")
            .requestFactory(new JdkClientHttpRequestFactory(jdkClient))
            .build();
}

// 方案 2：OkHttp 作为底层（需要 OkHttp 拦截器生态时）
@Bean
public RestClient restClientWithOkHttp(RestClient.Builder builder) {
    OkHttpClient okHttpClient = new OkHttpClient.Builder()
            .connectTimeout(3, TimeUnit.SECONDS)
            .readTimeout(5, TimeUnit.SECONDS)             // 覆盖响应体读取
            .callTimeout(10, TimeUnit.SECONDS)            // 总时限兜底
            .connectionPool(new ConnectionPool(20, 5, TimeUnit.MINUTES))
            .build();
    return builder
            .baseUrl("https://api.github.com")
            .requestFactory(new OkHttp3ClientHttpRequestFactory(okHttpClient))
            .build();
}

// 方案 3：Apache HttpClient 5（Spring Boot 3.x 官方文档的默认推荐）
// 引入 httpclient5 依赖后，SimpleClientHttpRequestFactory 自动用它，
// 支持连接池精细参数（最大连接数、每路由连接数、空闲回收）

    超时职责分工（呼应第 3 章）：

    RestClient 本身：不管超时（它只是流式门面）
底层 Factory：connectTimeout / readTimeout / callTimeout 都在这里配
⚠️ JdkClientHttpRequestFactory 默认无读超时——必须显式设置，
   否则下游慢响应会无限期占用线程

    8.7 四大客户端终极对比 ⭐¶

    维度            RestTemplate   RestClient    WebClient      OkHttp
──────────────────────────────────────────────────────────────────────
模型            同步命令式      同步流式       异步响应式      同步命令式
维护状态        ❌ 废弃         ✅ 推荐        ✅ 维护         ✅ 第三方活跃
依赖            spring-web     spring-web    webflux+reactor 独立
泛型处理        弱（有类型丢失坑）TypeReference TypeReference TypeToken
拦截器          ✅             ✅             ExchangeFilter  ✅（生态丰富）
底层可换        ✅             ✅             Reactor Netty   —（自身即底层）
测试            MockRest...    MockRest...   StepVerifier    MockWebServer

    选型一句话：非 Spring 项目 → java.net.http 或 OkHttp；Spring Boot 同步调用 → RestClient； 响应式栈 → WebClient；微服务声明式调用 → HTTP Interface（底层 RestClient）。 本章讲的超时/重试/并发原则在任何客户端上通用。

    9. 常见面试题¶

    Q1：java.net.http 的 timeout() 覆盖整个请求吗？ 不覆盖（JDK ≤25）。它只限制"发送请求 + 等待响应头"的时间，响应体的读取不受约束—— 实测响应头秒回但 body 延迟 2 秒时，timeout(500ms) 并不中断。JDK 26 起才扩展为覆盖响应体。 需要管住 body 用 OkHttp 的 readTimeout/callTimeout，或自己用 ofInputStream() 控制读取。

    Q2：为什么 HttpClient/OkHttpClient 要全局复用，不能每次请求 new？ 客户端内部持有线程池、连接池、路由缓存。每次 new：① 连接池无法复用，每次 TCP+TLS 握手 （HTTPS 一次握手就是 2-3 个 RTT）；② 线程和文件句柄泄漏风险；③ HTTP/2 多路复用完全失效。 正确姿势：全局单例 + 每个请求单独设置请求级参数。

    Q3：HTTP 重试要注意什么？POST 能重试吗？ 只重试幂等请求（GET/PUT/DELETE）和连接级失败；状态码只重试 502/503/504 这类过载错误， 4xx 重试无意义。POST 非幂等，盲目重试可能重复下单——必须配合幂等键（客户端生成唯一 ID， 服务端去重）。策略上用指数退避 + 随机抖动并设重试上限，防止重试风暴。

    Q4：OkHttp 的 retryOnConnectionFailure 会重试 5xx 吗？ 不会。它只处理连接层面的失败（比如复用了一个已被服务端关闭的连接）。HTTP 状态码层面的 重试需要自己写拦截器，或用 Resilience4j。另外它默认是 true。

    Q5：OkHttp 的四个超时分别管什么阶段？默认值多少？ connectTimeout（建连+TLS 握手，默认 10s）、readTimeout（两次收到数据的间隔，含 body， 默认 10s）、writeTimeout（写请求体，默认 10s）、callTimeout（整个调用总时限，默认 0=不限）。 生产上通常收紧 connect（3s）并加 callTimeout 兜底。

    Q6：RestClient 和 RestTemplate 的区别？为什么废弃 RestTemplate？ RestClient（Spring 6.1 / Boot 3.2）是流式 API，链式调用可读性好、支持泛型返回 （ParameterizedTypeReference）、onStatus 精细错误处理；RestTemplate 是命令式老接口， 泛型有类型擦除坑。RestTemplate 5.0 进入维护模式，Framework 7.0 正式废弃。 新项目同步调用一律 RestClient，响应式用 WebClient。

    Q7：RestClient 的超时配置在哪里？默认行为有什么坑？ RestClient 本身不管超时，超时都在底层 ClientHttpRequestFactory 上： JdkClientHttpRequestFactory（配 connectTimeout）、OkHttp3ClientHttpRequestFactory （配 OkHttp 四级超时）、或 Apache HttpClient 5。 坑：JdkClientHttpRequestFactory 默认无读超时，下游慢响应会无限占线程，必须显式配置。

    10. 练习题¶

    1. 基础 GET/POST：用 java.net.http 调用 https://jsonplaceholder.typicode.com/posts， GET 拉取列表、POST 提交一条 JSON，打印状态码和响应体。

    2. 并发扇出：用 sendAsync + CompletableFuture.allOf 并发请求 5 个 URL， 统计总耗时，并与串行循环对比。

    3. 超时实验：写一个本地 HttpServer（见练习 4），让某个接口延迟 3 秒返回响应头， 验证 request.timeout(1s) 会抛 HttpTimeoutException。

    4. 离线测试服务器：用 com.sun.net.httpserver.HttpServer 在 18080 端口起一个服务， 提供 /hello（返回 JSON）、/slow（延迟 3 秒）两个接口，供上面各题使用。

    5. 重试：给练习 1 的 GET 加上 5.1 节的 sendWithRetry，用 /slow 接口模拟 503 验证重试逻辑。

    参考答案¶

    import com.sun.net.httpserver.*;
import java.net.InetSocketAddress;
import java.net.URI;
import java.net.http.*;
import java.time.Duration;
import java.util.concurrent.*;

public class Exercises {
    public static void main(String[] args) throws Exception {
        // 练习 4：本地测试服务器（离线跑所有实验）
        HttpServer server = HttpServer.create(new InetSocketAddress(18080), 0);
        server.createContext("/hello", ex -> {
            byte[] body = "{\"msg\":\"hi\"}".getBytes();
            ex.getResponseHeaders().add("Content-Type", "application/json");
            ex.sendResponseHeaders(200, body.length);
            ex.getResponseBody().write(body);
            ex.close();
        });
        server.createContext("/slow", ex -> {
            try { Thread.sleep(3000); } catch (InterruptedException ignored) {}
            byte[] body = "late".getBytes();
            ex.sendResponseHeaders(200, body.length);
            ex.getResponseBody().write(body);
            ex.close();
        });
        server.setExecutor(Executors.newFixedThreadPool(4));
        server.start();

        HttpClient client = HttpClient.newBuilder()
                .connectTimeout(Duration.ofSeconds(2)).build();

        // 练习 1：GET / POST
        HttpResponse<String> get = client.send(
                HttpRequest.newBuilder(URI.create("https://jsonplaceholder.typicode.com/posts/1"))
                        .timeout(Duration.ofSeconds(5)).GET().build(),
                HttpResponse.BodyHandlers.ofString());
        System.out.println("GET: " + get.statusCode());

        HttpResponse<String> post = client.send(
                HttpRequest.newBuilder(URI.create("https://jsonplaceholder.typicode.com/posts"))
                        .header("Content-Type", "application/json")
                        .POST(HttpRequest.BodyPublishers.ofString("{\"title\":\"t\",\"body\":\"b\",\"userId\":1}"))
                        .timeout(Duration.ofSeconds(5)).build(),
                HttpResponse.BodyHandlers.ofString());
        System.out.println("POST: " + post.statusCode() + " " + post.body());

        // 练习 2：并发扇出 vs 串行
        String[] urls = {"/hello", "/hello", "/hello", "/hello", "/hello"};
        long t0 = System.currentTimeMillis();
        CompletableFuture<?>[] futs = new CompletableFuture[urls.length];
        for (int i = 0; i < urls.length; i++) {
            futs[i] = client.sendAsync(
                    HttpRequest.newBuilder(URI.create("http://localhost:18080" + urls[i])).GET().build(),
                    HttpResponse.BodyHandlers.ofString());
        }
        CompletableFuture.allOf(futs).join();
        System.out.println("并发: " + (System.currentTimeMillis() - t0) + "ms");

        // 练习 3 + 5：超时实验（/slow 延迟 3 秒发响应头）
        try {
            client.send(HttpRequest.newBuilder(URI.create("http://localhost:18080/slow"))
                            .timeout(Duration.ofSeconds(1)).GET().build(),
                    HttpResponse.BodyHandlers.ofString());
        } catch (HttpTimeoutException e) {
            System.out.println("超时如期发生: " + e.getMessage());
        }

        server.stop(0);
        System.exit(0);
    }
}

    11. 本章小结¶

    核心知识点¶

    ✅ 选型：JDK 11+ 首选 java.net.http，需要拦截器/精细控制选 OkHttp，HttpURLConnection 别再用
    ✅ 三件套：HttpClient（全局单例复用）+ HttpRequest（不可变可重发）+ HttpResponse
    ✅ 超时：JDK timeout() 只管到响应头（≤25）⚠️；OkHttp 四级超时，readTimeout 覆盖 body，callTimeout 兜底
    ✅ 并发：sendAsync + CompletableFuture 扇出；HTTP/2 一条连接多路复用；客户端复用是免费性能提升
    ✅ 重试：只重试幂等请求 + 502/503/504，指数退避 + 抖动，Resilience4j 或拦截器实现
    ✅ OkHttp：Maven 用 okhttp-jvm artifact；Response 必须关；dispatcher 默认 64/5、池默认 5 空闲/5 分钟
    ✅ RestClient：Spring 6.1+ 同步首选（替代废弃的 RestTemplate）；流式 API + onStatus 错误处理 + requestInterceptor；超时配在底层 Factory（JDK/OkHttp/HttpClient5 可换）；测试用 MockRestServiceServer

    最佳实践¶

    1. 客户端全局单例，请求级参数单独设
    2. 超时全链路配置：connect + read + 总时限兜底，和下游 SLA 对齐
    3. POST 重试必须配幂等键
    4. 所有调用加监控埋点：耗时、状态码、成功率
    5. Spring Boot 同步调用用 RestClient（6.1+），RestTemplate 已废弃
