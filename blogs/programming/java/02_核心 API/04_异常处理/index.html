    1. 异常概述¶

    知识点：

    • 异常是程序运行中发生的错误事件，会中断正常流程；Throwable 是所有错误和异常的根父类
    • 体系分两支：Error（OOM、栈溢出等系统级错误，程序无法处理）与 Exception（可处理）
    • Exception 再分：RuntimeException（运行时异常，可选处理）与编译时异常（IO/SQL 异常，必须处理）
    • ⭐ 面试重点：能画出 Throwable 层次结构，说清 Error、运行时异常、编译时异常的处理规则

    1.1 什么是异常¶

    异常（Exception）是程序运行过程中发生的错误事件，会中断正常的程序流程。

    错误 vs 异常：

    Throwable（所有错误和异常的父类）
├── Error（错误）- 严重问题，程序无法处理
│   ├── OutOfMemoryError（内存溢出）
│   └── StackOverflowError（栈溢出）
└── Exception（异常）- 可以处理
    ├── RuntimeException（运行时异常）
    └── 其他 Exception（编译时异常）
    类型 说明 处理 示例
    Error 系统级错误 无法处理 内存溢出
    RuntimeException 运行时异常 可选处理 空指针、数组越界
    Checked Exception 编译时异常 必须处理 IO 异常、SQL 异常

    2. 常见异常¶

    知识点：

    • 运行时异常（RuntimeException 子类）不强制处理：NullPointerException、ArrayIndexOutOfBoundsException、ClassCastException、IllegalArgumentException、NumberFormatException、ArithmeticException
    • 编译时异常必须处理（捕获或 throws 声明）：IOException、SQLException、ClassNotFoundException、InterruptedException

    2.1 运行时异常¶

    // NullPointerException - 空指针
String str = null;
int len = str.length();  // ❌ NullPointerException

// ArrayIndexOutOfBoundsException - 数组越界
int[] arr = new int[5];
int val = arr[10];  // ❌ ArrayIndexOutOfBoundsException

// ClassCastException - 类型转换异常
Object obj = "Hello";
Integer num = (Integer) obj;  // ❌ ClassCastException

// IllegalArgumentException - 非法参数
public void setAge(int age) {
    if (age < 0) {
        throw new IllegalArgumentException("年龄不能为负");
    }
}

// NumberFormatException - 数字格式异常
int num = Integer.parseInt("abc");  // ❌ NumberFormatException

// ArithmeticException - 算术异常
int result = 10 / 0;  // ❌ ArithmeticException

    2.2 编译时异常¶

    // IOException - IO 异常
FileInputStream fis = new FileInputStream("file.txt");  // ❌ 必须处理

// SQLException - 数据库异常
Connection conn = DriverManager.getConnection(url);  // ❌ 必须处理

// ClassNotFoundException - 类未找到
Class.forName("com.mysql.Driver");  // ❌ 必须处理

// InterruptedException - 中断异常
Thread.sleep(1000);  // ❌ 必须处理

    3. 异常处理机制 ⭐⭐⭐¶

    知识点：

    • try 包裹可能抛异常的代码，catch 捕获处理，finally 无论是否异常都会执行（System.exit() 除外）
    • ⚠️ 多个 catch 块必须从具体到一般排序，Exception 兜底放最后
    • ⭐ try-with-resources（Java 7+）自动关闭实现了 AutoCloseable 的资源，替代手写 finally close

    3.1 try-catch-finally¶

    try {
    // 可能抛出异常的代码
    int result = 10 / 0;
} catch (ArithmeticException e) {
    // 捕获并处理异常
    System.out.println("除数不能为零");
    e.printStackTrace();
} finally {
    // 总会执行（通常用于资源清理）
    System.out.println("清理资源");
}

    3.2 多个 catch 块¶

    try {
    int[] arr = new int[10];
    arr[10] = 10 / 0;
} catch (ArithmeticException e) {
    System.out.println("算术异常：" + e.getMessage());
} catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("数组越界：" + e.getMessage());
} catch (Exception e) {
    // 捕获所有其他异常（必须放在最后）
    System.out.println("其他异常：" + e.getMessage());
}

    注意：catch 块顺序是从具体到一般

    3.3 finally 块¶

    // finally 总会执行
try {
    System.out.println("try 块");
    return;
} catch (Exception e) {
    System.out.println("catch 块");
} finally {
    System.out.println("finally 块");  // 总会输出
}

// 例外情况：System.exit()
try {
    System.exit(0);  // finally 不会执行
} finally {
    System.out.println("不会输出");
}

    3.4 try-with-resources（Java 7+）⭐¶

    自动关闭实现了 AutoCloseable 接口的资源。

    // 传统方式
FileInputStream fis = null;
try {
    fis = new FileInputStream("file.txt");
    // 读取文件
} catch (IOException e) {
    e.printStackTrace();
} finally {
    if (fis != null) {
        try {
            fis.close();
        } catch (IOException e) {
            e.printStackTrace();
        }
    }
}

// try-with-resources（推荐）
try (FileInputStream fis = new FileInputStream("file.txt");
     BufferedInputStream bis = new BufferedInputStream(fis)) {
    // 读取文件
    // 自动关闭，不需要 finally
} catch (IOException e) {
    e.printStackTrace();
}

    4. 抛出异常¶

    知识点：

    • throw：在方法内部主动抛出一个异常实例（一次只能抛一个）
    • throws：在方法签名声明可能抛出的异常（可多个，逗号分隔），调用者必须处理或继续向上抛
    • ⭐ 受检异常必须 throws 声明；运行时异常不强制声明

    4.1 throw（抛出单个异常）¶

    // 方法内部抛出异常
public void setAge(int age) {
    if (age < 0 || age > 150) {
        throw new IllegalArgumentException("年龄不合法：" + age);
    }
    this.age = age;
}

    4.2 throws（声明异常）¶

    // 声明方法可能抛出的异常
public void readFile(String path) throws IOException {
    FileInputStream fis = new FileInputStream(path);
    // ...
}

// 调用者必须处理
try {
    readFile("test.txt");
} catch (IOException e) {
    e.printStackTrace();
}

// 或者继续抛出
public void processFile(String path) throws IOException {
    readFile(path);  // 不处理，继续向上抛
}

    4.3 throw vs throws¶

    特性 throw throws
    位置 方法内部 方法签名
    作用 抛出异常对象 声明可能抛出的异常
    数量 单个 多个（逗号分隔） 
    public void method() throws IOException, SQLException {
    throw new IOException("IO 错误");
}

    5. 自定义异常 ⭐¶

    知识点：

    • 继承 RuntimeException → 运行时异常（不强制处理）；继承 Exception → 编译时异常（强制处理）
    • 通常提供两个构造器：只带 message 的、带 message + cause 的（用于异常链）
    • 业务场景用自定义异常表达有意义的错误（如余额不足）

    5.1 创建自定义异常¶

    // 运行时异常（继承 RuntimeException）
public class BusinessException extends RuntimeException {
    public BusinessException(String message) {
        super(message);
    }

    public BusinessException(String message, Throwable cause) {
        super(message, cause);
    }
}

// 编译时异常（继承 Exception）
public class InsufficientFundsException extends Exception {
    public InsufficientFundsException(String message) {
        super(message);
    }
}

    5.2 使用自定义异常¶

    public class BankAccount {
    private double balance;

    public void withdraw(double amount) throws InsufficientFundsException {
        if (amount > balance) {
            throw new InsufficientFundsException("余额不足");
        }
        balance -= amount;
    }
}

// 调用
try {
    account.withdraw(1000);
} catch (InsufficientFundsException e) {
    System.out.println("错误：" + e.getMessage());
}

    6. 异常最佳实践 ⭐⭐⭐¶

    知识点：

    • 捕获具体异常，不要笼统 catch Exception；空 catch 块（吞异常）非常危险
    • ⚠️ 捕获后要么记录日志处理，要么带原因重新抛出（异常链 new BusinessException(msg, e)），不能丢失原始异常
    • 资源清理优先用 try-with-resources

    6.1 捕获异常的原则¶

    // ✅ 正确：捕获具体异常
try {
    readFile();
} catch (FileNotFoundException e) {
    System.out.println("文件未找到");
} catch (IOException e) {
    System.out.println("IO 错误");
}

// ❌ 错误：捕获过于宽泛
try {
    readFile();
} catch (Exception e) {
    // 可能隐藏其他问题
}

// ❌ 错误：空 catch 块
try {
    riskyOperation();
} catch (Exception e) {
    // 什么都不做 - 非常危险！
}

    6.2 不要吞掉异常¶

    // ❌ 错误：吞掉异常
try {
    doSomething();
} catch (Exception e) {
    // 什么都不做
}

// ✅ 正确：记录日志或处理
try {
    doSomething();
} catch (Exception e) {
    logger.error("操作失败", e);
    throw new BusinessException("操作失败", e);
}

    6.3 使用异常链¶

    // 保留原始异常信息
try {
    readFile();
} catch (IOException e) {
    throw new BusinessException("读取文件失败", e);  // ✅ 保留原因
}

// ❌ 错误：丢失原始异常
try {
    readFile();
} catch (IOException e) {
    throw new BusinessException("读取文件失败");  // 丢失 e
}

    6.4 资源清理¶

    // ✅ 推荐：try-with-resources
try (FileInputStream fis = new FileInputStream("file.txt")) {
    // 使用资源
} catch (IOException e) {
    e.printStackTrace();
}

    7. 经典场景¶

    知识点：

    • 文件读写：try-with-resources 自动关流
    • 数据库操作：异常回滚事务 + 资源释放

    7.1 文件读写¶

    public String readFile(String path) {
    try (BufferedReader reader = new BufferedReader(
            new FileReader(path))) {
        StringBuilder content = new StringBuilder();
        String line;
        while ((line = reader.readLine()) != null) {
            content.append(line).append("\n");
        }
        return content.toString();
    } catch (IOException e) {
        throw new BusinessException("读取文件失败", e);
    }
}

    7.2 数据库操作¶

    public User getUserById(int id) throws SQLException {
    String sql = "SELECT * FROM users WHERE id = ?";

    try (Connection conn = dataSource.getConnection();
         PreparedStatement stmt = conn.prepareStatement(sql)) {

        stmt.setInt(1, id);

        try (ResultSet rs = stmt.executeQuery()) {

    8. 实战：为大型项目设计异常体系 ⭐⭐⭐⭐¶

    知识点：

    • 大型项目不会直接用 RuntimeException/Exception，而是设计一套自己的异常体系：统一业务异常 + 错误码 + 全局兜底处理
    • 体系三要素：① 统一基类（BizException，非受检）② 错误码枚举（集中管理、前后端约定）③ 分层处理（业务层抛、边界层转换、入口层兜底）
    • ⚠️ 关键坑：异常链丢失、受检异常滥用、Spring 事务默认只回滚非受检异常、异常不能当流程控制、序列化 UID、高频抛异常的性能开销

    8.1 为什么要自定义异常体系¶

    直接用 JDK 异常的问题：

    问题 直接用 JDK 异常 自定义异常体系
    错误码 没有，前端无法按码处理 每个异常带错误码，统一响应
    区分业务错误 IllegalArgumentException 什么都能是 InventoryException 一看就知道是库存问题
    统一处理 各层各写一套 try-catch 入口一个兜底处理器
    面向用户的信息 堆栈细节直接暴露，可能泄露内部信息 错误码映射友好文案，细节只进日志

    设计原则（业界主流做法，Spring、MyBatis、各大厂内部框架都是这个思路）：

    1. 业务异常继承 RuntimeException（非受检）：不强制调用方 try-catch，避免满屏 throws；让异常向上传播到统一入口处理
    2. 一个项目一个统一基类（如 BizException），领域模块可继承它细分子类（InventoryException、PaymentException）
    3. 错误码用枚举集中管理：编号 + 面向用户的文案，前后端按码约定；日志里另外记录技术细节
    4. 编程错误仍用 JDK 内置异常：空指针、非法参数属于 bug，不该包装成业务异常

    8.2 完整实现（JDK 17 实机验证）¶

    import java.io.*;
import java.net.SocketTimeoutException;

public class ExceptionPractice {

    // ========== 1. 错误码枚举：集中管理所有错误码 ==========
    public enum ErrorCode {
        USER_NOT_FOUND(10001, "用户不存在"),
        INSUFFICIENT_STOCK(20001, "库存不足"),
        PAYMENT_FAILED(30001, "支付失败，请稍后重试"),
        SYSTEM_ERROR(99999, "系统繁忙，请稍后重试");

        private final int code;
        private final String userMessage; // 面向终端用户的友好文案

        ErrorCode(int code, String userMessage) {
            this.code = code;
            this.userMessage = userMessage;
        }
        public int getCode() { return code; }
        public String getUserMessage() { return userMessage; }
    }

    // ========== 2. 统一业务异常：非受检 + 错误码 ==========
    public static class BizException extends RuntimeException {
        // 异常实现 Serializable，固定 UID 避免反序列化 InvalidClassException
        private static final long serialVersionUID = 1L;

        private final int code;

        public BizException(ErrorCode errorCode, String detail) {
            super(detail); // detail 是给开发看日志的，不是给用户的
            this.code = errorCode.getCode();
        }

        public BizException(ErrorCode errorCode, String detail, Throwable cause) {
            super(detail, cause); // 保留异常链，根因不丢
            this.code = errorCode.getCode();
        }
        public int getCode() { return code; }
    }

    // ========== 3. 领域子类：库存模块专用 ==========
    public static class InventoryException extends BizException {
        private static final long serialVersionUID = 1L;
        public InventoryException(ErrorCode errorCode, String detail) {
            super(errorCode, detail);
        }
    }

    // ========== 4. 业务层：校验 + 边界转换 ==========
    public static class OrderService {
        private final int stock = 5;

        public void placeOrder(long userId, int quantity) {
            // 编程错误 → JDK 内置非受检异常（这是 bug，不是业务错误）
            if (quantity <= 0) {
                throw new IllegalArgumentException("quantity must be positive: " + quantity);
            }
            // 业务规则违反 → 自定义业务异常
            if (userId != 1001L) {
                throw new BizException(ErrorCode.USER_NOT_FOUND, "userId=" + userId);
            }
            if (quantity > stock) {
                throw new InventoryException(ErrorCode.INSUFFICIENT_STOCK,
                        "requested=" + quantity + ", stock=" + stock);
            }
            // 边界：受检异常不跨层泄漏，转成业务异常并保留根因
            try {
                callThirdPartyPayment();
            } catch (IOException e) {
                throw new BizException(ErrorCode.PAYMENT_FAILED, "调用支付渠道失败", e);
            }
        }

        private void callThirdPartyPayment() throws IOException {
            throw new SocketTimeoutException("connect timeout: pay.example.com");
        }
    }

    // ========== 5. 全局兜底（模拟 Web 层统一异常处理器）==========
    public static class GlobalExceptionHandler {
        public static String handle(Throwable t) {
            if (t instanceof BizException biz) {
                // 业务异常：给用户友好文案，技术细节只留在日志里
                return "{\"code\":" + biz.getCode()
                        + ",\"message\":\"" + friendlyMessage(biz.getCode()) + "\"}";
            }
            if (t instanceof IllegalArgumentException) {
                return "{\"code\":400,\"message\":\"请求参数错误\"}";
            }
            // 未知异常：绝不暴露堆栈和内部细节（安全）
            return "{\"code\":99999,\"message\":\"系统繁忙，请稍后重试\"}";
        }

        private static String friendlyMessage(int code) {
            for (ErrorCode ec : ErrorCode.values()) {
                if (ec.getCode() == code) return ec.getUserMessage();
            }
            return ErrorCode.SYSTEM_ERROR.getUserMessage();
        }
    }

    public static void main(String[] args) {
        OrderService orderService = new OrderService();
        demo(orderService, 1001L, 99);  // 库存不足
        demo(orderService, 1001L, 1);   // 支付超时（异常链）
    }

    private static void demo(OrderService svc, long userId, int quantity) {
        try {
            svc.placeOrder(userId, quantity);
        } catch (Exception e) {
            System.out.println("捕获异常: " + e.getClass().getSimpleName());
            System.out.println("  统一响应: " + GlobalExceptionHandler.handle(e));
            System.out.println("  日志记录: " + e);  // toString 含 detail
            if (e.getCause() != null) {
                System.out.println("  根因 Caused by: " + e.getCause());
            }
        }
    }
}

    捕获异常: InventoryException
  统一响应: {"code":20001,"message":"库存不足"}
  日志记录: InventoryException: requested=99, stock=5
捕获异常: BizException
  统一响应: {"code":30001,"message":"支付失败，请稍后重试"}
  日志记录: BizException: 调用支付渠道失败
  根因 Caused by: java.net.SocketTimeoutException: connect timeout: pay.example.com

    注意异常信息的分层：detail（"requested=99, stock=5"）进日志给开发排查；userMessage（"库存不足"）返回给用户。两者绝不能混用——把堆栈或 SQL 细节直接返回给用户是常见的安全漏洞。

    8.3 关键问题与易错点 ⚠️¶

    ① 异常链丢失（最高频的错误）¶

    try {
    callThirdPartyPayment();
} catch (IOException e) {
    throw new BizException(ErrorCode.PAYMENT_FAILED, "支付失败");     // ❌ 根因丢了
    // throw new BizException(ErrorCode.PAYMENT_FAILED, "支付失败", e); // ✅ 保留 cause
}

    实测对比：丢失 cause 时 getCause() 为 null，日志里只剩"支付失败"四个字，排查时完全不知道是超时、拒连还是证书问题。凡是 catch 后重新抛出，必须把原异常作为 cause 传入。

    ② 受检异常不要滥用¶

    大型项目业务异常几乎都选非受检（继承 RuntimeException）。原因：

    • 受检异常要求每个调用方都 try-catch 或 throws，层层声明污染方法签名，最后大家只会写 catch (Exception e) 敷衍
    • 业务异常（余额不足、库存不足）调用方通常也"处理不了"，只能向上传播到统一入口——这正是非受检异常 + 全局兜底的模型
    • 受检异常适合"调用方确实能做点什么"的场景（如 FileNotFoundException 时调用方可以换路径）

    ③ Spring 事务回滚规则（面试高频 ⭐）¶

    @Transactional 默认只对 RuntimeException 和 Error 回滚，受检异常默认提交（Spring 官方文档明确说明）。这就是业务异常选非受检的现实原因之一：

    // 业务异常继承 RuntimeException → 默认就能回滚 ✅
@Transactional
public void placeOrder(Order order) {
    stockMapper.decrease(order.getSkuId(), order.getQuantity());
    throw new BizException(ErrorCode.INSUFFICIENT_STOCK, "库存不足"); // 回滚
}

// 若坚持用受检业务异常，必须显式声明，否则不回滚 ⚠️
@Transactional(rollbackFor = Exception.class)
public void transfer(...) throws InsufficientFundsException { ... }

    ④ 异常不能当流程控制¶

    // ❌ 用异常控制循环退出：性能差、可读性差、掩盖真实异常
try {
    while (true) list.get(i++);
} catch (IndexOutOfBoundsException e) { }

// ✅ 正常逻辑判断
while (i < list.size()) { ... }

    异常对象的创建开销主要在 fillInStackTrace()（采集栈轨迹）。实测（JDK 17，10 万次）：普通 new RuntimeException() 约 32ms，重写 fillInStackTrace() 跳过的版本约 3ms——差一个数量级。热路径上高频抛异常（如用异常表示"没数据"）会拖垮性能；确有需要时（如 Netty 的某些信号异常）可重写 fillInStackTrace()。

    ⑤ 序列化与 serialVersionUID¶

    Throwable 实现了 Serializable（异常对象可随 RMI/分布式调用传输、可被框架序列化到日志系统）。异常类应显式声明 private static final long serialVersionUID = 1L;：

    • 不声明时 UID 由编译器根据类结构自动计算（实测某类为 2142944440550607790），类稍作修改（加个字段）UID 就变，反序列化旧数据直接 InvalidClassException
    • RuntimeException/Throwable 自带 UID 字段，但子类的 UID 是各自独立计算的，不能依赖父类

    ⑥ 分层职责要清晰¶

    层 职责 反例
    业务层 抛业务异常，携带错误码和上下文 在 service 里 try-catch 后只打日志不抛（吞异常）
    边界层（调用第三方/IO） 把受检异常转成业务异常，保留 cause 让 SQLException/IOException 直接穿透到 Controller
    入口层（Controller/全局处理器） 兜底：业务异常→友好响应；未知异常→通用响应 + 完整日志 每个 Controller 方法各写一套 try-catch

    ⑦ 其他注意¶

    • message 写上下文，不写结论："库存不足" 不如 "库存不足: requested=99, stock=5"——日志排查时上下文就是线索
    • 异常类按模块分包：com.shop.order.exception、com.shop.pay.exception，而不是全塞一个包
    • JDK 14+ 的 Helpful NPE（JEP 358）：JVM 抛出的 NPE 会说明哪个变量为 null（JDK 14 引入、JDK 15+ 默认开启），实测输出 Cannot invoke "String.trim()" because "s" is null——自定义异常设计时也应学习这种"消息带定位信息"的思路
    • 不要用异常类名做业务判断：先 catch (BizException e) { if (e.getCode() == ...) } 可以，但别写 if (e.getMessage().contains("库存")) 这种靠字符串匹配的逻辑

    10. 高频面试题¶

    Q1：Error 和 Exception 的区别？

    都继承 Throwable。Error 是 JVM 层面的严重问题（OutOfMemoryError、StackOverflowError），程序无法也不应捕获；Exception 是程序可处理的异常。Exception 又分受检异常（编译期强制处理，如 IOException）和非受检异常（RuntimeException，如 NPE、数组越界）。

    Q2：受检异常和非受检异常怎么选？

    调用方可恢复、且必须感知的场景用受检（如文件不存在要提示用户）；编程错误（空指针、越界、参数非法）用非受检——这类问题应该修代码而不是捕获。现代趋势：滥用受检异常污染签名，业务异常多用 RuntimeException 子类 + 全局兜底。

    Q3：final、finally、finalize 的区别？

    final 修饰符（不可变）；finally 是 try 后必定执行的块（释放资源）；finalize 是 Object 的回收前回调（JDK 9 已废弃，不可依赖）。经典追问：try 里 return 后 finally 还执行吗？执行——finally 在 return 之前（除非 System.exit）。

    Q4：try-with-resources 的原理？

    资源类实现 AutoCloseable 接口，try (Resource r = ...) 结束时编译器自动生成 r.close() 调用，且异常时也会关闭。比 finally 手写更简洁，close 抛异常还会被抑制（addSuppressed）不丢失主异常。

    Q5：throw 和 throws 的区别？

    throw 在方法体内抛出一个具体的异常实例；throws 在方法签名上声明可能抛出的异常类型，把处理责任推给调用者。

    Q6：异常链（cause）为什么重要？

    捕获底层异常后包装成业务异常时，要用 new BizException("下单失败", e) 保留原始异常，否则排查时丢失真正的根因堆栈。日志框架记日志时也要把异常对象作为最后一个参数传入。

    11. 本章小结¶

    核心知识点¶

    ✅ 异常体系：Error、Exception、RuntimeException
    ✅ 处理机制：try-catch-finally、try-with-resources
    ✅ 抛出异常：throw、throws
    ✅ 自定义异常：继承 Exception 或 RuntimeException
    ✅ 最佳实践：异常链、资源清理、日志记录
    ✅ 实战设计：统一业务异常 + 错误码枚举 + 全局兜底，分层职责清晰

    最佳实践¶

    1. 优先使用 try-with-resources：自动关闭资源
    2. 捕获具体异常：不要捕获 Exception
    3. 不要吞掉异常：记录日志或重新抛出
    4. 使用异常链：保留原始异常信息
    5. 自定义异常：业务场景使用有意义的异常
    6. 大型项目：统一非受检业务异常 + 错误码，受检异常只在边界层转换，入口全局兜底
