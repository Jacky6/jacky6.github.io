    选型建议：pyenv / uv / conda 怎么选¶

    三者不在同一层级，先分清职责再选：

    工具 核心职责 管解释器 管依赖/lock 管虚拟环境
    pyenv Python 解释器多版本安装与切换 ✅ 主业 ❌ ❌（需 pyenv-virtualenv 插件）
    uv 项目环境管理（venv + 依赖 + lock + 运行） ✅ uv python install（预编译版） ✅ ✅ 项目级 .venv
    conda 科学计算生态（含非 Python 二进制依赖） ✅ ✅（conda 生态） ✅

    默认推荐：uv 一站式¶

    绝大多数新项目只需要 uv：

    uv python install 3.13     # 代替 pyenv install（下载 python-build-standalone 预编译包，秒级）
uv init myproj --python 3.13
uv add requests
uv run main.py

    uv 的 uv python 覆盖约 3.7～3.15 的常见版本，装得快且不污染系统 Python。

    什么情况才需要 pyenv¶

    场景 说明
    定制编译 --enable-optimizations、debug 构建、--with-pydebug 等预编译版没有的选项
    极老版本 uv 下载范围外的 Python（如 3.6 及更早）
    系统级切换习惯 依赖 pyenv global/shell 工作流或已有 shims 的脚本

    💡 两者可共存：uv 优先使用 PATH 中的 python；也可用 uv python pin 指定本项目解释器。

    什么时候上 conda¶

    需要 CUDA、MKL 等非 Python 二进制依赖（深度学习、科学计算）时，conda（miniconda/mamba）生态仍是首选。

    一句话结论¶

    • 新项目、Web、脚本、工具开发 → uv
    • 要定制编译/老版本共存 → pyenv 管解释器 + uv 管项目（或不装 pyenv，直接 uv python）
    • 科学计算需要二进制依赖 → conda

    pyenv¶

    ​ pyenv 主要功能

    • 安装多个 Python 版本：可以在同一台机器上安装 Python 2.7、3.6、3.8、3.9、3.11、3.12 等。
    • 按项目设置 Python 版本：通过 .python-version 文件指定项目使用的 Python 版本。
    • 全局/局部版本切换：可设置全局默认版本，也可为特定目录设置局部版本。
    • 与 pyenv-virtualenv 插件集成：支持创建和管理虚拟环境（类似 venv 或 virtualenv）。
    • 非侵入式：不会修改系统 Python，所有操作通过 shims 实现。

    1. 安装¶

    # Linux（pyenv-installer；安装后按其说明配置 shell）
curl -fsSL https://pyenv.run | bash
# macos
brew install pyenv

    2. 基本使用¶

    1. 查看可安装的 Python 版本
pyenv install --list

2. 安装指定版本python
pyenv install 3.11.6

3. 查看已经安装的版本
pyenv versions

4. 设置全局 python 版本
pyenv global 3.11.6

5. 设置局部文件夹 python 版本（仅对当前目录和子目录生效）
cd ~/dir
pyenv local 3.11.6

6. 临时设置shell python 版本

pyenv shell 3.11.6

    3. 虚拟环境管理工具 pyenv-virtualenv¶

    ​ pyenv-virtualenv 是一个插件，用于创建独立的 Python 虚拟环境。

    ## 1. 安装
git clone https://github.com/pyenv/pyenv-virtualenv.git $(pyenv root)/plugins/pyenv-virtualenv

# 添加到 shell 配置文件
echo 'eval "$(pyenv virtualenv-init -)"' >> ~/.zshrc  # 或 .bashrc

## 2. 创建虚拟环境
pyenv virtualenv 3.11.6 myproject-3.11

## 3. 激活虚拟环境
pyenv activate myproject-3.11

## 4. 局部使用虚拟环境
cd /path/to/project
pyenv local myproject-3.11

## 5. 退出虚拟环境
pyenv deactivate

    例子：

    # 进入项目目录
cd my_django_project

# 设置该项目使用 Python 3.10
pyenv local 3.10.12

# 创建虚拟环境
pyenv virtualenv 3.10.12 django-env

# 设置项目使用该虚拟环境
pyenv local django-env

# 此时 python、pip 都指向虚拟环境
python --version    # Python 3.10.12
pip install django

    UV¶

    uv 是由 Astral（Ruff 的开发团队）用 Rust 编写的 Python 一体化工具链：既是极快的包安装器与依赖解析器，也是项目管理器、Python 版本管理器、命令行工具管理器，目标是用一个工具替代 pip + pip-tools + virtualenv + pyenv + pipx + poetry 的组合。

    • 官方定位："An extremely fast Python package and project manager"
    • 官网：https://docs.astral.sh/uv/ ｜ GitHub：https://github.com/astral-sh/uv
    • 兼容性：完全兼容 PyPI 与 PEP 标准（PEP 508 依赖声明、PEP 621 pyproject.toml、PEP 735 依赖组等）
    • 本节命令均基于 uv 0.9.3 实机验证

    一、两套接口：先分清，再使用¶

    理解 uv 最重要的一张图——它内部有两条命令线，用途完全不同：

    接口 命令族 管什么 适用场景
    🏗️ 项目接口 uv init add remove sync lock run tree 同时管理 pyproject.toml + uv.lock + .venv 三件套 正式项目（推荐）
    🔧 pip 兼容接口 uv pip install/sync/list ... 只装包，不碰任何项目配置文件 临时环境、脚本、CI、老项目

    ⚠️ 新手最大的坑：在 uv 项目里混用两套接口。 用 uv pip install xxx 装的包不会写进 pyproject.toml 和 uv.lock，下次执行 uv sync 时会被当作"多余包"直接清掉。项目里请始终使用 uv add。

    二、安装¶

    方法 1：使用官方脚本（推荐）¶

    # Linux/macOS
curl -LsSf https://astral.sh/uv/install.sh | sh

    方法 2：通过 pipx（如果已安装）¶

    pipx install uv

    方法 3：Homebrew（macOS/Linux）¶

    brew install uv

    验证安装¶

    uv --version

    三、项目管理（核心）¶

    3.1 项目四件套：uv init 到底生成了什么¶

    uv init hello-web --python 3.12
cd hello-web

    实测生成的文件：

    hello-web/
├── .gitignore          # 已预置 .venv 等忽略项
├── .python-version     # 固定本项目的 Python 版本
├── README.md
├── main.py             # 入口示例
└── pyproject.toml      # 项目配置 + 依赖声明

    首次执行 uv add / uv sync 后会再出现两个：

    ├── uv.lock             # 锁文件：解析后的精确版本 + 哈希
└── .venv/              # 项目虚拟环境（uv 自动创建）

    四件套的职责：

    文件 职责 提交 Git？
    pyproject.toml 声明依赖范围（如 requests>=2.34.2）与项目元数据 ✅ 提交
    uv.lock 锁定精确版本与哈希，任何人同步出完全相同的环境 ✅ 提交
    .python-version 固定解释器版本（如 3.12） ✅ 提交
    .venv/ 实际安装依赖的环境 ❌ 不提交（.gitignore 已包含）

    💡 记忆法：pyproject 说"要什么"，uv.lock 说"具体是哪批"，.venv 是"装好后的结果"。

    3.2 uv init 的三种模式¶

    uv init hello-web          # 应用（默认）：生成 main.py 入口
uv init mylib --lib        # 库：src/ 布局，可构建发布到 PyPI
cd 已有项目 && uv init      # 不新建目录，直接在当前目录初始化

    --lib 模式的差异（实测）：生成 src/mylib/__init__.py 结构，并在 pyproject.toml 中追加构建配置：

    [build-system]
requires = ["uv_build>=0.9.3,<0.10.0"]
build-backend = "uv_build"

    --lib 项目：代码必须放在 src/ 下吗？¶

    不是必须。 src/mylib/ 只是 uv_build 后端的默认约定。因为 --lib 项目是可安装的包（多了 build-system），构建后端必须知道"哪个目录是包"，位置和名字都可以配置：

    布局 需要的配置 实测结果（uv 0.9.3）
    src/mylib/（默认） 无 ✅ uv build 成功
    根目录 mylib/（扁平布局） [tool.uv.build-backend] 下 module-root = "" ✅ 成功
    包名 ≠ 项目名（如 src/mypkg/） module-name = "mypkg" ✅ 成功，import mypkg 正常
    单文件模块 mylib.py uv_build 不支持 ❌ 报错；改用 hatchling 后端才行

    配置示例（扁平布局 + 自定义包名）：

    [tool.uv.build-backend]
module-name = "mypkg"
module-root = ""      # 包目录放在项目根目录而非 src/

    💡 为什么推荐保持 src 布局：① 防止 import 遮蔽（当前目录的同名包意外覆盖已安装的包）；② 逼你先 uv sync 再 import，测试的是用户实际拿到的包；③ 仓库根目录更干净。

    --lib 与默认（应用）模式对比：

    uv init app（默认） uv init mylib --lib
    有无 build-system 无 有
    是否"包" 否，纯应用 是，可安装可发布
    代码放哪 任意（main.py 在根目录） 有布局约定（可配置）
    常见命令 uv run main.py uv build 构建发布

    3.3 添加依赖：uv add¶

    uv add requests                            # 运行时依赖 → [project.dependencies]
uv add "requests>=2.30,<3"                 # 带版本约束
uv add --dev pytest ruff                   # 开发依赖 → [dependency-groups]（PEP 735）
uv add --group docs mkdocs                 # 自定义依赖组
uv add "fastapi[all]"                      # 带 extras
uv add git+https://github.com/psf/requests.git   # git 依赖

    执行 uv add requests 后，pyproject.toml 实测变为：

    [project]
name = "hello-web"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
    "requests>=2.34.2",
]

[dependency-groups]
dev = [
    "pytest>=9.2.0",
]

    ⭐ 一次 uv add 自动完成四件事：解析版本 → 写入 pyproject.toml → 更新 uv.lock → 安装进 .venv。

    3.4 运行代码：uv run（杀手级特性）¶

    uv run main.py        # 运行项目入口
uv run python -c "import requests; print(requests.__version__)"
uv run pytest         # 直接调用开发依赖里的工具

    ⭐ 完全不需要 source .venv/bin/activate！ uv run 自动使用项目的 .venv；发现环境落后于 uv.lock 时还会先自动同步再运行。

    3.5 锁定与同步：uv lock / uv sync¶

    uv lock                  # 只解析依赖、生成/更新 uv.lock，不安装
uv sync                  # 按 uv.lock 精确重建 .venv

    uv sync 常用选项：

    选项 行为 典型场景
    （无） 确保 .venv 与 uv.lock 一致 克隆项目后第一步
    --locked 先校验 lock 与 pyproject 一致，不一致则报错 CI，防止有人忘提交 lock
    --frozen 完全使用现成 lock，不检查 pyproject 部署
    --no-dev 不安装 dev 依赖组 生产环境

    升级依赖：

    uv lock --upgrade                    # 全部依赖升到约束允许的最新版
uv lock --upgrade-package requests   # 只升级 requests（简写 -P requests）
uv sync                              # 升级后同步进环境

    3.6 查看依赖：uv tree¶

    uv tree

    实测输出（一眼看清直接依赖与传递依赖）：

    hello-web v0.1.0
├── requests v2.34.2
│   ├── certifi v2026.10.23
│   ├── charset-normalizer v3.5.2
│   ├── idna v3.20
│   └── urllib3 v2.8.0
└── pytest v9.2.0 (group: dev)
    ├── iniconfig v2.3.1
    ├── packaging v26.3
    ├── pluggy v1.7.0
    └── pygments v2.21.0

    3.7 移除依赖：uv remove¶

    uv remove requests

    会从 pyproject.toml、uv.lock、.venv 三处移除，并级联清理不再被需要的传递依赖（实测移除 requests 时，urllib3 等孤儿依赖一并清除）。

    3.8 与非 uv 环境协作：uv export¶

    部署目标机器没有 uv 时，导出标准 requirements.txt（默认带哈希校验）：

    uv export --no-dev > requirements.txt
uv export --no-hashes > requirements.txt   # 不要哈希（兼容性更好）

    3.9 日常开发循环（速查）¶

    克隆项目          uv sync
加依赖            uv add xxx          （开发工具：uv add --dev xxx）
跑代码/测试       uv run xxx          （无需激活环境！）
看依赖结构        uv tree
删依赖            uv remove xxx
升级依赖          uv lock --upgrade [-P 包名] && uv sync
交付非 uv 环境    uv export > requirements.txt

    附：命令对两个文件的影响一览（uv 0.9.3 实测）¶

    命令 pyproject.toml uv.lock
    uv init 📄 新建 不生成
    uv add xxx ✅ 写入依赖 ✅ 生成/更新
    uv remove xxx ✅ 删除依赖 ✅ 更新
    uv lock ❌ ✅ 仅在过期时更新
    uv sync ❌ ✅ 过期时自动重新锁定
    uv run xxx ❌ ✅ 过期时自动重新锁定（先自动 sync）
    uv pip install ❌ ❌（装的包下次 sync 会被清掉）

    💡 实用含义： - 手改 pyproject.toml 合法，下次 uv sync / uv run 会自动跟进并重新生成 lock；但推荐 uv add（一步完成解析+写lock+安装）。 - uv.lock 不要手改：机器生成的严格格式（精确版本 + 哈希 + 镜像 URL），手改会被覆盖或哈希校验报错。 - uv sync --locked / --frozen 用于 CI/部署：前者在 lock 过期时报错，后者完全跳过检查。

    四、Python 版本管理（可替代 pyenv）¶

    uv 能自己下载、管理 Python 解释器，不依赖系统 Python：

    uv python list           # 查看可用版本（含可下载的 3.13 / 3.14 / 3.15.0a1 ...）
uv python install 3.13   # 下载安装指定版本
uv python pin 3.12       # 把版本写入当前项目的 .python-version

    💡 .python-version（本项目用什么）与 pyproject.toml 里的 requires-python = ">=3.12"（本项目兼容什么）配合工作：前者钉住开发环境，后者声明兼容范围。

    五、命令行工具管理（可替代 pipx）¶

    uvx ruff check .          # 免安装、直接运行工具（uvx 是 uv tool run 的别名）
uv tool install ruff      # 长期安装（装进 ~/.local/share/uv/tools）
uv tool list              # 查看已安装工具

    六、uv pip 兼容接口（临时场景专用）¶

    只在不管项目配置的场景使用：临时脚本、老项目、CI 缓存层。

    # 创建虚拟环境（比 python -m venv 快；⚠️ 默认不含 pip，配合 uv pip 使用）
uv venv myenv
source myenv/bin/activate   # Linux/macOS

# 装包（只进环境，不写 pyproject.toml）
uv pip install requests
uv pip install -r requirements.txt
uv pip install -e .          # 可编辑安装

# 按 requirements 精确同步环境
uv pip sync -r requirements.txt

# 指定目标环境
uv pip install --python 3.11 django
uv pip install --python .venv flask

    ⚠️ 再次提醒：uv 项目里请用 uv add，uv pip install 装的包会在下次 uv sync 时被清除。

    七、镜像源配置¶

    uv 支持在用户级、项目级配置镜像源，或命令行临时指定。

    用户级别配置文件¶

    文件路径 ~/.config/uv/uv.toml（遵循 XDG 规范；即 $XDG_CONFIG_HOME/uv/uv.toml，已经 uv 0.9.3 实测验证）：

    [[index]]
url = "https://pypi.tuna.tsinghua.edu.cn/simple"
default = true
    项目级别配置文件¶

    在项目 pyproject.toml 中：

    [[tool.uv.index]]
url = "https://pypi.tuna.tsinghua.edu.cn/simple"
default = true

    或在项目根的 uv.toml 中（写法同用户级）。

    命令行指定（uv add 会持久化到 pyproject.toml）¶
    uv add --default-index https://pypi.tuna.tsinghua.edu.cn/simple requests

    ⚠️ 实测行为差异：uv add --default-index <URL> <包> 会把索引配置写入 pyproject.toml（[[tool.uv.index]] + default = true）；而已有配置时再次执行会覆盖更新原条目。相反，uv lock/sync/run/export --default-index 只影响当次执行，不写文件。

    💡 限制：uv add 必须同时添加包名（无"只配源不装包"的命令）。纯配置镜像请直接编辑 pyproject.toml（--index <URL> 则写入不带 default = true 的附加索引）。

    常用镜像：清华 https://pypi.tuna.tsinghua.edu.cn/simple、阿里云 https://mirrors.aliyun.com/pypi/simple/。

    八、传统工具迁移对照表¶

    传统做法 uv 等价命令
    python -m venv .venv uv sync（自动创建）或 uv venv
    pip install xxx 项目里 uv add xxx；临时用 uv pip install xxx
    pip uninstall xxx uv remove xxx
    pip freeze > requirements.txt uv export > requirements.txt
    pip list uv tree（看结构）/ uv pip list（看清单）
    pip-compile + pip-sync（pip-tools） uv lock + uv sync
    pyenv install/local uv python install / uv python pin
    pipx install xxx uv tool install xxx；一次性运行用 uvx xxx
    poetry add/install uv add / uv sync
    python xxx.py（激活环境后） uv run xxx.py（免激活）

    九、最佳实践：完整项目流程¶

    # 1. 创建项目
uv init hello-web --python 3.12
cd hello-web

# 2. 添加生产依赖
uv add flask requests

# 3. 添加开发依赖
uv add --dev pytest ruff

# 4. 查看依赖结构
uv tree

# 5. 运行与测试（全程无需激活环境）
uv run python app.py
uv run pytest

# 6. 提交四件套中的三个（.venv 已在 .gitignore 中）
git add pyproject.toml uv.lock .python-version

# 7. 队友克隆后一条命令还原环境
uv sync

    💡 团队协作要点：pyproject.toml 与 uv.lock 必须一起提交；CI 里用 uv sync --locked 防止 lock 过期。
