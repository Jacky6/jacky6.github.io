    RPC 教程（二）：Protocol Buffers与序列化详解¶

    参考： Protocol Buffers 官方文档、gRPC 文档

    一、什么是序列化？¶

    序列化（Serialization） 是将内存中的对象转换为可存储或传输的格式（字节流、文本等）的过程。

    反序列化（Deserialization） 是将序列化后的数据还原为内存对象的过程。

    序列化：
  内存对象 → 字节流/文本 → 存储到磁盘或网络传输

反序列化：
  字节流/文本 → 内存对象 → 程序使用

    1.1 为什么需要序列化？¶

    在 RPC 中，数据需要在网络上传输：

    客户端                          服务器
  |                              |
  |  内存对象（Python/Java）      |
  |        ↓                     |
  |  序列化（Protobuf/JSON）      |
  |        ↓                     |
  |  字节流 → 网络传输 → 字节流   |
  |                              |
  |        ↓                     |
  |  反序列化                    |
  |        ↓                     |
  |  内存对象（Java/Go）          |

    关键点： - 不同语言的对象模型不同（Python dict vs Java Map vs Go map） - 网络只能传输字节流 - 需要一种通用的格式来描述数据

    二、🎯 面试考点：常见的序列化协议¶

    面试官：有哪些常见的序列化协议？各有什么特点？

    协议 格式 性能 跨语言 可读性 适用场景
    JSON 文本 慢 ✅ ✅ 好 Web API、配置文件
    XML 文本 慢 ✅ ✅ 好 SOAP、遗留系统
    Protocol Buffers 二进制 快 ✅ ❌ 差 gRPC、高性能系统
    Thrift 二进制 快 ✅ ❌ 差 Facebook、大数据
    MessagePack 二进制 快 ✅ ❌ 差 Redis、轻量级
    Avro 二进制 快 ✅ ❌ 差 Hadoop、Kafka

    2.1 🎯 面试考点：JSON vs Protobuf¶

    面试官：JSON 和 Protobuf 有什么区别？什么时候用哪个？

    答案：

    对比维度 JSON Protobuf
    格式 文本（UTF-8） 二进制
    可读性 ✅ 好（人类可读） ❌ 差（需要 .proto 文件解析）
    序列化速度 慢（字符串解析） 快（直接编码字节）
    数据大小 大（包含字段名） 小（只包含字段编号）
    Schema 无（动态类型） 有（.proto 文件定义）
    向后兼容 需要手动处理 ✅ 原生支持
    跨语言 ✅ 所有语言支持 ✅ 通过 protoc 生成代码
    适用场景 Web API、配置 高性能 RPC、微服务

    性能对比示例：

    // JSON 格式（100 字节）
{
  "id": 12345,
  "name": "Alice",
  "email": "alice@example.com",
  "age": 30
}

    // Protobuf 格式（约 40 字节）
message User {
  int32 id = 1;      // 字段编号 1
  string name = 2;   // 字段编号 2
  string email = 3;  // 字段编号 3
  int32 age = 4;     // 字段编号 4
}

    Protobuf 更小的原因： - 不包含字段名（只用编号） - 二进制编码（数字直接存储，不转为字符串） - 可选字段不占空间（默认值不编码）

    三、Protocol Buffers 基础语法¶

    3.1 定义消息类型¶

    // user.proto
syntax = "proto3";  // 指定语法版本

package example;  // 包名（避免命名冲突）

// 定义消息类型
message User {
  int32 id = 1;           // 字段编号（唯一标识）
  string name = 2;
  string email = 3;
  int32 age = 4;
  bool is_active = 5;
}

message Order {
  string order_id = 1;
  User user = 2;          // 嵌套其他消息类型
  repeated string items = 3;  // 数组（列表）
  double total_amount = 4;
}

    3.2 🎯 面试考点：字段编号的规则¶

    面试官：Protobuf 的字段编号有什么规则？

    message Example {
  int32 id = 1;       // ✅ 字段编号从 1 开始
  string name = 2;    // ✅ 编号必须唯一
  // int32 age = 2;   // ❌ 错误：编号 2 重复

  // 字段编号范围：1-536,870,911 (2^29 - 1)
  // 但不能使用 19000-19999（保留给 Protobuf 内部）

  int32 small_field = 1;     // ✅ 小编号（1-15）占 1 字节
  int32 large_field = 20000; // ⚠️ 大号（16-2047）占 2 字节
}

    字段编号规则： - 1-15：占 1 字节（包括字段编号 + 类型）→ 常用字段用小编号 - 16-2047：占 2 字节 → 不常用字段用大号 - 19000-19999：保留，不能使用 - 编号一旦使用，不能更改（否则破坏兼容性） - 编号一旦删除，不能重用（除非确定旧数据已清理）

    3.3 🎯 面试考点：字段规则（proto3）¶

    面试官：proto3 的字段有什么规则？

    message Example {
  // proto3 默认所有字段都是可选的（singular）
  int32 id = 1;              // 可选，默认值 0
  string name = 2;           // 可选，默认值 ""

  // repeated 字段（数组/列表）
  repeated string tags = 3;  // 可以有 0 个或多个元素

  // map 字段（键值对）
  map<string, string> metadata = 4;

  // oneof 字段（互斥字段，同一时刻只能有一个）
  oneof contact {
    string email = 5;
    string phone = 6;
  }
}

    字段规则说明：

    规则 说明 示例
    singular 可选字段（默认） int32 id = 1;
    repeated 数组（可以有 0 个或多个） repeated string tags = 3;
    map 键值对 map<string, string> metadata = 4;
    oneof 互斥字段（同一时刻只能有一个） oneof contact { ... }

    3.4 🎯 面试考点：默认值¶

    面试官：proto3 的默认值是什么？

    message Example {
  int32 id = 1;           // 默认值：0
  string name = 2;        // 默认值：""
  bool is_active = 3;     // 默认值：false
  repeated string tags = 4; // 默认值：空列表 []
  User user = 5;          // 默认值：null（未设置）
}

    默认值规则（proto3）：

    类型 默认值
    int32/int64/uint32/uint64 0
    float/double 0.0
    bool false
    string ""
    bytes ""
    enum 第一个枚举值（必须是 0）
    message null（未设置）
    repeated 空列表
    map 空 map
    oneof 未设置的字段

    ⚠️ 重要： proto3 中，如果字段值等于默认值，不会被编码（节省空间）。

    四、🎯 面试考点：Protobuf 编码原理¶

    面试官：Protobuf 是如何编码的？为什么比 JSON 快？

    4.1 Varint 编码（变长整数编码）¶

    Protobuf 使用 Varint 编码整数，用更少的字节表示小的数字：

    Varint 编码规则：
- 每个字节的最高位（MSB）是标志位
  - 1 = 后面还有字节
  - 0 = 这是最后一个字节
- 其余 7 位存储数据（小端序）

示例：编码数字 300
300 的二进制：100101100

分块（7 位一组，小端序）：
  10101100  →  设置 MSB=1（后面还有）→  110101100
  00000010  →  设置 MSB=0（最后一个）→  000000010

编码结果：
  字节 1: 10101100 (0xAC)
  字节 2: 00000010 (0x02)

解码：
  字节 1: 10101100 → 去掉 MSB → 0101100
  字节 2: 00000010 → 去掉 MSB → 0000010
  拼接（小端序）：0000010 0101100 → 100101100 = 300

    Varint 的优势：

    数字 二进制 Varint 字节数 固定 32 位字节数
    1 1 1 字节 4 字节
    127 1111111 1 字节 4 字节
    128 10000000 2 字节 4 字节
    300 100101100 2 字节 4 字节
    16384 100000000000000 3 字节 4 字节

    结论： 小的数字用更少的字节，大的数字也不会超过 5 字节（32 位整数）。

    4.2 消息编码结构¶

    message User {
  int32 id = 1;      // 字段编号 1
  string name = 2;   // 字段编号 2
}

    编码结构：

    每个字段编码为：
  [Key] [Value]

Key = (field_number << 3) | wire_type
  - field_number: 字段编号
  - wire_type: 数据类型（3 位）

Wire types:
  0: Varint (int32, int64, uint32, uint64, sint32, sint64, bool, enum)
  1: 64-bit (double, fixed64, sfixed64)
  2: Length-delimited (string, bytes, embedded messages, repeated fields)
  5: 32-bit (float, fixed32, sfixed32)

    编码示例：

    message User {
  int32 id = 1;      // 字段编号 1，wire_type=0 (Varint)
  string name = 2;   // 字段编号 2，wire_type=2 (Length-delimited)
}

// 实例
User {
  id: 150,
  name: "Alice"
}

    编码过程：

    字段 1 (id: 150):
  Key = (1 << 3) | 0 = 8 (0x08)
  Value = Varint(150) = 0x96 0x01
  编码：08 96 01

字段 2 (name: "Alice"):
  Key = (2 << 3) | 2 = 18 (0x12)
  Value = Length(5) + "Alice" = 05 41 6C 69 63 65
  编码：12 05 41 6C 69 63 65

完整编码：
  08 96 01 12 05 41 6C 69 63 65
  (11 字节)

    对比 JSON：

    {"id":150,"name":"Alice"}
// 25 字节（包含字段名、引号、冒号等）

    Protobuf 更小： - 不包含字段名（只用编号） - 数字用 Varint 编码（150 只占 2 字节） - 字符串直接存储（不需要引号）

    4.3 🎯 面试考点：为什么 Protobuf 快？¶

    面试官：为什么 Protobuf 比 JSON 快？

    答案：

    1. 二进制编码 vs 文本编码
    2. JSON：需要解析字符串（查找引号、冒号、逗号等）

    3. Protobuf：直接读取字节（无需字符串解析）

    4. 字段编号 vs 字段名

    5. JSON：每个字段都要解析字段名（字符串比较）

    6. Protobuf：只用字段编号（整数比较，更快）

    7. Varint 编码

    8. JSON：数字转为字符串（"150" 占 3 字节）

    9. Protobuf：Varint 编码（150 占 2 字节）

    10. Schema 预编译

    11. JSON：动态解析（运行时才知道字段类型）
    12. Protobuf：预编译 Schema（编译时已知字段类型）

    性能对比（实测）：

    操作 JSON Protobuf Protobuf 快多少
    序列化（1KB 数据） 10 μs 2 μs 5 倍
    反序列化（1KB 数据） 15 μs 3 μs 5 倍
    数据大小（1KB 数据） 1000 字节 400 字节 2.5 倍

    五、🎯 面试考点：Protobuf 的向后兼容性¶

    面试官：Protobuf 如何保证向后兼容？

    5.1 兼容性规则¶

    // 版本 1
message User {
  int32 id = 1;
  string name = 2;
}

// 版本 2（新增字段）
message User {
  int32 id = 1;
  string name = 2;
  string email = 3;  // ✅ 新增字段（向后兼容）
}

    兼容性规则：

    操作 兼容性 说明
    新增字段 ✅ 兼容 旧代码忽略新字段
    删除字段 ⚠️ 谨慎 新代码无法读取旧数据（使用默认值）
    更改字段编号 ❌ 不兼容 旧数据无法解析
    更改字段类型 ❌ 不兼容 类型不匹配
    重命名字段 ✅ 兼容 只要编号不变

    5.2 🎯 面试考点：reserved 关键字¶

    面试官：如何安全地删除字段？

    // ❌ 错误做法：直接删除字段
message User {
  int32 id = 1;
  string name = 2;
  // string email = 3;  // 删除字段 3（危险！）
}

// ✅ 正确做法：使用 reserved
message User {
  int32 id = 1;
  string name = 2;
  reserved 3;           // 保留字段编号 3
  reserved "email";     // 保留字段名 "email"
}

    reserved 的作用： - 防止字段编号被重用（避免与旧数据冲突） - 防止字段名被重用（避免命名混淆） - protoc 编译器会检查，如果有人使用 reserved 的编号/名字，会报错

    5.3 🎯 面试考点：枚举的兼容性¶

    面试官：枚举如何保证兼容性？

    // 版本 1
enum Status {
  UNKNOWN = 0;  // ✅ 第一个值必须是 0（proto3 要求）
  ACTIVE = 1;
  INACTIVE = 2;
}

// 版本 2（新增枚举值）
enum Status {
  UNKNOWN = 0;
  ACTIVE = 1;
  INACTIVE = 2;
  PENDING = 3;  // ✅ 新增枚举值（向后兼容）
}

    枚举兼容性规则： - ✅ 可以新增枚举值 - ❌ 不能删除枚举值（旧数据可能包含该值） - ❌ 不能更改枚举值的编号 - ✅ 第一个枚举值必须是 0（proto3 要求，作为默认值）

    六、🎯 面试考点：定义 RPC 服务¶

    面试官：如何在 Protobuf 中定义 RPC 服务？

    // user_service.proto
syntax = "proto3";

package example;

// 定义请求消息
message GetUserRequest {
  int32 user_id = 1;
}

// 定义响应消息
message GetUserResponse {
  int32 id = 1;
  string name = 2;
  string email = 3;
}

// 定义 RPC 服务
service UserService {
  // 一元调用（Unary RPC）
  rpc GetUser (GetUserRequest) returns (GetUserResponse);

  // 服务端流式调用（Server Streaming RPC）
  rpc ListUsers (GetUserRequest) returns (stream GetUserResponse);

  // 客户端流式调用（Client Streaming RPC）
  rpc CreateUsers (stream GetUserRequest) returns (GetUserResponse);

  // 双向流式调用（Bidirectional Streaming RPC）
  rpc Chat (stream GetUserRequest) returns (stream GetUserResponse);
}

    6.1 🎯 面试考点：四种调用模式¶

    面试官：gRPC 的四种调用模式有什么区别？

    模式 说明 适用场景
    Unary RPC 客户端发送一个请求，服务器返回一个响应 简单的查询（如获取用户信息）
    Server Streaming RPC 客户端发送一个请求，服务器返回一个流 批量查询（如获取用户列表）
    Client Streaming RPC 客户端发送一个流，服务器返回一个响应 批量上传（如批量创建用户）
    Bidirectional Streaming RPC 客户端和服务器都可以发送流 实时通信（如聊天、协作编辑）

    调用模式示意图：

    1. Unary RPC（一元调用）
   客户端 → 请求 → 服务器
   客户端 ← 响应 ← 服务器

2. Server Streaming RPC（服务端流式）
   客户端 → 请求 → 服务器
   客户端 ← 响应 1 ← 服务器
   客户端 ← 响应 2 ← 服务器
   客户端 ← 响应 3 ← 服务器

3. Client Streaming RPC（客户端流式）
   客户端 → 请求 1 → 服务器
   客户端 → 请求 2 → 服务器
   客户端 → 请求 3 → 服务器
   客户端 ← 响应 ← 服务器

4. Bidirectional Streaming RPC（双向流式）
   客户端 → 请求 1 → 服务器
   客户端 ← 响应 1 ← 服务器
   客户端 → 请求 2 → 服务器
   客户端 ← 响应 2 ← 服务器

    八、Protobuf 的最佳实践¶

    8.1 🎯 面试考点：字段编号的选择¶

    面试官：字段编号应该如何选择？

    // ✅ 推荐做法
message User {
  int32 id = 1;        // 常用字段用小编号（1-15）
  string name = 2;     // 常用字段用小编号
  string email = 3;    // 常用字段用小编号

  // 不常用字段用大号
  string address = 16;
  string phone = 17;
}

// ❌ 错误做法
message User {
  int32 id = 100;      // ❌ 小编号留给常用字段
  string name = 200;   // ❌ 浪费空间
}

    最佳实践： - 1-15：留给最常用的字段（占 1 字节） - 16-2047：留给不常用的字段（占 2 字节） - 一旦分配，不要更改字段编号 - 删除字段时，使用 reserved 保留编号

    8.2 🎯 面试考点：repeated vs map¶

    面试官：什么时候用 repeated，什么时候用 map？

    message Example {
  // repeated：有序列表，可以有重复元素
  repeated string tags = 1;        // ["tag1", "tag2", "tag1"]

  // map：键值对，键唯一
  map<string, string> metadata = 2; // {"key1": "value1", "key2": "value2"}
}

    选择建议：

    场景 推荐 原因
    列表数据 repeated 有序，可以有重复元素
    字典数据 map 键唯一，快速查找
    需要排序 repeated map 无序
    需要去重 map 键唯一，自动去重

    8.3 🎯 面试考点：oneof 的使用场景¶

    面试官：什么时候用 oneof？

    message Payment {
  string order_id = 1;

  // 支付方式（互斥，只能选一种）
  oneof payment_method {
    CreditCard credit_card = 2;
    PayPal paypal = 3;
    BankTransfer bank_transfer = 4;
  }
}

message CreditCard {
  string card_number = 1;
  string expiry_date = 2;
  int32 cvv = 3;
}

message PayPal {
  string email = 1;
}

message BankTransfer {
  string bank_name = 1;
  string account_number = 2;
}

    oneof 的特点： - 同一时刻只能设置一个字段 - 设置新字段会自动清除旧字段 - 节省空间（只编码一个字段） - 适用于互斥场景（如支付方式、错误类型）

    九、小结¶

    要点 内容
    序列化是什么 将对象转换为字节流（序列化）和还原（反序列化）
    常见协议 JSON、XML、Protobuf、Thrift、MessagePack
    JSON vs Protobuf JSON 可读性好但慢，Protobuf 快但不可读
    Protobuf 编码 Varint 编码、字段编号 + wire_type、二进制格式
    为什么快 二进制编码、字段编号、Varint、Schema 预编译
    向后兼容 新增字段兼容、删除字段用 reserved、枚举第一个值必须是 0
    四种调用模式 Unary、Server Stream、Client Stream、Bidirectional
    生成代码 protoc 编译器 + 语言插件
    最佳实践 字段编号选择、repeated vs map、oneof 使用场景

    🎯 面试必备： - JSON vs Protobuf 对比 - Protobuf 编码原理（Varint、字段编号、wire_type） - 向后兼容性规则（新增字段、reserved、枚举） - 四种调用模式（Unary、Server Stream、Client Stream、Bidirectional） - 字段编号选择（1-15 常用，16-2047 不常用）
