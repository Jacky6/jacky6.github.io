    RPC 教程（一）：协议基础¶

    参考： gRPC 官方文档、RFC 7540 (HTTP/2)

    一、什么是 RPC？¶

    RPC（Remote Procedure Call，远程过程调用） 是一种通信协议，允许程序调用另一台机器上的函数/方法，就像调用本地函数一样。

    核心特点： - 🌐 透明性：远程调用和本地调用在代码层面看起来一样 - 📡 跨网络：调用方和被调用方可以在不同机器上 - 📦 序列化：数据需要在网络上传输，必须编码/解码 - 🔌 协议支持：通常基于 TCP 或 HTTP/2

    本地调用:                         RPC 远程调用:
result = add(1, 2)                result = add(1, 2)
// 直接执行                        // 实际发生：
                                  // 1. 序列化参数 (1, 2)
                                  // 2. 通过网络发送到远程服务器
                                  // 3. 远程服务器反序列化参数
                                  // 4. 执行 add(1, 2)
                                  // 5. 序列化结果
                                  // 6. 通过网络发送回客户端
                                  // 7. 客户端反序列化结果

    二、RPC 的诞生背景¶

    2.1 为什么需要 RPC？¶

    在分布式系统中，服务部署在不同机器上，需要互相通信：

    方案 1：直接操作 Socket（原始方式）

    # 客户端：手动构造字节流
import socket

sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
sock.connect(("server", 8080))

# 手动编码：4字节方法名长度 + 方法名 + 4字节参数长度 + 参数
method = b"add"
params = b"1,2"
data = len(method).to_bytes(4, "big") + method + len(params).to_bytes(4, "big") + params
sock.send(data)

# 手动解码响应...
response = sock.recv(1024)

    ❌ 问题： - 需要手动处理序列化/反序列化 - 需要手动处理网络异常、超时、重试 - 代码耦合度高，难以维护

    方案 2：RPC 框架

    # 客户端：像调用本地函数一样
result = stub.add(1, 2)  # 框架自动处理序列化、网络、重试等

    ✅ 优势： - 开发者只需关注业务逻辑 - 框架处理序列化、网络、重试、负载均衡等 - 跨语言调用（Python 调 Java、Go 调 C++）

    三、🎯 面试高频题：RPC vs REST vs 消息队列¶

    这是必考题，务必掌握：

    对比维度 RPC REST 消息队列（MQ）
    通信模式 同步请求-响应 同步请求-响应 异步解耦
    协议 自定义/TCP/HTTP/2 HTTP/HTTPS AMQP/Kafka 协议
    数据格式 二进制（Protobuf 等） 文本（JSON/XML） 文本/二进制
    性能 高（二进制序列化） 中（JSON 解析开销） 高（异步批量）
    跨语言 ✅ 通过 IDL ✅ 通过 HTTP ✅ 通过消息协议
    服务发现 需要（Consul/etcd） 需要（DNS/LB） 不需要（Broker 中转）
    耦合度 低（IDL 解耦） 低（URL 解耦） 极低（完全解耦）
    适用场景 微服务内部调用 对外 API 异步任务、事件驱动
    典型框架 gRPC、brpc、Dubbo Spring MVC、Express Kafka、RabbitMQ

    面试回答模板¶

    面试官：什么时候用 RPC，什么时候用 REST？

    回答：

    "选择取决于系统架构需求：

    用 RPC 的场景： - 微服务内部调用（高并发、低延迟要求） - 需要跨语言调用（Python 调 Java、Go 调 C++） - 需要强类型约束（通过 IDL 定义接口） - 对性能要求高（二进制序列化比 JSON 快 3-5 倍）

    用 REST 的场景： - 对外 API（浏览器、移动端、第三方调用） - 需要广泛的兼容性（HTTP 协议通用） - 服务数量少，不需要复杂的服务发现 - 对性能要求不高（JSON 解析开销可接受）

    用消息队列的场景： - 异步解耦（下单后异步发邮件、短信） - 削峰填谷（秒杀场景缓冲请求） - 事件驱动（订单支付后触发多个下游服务） - 不需要立即返回结果

    实际案例： - 电商系统：订单服务 → 库存服务用 gRPC（同步、高性能），订单服务 → 邮件服务用 Kafka（异步解耦），对外 API 用 REST（兼容浏览器）"

    四、🎯 面试考点：RPC 的核心组件¶

    面试官：RPC 框架有哪些核心组件？

    一个完整的 RPC 调用涉及以下组件：

    客户端                                                服务器
  |                                                      |
  |  1. 调用本地 Stub（桩）                               |
  |     stub.add(1, 2)                                   |
  |                                                      |
  |  2. 序列化（Serialization）                          |
  |     (1, 2) → 二进制字节流                            |
  |                                                      |
  |  3. 网络传输（Transport）                            |
  |     TCP / HTTP/2                                     |
  |                                                      |
  |  4. 反序列化（Deserialization）         5. 查找服务   |
  |     字节流 → (1, 2)                     ServiceRegistry
  |                                                      |
  |                                        6. 执行业务逻辑
  |                                           add(1, 2) = 3
  |                                                      |
  |  7. 序列化结果                          8. 序列化结果 |
  |     3 → 字节流                          3 → 字节流   |
  |                                                      |
  |  9. 网络传输                            10. 网络传输 |
  |     <────────────────────────────────────────────    |
  |                                                      |
  |  11. 反序列化结果                                    |
  |      字节流 → 3                                      |
  |                                                      |
  |  12. 返回结果给调用方                                |
  |      return 3                                        |

    核心组件说明：

    组件 作用 示例
    Stub（客户端桩） 客户端的代理，负责序列化、网络调用 gRPC Stub
    Skeleton（服务端骨架） 服务端的代理，负责反序列化、调用服务 gRPC Service
    序列化协议 将对象转换为字节流 Protobuf、JSON、Thrift
    传输协议 网络传输层 TCP、HTTP/2、QUIC
    服务注册中心 管理服务的地址 Consul、etcd、ZooKeeper
    负载均衡器 选择可用的服务实例 Nginx、HAProxy、客户端 LB

    五、🎯 面试考点：RPC 的调用流程¶

    面试官：RPC 的完整调用流程是什么？

    1. 服务注册阶段
   服务启动时 → 向注册中心注册自己的地址（IP:Port）
   注册中心记录：service_name → [instance1, instance2, ...]

2. 服务发现阶段
   客户端调用服务时 → 向注册中心查询可用实例
   注册中心返回：[192.168.1.1:8080, 192.168.1.2:8080, ...]
   客户端通过负载均衡选择一个实例

3. 远程调用阶段
   客户端 Stub → 序列化参数 → 网络传输 → 服务端 Skeleton
   服务端 Skeleton → 反序列化 → 调用服务方法 → 序列化结果
   服务端 Skeleton → 网络传输 → 客户端 Stub
   客户端 Stub → 反序列化 → 返回结果

4. 服务更新阶段
   服务实例上下线时 → 通知注册中心
   注册中心 → 推送变更到客户端
   客户端更新本地缓存

    5.1 🎯 面试考点：同步调用 vs 异步调用¶

    面试官：RPC 支持异步调用吗？

    答案：

    同步调用（Blocking）： 

    # 客户端阻塞等待结果
result = stub.add(1, 2)  # 阻塞，直到收到响应
print(result)  # 3

    异步调用（Non-blocking）： 

    # 客户端立即返回，通过回调处理结果
future = stub.add.async(1, 2)  # 立即返回 Future 对象
future.add_done_callback(lambda f: print(f.result()))  # 回调
print("继续执行其他逻辑")  # 不阻塞

    单向调用（One-way）： 

    # 客户端发送请求后不等待响应（类似消息队列）
stub.notify(event)  # 立即返回，不等待服务器响应

    六、🎯 面试考点：常见的 RPC 框架¶

    面试官：有哪些主流的 RPC 框架？

    框架 语言支持 协议 序列化 特点 适用场景
    gRPC 多语言 HTTP/2 Protobuf Google 开源，高性能，流式支持 微服务、云原生
    brpc C++/Java/Python 多协议 Protobuf/JSON 百度开源，高并发，低延迟 高并发后端
    Dubbo Java 为主 自定义/TCP Hessian2 阿里开源，生态完善 Java 微服务
    Thrift 多语言 自定义/TCP Thrift Facebook 开源，跨语言 大数据、多语言
    Tars 多语言 自定义/TCP Tars 腾讯开源，运维友好 腾讯系项目

    6.1 gRPC 简介¶

    gRPC（Google Remote Procedure Call） 是 Google 开源的高性能 RPC 框架：

    核心特性：
- 基于 HTTP/2（多路复用、头部压缩、流式传输）
- 使用 Protocol Buffers 序列化（高效、跨语言）
- 支持四种调用模式（Unary / Server Stream / Client Stream / Bidirectional）
- 自动代码生成（通过 .proto 文件生成客户端/服务端代码）

    6.2 brpc 简介¶

    brpc（Baidu Remote Procedure Call） 是百度开源的工业级 RPC 框架：

    核心特性：
- 基于 C++ 开发，极致性能
- 支持多协议（HTTP/HTTPS、gRPC、Thrift、Redis 等）
- 支持多语言客户端（Java/Python/Go）
- 内置负载均衡、熔断、限流
- 低延迟（P99 < 1ms）

    七、RPC 的适用场景¶

    ✅ 适合用 RPC 的场景¶

    场景 原因
    微服务内部调用 高性能、低延迟、强类型
    跨语言调用 通过 IDL 统一接口定义
    高并发系统 二进制序列化比 JSON 快 3-5 倍
    需要流式传输 gRPC 支持双向流（如实时音视频）
    需要强一致性 同步调用确保数据一致

    ❌ 不适合用 RPC 的场景¶

    场景 原因 推荐方案
    对外 API 浏览器/移动端兼容性差 REST / GraphQL
    异步解耦 同步调用阻塞资源 消息队列（Kafka）
    事件驱动 耦合度高 消息队列
    简单脚本 过度设计 HTTP + JSON

    八、🎯 面试考点：RPC 的挑战与解决方案¶

    面试官：RPC 有哪些常见问题？如何解决？

    8.1 常见挑战¶

    问题 说明 解决方案
    服务发现 如何找到可用的服务实例 Consul、etcd、ZooKeeper
    负载均衡 如何选择服务实例 轮询、随机、加权、一致性哈希
    超时与重试 网络异常如何处理 设置超时、指数退避重试
    熔断降级 服务故障如何保护系统 Hystrix、Sentinel、熔断器模式
    链路追踪 如何追踪跨服务调用 Jaeger、Zipkin、SkyWalking
    版本兼容 接口变更如何兼容 Protobuf 向后兼容、API 版本化

    8.2 服务发现机制¶

    客户端发现模式： 

    客户端 → 查询注册中心 → 获取服务列表 → 负载均衡选择 → 调用服务

    服务端发现模式： 

    客户端 → 负载均衡器（LB） → LB 查询注册中心 → 转发到服务

    8.3 负载均衡策略¶

    策略 说明 适用场景
    轮询（Round Robin） 依次调用每个实例 实例性能相近
    随机（Random） 随机选择一个实例 简单场景
    加权轮询 按权重分配 实例性能差异大
    一致性哈希 相同请求路由到相同实例 有状态服务（缓存）
    最少连接 选择连接数最少的实例 长连接场景

    九、小结¶

    要点 内容
    RPC 是什么 远程过程调用，像调用本地函数一样调用远程服务
    核心组件 Stub、Skeleton、序列化、传输、服务注册中心
    调用流程 服务注册 → 服务发现 → 远程调用 → 服务更新
    调用模式 同步、异步、单向
    主流框架 gRPC、brpc、Dubbo、Thrift
    适用场景 微服务内部调用、跨语言、高并发
    不适用场景 对外 API、异步解耦
    常见挑战 服务发现、负载均衡、超时重试、熔断降级
