    RPC 教程（五）：生产部署与面试真题¶

    涵盖服务发现、负载均衡、限流熔断、监控排错，附面试高频真题集。

    一、服务发现¶

    1.1 🎯 面试考点：什么是服务发现？¶

    面试官：RPC 中服务发现的作用是什么？

    在微服务架构中，服务实例的 IP 地址是动态变化的（容器化部署、弹性伸缩），服务发现机制用于动态获取可用服务实例的地址。

    没有服务发现：
  客户端 → 硬编码服务器地址 → 服务器
  问题：服务器地址变化时，客户端需要更新代码

有服务发现：
  客户端 → 查询注册中心 → 获取服务器地址列表 → 调用服务器
  优势：服务器地址变化时，注册中心自动更新

    1.2 🎯 面试考点：服务发现的两种模式¶

    面试官：服务发现有哪些模式？

    客户端发现模式（Client-side Discovery）：

    客户端 → 查询注册中心 → 获取服务列表 → 负载均衡选择 → 调用服务

优点：客户端可以直接选择实例，灵活
缺点：客户端需要实现负载均衡逻辑
代表：Netflix OSS（Eureka + Ribbon）

    服务端发现模式（Server-side Discovery）：

    客户端 → 负载均衡器（LB） → LB 查询注册中心 → 转发到服务

优点：客户端不需要知道服务实例，简单
缺点：多一跳，增加延迟
代表：AWS ALB、Kubernetes Service

    1.3 🎯 面试考点：常见的注册中心¶

    面试官：有哪些常见的注册中心？

    注册中心 语言 一致性协议 健康检查 适用场景
    Consul Go Raft ✅ 支持 多数据中心、服务网格
    etcd Go Raft ✅ 支持 Kubernetes、分布式系统
    ZooKeeper Java ZAB ✅ 支持 Hadoop、HBase
    Nacos Java AP/CP 可切换 ✅ 支持 阿里生态、微服务
    Eureka Java AP（最终一致性） ✅ 支持 Netflix OSS

    1.4 🎯 面试考点：Consul vs etcd vs ZooKeeper¶

    面试官：Consul、etcd、ZooKeeper 有什么区别？

    对比维度 Consul etcd ZooKeeper
    一致性协议 Raft Raft ZAB
    健康检查 ✅ 内置 ✅ 支持 ✅ 支持
    多数据中心 ✅ 原生支持 ❌ 需要额外配置 ❌ 需要额外配置
    KV 存储 ✅ 支持 ✅ 核心功能 ✅ 支持
    服务网格 ✅ 集成 Envoy ❌ 不支持 ❌ 不支持
    Web UI ✅ 内置 ❌ 需要第三方 ❌ 需要第三方
    适用场景 多数据中心、服务网格 Kubernetes、分布式锁 Hadoop、HBase

    选择建议： - Kubernetes → etcd（K8s 默认使用） - 多数据中心 → Consul（原生支持） - Hadoop 生态 → ZooKeeper（Hadoop 默认使用） - 阿里生态 → Nacos（Dubbo 默认使用）

    二、负载均衡¶

    2.1 🎯 面试考点：负载均衡策略¶

    面试官：RPC 有哪些负载均衡策略？

    策略 说明 适用场景
    轮询（Round Robin） 依次调用每个实例 实例性能相近
    随机（Random） 随机选择一个实例 简单场景
    加权轮询（Weighted Round Robin） 按权重分配 实例性能差异大
    加权随机（Weighted Random） 按权重随机选择 实例性能差异大
    一致性哈希（Consistent Hashing） 相同请求路由到相同实例 有状态服务（缓存）
    最少连接（Least Connections） 选择连接数最少的实例 长连接场景
    P2C（Power of Two Choices） 随机选两个，挑负载低的 高并发场景

    2.2 🎯 面试考点：一致性哈希¶

    面试官：什么是一致性哈希？为什么用一致性哈希？

    一致性哈希（Consistent Hashing） 用于将请求路由到固定的实例，适用于有状态服务（如缓存）。

    传统哈希：
  hash(key) % N = 实例编号
  问题：实例数量变化时，大量请求需要重新路由

一致性哈希：
  将实例和请求都映射到一个哈希环上
  请求顺时针找到最近的实例

  优势：实例增减时，只影响相邻的请求

    一致性哈希示意图：

            哈希环
          ↑
    Instance A
          |
          |
Request 1 |--------→ Instance B
          |
          |
    Instance C
          |
          ↓

实例 B 下线后：
  原来路由到 B 的请求会路由到 C
  其他请求不受影响

    2.3 🎯 面试考点：P2C 算法¶

    面试官：什么是 P2C 算法？

    P2C（Power of Two Choices） 是一种高效的负载均衡算法：

    P2C 算法：
1. 随机选择两个实例
2. 比较两个实例的负载（如连接数、CPU 使用率）
3. 选择负载较低的实例

优势：
- 比轮询更智能（考虑实际负载）
- 比最少连接更高效（不需要全局信息）
- 适合高并发场景

    三、限流与熔断¶

    3.1 🎯 面试考点：什么是限流？¶

    面试官：RPC 中为什么要限流？

    限流（Rate Limiting） 用于控制请求的速率，防止系统过载。

    常见限流算法：

    算法 说明 适用场景
    固定窗口 在固定时间窗口内限制请求数 简单场景
    滑动窗口 在滑动时间窗口内限制请求数 更精确
    令牌桶（Token Bucket） 以固定速率生成令牌，请求需要令牌 允许突发流量
    漏桶（Leaky Bucket） 以固定速率处理请求 平滑流量

    3.2 🎯 面试考点：令牌桶 vs 漏桶¶

    面试官：令牌桶和漏桶有什么区别？

    令牌桶（Token Bucket）：
  - 以固定速率生成令牌（如每秒 10 个）
  - 请求需要获取令牌才能处理
  - 桶满时，新令牌被丢弃
  - 允许突发流量（桶中有足够令牌时）

漏桶（Leaky Bucket）：
  - 以固定速率处理请求（如每秒 10 个）
  - 请求进入桶中排队
  - 桶满时，新请求被丢弃
  - 平滑流量（无论进入速率如何，处理速率固定）

    对比：

    对比维度 令牌桶 漏桶
    处理速率 可变（允许突发） 固定（平滑流量）
    桶满时 丢弃新令牌 丢弃新请求
    适用场景 允许突发流量 需要平滑流量
    实现复杂度 中 低

    3.3 🎯 面试考点：什么是熔断？¶

    面试官：RPC 中为什么要熔断？

    熔断（Circuit Breaking） 用于防止级联故障，当下游服务故障时，快速失败，避免拖垮上游服务。

    熔断器状态机：

  ┌──────────┐    失败率 > 阈值    ┌──────────┐
  │  Closed  │ ─────────────────→ │   Open   │
  │ (正常)   |                     │ (熔断)   |
  └──────────┘ ←───────────────── └──────────┘
       ↑          超时后进入半开         ↓
       |                               ↓
       |         ┌──────────┐          |
       └──────── │ HalfOpen │ ←────────┘
                 │ (半开)   |  成功
                 └──────────┘
                      ↓ 失败
                      └→ Open

    熔断器状态说明：

    状态 说明
    Closed（关闭） 正常状态，请求正常通过
    Open（打开） 熔断状态，请求直接失败（快速失败）
    HalfOpen（半开） 探测状态，允许少量请求通过，探测服务是否恢复

    3.4 🎯 面试考点：熔断器的参数¶

    面试官：熔断器有哪些关键参数？

    参数 说明 默认值
    失败率阈值 失败率达到多少时熔断 50%
    慢调用阈值 慢调用率达到多少时熔断 100%
    等待时间 熔断后多久进入半开状态 60 秒
    半开最大请求数 半开状态允许多少请求探测 10
    统计窗口 统计失败率的时间窗口 60 秒
    最小请求数 窗口内最少多少请求才计算失败率 10

    3.5 🎯 面试考点：限流 vs 熔断 vs 降级¶

    面试官：限流、熔断、降级有什么区别？

    对比维度 限流 熔断 降级
    目的 防止系统过载 防止级联故障 保证核心功能
    触发条件 请求速率过高 下游服务故障 系统负载过高
    处理方式 拒绝多余请求 快速失败 返回兜底数据
    恢复方式 速率降低后恢复 下游恢复后恢复 负载降低后恢复
    示例 秒杀限流 支付服务熔断 评论服务降级

    四、监控与排错¶

    4.1 🎯 面试考点：RPC 监控指标¶

    面试官：RPC 需要监控哪些指标？

    指标 说明 告警阈值
    QPS 每秒请求数 超过容量
    延迟 请求处理时间（P50/P90/P99） P99 > 100ms
    错误率 失败请求占比 > 1%
    饱和度 系统资源使用率（CPU/内存/连接数） > 80%
    流量 网络带宽使用率 > 80%

    4.2 🎯 面试考点：链路追踪¶

    面试官：如何追踪跨服务调用？

    链路追踪（Distributed Tracing） 用于追踪跨多个服务的请求路径。

    请求路径：
  Client → Service A → Service B → Service C

链路追踪记录：
  Trace ID: abc123
  Span 1: Client → Service A (10ms)
  Span 2: Service A → Service B (20ms)
  Span 3: Service B → Service C (30ms)

  总延迟：60ms
  瓶颈：Service C

    常见的链路追踪系统：

    系统 语言 特点
    Jaeger Go Uber 开源，CNCF 项目
    Zipkin Java Twitter 开源
    SkyWalking Java 阿里开源，APM 系统
    OpenTelemetry 多语言 CNCF 项目，统一标准

    4.3 🎯 面试考点：常见故障排查¶

    面试官：RPC 调用失败，如何排查？

    排查步骤：

    1. 检查网络连通性
   - ping 服务器 IP
   - telnet 服务器端口
   - 检查防火墙规则

2. 检查服务状态
   - 服务是否启动
   - 服务是否注册到注册中心
   - 服务健康检查是否通过

3. 检查日志
   - 客户端日志（错误信息、堆栈）
   - 服务端日志（请求处理、异常）

4. 检查监控
   - QPS 是否异常
   - 延迟是否异常
   - 错误率是否异常

5. 检查链路追踪
   - 请求路径
   - 各 Span 延迟
   - 瓶颈定位

    五、面试真题集¶

    5.1 基础概念题¶

    Q1：什么是 RPC？和 REST 有什么区别？

    答案：

    RPC（Remote Procedure Call）是远程过程调用协议，允许程序像调用本地函数一样调用远程服务。

    对比维度 RPC REST
    协议 自定义/TCP/HTTP/2 HTTP/HTTPS
    数据格式 二进制（Protobuf） 文本（JSON）
    性能 高 中
    跨语言 ✅ 通过 IDL ✅ 通过 HTTP
    适用场景 微服务内部调用 对外 API

    Q2：gRPC 的四种调用模式是什么？各有什么特点？

    答案：

    模式 说明 适用场景
    Unary RPC 客户端发送一个请求，服务器返回一个响应 简单查询
    Server Streaming RPC 客户端发送一个请求，服务器返回一个流 批量查询
    Client Streaming RPC 客户端发送一个流，服务器返回一个响应 批量上传
    Bidirectional Streaming RPC 客户端和服务器都可以发送流 实时通信

    Q3：Protocol Buffers 和 JSON 有什么区别？

    答案：

    对比维度 Protobuf JSON
    格式 二进制 文本
    可读性 ❌ 差 ✅ 好
    序列化速度 快 慢
    数据大小 小 大
    Schema 有（.proto 文件） 无
    向后兼容 ✅ 原生支持 需要手动处理
    适用场景 高性能 RPC Web API

    5.2 架构设计题¶

    Q4：如何设计一个高可用的 RPC 系统？

    答案：

    1. 服务发现
   - 使用 Consul/etcd 作为注册中心
   - 服务实例启动时注册，下线时注销
   - 客户端定期刷新服务列表

2. 负载均衡
   - 客户端负载均衡（如 Ribbon）
   - 使用轮询/随机/一致性哈希策略
   - 支持权重配置

3. 超时重试
   - 设置合理的超时时间（如 5 秒）
   - 配置重试策略（指数退避）
   - 重试次数限制（如 3 次）

4. 熔断降级
   - 使用 Hystrix/Sentinel 实现熔断
   - 失败率阈值（如 50%）
   - 降级策略（返回兜底数据）

5. 限流
   - 使用令牌桶/漏桶算法
   - 限制 QPS（如 1000 QPS）
   - 拒绝多余请求

6. 监控告警
   - 监控 QPS、延迟、错误率
   - 设置告警阈值
   - 使用 Prometheus + Grafana

    Q5：gRPC 和 brpc 有什么区别？如何选择？

    答案：

    对比维度 gRPC brpc
    开发语言 多语言（11+） C++ 为主
    性能 高 极高（P99 < 1ms）
    协议 HTTP/2 + Protobuf 多协议
    服务发现 ⚠️ 需要外部组件 ✅ 内置
    负载均衡 ⚠️ 需要外部组件 ✅ 内置
    适用场景 多语言微服务 高并发 C++ 后端

    选择建议： - 多语言团队 → gRPC - C++ 团队 + 极致性能 → brpc - 需要内置功能 → brpc - 云原生生态 → gRPC

    5.3 实战场景题¶

    Q6：RPC 调用超时，如何排查？

    答案：

    排查步骤：

1. 检查网络
   - ping 服务器 IP（网络是否通）
   - telnet 服务器端口（端口是否开放）
   - 检查防火墙规则

2. 检查服务状态
   - 服务是否启动
   - 服务是否注册到注册中心
   - 服务健康检查是否通过

3. 检查服务端日志
   - 是否收到请求
   - 处理是否耗时过长
   - 是否有异常

4. 检查监控
   - QPS 是否异常（是否过载）
   - 延迟是否异常（是否变慢）
   - 错误率是否异常

5. 检查链路追踪
   - 请求路径
   - 各 Span 延迟
   - 瓶颈定位

    Q7：如何设计一个限流方案？

    答案：

    限流方案设计：

1. 选择限流算法
   - 令牌桶：允许突发流量
   - 漏桶：平滑流量

2. 限流维度
   - 全局限流（所有请求）
   - 用户限流（每个用户）
   - IP 限流（每个 IP）
   - 接口限流（每个接口）

3. 限流实现
   - 单机限流（Guava RateLimiter）
   - 分布式限流（Redis + Lua）

4. 限流策略
   - 拒绝策略（返回 429）
   - 排队策略（等待处理）
   - 降级策略（返回兜底数据）

5. 监控告警
   - 监控限流触发次数
   - 设置告警阈值

    Q8：如何保证 RPC 调用的幂等性？

    答案：

    幂等性保证：

1. 唯一请求 ID
   - 客户端生成唯一请求 ID
   - 服务端根据请求 ID 去重

2. 数据库唯一约束
   - 使用唯一索引防止重复插入
   - 如：订单号唯一约束

3. 乐观锁
   - 使用版本号控制
   - 更新时检查版本号

4. 分布式锁
   - 使用 Redis/ZooKeeper 实现分布式锁
   - 防止并发操作

5. 状态机
   - 使用状态机控制流程
   - 如：订单状态（待支付 → 已支付 → 已发货）

    5.4 深度原理题¶

    Q9：gRPC 基于 HTTP/2，HTTP/2 有哪些优势？

    答案：

    特性 HTTP/1.1 HTTP/2
    连接方式 短连接/Keep-Alive 多路复用（单连接多请求）
    头部压缩 ❌ ✅ HPACK
    二进制分帧 ❌ ✅ 二进制帧
    服务器推送 ❌ ✅ 支持
    流式传输 ❌ ✅ 支持
    优先级 ❌ ✅ 支持

    HTTP/2 的优势： - 多路复用：单连接可以并行处理多个请求，避免队头阻塞 - 头部压缩：HPACK 算法压缩头部，减少传输开销 - 二进制分帧：二进制帧比文本更高效 - 服务器推送：服务器可以主动推送资源 - 流式传输：支持双向流（gRPC 的四种调用模式）

    Q10：Protobuf 的编码原理是什么？为什么比 JSON 快？

    答案：

    Protobuf 编码原理：

1. Varint 编码（变长整数编码）
   - 用更少的字节表示小的数字
   - 每个字节最高位是标志位（1=后面还有，0=最后一个）
   - 其余 7 位存储数据

2. 字段编码
   - Key = (field_number << 3) | wire_type
   - Value = 字段值
   - 不包含字段名（只用编号）

3. 为什么比 JSON 快
   - 二进制编码 vs 文本编码（无需字符串解析）
   - 字段编号 vs 字段名（整数比较更快）
   - Varint 编码（数字占更少字节）
   - Schema 预编译（编译时已知字段类型）
