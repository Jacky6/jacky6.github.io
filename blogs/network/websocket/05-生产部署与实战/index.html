    WebSocket 教程（五）：生产部署与实战¶

    Nginx 配置、负载均衡、水平扩展、监控排错、🎯 面试场景题

    一、Nginx 反向代理配置¶

    1.1 🎯 面试考点：Nginx 如何代理 WebSocket？¶

    面试官：Nginx 默认不支持 WebSocket，怎么配置？

    WebSocket 需要 HTTP Upgrade，Nginx 默认不会转发 Upgrade 头，必须手动配置：

    map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

upstream websocket_backend {
    server 127.0.0.1:8080;
    server 127.0.0.1:8081;
}

server {
    listen 443 ssl http2;
    server_name example.com;

    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;

    location /ws {
        proxy_pass http://websocket_backend;

        # 关键：传递 Upgrade 头
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;

        # 传递真实客户端信息
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 超时设置（关键！）
        proxy_read_timeout 3600s;   # 1 小时
        proxy_send_timeout 3600s;

        # 禁用缓冲
        proxy_buffering off;
    }
}

    关键配置说明：

    配置项 作用 为什么需要
    proxy_http_version 1.1 使用 HTTP/1.1 WebSocket 需要 HTTP/1.1
    proxy_set_header Upgrade 传递 Upgrade 头 告诉后端要升级协议
    proxy_set_header Connection 传递 Connection 头 配合 Upgrade
    proxy_read_timeout 读超时 防止空闲连接被断开

    1.2 完整生产配置¶

    # 连接升级映射
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

# 后端集群
upstream websocket_backend {
    ip_hash;  # 同一 IP 连到同一后端（保持会话）
    server 127.0.0.1:8080 weight=1 max_fails=3 fail_timeout=30s;
    server 127.0.0.1:8081 weight=1 max_fails=3 fail_timeout=30s;
    server 127.0.0.1:8082 weight=1 max_fails=3 fail_timeout=30s;
    keepalive 100;
}

server {
    listen 443 ssl http2;
    server_name example.com;

    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;
    ssl_protocols TLSv1.2 TLSv1.3;

    # WebSocket 端点
    location /ws {
        proxy_pass http://websocket_backend;

        # WebSocket 必需配置
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;

        # 请求头传递
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 超时设置
        proxy_connect_timeout 10s;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;

        # 禁用缓冲
        proxy_buffering off;

        # 限制连接数
        limit_conn addr 20;
    }

    # 健康检查端点
    location /health {
        proxy_pass http://websocket_backend/health;
    }
}

# HTTP 重定向到 HTTPS
server {
    listen 80;
    server_name example.com;
    return 301 https://$host$request_uri;
}

    二、🎯 面试考点：负载均衡¶

    面试官：WebSocket 连接如何做负载均衡？

    2.1 挑战¶

    WebSocket 是长连接，负载均衡有特殊问题：

    问题 1：连接粘性
- 客户端 A 连接到后端 1
- 后端 1 挂了 → 客户端重连可能到后端 2
- 后端 2 没有 A 的会话状态

问题 2：连接分布不均
- 先启动的后端可能积累更多连接
- 新连接不一定均匀分布

问题 3：跨服务器通信
- 用户 A 在后端 1，用户 B 在后端 2
- A 发消息给 B，需要跨服务器传递

    2.2 解决方案¶

    方案 1：ip_hash（会话亲和）

    upstream websocket_backend {
    ip_hash;  # 同一 IP 始终连到同一后端
    server 127.0.0.1:8080;
    server 127.0.0.1:8081;
}

    优点：简单，同一用户始终连到同一后端 缺点：后端挂了，用户必须重连

    方案 2：共享存储（Redis）

    客户端 → Nginx → 任意后端
                    ↓
              Redis（存储会话状态）

    # 后端从 Redis 读取会话状态
async def handler(websocket):
    session_id = websocket.headers.get("X-Session-ID")

    # 从 Redis 恢复会话
    session = await redis.get(f"session:{session_id}")
    if session:
        state = json.loads(session)
    else:
        state = {}

    # 处理消息...

    # 保存会话到 Redis
    await redis.set(f"session:{session_id}", json.dumps(state))

    方案 3：消息总线（Redis Pub/Sub）

    后端 1 ←→ Redis Pub/Sub ←→ 后端 2
  ↑                            ↑
用户 A                       用户 B

    import redis.asyncio as redis

# 每个后端都订阅同一个频道
async def handler(websocket):
    r = redis.Redis()
    pubsub = r.pubsub()
    await pubsub.subscribe("chat")

    async for message in pubsub.listen():
        if message["type"] == "message":
            # 广播给本后端的所有连接
            await local_broadcast(message["data"].decode())

    3.3 速率限制¶

    from collections import defaultdict
import time

# 每个 IP 的连接限制
ip_connections = defaultdict(int)
MAX_CONNECTIONS_PER_IP = 5

# 每个 IP 的消息速率限制
ip_message_count = defaultdict(list)
MAX_MESSAGES_PER_SECOND = 10

async def handler(websocket: WebSocket):
    client_ip = websocket.client.host

    # 检查连接数
    if ip_connections[client_ip] >= MAX_CONNECTIONS_PER_IP:
        await websocket.close(code=4002, reason="Too many connections")
        return

    ip_connections[client_ip] += 1

    try:
        await websocket.accept()

        async for message in websocket:
            # 检查消息速率
            now = time.time()
            ip_message_count[client_ip] = [
                t for t in ip_message_count[client_ip] if now - t < 1
            ]

            if len(ip_message_count[client_ip]) >= MAX_MESSAGES_PER_SECOND:
                await websocket.close(code=4004, reason="Rate limit exceeded")
                return

            ip_message_count[client_ip].append(now)

            # 处理消息...
    finally:
        ip_connections[client_ip] -= 1

    四、监控与指标¶

    4.1 🎯 面试考点：WebSocket 需要监控哪些指标？¶

    面试官：生产环境的 WebSocket 服务需要监控什么？

    指标 说明 告警阈值
    活跃连接数 当前 WebSocket 连接数量 > 80% 容量
    连接建立速率 每秒新建连接数 突增 3 倍
    连接关闭速率 每秒关闭连接数 突增 3 倍
    消息吞吐量 每秒收发消息数 接近上限
    消息延迟 从发送到接收的延迟 > 100ms
    错误率 连接失败/异常关闭比例 > 1%
    内存使用 每个连接的内存占用 持续增长
    重连率 客户端重连频率 > 10% / 分钟

    4.2 Prometheus 指标（Python）¶

    from prometheus_client import Counter, Gauge, Histogram, Summary

# 连接指标
ws_connections_active = Gauge(
    "ws_connections_active",
    "Number of active WebSocket connections",
    ["server_id"]
)

ws_connections_total = Counter(
    "ws_connections_total",
    "Total WebSocket connections",
    ["server_id", "status"]  # status: opened, closed, error
)

# 消息指标
ws_messages_total = Counter(
    "ws_messages_total",
    "Total WebSocket messages",
    ["server_id", "direction"]  # direction: sent, received
)

ws_message_size = Histogram(
    "ws_message_size_bytes",
    "WebSocket message size",
    buckets=(128, 256, 512, 1024, 4096, 16384, 65536)
)

# 延迟指标
ws_message_latency = Histogram(
    "ws_message_latency_seconds",
    "WebSocket message processing latency"
)

# 使用
async def handler(websocket):
    server_id = "server-1"
    ws_connections_active.labels(server_id).inc()
    ws_connections_total.labels(server_id, "opened").inc()

    try:
        async for message in websocket:
            ws_messages_total.labels(server_id, "received").inc()
            ws_message_size.observe(len(message))

            start = time.time()
            # 处理消息...
            ws_message_latency.observe(time.time() - start)

            ws_messages_total.labels(server_id, "sent").inc()
    except Exception:
        ws_connections_total.labels(server_id, "error").inc()
    finally:
        ws_connections_active.labels(server_id).dec()
        ws_connections_total.labels(server_id, "closed").inc()

    五、常见问题排查¶

    5.1 🎯 面试场景题：连接频繁断开¶

    面试官：用户反馈 WebSocket 连接经常断开，怎么排查？

    排查步骤：

    # 1. 检查 Nginx 超时配置
grep -r "proxy_read_timeout" /etc/nginx/
# 如果 < 60s，可能被 Nginx 断开

# 2. 检查防火墙/安全组
# 云服务器的安全组可能限制长连接

# 3. 检查心跳配置
# 如果没有心跳，中间设备会断开空闲连接

# 4. 检查服务器日志
tail -f /var/log/app/websocket.log | grep "close"
# 看关闭原因（code 和 reason）

# 5. 检查客户端日志
# 看 onclose 的 code
# 1006 = 异常关闭（通常是网络问题）
# 1001 = 端点离开（浏览器关闭）

    常见原因及解决：

    原因 现象 解决
    Nginx 超时 60s 后断开 增大 proxy_read_timeout
    防火墙断开 不定时断开 实现心跳保活
    NAT 超时 几分钟到几小时断开 心跳 + 自动重连
    服务器重启 所有连接同时断开 优雅停机 + 客户端重连
    客户端休眠 移动端切后台断开 自动重连

    5.2 内存泄漏¶

    # 问题：连接断开后资源未释放
connections = set()

async def handler(websocket):
    connections.add(websocket)
    # ❌ 忘记在 finally 中移除

# 修复
async def handler(websocket):
    connections.add(websocket)
    try:
        async for message in websocket:
            pass
    finally:
        connections.discard(websocket)  # ✅ 确保移除

    5.3 消息积压¶

    # 问题：客户端处理慢，服务端发送缓冲区堆积
async def broadcast(message, clients):
    for client in clients:
        await client.send(message)  # ❌ 一个慢客户端阻塞所有人

# 修复：并发发送 + 超时
async def broadcast(message, clients):
    await asyncio.gather(
        *[asyncio.wait_for(c.send(message), timeout=5) for c in clients],
        return_exceptions=True
    )

    六、🎯 面试场景题汇总¶

    6.1 设计一个实时聊天系统¶

    面试官：设计一个支持 10 万用户同时在线的聊天系统

    架构设计：

1. 接入层
   - Nginx 集群（3 台），ip_hash 负载均衡
   - 每台支持 3-5 万连接

2. 业务层
   - WebSocket 服务器集群（10 台）
   - 每台支持 1 万连接
   - 使用 Redis Pub/Sub 跨服务器广播

3. 存储层
   - Redis：在线状态、会话缓存
   - MySQL/MongoDB：历史消息持久化

4. 消息流
   用户 A (Server 1) → Redis Pub/Sub → Server 2 → 用户 B

5. 关键设计
   - 消息 ID：雪花算法，全局唯一
   - 消息确认：ACK 机制保证不丢失
   - 离线消息：登录后从数据库拉取
   - 消息漫游：多端同步

    6.2 WebSocket 和 HTTP 能共存吗？¶

    面试官：一个项目能同时用 WebSocket 和 HTTP 吗？

    可以，而且推荐：

    HTTP 用于：
- 用户登录/注册
- 获取历史数据
- 文件上传/下载
- REST API

WebSocket 用于：
- 实时消息推送
- 在线状态同步
- 实时通知

典型架构：
1. 用户通过 HTTP 登录，获取 Token
2. 用 Token 建立 WebSocket 连接
3. 历史数据通过 HTTP 获取
4. 新消息通过 WebSocket 推送

    6.3 如何保证消息顺序？¶

    面试官：WebSocket 如何保证消息顺序？

    WebSocket 基于 TCP，TCP 本身保证顺序。但应用层需要注意：

    # 问题：并发处理可能导致乱序
async def handler(websocket):
    async for message in websocket:
        # ❌ 每个消息开一个协程处理，可能乱序
        asyncio.create_task(process(message))

# 修复：顺序处理
async def handler(websocket):
    async for message in websocket:
        # ✅ 按顺序处理
        await process(message)

# 或者：给消息加序号
async def handler(websocket):
    seq = 0
    async for message in websocket:
        data = json.loads(message)
        if data["seq"] != seq + 1:
            # 检测到乱序，处理...
            pass
        seq = data["seq"]

    7.2 Nginx¶

    • proxy_http_version 1.1
    • proxy_set_header Upgrade $http_upgrade
    • proxy_set_header Connection $connection_upgrade
    • 设置合理的 proxy_read_timeout
    • 启用 keepalive 长连接
    • 配置 limit_conn 限制连接数

    7.3 架构¶

    • Redis Pub/Sub 实现跨服务器广播
    • 共享存储（Redis）管理会话状态
    • 水平扩展时保持无状态
    • 监控关键指标（连接数、消息量、延迟）
    • 配置告警（连接数突增、错误率上升）
    • 优雅停机（通知客户端重连）

    7.4 安全¶

    • 使用 WSS（WebSocket Secure）
    • 验证 Origin 头
    • 认证鉴权（Token、Cookie）
    • 速率限制（连接数、消息频率）
    • 输入验证（消息大小、格式）

    八、小结¶

    主题 关键点
    Nginx 配置 Upgrade 头 + proxy_read_timeout
    负载均衡 ip_hash + Redis 共享状态
    水平扩展 Redis Pub/Sub 跨服务器广播
    监控 连接数、消息量、延迟、错误率
    排错 检查超时配置、心跳、日志
    安全 WSS + Origin + 认证 + 限流
