    第十二章：自定义与扩展¶

    create_deep_agent 参数全景 | 默认中间件栈 | 系统提示组装 | 自定义 middleware 依据官方文档 https://docs.langchain.com/oss/python/deepagents/customization 整理

    12.1 create_deep_agent 参数全景¶

    create_deep_agent 是所有定制的入口：

    agent = create_deep_agent(
    model=...,              # provider:model 字符串或模型实例（第 3 章）
    tools=[...],            # 自定义工具 / MCP 工具（第 4 章）
    system_prompt="...",    # 你的指令
    backend=...,            # 文件系统后端（第 5 章）
    permissions=[...],      # 文件系统权限（第 6 章）
    skills=[...],           # 技能路径（第 7 章）
    memory=[...],           # 记忆文件路径（第 8 章）
    subagents=[...],        # 子代理（第 10 章）
    interrupt_on={...},     # HITL 配置（第 11 章）
    middleware=[...],       # 追加/覆盖中间件（本章）
    checkpointer=...,       # 状态检查点（HITL/多轮必需）
    store=...,              # LangGraph Store（StoreBackend 用）
    context_schema=...,     # 运行时 context 类型
    state_schema=...,       # 自定义状态 schema
)

    12.2 系统提示组装¶

    系统提示不只是一个字符串——它是分层组装的：

    最终系统提示 =
    [caller 的 system_prompt]          ← 永远在最前面
  + [base 基础提示]                     ← Deep Agents 默认（v0.7 起默认为空）
  + [记忆内容 / 技能元数据 / 工具提示]    ← 各 middleware 注入
  + [profile 的 system_prompt_suffix]  ← 永远在最后面

    规则：

    • caller 的 system_prompt= 永远在最前，system_prompt_suffix 永远在最后——与选择哪个模型无关
    • 同样的叠加规则适用于子代理：每个子代理按自己的模型重新解析 profile
    • harness profile 的 base_system_prompt 可以替换基础提示

    12.3 默认中间件栈（Deep Agents stack）¶

    create_deep_agent 按固定顺序构建 middleware。Bare stack（只传 model）：

    1. FilesystemMiddleware —— 文件操作
    2. SubAgentMiddleware —— GP（general-purpose）子代理，默认自动添加
    3. SummarizationMiddleware —— 上下文摘要
    4. PatchToolCallsMiddleware —— 修复中断/畸形工具调用后的消息历史
    5. Prompt caching 中间件（总是注册，不支持的模型上 no-op）
    6. Harness profile 的 extras + excluded-tool 过滤（如果 profile 定义了）

    Full stack（完整组装顺序，从前到后）：

    # 中间件 出现条件
    1 SkillsMiddleware 传了 skills。注入在 filesystem 之前（技能元数据先于文件工具可用）
    2 FilesystemMiddleware 总是。传了 permissions 时权限执行也在这里
    3 SubAgentMiddleware 至少一个同步子代理存在时
    4 SummarizationMiddleware 总是
    5 PatchToolCallsMiddleware 总是
    6 AsyncSubAgentMiddleware 配置了异步子代理时
    7 你的 middleware= 参数 合并规则见下
    8 Harness profile extras profile 贡献的 Provider 特定中间件
    9 Excluded-tool 过滤 profile 列了 excluded_tools 时
    10 Prompt caching（Anthropic + Bedrock） 总是注册；在 Patch 和你的 middleware 之后，保证缓存前缀与实际发送内容一致；各自在不支持的模型上 no-op
    11 MemoryMiddleware 传了 memory。故意放在 caching 之后——记忆更新尽量不破坏缓存前缀
    12 HumanInTheLoopMiddleware 传了 interrupt_on

    同步子代理栈¶

    GP 子代理和声明式子代理用相似的栈（filesystem、summarization、Patch、profile extras、缓存、可选权限），两个差异：

    • 子代理内部 skills 在 PatchToolCallsMiddleware 之后（主 Agent 是 skills 在 filesystem 之前）
    • 子代理图内没有 SubAgentMiddleware（只有父 Agent 暴露 task 工具）

    子代理设了 interrupt_on 时转发给子代理的 create_agent。

    12.4 传入自定义 middleware¶

    传 middleware= 的合并规则（v0.7 语义）：

    • 实例的 .name 匹配内置中间件 → 原位替换该默认实例（不报重复错误）
    • 不匹配 → 插入到 PatchToolCallsMiddleware 之后、profile extras 之前

    原位替换的用途：传自己的 SummarizationMiddleware(...) 改触发阈值/摘要模型；传 FilesystemMiddleware(tools=[...]) 限制文件工具子集。

    from langchain.agents.middleware import wrap_tool_call
from langchain.tools import tool
from deepagents import create_deep_agent


@tool
def get_weather(city: str) -> str:
    """Get the weather in a city."""
    return f"The weather in {city} is sunny."


call_count = [0]


@wrap_tool_call
def log_tool_calls(request, handler):
    """Intercept and log every tool call - demonstrates cross-cutting concern."""
    call_count[0] += 1
    tool_name = request.name if hasattr(request, "name") else str(request)
    print(f"[Middleware] Tool call #{call_count[0]}: {tool_name}")

    # Execute the tool call
    result = handler(request)

    print(f"[Middleware] Tool call #{call_count[0]} completed")
    return result


agent = create_deep_agent(
    model="anthropic:claude-sonnet-4-6",
    tools=[get_weather],
    middleware=[log_tool_calls],
)

    middleware 钩子类型（来自 LangChain）：wrap_model_call（包装模型调用，第 3 章的运行时切模型就是它）、wrap_tool_call（包装工具调用）、以及修改请求/状态的各类 hook。

    可用的预构建 middleware¶

    • LangChain 内置：重试、fallback、PII 检测、TodoList（任务规划）等
    • deepagents 自带：create_summarization_tool_middleware（按需压缩工具）、create_summarization_middleware、RubricMiddleware（第 11 章）、CodeInterpreterMiddleware（第 6 章）
    • Provider 特定：integrations/middleware 页面（各家缓存、特定优化）

    12.5 自定义状态 schema¶

    默认状态包含 messages、files、todos（opt-in）等通道。需要 Agent 携带额外结构化状态（如当前用户 ID、任务元数据）时传 state_schema；需要向 Agent 传运行时配置（如用户选择的模型、组织 ID）时用 context_schema + context=Context(...) 调用。

    12.6 结构化输出¶

    主 Agent 和子代理都支持结构化输出（response_format）：Pydantic 模型、ToolStrategy(...)、ProviderStrategy(...) 或裸 schema。子代理设了之后，task 返回 JSON 给父级。

    12.7 定制决策树¶

    我想... 用什么
    改 Agent 指令 system_prompt
    按模型调整 harness 行为 harness profile（第 11 章）
    加横切逻辑（日志/限流/审计） 自定义 middleware（wrap_tool_call / wrap_model_call）
    改摘要阈值 传自己的 SummarizationMiddleware（原位替换）
    限制文件工具 FilesystemMiddleware(tools=[...]) 或 profile excluded_tools
    去掉子代理 profile 禁用 GP + 不传同步子代理
    加自定义状态 state_schema / context_schema
    完全控制流程 放弃 harness，用 LangChain create_agent 或裸 LangGraph

    12.8 本章小结¶

    关键要点¶

    1. 系统提示分层组装：caller 在最前、suffix 在最后、中间是各 middleware 注入
    2. 默认栈 12 层，顺序固定；三个必需中间件（Filesystem/SubAgent/权限）不可移除
    3. v0.7 起同名 middleware 原位替换而非报错——改默认行为的官方姿势
    4. wrap_tool_call/wrap_model_call 是扩展横切能力的主要手段
