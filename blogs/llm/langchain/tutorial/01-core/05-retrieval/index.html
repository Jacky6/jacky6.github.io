    第 26 章：检索与 RAG - Retrieval¶

    本章内容：检索基础、知识库构建、三种 RAG 架构（2-step / Agentic / Hybrid）

    官方文档：https://docs.langchain.com/oss/python/langchain/retrieval

    📚 本章目标¶

    学完本章后，你将掌握：

    • ✅ 理解 LLM 为什么需要检索（有限上下文 + 静态知识）
    • ✅ 掌握检索管线的构建块（loaders / splitters / embeddings / vector stores / retrievers）
    • ✅ 区分三种 RAG 架构并选型
    • ✅ 用 create_agent + 检索工具实现 Agentic RAG
    • ✅ 了解 Hybrid RAG 的查询增强/检索校验/答案校验

    26.1 为什么需要检索？¶

    LLM 很强大，但有两个关键限制：

    • 有限上下文（Finite context）：无法一次吞下整个语料库
    • 静态知识（Static knowledge）：训练数据冻结在某个时间点

    检索（Retrieval）通过在查询时拉取相关外部知识来解决这两个问题。这就是 RAG（Retrieval-Augmented Generation，检索增强生成）的基础——用上下文特定的信息增强 LLM 的回答。

    从检索到 RAG¶

    检索让 LLM 在运行时访问相关上下文。但多数真实应用更进一步：把检索与生成结合，产出有依据、有上下文感知的回答。这就是 RAG 的核心思想——检索管线成为更广阔系统的基础，把搜索和生成结合起来。

    💡 已有知识库不用重建：如果你已经有知识库（SQL 数据库、文档库、CRM、内部文档系统），可以直接把它作为工具连给 Agent（Agentic RAG），或查询后把检索内容作为上下文喂给 LLM（2-step RAG）。

    26.2 检索管线的构建块¶

    典型检索工作流：

    Sources（Google Drive, Slack, Notion...）
    ↓ Document Loaders（文档加载器）
Documents（文档）
    ↓ Text Splitters（文本切分器）
Chunks（分块）
    ↓ Embedding Models（嵌入模型）
Vector Store（向量库）
    ↑ Query embedding（查询嵌入）
User Query（用户查询）
    ↓ Retriever（检索器）
LLM uses retrieved info（LLM 使用检索信息）
    ↓
Answer（答案）

    每个组件都是模块化的：可以替换 loaders、splitters、embeddings、vector stores 而不用重写应用逻辑。

    构建块 作用
    Document loaders 从外部源（Google Drive、Slack、Notion 等）摄入数据，返回标准化的 Document 对象
    Text splitters 把大文档切成小块，便于单独检索、适配模型上下文窗口
    Embedding models 把文本转成数字向量，让语义相近的文本在向量空间中距离更近
    Vector stores 存储和搜索 embeddings 的专用数据库
    Retrievers 给定非结构化查询、返回文档的接口

    官方教程：Semantic search——用自己的数据构建可搜索知识库（document loaders + embeddings + vector stores），并在其上跑最小化的"检索→生成" RAG 工作流。

    26.3 三种 RAG 架构¶

    RAG 可以有多种实现方式，取决于系统需求：

    架构 说明 控制力 灵活性 延迟 典型用例
    2-Step RAG 检索总在生成前执行，简单可预测 高 低 ⚡ 快 FAQ、文档机器人
    Agentic RAG LLM 驱动的 Agent 在推理中决定何时、如何检索 低 高 ⏳ 不定 带多工具的研究助理
    Hybrid 结合两者 + 校验步骤 中 中 ⏳ 不定 带质量校验的领域问答

    📌 延迟说明：2-Step RAG 的延迟通常更可预测，因为 LLM 调用次数已知且有上限（假设推理时间是主导因素）。但真实延迟还受检索步骤影响——API 响应时间、网络延迟、数据库查询，这些因工具和基础设施而异。

    26.4 2-Step RAG（两步 RAG）¶

    检索步骤总在生成步骤之前执行。这种架构直接、可预测，适合"检索相关文档是生成回答的明确前提"的应用。

    用户问题 → 检索相关文档 → 生成答案 → 返回用户

    特点：

    • 固定管线：检索 → 生成，顺序不变
    • 每次请求恰好一次检索 + 一次生成
    • 延迟可预测、易于监控和评测

    适合：FAQ 机器人、文档问答、检索是明确前置条件的场景。

    官方教程：

    • Semantic search：构建可搜索知识库 + 最小化"检索→生成"工作流
    • Evaluate a RAG application：用 LangSmith 测答案正确性、相关性、有据性（groundedness）、检索质量

    26.5 Agentic RAG（智能体 RAG）¶

    Agentic RAG 结合 RAG 和智能体推理。Agent（由 LLM 驱动）逐步推理，在交互过程中决定何时、如何检索信息——而不是回答前先检索。

    💡 Agent 启用 RAG 行为唯一需要的，是访问一个或多个能获取外部知识的工具——文档加载器、Web API、数据库查询都行。

    用户输入 → Agent(LLM) ──需要外部信息?──是──→ 用工具搜索 ──足够回答?──否──→ 回到 Agent
                          │                              │是
                          否                             ↓
                          └────────────────────→ 生成最终答案 → 返回用户

    最小实现¶

    import requests
from langchain.tools import tool
from langchain.chat_models import init_chat_model
from langchain.agents import create_agent


@tool
def fetch_url(url: str) -> str:
    """Fetch text content from a URL"""
    response = requests.get(url, timeout=10.0)
    response.raise_for_status()
    return response.text

system_prompt = """\
Use fetch_url when you need to fetch information from a web-page; quote relevant snippets.
"""

agent = create_agent(
    model="anthropic:claude-sonnet-4-6",
    tools=[fetch_url],  # A tool for retrieval
    system_prompt=system_prompt,
)

    要点：检索就是一个普通工具，Agent 自主决定何时调用、调几次、要不要补充检索。

    扩展示例：基于 llms.txt 的文档问答¶

    这个例子实现一个 Agentic RAG 系统帮用户查询 LangGraph 文档。Agent 先加载 llms.txt（列出可用文档 URL），然后根据用户问题动态用 fetch_documentation 工具检索处理相关内容。

    import requests
from langchain.agents import create_agent
from langchain.chat_models import init_chat_model
from langchain.messages import HumanMessage
from langchain.tools import tool
from markdownify import markdownify


ALLOWED_DOMAINS = ["https://langchain-ai.github.io/"]
LLMS_TXT = 'https://langchain-ai.github.io/langgraph/llms.txt'


@tool
def fetch_documentation(url: str) -> str:
    """Fetch and convert documentation from a URL"""
    if not any(url.startswith(domain) for domain in ALLOWED_DOMAINS):
        return (
            "Error: URL not allowed. "
            f"Must start with one of: {', '.join(ALLOWED_DOMAINS)}"
        )
    response = requests.get(url, timeout=10.0)
    response.raise_for_status()
    return markdownify(response.text)


# Fetch llms.txt ahead of time (no LLM request needed)
llms_txt_content = requests.get(LLMS_TXT).text

system_prompt = f"""
You are an expert Python developer and technical assistant.
Your primary role is to help users with questions about LangGraph and related tools.

Instructions:

1. If a user asks a question you're unsure about—or one that likely involves API usage,
   behavior, or configuration—you MUST use the `fetch_documentation` tool to consult the relevant docs.
2. When citing documentation, summarize clearly and include relevant context from the content.
3. Do not use any URLs outside of the allowed domain.
4. If a documentation fetch fails, tell the user and proceed with your best expert understanding.

You can access official documentation from the following approved sources:

{llms_txt_content}

You MUST consult the documentation to get up to date documentation
before answering a user's question about LangGraph.

Your answers should be clear, concise, and technically accurate.
"""

model = init_chat_model("anthropic:claude-sonnet-4-6", max_tokens=32_000)

agent = create_agent(
    model=model,
    tools=[fetch_documentation],
    system_prompt=system_prompt,
    name="Agentic RAG",
)

response = agent.invoke({
    'messages': [
        HumanMessage(content=(
            "Write a short example of a langgraph agent using the "
            "prebuilt create react agent. the agent should be able "
            "to look up stock pricing information."
        ))
    ]
})

print(response['messages'][-1].content)

    这个模式的关键设计：

    • 白名单域名：ALLOWED_DOMAINS 防止 Agent 被诱导抓取任意 URL（安全防护）
    • llms.txt 预加载进系统提示：Agent 启动就知道有哪些文档可查，不用先花一次调用去发现
    • markdownify 转换：HTML → Markdown，更适合 LLM 阅读、更省 token
    • 明确的检索指令：系统提示要求"不确定就必须查文档"

    📌 Deep Agents + RAG：官方还有 RAG with Deep Agents 教程——构建文档问答 Agent，查询时检索相关分块、卸载到文件系统、委派分析给子代理。见 deep-agents 教程第 9 章（上下文工程）。

    26.6 Hybrid RAG（混合 RAG）¶

    Hybrid RAG 结合 2-Step 和 Agentic RAG 的特点，引入中间步骤：查询预处理、检索校验、生成后检查。比固定管线更灵活，同时保留对执行的一定控制。

    典型组件：

    • 查询增强（Query enhancement）：修改输入问题以提高检索质量——重写模糊查询、生成多个变体、用额外上下文扩展查询
    • 检索校验（Retrieval validation）：评估检索到的文档是否相关、充分。不够就优化查询重新检索
    • 答案校验（Answer validation）：检查生成答案的准确性、完整性、与源内容的一致性。需要就重新生成或修订

    架构支持这些步骤间的多次迭代：

    用户问题 → 查询增强 → 检索文档 ──信息足够?──否──→ 优化查询 ──→ 重新检索
                          │是
                          ↓
                      生成答案 ──答案质量OK?──否──→ 换方法? ──是──→ 优化查询
                          │是                        │否
                          ↓                          ↓
                      返回最佳答案 ←──────────────────┘
                          ↓
                      返回用户

    适合：

    • 查询模糊或信息不全的应用
    • 需要校验或质量控制步骤的系统
    • 涉及多来源或迭代优化的工作流

    官方教程：Agentic RAG with Self-Correction——结合智能体推理、检索、自我纠错的 Hybrid RAG 示例。

    26.7 RAG 选型速查¶

    我的场景 选
    检索是明确前置条件、要可预测延迟 2-Step RAG
    Agent 需要自主决定查什么、查几次、多工具协作 Agentic RAG
    查询模糊、需要质量校验、多来源迭代 Hybrid RAG
    快速原型、验证检索质量 2-Step RAG 起步，再演进
    长文档/大量分块 + 需要上下文管理 Agentic RAG + Deep Agents（文件系统卸载 + 子代理）

    演进路径：多数项目从 2-Step RAG 起步（简单、可评测），发现检索时机/质量需要动态决策时升级到 Agentic RAG，需要质量兜底时加校验环节变 Hybrid。

    📝 本章小结¶

    关键要点¶

    1. 检索解决 LLM 两大限制：有限上下文 + 静态知识；RAG = 检索 + 生成结合
    2. 检索管线五构建块：document loaders → text splitters → embeddings → vector stores → retrievers，全部模块化可替换
    3. 三种 RAG 架构：2-Step（检索总在生成前，可预测）、Agentic（Agent 决定何时如何检索）、Hybrid（查询增强 + 检索校验 + 答案校验）
    4. Agentic RAG 的本质：检索就是一个工具，Agent 自主调用；配合 llms.txt + 白名单 + markdownify 是文档问答的成熟模式
    5. 选型看：检索是否是明确前置条件、是否需要动态决策、是否需要质量校验
    6. 与记忆（第 25 章）的区别：记忆存"关于用户/交互的持久事实"，检索取"外部知识库的内容"
