    第 14 章：多代理系统 - Multi-Agent Systems¶

    本章内容：官方 5 大多代理模式——Subagents / Handoffs / Skills / Router / Custom Workflow

    官方文档：https://docs.langchain.com/oss/python/langchain/multi-agent/index 对齐版本：langchain v1.3（2026-08 重写，替代旧版"StateGraph + name 参数"内容）

    📚 本章目标¶

    学完本章后，你将掌握：

    • ✅ 理解何时需要多代理（以及何时不需要）
    • ✅ 掌握官方 5 种多代理模式及其适用场景
    • ✅ 用 create_agent + @tool 包装实现 Subagents 模式
    • ✅ 用 Command + middleware 实现 Handoffs 模式
    • ✅ 用 Command/Send 实现 Router 模式
    • ✅ 按需求矩阵和性能特征选择正确的模式

    14.1 多代理系统概述¶

    多代理系统协调多个专业化组件处理复杂工作流。但不是每个复杂任务都需要多代理——一个配有合适工具（有时是动态工具）和提示的单 Agent 往往能达到同样效果。

    💡 想要内置的多代理支持（子代理、技能、规划、虚拟文件系统、上下文管理），直接用 Deep Agents——它是构建在 LangChain 之上的更高层 harness。

    为什么需要多代理？¶

    开发者说"我需要多代理"时，通常想要以下一种或多种能力：

    能力 说明
    🧠 上下文管理 提供专业知识但不撑爆上下文窗口。如果上下文无限、延迟为零，把所有知识塞进一个提示就行——现实不行，所以需要模式来按需呈现相关信息
    👥 分布式开发 不同团队独立开发维护各自能力，以清晰边界组合成更大系统
    🌿 并行化 为子任务派出专门的 worker 并发执行，加速出结果

    多代理模式特别有价值的场景：

    • 单 Agent 工具太多，开始乱选工具
    • 任务需要带大量上下文的专业知识（长提示 + 领域专用工具）
    • 需要强制顺序约束（满足前置条件才解锁后续能力）

    📌 多代理设计的核心是上下文工程（第 20 章）——决定每个 Agent 看到什么信息。系统质量取决于每个 Agent 是否拿到了完成任务所需的正确数据。

    官方 5 种模式总览¶

    模式 工作方式
    Subagents（子代理） 主 Agent 把子代理当工具调用。所有路由经过主 Agent，由它决定何时、如何调用每个子代理
    Handoffs（交接） 行为随状态动态变化。工具调用更新状态变量，触发路由切换或配置变更（换 Agent，或调整当前 Agent 的工具/提示）
    Skills（技能） 按需加载的专业提示和知识。单 Agent 保持控制，需要时才加载技能上下文（详见第 19 章）
    Router（路由） 路由步骤对输入分类，分发给一个或多个专业 Agent，结果综合成统一回复
    Custom workflow（自定义工作流） 用 LangGraph 构建定制执行流，混合确定性逻辑和智能体行为，其他模式可作为节点嵌入

    14.2 模式选择指南¶

    需求矩阵（官方）¶

    模式 分布式开发 并行化 多跳 与用户直接交互
    Subagents ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐
    Handoffs - - ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐
    Skills ⭐⭐⭐⭐⭐ ⭐⭐⭐ ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐
    Router ⭐⭐⭐ ⭐⭐⭐⭐⭐ - ⭐⭐⭐
    • 分布式开发：不同团队能否独立维护组件？
    • 并行化：多个 Agent 能否并发执行？
    • 多跳：能否串行调用多个子代理？
    • 与用户直接交互：子代理能否直接和用户对话？

    性能对比（官方数据）¶

    以"买杯咖啡"一次性请求为例（有专门的咖啡 Agent/技能可调 buy_coffee 工具）：

    模式 模型调用次数 说明
    Subagents 4 主 Agent 决策 → 子代理执行 → 子代理总结 → 主 Agent 综合
    Handoffs 3 ✅ 少一层综合
    Skills 3 ✅ 单 Agent 加载技能后直接执行
    Router 3 ✅ 分类 → 专业 Agent → 综合

    关键指标：

    • 模型调用次数：LLM 调用越多 = 延迟越高（尤其串行时）+ API 成本越高
    • 处理 token 数：所有调用的上下文窗口总消耗，越多越贵

    💡 模式可以混合！比如 Subagents 架构里可以调用 Router Agent 或自定义工作流；子代理还能用 Skills 模式按需加载上下文。

    14.3 Subagents 模式（子代理）¶

    架构：中心主 Agent（supervisor，主管）把子代理当工具调用来协调它们。主 Agent 决定调用哪个子代理、传什么输入、如何组合结果。

    子代理是无状态的——不记得过去的交互，所有会话记忆由主 Agent 维护。这提供了上下文隔离：每次子代理调用都在干净的上下文窗口中工作，防止主对话上下文膨胀。

    用户 → 主 Agent ─┬→ 子代理 A ─┐
                 ├→ 子代理 B ─┼→ 主 Agent → 回复用户
                 └→ 子代理 C ─┘

    关键特征¶

    • 集中控制：所有路由经过主 Agent
    • 无直接用户交互：子代理把结果返回主 Agent 而非用户（不过可以在子代理内用 interrupts 暂停收集用户输入）
    • 子代理即工具：通过工具调用子代理
    • 并行执行：主 Agent 可以一轮调用多个子代理

    📌 Supervisor vs Router：supervisor（本模式）是完整 Agent，维护对话上下文、跨多轮动态决定调用哪些子代理；router 通常是单次分类步骤，不维护持续对话状态。

    适用场景¶

    有多个不同领域（日历、邮件、CRM、数据库）、子代理不需要直接和用户对话、想要集中式工作流控制时用本模式。只有几个工具的简单场景用单 Agent 即可。

    基本实现¶

    核心机制：把子代理包装成主 Agent 可调用的工具：

    from langchain.tools import tool
from langchain.agents import create_agent

# Create a subagent
subagent = create_agent(model="openai:gpt-5.5", tools=[...])

# Wrap it as a tool
@tool("research", description="Research a topic and return findings")
def call_research_agent(query: str):
    result = subagent.invoke({"messages": [{"role": "user", "content": query}]})
    return result["messages"][-1].content

# Main agent with subagent as a tool
main_agent = create_agent(model="openai:gpt-5.5", tools=[call_research_agent])

    设计决策¶

    决策 选项
    同步 vs 异步 同步（阻塞）vs 异步（后台）
    工具模式 每个 Agent 一个工具 vs 单一分发工具
    子代理规格 系统提示列举 vs 枚举约束 vs 工具式发现
    子代理输入 只传查询 vs 传完整上下文
    子代理输出 返回子代理结果 vs 返回完整对话历史

    同步 vs 异步¶

    模式 主 Agent 行为 适合 权衡
    同步 等子代理完成 主 Agent 需要结果才能继续 简单，但阻塞对话
    异步 子代理后台跑，主 Agent 继续 独立任务、用户不该等待 响应快，但更复杂

    ⚠️ 这里的"异步"不是 Python 的 async/await，而是主 Agent 启动后台任务（通常在独立进程/服务）后不阻塞继续。

    异步三工具模式：

    1. 启动任务：启动后台任务，返回 job ID
    2. 查状态：返回当前状态（pending/running/completed/failed）
    3. 取结果：获取完成的结果

    工具模式一：每个 Agent 一个工具¶

    每个子代理包装成独立工具，可对每个子代理的输入输出精细控制：

    from langchain.tools import tool
from langchain.agents import create_agent

# Create a sub-agent
subagent = create_agent(model="...", tools=[...])

# Wrap it as a tool
@tool("subagent_name", description="subagent_description")
def call_subagent(query: str):
    result = subagent.invoke({"messages": [{"role": "user", "content": query}]})
    return result["messages"][-1].content

# Main agent with subagent as a tool
main_agent = create_agent(model="...", tools=[call_subagent])

    工具模式二：单一分发工具（task 模式）¶

    用一个参数化工具调用临时子代理。约定优于配置：任务描述作为 human message 传给子代理，子代理的最后一条消息作为工具结果返回。

    适合：多团队分布式开发 Agent、复杂任务隔离到独立上下文、可扩展地添加新 Agent 而不改协调者。

    from langchain.tools import tool
from langchain.agents import create_agent

# Sub-agents developed by different teams
research_agent = create_agent(
    model="openai:gpt-5.5",
    prompt="You are a research specialist..."
)

writer_agent = create_agent(
    model="openai:gpt-5.5",
    prompt="You are a writing specialist..."
)

# Registry of available sub-agents
SUBAGENTS = {
    "research": research_agent,
    "writer": writer_agent,
}

@tool
def task(agent_name: str, description: str) -> str:
    """Launch an ephemeral subagent for a task.

    Available agents:
    - research: Research and fact-finding
    - writer: Content creation and editing
    """
    agent = SUBAGENTS[agent_name]
    result = agent.invoke({
        "messages": [
            {"role": "user", "content": description}
        ]
    })
    return result["messages"][-1].content

# Main coordinator agent
main_agent = create_agent(
    model="openai:gpt-5.5",
    tools=[task],
    system_prompt=(
        "You coordinate specialized sub-agents. "
        "Available: research (fact-finding), "
        "writer (content creation). "
        "Use the task tool to delegate work."
    ),
)

    💡 有意思的是：子代理可以和主 Agent 能力完全相同。这时调用子代理的真正目的是上下文隔离——让复杂多步任务在隔离的上下文窗口里跑，不膨胀主 Agent 的对话历史。子代理自主完成工作，只返回简洁摘要。这就是 Deep Agents task 工具的设计思想。

    子代理规格：让主 Agent 知道有哪些子代理¶

    单一分发工具模式下，必须告诉主 Agent 有哪些子代理可调用：

    方法 适合 权衡
    系统提示列举 小而静态的 Agent 列表（<10 个） 简单，但 Agent 变化要改提示
    枚举约束 小而静态的 Agent 列表（<10 个） 类型安全、显式，但 Agent 变化要改代码
    工具式发现 大型或动态 Agent 注册表 灵活可扩展，但增加复杂度

    枚举约束示例（给 agent_name 参数加 Literal 类型）：

    from typing import Literal

@tool
def task(agent_name: Literal["research", "writer"], description: str) -> str:
    """Launch an ephemeral subagent for a task."""
    agent = SUBAGENTS[agent_name]
    result = agent.invoke({"messages": [{"role": "user", "content": description}]})
    return result["messages"][-1].content

    上下文工程三要素¶

    类别 目的 影响
    子代理规格（名称+描述） 确保子代理在该被调用时被调用 主 Agent 路由决策
    子代理输入 确保子代理用优化的上下文执行好 子代理性能
    子代理输出 确保 supervisor 能基于结果行动 主 Agent 性能
    • 名称：清晰、动作导向（research_agent、code_reviewer）
    • 描述：具体说明处理什么任务、何时使用——这是提示工程杠杆，认真写

    14.4 Handoffs 模式（交接）¶

    架构：行为随状态动态变化。核心机制：工具更新一个跨轮次持久的状态变量（如 current_step 或 active_agent），系统读取该变量调整行为——应用不同配置（系统提示、工具）或路由到不同 Agent。

    📌 "handoffs" 一词由 OpenAI 提出：用工具调用（如 transfer_to_sales_agent）在 Agent 或状态间转移控制权。

    典型场景（客服流程）：

    用户："我的手机坏了"
  → 步骤 1: 收集保修状态（工具: record_warranty_status）
Agent："您的设备还在保修期内吗？"
用户："还在保修期"
  → 工具更新状态 → 切换到步骤 2: 分类问题（工具: record_issue_type）
Agent："能描述一下问题吗？"
用户："屏幕碎了"
  → 工具更新状态 → 切换到步骤 3: 提供解决方案（工具: provide_solution, escalate_to_human）
Agent："这是保修维修流程..."

    关键特征¶

    • 状态驱动行为：行为随状态变量变化
    • 工具触发转换：工具更新状态变量实现状态迁移
    • 直接用户交互：每个状态的配置直接处理用户消息
    • 状态持久：状态跨对话轮次存活

    适用场景¶

    需要强制顺序约束（满足前置条件才解锁能力）、Agent 要在不同状态下直接和用户对话、构建多阶段对话流时。客服场景特别有价值——比如必须先收集保修 ID 才能处理退款。

    核心机制：返回 Command 的工具¶

    from langchain.tools import tool
from langchain.messages import ToolMessage
from langgraph.types import Command

@tool
def transfer_to_specialist(runtime) -> Command:
    """Transfer to the specialist agent."""
    return Command(
        update={
            "messages": [
                ToolMessage(
                    content="Transferred to specialist",
                    tool_call_id=runtime.tool_call_id
                )
            ],
            "current_step": "specialist"  # Triggers behavior change
        }
    )

    📌 为什么要包含 ToolMessage？ LLM 调用工具后期待一个响应。带匹配 tool_call_id 的 ToolMessage 完成这个请求-响应循环——没有它对话历史会畸形。handoff 工具更新 messages 时必须这样做。

    实现方式一：单 Agent + middleware（推荐）¶

    单 Agent 基于状态改变行为。middleware 拦截每次模型调用，动态调整系统提示和可用工具：

    from langchain.agents import AgentState, create_agent
from langchain.agents.middleware import wrap_model_call, ModelRequest, ModelResponse
from langchain.tools import tool, ToolRuntime
from langchain.messages import ToolMessage
from langgraph.types import Command
from langgraph.checkpoint.memory import InMemorySaver
from typing import Callable

# 1. Define state with current_step tracker
class SupportState(AgentState):
    """Track which step is currently active."""
    current_step: str = "triage"
    warranty_status: str | None = None

# 2. Tools update current_step via Command
@tool
def record_warranty_status(
    status: str,
    runtime: ToolRuntime[None, SupportState]
) -> Command:
    """Record warranty status and transition to next step."""
    return Command(update={
        "messages": [
            ToolMessage(
                content=f"Warranty status recorded: {status}",
                tool_call_id=runtime.tool_call_id
            )
        ],
        "warranty_status": status,
        "current_step": "specialist"    # Transition to next step
    })

# 3. Middleware applies dynamic configuration based on current_step
@wrap_model_call
def apply_step_config(
    request: ModelRequest,
    handler: Callable[[ModelRequest], ModelResponse]
) -> ModelResponse:
    """Configure agent behavior based on current_step."""
    step = request.state.get("current_step", "triage")

    configs = {
        "triage": {
            "prompt": "Collect warranty information...",
            "tools": [record_warranty_status]
        },
        "specialist": {
            "prompt": "Provide solutions based on warranty: {warranty_status}",
            "tools": [provide_solution, escalate]
        }
    }

    config = configs[step]
    request = request.override(
        system_prompt=config["prompt"].format(**request.state),
        tools=config["tools"]
    )
    return handler(request)

# 4. Create agent with middleware
agent = create_agent(
    model,
    tools=[record_warranty_status, provide_solution, escalate],
    state_schema=SupportState,
    middleware=[apply_step_config],
    checkpointer=InMemorySaver()  # Persist state across turns
)

    要点：

    1. 状态 schema 继承 AgentState，加 current_step 跟踪字段
    2. 工具返回 Command 更新状态变量触发转换
    3. wrap_model_call middleware 在每次模型调用前根据状态动态替换提示和工具
    4. checkpointer 必需——状态要跨轮次持久

    实现方式二：多 Agent 子图¶

    不同 Agent 作为图节点，Command(goto=...) 在节点间转移控制权。适合真正需要不同模型/完全不同工具集的场景。单 Agent + middleware 方式更轻量，优先选它。

    14.5 Skills 模式（按需技能）¶

    架构：单 Agent 保持控制，按需加载专业的提示和知识。

    这是 Subagents 和 Handoffs 的轻量替代：不创建多个 Agent，而是让一个 Agent 拥有多个"专业人格"，任务需要时才加载对应的技能内容。

    用户 → Agent ──需要时加载──→ Skill A / Skill B / Skill C
              ←──专业上下文──┘

    核心思想：Agent 在系统提示中只看到轻量的技能描述（渐进披露），任务匹配时才通过工具调用加载完整技能内容。

    完整实现见 第 19 章：Skills — 按需技能架构（02-tools/02-skills.md），包括渐进披露机制和 SQL Assistant 实战。

    14.6 Router 模式（路由）¶

    架构：路由步骤对输入分类，分发给专业 Agent。适合有清晰垂直领域（每个知识域需要自己的 Agent）的场景。

    查询 → Router ─┬→ Agent A ─┐
               ├→ Agent B ─┼→ Synthesize → 综合答案
               └→ Agent C ─┘

    关键特征¶

    • Router 分解查询
    • 零个或多个专业 Agent 并行调用
    • 结果综合成连贯回复

    适用场景¶

    有清晰垂直领域、需要并行查询多个来源、要把结果综合成统一回复时。

    基本实现¶

    单 Agent 路由用 Command，并行 fan-out 用 Send：

    单 Agent 路由：

    from langgraph.types import Command

def classify_query(query: str) -> str:
    """Use LLM to classify query and determine the appropriate agent."""
    # Classification logic here
    ...

def route_query(state: State) -> Command:
    """Route to the appropriate agent based on query classification."""
    active_agent = classify_query(state["query"])

    # Route to the selected agent
    return Command(goto=active_agent)

    多 Agent 并行（Send fan-out）：

    from typing import TypedDict
from langgraph.types import Send

class ClassificationResult(TypedDict):
    query: str
    agent: str

def classify_query(query: str) -> list[ClassificationResult]:
    """Use LLM to classify query and determine which agents to invoke."""
    # Classification logic here
    ...

def route_query(state: State):
    """Route to relevant agents based on query classification."""
    classifications = classify_query(state["query"])

    # Fan out to selected agents in parallel
    return [
        Send(c["agent"], {"query": c["query"]})
        for c in classifications
    ]

    Stateless vs Stateful¶

    • 无状态路由：每个请求独立处理（分类 → 分发 → 综合），适合一次性查询
    • 有状态路由：维护跨请求的对话历史，路由决策可参考上下文

    官方教程：Build a multi-source knowledge base with routing（并行查 GitHub/Notion/Slack 后综合）。

    14.7 Custom Workflow 模式（自定义工作流）¶

    架构：用 LangGraph 构建定制执行流，混合确定性逻辑和智能体行为，其他模式可作为节点嵌入。

    适合：流程有明确的阶段划分、部分步骤必须确定性执行（不经过 LLM）、需要条件分支/循环/并行的复杂编排。

    from langchain.agents import create_agent
from langgraph.graph import StateGraph, MessagesState, START, END

# Specialized agents (each is a compiled LangGraph graph)
researcher = create_agent(
    model="openai:gpt-5.5",
    tools=[search_tool],
    system_prompt="You are a research specialist",
)

writer = create_agent(
    model="openai:gpt-5.5",
    tools=[writing_tool],
    system_prompt="You are a writing specialist",
)

# Deterministic node (no LLM)
def validate(state: MessagesState):
    """Deterministic validation step."""
    # Pure Python logic, no model call
    return state

# Build the workflow
graph = StateGraph(MessagesState)
graph.add_node("research", researcher)   # Agentic node
graph.add_node("validate", validate)     # Deterministic node
graph.add_node("write", writer)          # Agentic node

graph.add_edge(START, "research")
graph.add_edge("research", "validate")
graph.add_edge("validate", "write")
graph.add_edge("write", END)

app = graph.compile()
result = app.invoke({
    "messages": [{"role": "user", "content": "Research AI in healthcare and write a report"}]
})

    要点：

    • create_agent 返回的对象本身就是编译好的 LangGraph 图，可直接 add_node 嵌入
    • 确定性节点（校验、格式转换、数据查询）不经过 LLM，快且免费
    • 条件边（add_conditional_edges）实现动态分支

    深入 LangGraph 编排见本知识库的 langgraph 教程。

    14.8 实战：多代理研究系统（Subagents 模式完整示例）¶

    综合运用本章知识，构建一个研究系统：主 Agent 协调研究员和写手两个子代理。

    # research_system.py
from langchain.tools import tool
from langchain.agents import create_agent

# ========== 1. Subagent: researcher ==========
research_agent = create_agent(
    model="openai:gpt-5.5",
    tools=[internet_search],
    system_prompt=(
        "You are a meticulous researcher. Search thoroughly, "
        "and return CONCISE findings with sources."
    ),
)

# ========== 2. Subagent: writer ==========
writer_agent = create_agent(
    model="openai:gpt-5.5",
    tools=[],
    system_prompt=(
        "You are a professional writer. Turn research findings "
        "into a polished, well-structured report."
    ),
)

# ========== 3. Wrap subagents as tools ==========
@tool("research", description="Research a topic in depth. Input: research question.")
def do_research(query: str) -> str:
    result = research_agent.invoke(
        {"messages": [{"role": "user", "content": query}]}
    )
    return result["messages"][-1].content


@tool("write_report", description="Write a report from research findings.")
def do_write(findings: str) -> str:
    result = writer_agent.invoke(
        {"messages": [{"role": "user", "content": findings}]}
    )
    return result["messages"][-1].content

# ========== 4. Main coordinator agent ==========
main_agent = create_agent(
    model="openai:gpt-5.5",
    tools=[do_research, do_write],
    system_prompt=(
        "You coordinate a research team. For research requests:\n"
        "1. Use `research` to gather findings (call multiple times "
        "for different aspects)\n"
        "2. Use `write_report` to produce the final report\n"
        "Keep your own responses brief; the report is the deliverable."
    ),
)

# ========== 5. Run ==========
result = main_agent.invoke({
    "messages": [{
        "role": "user",
        "content": "Research the state of LLM agents in 2026 and write a report"
    }]
})
print(result["messages"][-1].content)

    这个系统的上下文流：

    1. 主 Agent 收到请求，决定先调研（调用 research，可能多次）
    2. 每次调研在独立上下文中进行，搜索的中间结果不污染主对话
    3. 主 Agent 只收到紧凑的调研摘要
    4. 调研结果交给 write_report，又在独立上下文中写成报告
    5. 主 Agent 把报告返回用户

    14.9 概念参考：Frameworks, Runtimes, and Harnesses¶

    LangChain 生态的三个层次（详见 langchain 顶层 README）：

    层次 产品 定位
    Frameworks LangChain (create_agent) Agent 框架：抽象 + 集成，灵活可控
    Runtimes LangGraph 有状态编排运行时（持久化、流式、HITL）
    Harnesses Deep Agents 开箱即用 harness（任务规划、子代理、文件系统、上下文管理）

    构建多代理时按需求选层次：

    • 标准多代理模式：LangChain create_agent + 本章的模式
    • 需要持久化/流式/复杂编排：LangGraph StateGraph（custom workflow 模式）
    • 需要完整 Agent 系统（自动上下文管理、虚拟文件系统、内置子代理）：Deep Agents

    📝 本章小结¶

    关键要点¶

    1. 不是所有复杂任务都需要多代理——先考虑单 Agent + 好工具/提示
    2. 官方 5 模式：Subagents（子代理当工具）、Handoffs（状态驱动切换）、Skills（按需加载）、Router（分类分发）、Custom workflow（LangGraph 定制）
    3. Subagents 核心：子代理无状态、上下文隔离、主 Agent 集中控制；两种工具模式（每 Agent 一工具 / 单一 task 分发）
    4. Handoffs 核心：工具返回 Command 更新状态变量 + middleware 动态配置；必须带 ToolMessage 保持对话历史合法
    5. Router 核心：Command(goto=...) 单路由、Send(...) 并行 fan-out
    6. 选型看需求矩阵（分布式开发/并行/多跳/用户交互）和性能（模型调用次数）

    模式速查¶

    我的需求 选
    多领域、集中控制、并行委派 Subagents
    客服式多阶段对话、顺序约束 Handoffs
    单 Agent 多专长、轻量切换 Skills
    按问题类型分发给专家 Router
    确定性 + AI 混合流程 Custom workflow
