    第 24 章：测试与评估 - Testing & Evals¶

    本章内容：Agent 测试三层策略——单元测试（假模型）、集成测试（真实 API）、轨迹评估（AgentEvals）

    官方文档：https://docs.langchain.com/oss/python/langchain/test/index

    📚 本章目标¶

    学完本章后，你将掌握：

    • ✅ 理解 Agent 测试为什么和传统软件测试不同
    • ✅ 用 GenericFakeChatModel 写零 API 调用的单元测试
    • ✅ 用 pytest markers 组织集成测试、管理 key、控制成本
    • ✅ 掌握"断言结构不断言内容"的原则
    • ✅ 用 agentevals 做轨迹匹配和 LLM-as-judge 评估
    • ✅ 在 LangSmith 中规模化运行 evals

    24.1 Agent 测试的挑战¶

    Agent 应用让 LLM 自己决定下一步。这种灵活性很强大，但模型的黑盒特性让你难以预测：改动 Agent 的某一部分会如何影响整体。要构建生产级 Agent，彻底测试必不可少。

    三种测试方法：

    方法 做什么 特点
    单元测试 用内存假对象（fake）隔离测试 Agent 小而确定的部分 快速、免费、可重复，断言精确行为
    集成测试 用真实网络调用测试 Agent 确认组件协作、凭证/schema 正确、延迟可接受
    Evals 用评估器评估执行轨迹 确定性匹配或 LLM 评审

    📌 Agent 应用更依赖集成测试——因为它们串联多个组件，且必须应对 LLM 非确定性带来的不稳定性（flakiness）。

    💡 规模化运行评估、随时间跟踪结果、对比实验，用 LangSmith。

    24.2 单元测试：假模型 + 内存持久化¶

    单元测试隔离测试小而确定的部分。把真实 LLM 换成内存假对象（fixture），你可以脚本化精确响应（文本、工具调用、错误），让测试快速、免费、无需 API key 可重复。

    GenericFakeChatModel（模拟响应）¶

    接受一个响应迭代器（AIMessage 对象或字符串），每次调用返回一个。支持普通和流式用法：

    from langchain_core.language_models.fake_chat_models import GenericFakeChatModel
from langchain_core.messages import AIMessage
from langchain_core.messages.tool import ToolCall

model = GenericFakeChatModel(messages=iter([
    AIMessage(content="", tool_calls=[ToolCall(name="foo", args={"bar": "baz"}, id="call_1")]),
    "bar"
]))

model.invoke("hello")
# AIMessage(content='', ..., tool_calls=[{'name': 'foo', 'args': {'bar': 'baz'}, 'id': 'call_1', 'type': 'tool_call'}])

    再次调用会返回迭代器的下一项：

    model.invoke("hello, again!")
# AIMessage(content='bar', ...)

    这让你可以精确编排"第一次调用发起工具调用，第二次返回最终文本"这样的多轮剧本。

    InMemorySaver（模拟多轮状态）¶

    测试状态相关行为时，用 InMemorySaver 模拟多轮对话：

    from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(
    model,
    tools=[],
    checkpointer=InMemorySaver()
)

# First invocation
agent.invoke(
    {"messages": [HumanMessage(content="I live in Sydney, Australia")]},
    config={"configurable": {"thread_id": "session-1"}}
)

# Second invocation: the first message is persisted (Sydney location), so the model returns GMT+10 time
agent.invoke(
    {"messages": [HumanMessage(content="What's my local time?")]},
    config={"configurable": {"thread_id": "session-1"}}
)

    单元测试还能测什么¶

    • 中间件逻辑：自定义 middleware 的状态变换（用假模型驱动）
    • 工具本身：工具函数的输入输出（不经过模型，直接调用）
    • 防护逻辑：第 23 章的 before_agent/after_agent guardrails，用构造的消息直接触发

    24.3 集成测试：真实 API¶

    集成测试验证 Agent 与模型 API、外部服务的真实协作。因为 LLM 响应非确定性，集成测试需要不同于传统软件的策略。

    分离单元测试和集成测试¶

    集成测试慢且需要 API 凭证——和单元测试分开，让快速单测每次变更都跑，集成测试留给 CI 或部署前。

    用 pytest markers 标记：

    import pytest

@pytest.mark.integration
def test_agent_with_real_model():
    agent = create_agent("anthropic:claude-sonnet-4-6", tools=[get_weather])
    result = agent.invoke({
        "messages": [HumanMessage(content="What's the weather in SF?")]
    })
    assert len(result["messages"]) > 1

    配置 pytest 识别 marker，默认排除集成测试：

    # pyproject.toml
[tool.pytest.ini_options]
markers = [
  "integration: tests that call real LLM APIs"
]
addopts = "-m 'not integration'"

    显式运行集成测试：

    pytest -m integration

    管理 API key¶

    从环境变量加载，key 不进源码。用 conftest.py fixture 校验 key 可用：

    import os
import pytest

@pytest.fixture(autouse=True)
def check_api_keys():
    if not os.environ.get("OPENAI_API_KEY"):
        pytest.skip("OPENAI_API_KEY not set")

    本地开发用 .env + python-dotenv：

    # conftest.py
from dotenv import load_dotenv

load_dotenv()

    ⚠️ .env 加入 .gitignore。CI 里用平台的 secrets 管理（如 GitHub Actions secrets）注入。

    断言结构，不断言内容¶

    LLM 响应每次运行都不同。不要断言精确输出字符串，验证结构属性：消息类型、工具调用名称、参数形状、消息数量。

    def test_agent_calls_weather_tool():
    agent = create_agent("anthropic:claude-sonnet-4-6", tools=[get_weather])
    result = agent.invoke({
        "messages": [HumanMessage(content="What's the weather in SF?")]
    })

    messages = result["messages"]
    tool_calls = [
        tc
        for msg in messages
        if hasattr(msg, "tool_calls")
        for tc in (msg.tool_calls or [])
    ]

    assert any(tc["name"] == "get_weather" for tc in tool_calls)
    assert isinstance(messages[-1], AIMessage)
    assert len(messages[-1].content) > 0

    💡 需要更严格的轨迹断言，用 AgentEvals 评估器（24.4 节），支持 unordered、superset 等模糊匹配模式。

    控制成本和延迟¶

    集成测试花真钱。控制方法：

    • 用小模型：只验证工具调用和响应结构的测试用 gemini-3.1-flash-lite 级别
    • 设 max_tokens：限制响应长度，避免又长又贵的补全
    • 限制测试范围：一个测试测一个行为；单轮测试够用就别跑多轮端到端
    • 选择性运行：集成测试只在 CI 或部署前跑，不是每次保存文件都跑
    agent = create_agent(
    "google_genai:gemini-3.1-flash-lite",
    tools=[get_weather],
    model_kwargs={"max_tokens": 256},
)

    录制回放 HTTP 调用¶

    CI 里频繁运行的测试，可以第一次录制 HTTP 交互、后续回放，不再真实调用 API——录制后零成本零延迟。用 vcrpy（录制成 YAML "cassette" 文件）+ pytest-recording 插件。

    24.4 Evals：轨迹评估¶

    Evals 通过评估 Agent 的执行轨迹（产生的消息和工具调用序列）来衡量表现。与验证基本正确性的集成测试不同，evals 对照参考或标准给行为打分——在修改提示、工具、模型时捕捉回归特别有用。

    评估器是一个函数：接收 Agent 输出（和可选的参考输出），返回分数：

    def evaluator(*, outputs: dict, reference_outputs: dict):
    output_messages = outputs["messages"]
    reference_messages = reference_outputs["messages"]
    score = compare_messages(output_messages, reference_messages)
    return {"key": "evaluator_score", "score": score}

    agentevals 包提供预构建的轨迹评估器，两类方法：

    方法 何时用
    轨迹匹配（Trajectory match） 知道预期工具调用，要快速、确定性、免费的检查
    LLM-as-judge 想评估整体质量和推理，没有严格预期 
    pip install -U agentevals

    轨迹匹配评估器（4 种模式）¶

    create_trajectory_match_evaluator 把 Agent 轨迹与参考对比：

    模式 说明 用例
    strict 消息结构和工具调用同序精确匹配（消息内容可不同） 测试特定顺序（如授权前必须先查策略）
    unordered 同样的结构和工具调用，但顺序任意 验证信息检索但顺序不重要
    subset Agent 只调用参考中的工具（不允许多余） 确保 Agent 不超出预期范围
    superset Agent 至少调用参考的工具（允许多余） 验证最低必需动作都执行了

    strict 示例：

    from langchain.agents import create_agent
from langchain.tools import tool
from langchain.messages import HumanMessage, AIMessage, ToolMessage
from agentevals.trajectory.match import create_trajectory_match_evaluator


@tool
def get_weather(city: str):
    """Get weather information for a city."""
    return f"It's 75 degrees and sunny in {city}."

agent = create_agent("anthropic:claude-sonnet-4-6", tools=[get_weather])

evaluator = create_trajectory_match_evaluator(
    trajectory_match_mode="strict",
)

def test_weather_tool_called_strict():
    result = agent.invoke({
        "messages": [HumanMessage(content="What's the weather in San Francisco?")]
    })

    reference_trajectory = [
        HumanMessage(content="What's the weather in San Francisco?"),
        AIMessage(content="", tool_calls=[
            {"id": "call_1", "name": "get_weather", "args": {"city": "San Francisco"}}
        ]),
        ToolMessage(content="It's 75 degrees and sunny in San Francisco.", tool_call_id="call_1"),
        AIMessage(content="The weather in San Francisco is 75 degrees and sunny."),
    ]

    evaluation = evaluator(
        outputs=result["messages"],
        reference_outputs=reference_trajectory
    )
    # {
    #     'key': 'trajectory_strict_match',
    #     'score': True,
    #     'comment': None,
    # }
    assert evaluation["score"] is True

    LLM-as-judge 评估器¶

    用 LLM 评估执行路径，create_trajectory_llm_as_judge。不需要参考轨迹（有参考也可以提供）：

    无参考轨迹：

    from agentevals.trajectory.llm import create_trajectory_llm_as_judge, TRAJECTORY_ACCURACY_PROMPT

evaluator = create_trajectory_llm_as_judge(
    model="openai:o3-mini",
    prompt=TRAJECTORY_ACCURACY_PROMPT,
)

def test_trajectory_quality():
    result = agent.invoke({
        "messages": [HumanMessage(content="What's the weather in Seattle?")]
    })

    evaluation = evaluator(
        outputs=result["messages"],
    )
    assert evaluation["score"] is True

    有参考轨迹：用预构建的 TRAJECTORY_ACCURACY_PROMPT_WITH_REFERENCE 提示：

    from agentevals.trajectory.llm import create_trajectory_llm_as_judge, TRAJECTORY_ACCURACY_PROMPT_WITH_REFERENCE

evaluator = create_trajectory_llm_as_judge(
    model="openai:o3-mini",
    prompt=TRAJECTORY_ACCURACY_PROMPT_WITH_REFERENCE,
)
evaluation = evaluator(
    outputs=result["messages"],
    reference_outputs=reference_trajectory,
)

    异步支持¶

    所有 agentevals 评估器支持 asyncio——函数名 create_ 后加 async 即可（如 create_async_trajectory_llm_as_judge）。

    24.5 在 LangSmith 中运行 Evals¶

    本地 evals 适合开发迭代；规模化、跨时间跟踪、实验对比用 LangSmith：

    1. 在 LangSmith 创建 Dataset（输入 + 参考输出）
    2. 把 Agent 和评估器关联到 dataset 运行实验
    3. 每次改动提示/工具/模型后重跑，对比分数变化
    4. 跟踪回归：某个版本分数下降立刻可见

    官方教程：Evaluate an LLM application。

    24.6 测试策略速查¶

    我要验证 用什么
    中间件/工具/guardrail 的逻辑 单元测试（GenericFakeChatModel / 直接调用）
    多轮状态行为 单元测试 + InMemorySaver
    凭证有效、组件能协作、延迟可接受 集成测试（pytest -m integration）
    工具调用序列正确（有明确预期） agentevals 轨迹匹配（strict/unordered/subset/superset）
    整体推理质量（无严格预期） agentevals LLM-as-judge
    改动不引入回归 LangSmith dataset + evals 持续跟踪

    分层建议¶

    开发循环（每次改动，秒级）：单元测试（假模型）
        ↓
提交前（分钟级）：集成测试子集（小模型 + 结构断言）
        ↓
CI / 部署前：完整集成测试 + 轨迹 evals（LangSmith dataset）
        ↓
上线后：LangSmith tracing 监控 + 定期 evals 回归

    📝 本章小结¶

    关键要点¶

    1. Agent 测试三层：单元测试（假模型，确定性）、集成测试（真实 API，结构断言）、evals（轨迹打分）
    2. GenericFakeChatModel 脚本化精确响应，测试零成本可重复
    3. 集成测试铁律：断言结构不断言内容、pytest markers 分离、小模型 + max_tokens 控成本、key 走环境变量
    4. agentevals 四种轨迹匹配模式：strict（同序精确）/ unordered（任意序）/ subset（不许多余）/ superset（至少包含）
    5. LLM-as-judge 无需参考轨迹，评估整体推理质量
    6. 规模化 evals 上 LangSmith：dataset + 实验对比 + 回归跟踪
