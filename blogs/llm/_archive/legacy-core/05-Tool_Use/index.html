    Tool Use 工具使用¶

    ⚠️ 已弃用（2026-10-29）：本文档属于旧的"拟人化模块"结构，已由 02-Input-Tools-Structured-Output.md 取代（新结构按 Agent 系统执行生命周期组织）。本文件保留作为历史参考，不再更新。完整新目录见 README.md。

    Agent 的"手脚"——让模型从"纯思考"走向"能做事"。

    1. 总览¶

    Tool Use 是 Agent 从聊天机器人升级为生产力工具 的关键。没有工具，Agent 只能"说"不能"做"。

    纯 LLM:        用户: "帮我查天气"
              → "抱歉我无法访问实时数据..."

LLM + Tools:   用户: "帮我查天气"
              → [调用 weather API]
              → "北京今天晴，22-30°C"

    1.1 工具体系三层架构¶

    ┌────────────────────────────────────────────────────────────┐
│                      Tool Use Stack                         │
├────────────────────────────────────────────────────────────┤
│                                                            │
│  Application Layer:  Skills                                │
│    (工具组合 + Prompt + Workflow，领域技能包)                │
│                        ↑                                   │
│  Integration Layer:  Tool Access Methods                   │
│    ├─ MCP:  标准化协议（跨进程/跨语言，动态发现）            │
│    └─ CLI:  直接执行 shell（零配置，渐进式上下文）           │
│                        ↑                                   │
│  Execution Layer:  Tool Calling (Function Calling)         │
│    (LLM 输出结构化 JSON 调用工具的底层机制)                  │
│                                                            │
└────────────────────────────────────────────────────────────┘
    • Execution Layer：底层机制 — LLM 如何输出结构化的工具调用（JSON 格式的工具名+参数）
    • Integration Layer：工具接入方式 — MCP（标准化协议，跨进程/跨语言）和 CLI（直接执行 shell 命令，零配置）是两种互补的接入手段
    • Application Layer：上层封装 — 将工具组合为可复用的领域技能（Skills = Tools + Prompts + Workflow）

    2. Tool Calling 原理与实现¶

    2.1 核心流程¶

    ┌──────────┐    Tool Definitions     ┌──────────┐
│          │  ────────────────────→  │          │
│   User   │                         │   LLM    │
│  Input   │  ←────────────────────  │          │
│          │   Tool Call Request     │          │
└──────────                         └────┬─────┘
                                          │
                                    Execute Tool
                                          │
                                          ▼
                                    ┌──────────┐
                                    │  Tool    │
                                    │  Result  │
                                    └────┬─────┘
                                         │
                                         ▼
                                    ┌──────────┐
                                    │   LLM    │ ← 用结果生成最终回答
                                    └────┬─────┘
                                         │
                                         ▼
                                    ┌──────────┐
                                    │  Final   │
                                    │  Answer  │
                                    └──────────┘

    六步走：

    1. 开发者定义工具 schema（名称、描述、参数 JSON Schema）
    2. 工具定义随 System Prompt 一起发送给 LLM
    3. LLM 判断需要调用工具时，输出结构化 JSON（工具名 + 参数）
    4. 框架解析 JSON，执行对应函数
    5. 执行结果作为 Observation 送回给 LLM
    6. LLM 基于结果生成最终回答

    关键细节： - OpenAI 用 function_calling，Anthropic 用 tool_use block - 现代框架统一为 llm.bind_tools(tools) → 自动处理各 provider 差异 - 工具描述质量直接影响调用准确率 - Tool Calling（结构化 JSON）比 ReAct（文本推理）更精确

    2.2 Tool Calling 是怎么训练出来的¶

    面试加分题：模型"怎么就知道"要输出 JSON 格式的 tool_call？

    Tool Calling 能力不是 prompt 工程，而是微调出来的：

    预训练 LLM（只会生成文本）
        │
        ▼  ① 构造训练数据
┌─────────────────────────────────────────────┐
│  System: You have access to these tools...  │
│  User: 北京今天天气怎么样？                    │
│  Assistant:                                  │
│    tool_calls: [{                             │
│      name: "get_weather",                    │
│      arguments: {"city": "北京"}              │
│    }]                                        │
│  Tool: 晴，22-30°C                           │
│  Assistant: 北京今天晴，22-30°C               │
└─────────────────────────────────────────────┘
        │
        ▼  ② SFT（监督微调）
   模型学会：遇到需要工具的场景 → 输出特殊 token/JSON
        │
        ▼  ③ RLHF / 强化学习
   优化：选对工具、填对参数、减少幻觉调用
        │
        ▼
   具备 Tool Calling 能力的模型

    关键实现细节：

    • 模型及其 chat template 会约定工具调用的特殊标记或消息结构；具体 token 形式因模型而异，并非所有模型都必须修改 tokenizer。
    • SFT 样本同时包含“何时调用、选择哪个工具、怎样填写参数、如何使用结果”等完整轨迹。
    • 推理服务把模型生成的工具调用片段解析为 API 中的结构化 tool_calls，再由 Agent Runtime 执行。

    LangChain BaseTool 示例：

    from langchain_core.tools import BaseTool


class WeatherTool(BaseTool):
    """继承 BaseTool，适合需要完全控制同步/异步执行逻辑的场景。"""

    name: str = "get_weather"
    description: str = "Get weather information for a city"

    def _run(self, city: str) -> str:
        return f"Weather in {city}: sunny, 25°C"

    async def _arun(self, city: str) -> str:
        return f"Weather in {city}: sunny, 25°C"

    工具描述的最佳实践：描述要精确、包含使用场景和示例。差的描述（"""Search for stuff."""）会导致 LLM 选错工具或填错参数。

    2.3 工具执行（LangGraph）¶

    ⚠️ API 版本提示：create_react_agent 是 LangGraph 旧 API。LangChain v1 推荐使用 langchain.agents.create_agent（重试、HITL、护栏等通过 middleware 实现）。当前 API 用法见 langchain/tutorial/。以下代码保留为概念演示。

    from typing import TypedDict
from langgraph.prebuilt import create_react_agent, ToolNode
from langgraph.graph import StateGraph, END
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o")

# 方式一：一行搞定（create_react_agent）
agent = create_react_agent(llm, tools)
result = agent.invoke({
    "messages": [{"role": "user", "content": "北京今天天气怎么样？"}]
})

# 方式二：手动构建（更灵活）
class ToolAgentState(TypedDict):
    messages: list

tool_node = ToolNode(tools)

def agent_node(state):
    response = llm.bind_tools(tools).invoke(state["messages"])
    return {"messages": [response]}

def should_continue(state):
    last_msg = state["messages"][-1]
    return "tools" if last_msg.tool_calls else END

builder = StateGraph(ToolAgentState)
builder.add_node("agent", agent_node)
builder.add_node("tools", tool_node)
builder.set_entry_point("agent")
builder.add_conditional_edges("agent", should_continue)
builder.add_edge("tools", "agent")  # 工具执行后回到 agent 继续推理
tool_graph = builder.compile()

    2.4 工具调度器（手写 — 面试高频）¶

    class ToolDispatcher:
    """工具调度器：注册、验证、执行"""

    def __init__(self):
        self.tools = {}

    def register(self, name: str, func: callable, schema: dict):
        self.tools[name] = {"func": func, "schema": schema}

    def validate(self, tool_name: str, args: dict) -> tuple[bool, str]:
        if tool_name not in self.tools:
            return False, f"Unknown tool: {tool_name}"
        schema = self.tools[tool_name]["schema"]
        for param in schema.get("required", []):
            if param not in args:
                return False, f"Missing required parameter: {param}"
        return True, ""

    def dispatch(self, tool_name: str, args: dict) -> dict:
        valid, error = self.validate(tool_name, args)
        if not valid:
            return {"status": "error", "message": error}
        try:
            result = self.tools[tool_name]["func"](**args)
            return {"status": "success", "result": result}
        except Exception as e:
            return {"status": "error", "message": str(e)}

    def get_schemas(self) -> list:
        """生成传给 LLM 的工具定义列表"""
        return [
            {
                "name": name,
                "description": info["schema"].get("description", ""),
                "input_schema": {
                    "type": "object",
                    "properties": info["schema"].get("properties", {}),
                    "required": info["schema"].get("required", []),
                },
            }
            for name, info in self.tools.items()
        ]

    3. MCP (Model Context Protocol)¶

    📌 事实源声明：MCP 协议细节（版本、传输、鉴权、Server/Client 实现）以 protocols/mcp/ 为准（主线版本 2026-07-28）。本节只讲概念与适用边界。以下 3.2 起的握手流程为 Legacy 协议（2025-11-25 及以前），Modern 协议无初始化握手，详见 protocols/mcp/03-通信过程与版本协商.md。

    3.1 什么是 MCP¶

    MCP 是 Anthropic 提出的标准化协议，让 AI 应用以统一方式接入各种数据源和工具。类比：USB-C 之于硬件设备。

    ┌──────────────────── MCP Host（AI 应用）───────────────────┐
│  LLM / Agent Runtime                                      │
│          │                                                 │
│    ┌─────▼─────┐        MCP / JSON-RPC       ┌──────────┐  │
│    │ MCP Client│ ←─────────────────────────→ │MCP Server│──┼─→ 文件/API/数据库
│    └───────────┘     stdio / Streamable HTTP └──────────┘  │
└────────────────────────────────────────────────────────────┘

    核心概念： - Host：承载 LLM、Agent Runtime 和权限/UI 的 AI 应用，例如 IDE 或桌面客户端 - Client：Host 内负责协议通信的组件；通常一个 Client 与一个 Server 维持一条逻辑连接 - Server：向 Client 暴露能力的进程或远程服务 - Tools：可执行操作，可能有副作用，通常由模型选择调用 - Resources：通过 URI 标识的可读上下文，通常由应用或用户选择 - Prompts：Server 提供的可复用提示模板及参数定义

    MCP vs Function Calling：

    维度 Function Calling MCP
    调用方式 LLM 单次调用工具 长期连接 Server，动态发现工具
    通信范围 模型内部 跨进程/跨语言
    类比 单次电话 USB 即插即用基础设施

    3.2 协议要点（面试必记）¶

    MCP 协议 = JSON-RPC 2.0 + stdio / Streamable HTTP

JSON-RPC 有三类消息：
    Request      = method + params + id    → 必须返回相同 id 的 Response
    Response     = result/error + id       → 与等待中的 Request 配对
    Notification = method + params，无 id  → 单向通知，不返回 Response

标准传输：
    stdio          每条 JSON-RPC 消息压成一行，以换行符分隔
    Streamable HTTP 每条客户端消息使用独立 HTTP POST；响应可以是 JSON 或 SSE 流

注意：Content-Length 头是 LSP 等协议常见的分帧方式，不是 MCP stdio 的标准格式。

    3.2.1 初始化：initialize 与 notifications/initialized¶

    初始化是一次版本协商 + 能力协商，而不只是普通的“连接成功”信号：

    Client                                      Server
  │── initialize(request, id=1) ─────────────→│
  │   protocolVersion / capabilities/clientInfo│
  │←─ initialize(response, id=1) ──────────────│
  │   protocolVersion / capabilities/serverInfo│
  │── notifications/initialized ──────────────→│
  │                                            │
  │        此后才进入正常操作阶段                 │
    • Client 在 initialize 中声明自己支持的协议版本和能力，如 roots、sampling。
    • Server 返回最终协议版本及 tools、resources、prompts 等能力。
    • Client 必须检查返回版本是否兼容，并且只能使用双方协商成功的能力。
    • notifications/initialized 没有 id，只表示 Client 已准备就绪，Server 不应回复。
    • 初始化完成前，双方除 ping（以及允许的日志消息）外不应开展普通业务调用。

    3.2.2 工具方法：发现与执行分离¶

    方法 关键参数 主要返回值 实现原理
    tools/list 可选 cursor tools[]、可选 nextCursor Client 动态发现工具并缓存定义；工具包含 name、description、inputSchema，还可包含 outputSchema
    tools/call name、arguments content[]、可选 structuredContent、isError Server 按名称路由工具，使用 JSON Schema 校验参数，执行后把文本、图片或结构化数据封装成结果

    调用链不是“LLM 直接访问 Server”，而是：

    1. Client 调用 tools/list，取得工具定义
2. Client 把相关工具定义提供给 LLM
3. LLM 选择工具并生成 name + arguments
4. Client 校验权限并发送 tools/call
5. Server 再次校验参数、执行工具并返回结果
6. Client 将结果作为 Tool Message/Observation 交给 LLM

    tools/call 有两类错误，必须区分：

    • 协议错误：未知工具、请求结构错误等，放在 JSON-RPC error 中。
    • 工具执行错误：参数值非法、上游 API 失败等，通常返回正常 JSON-RPC result，但设置 isError: true，以便 LLM 根据错误内容修正参数后重试。

    3.2.3 资源方法：先拿元数据，再按 URI 读取¶

    方法 关键参数 主要返回值 实现原理
    resources/list 可选 cursor resources[]、可选 nextCursor 只发现资源元数据，如 uri、name、mimeType，避免一次加载全部内容
    resources/read uri contents[] Server 校验 URI 和访问权限，再返回 text 或 Base64 编码的 blob
    resources/templates/list 可选 cursor resourceTemplates[] 用 URI Template 暴露带参数的资源，例如 file:///{path}
    resources/subscribe uri 空结果 可选能力；订阅指定资源，变化后由 Server 发送更新通知

    Tools 与 Resources 的语义不同：

    Tool     = 执行动作，可能产生副作用，通常由模型选择
Resource = 读取上下文，使用 URI 标识，通常由应用或用户选择

    3.2.4 notifications/* 为什么不需要响应¶

    Notification 是 JSON-RPC 的单向消息，因为它没有 id，接收方无法也不应返回 Response。常见通知包括：

    通知 方向 收到后的处理
    notifications/initialized Client → Server 标记初始化完成，开放正常方法调用
    notifications/tools/list_changed Server → Client 使工具缓存失效，重新调用 tools/list
    notifications/resources/list_changed Server → Client 重新调用 resources/list
    notifications/resources/updated Server → Client 根据 uri 重新调用 resources/read
    notifications/progress 双向 更新长任务进度，可延长软超时但仍应保留最大超时
    notifications/cancelled 双向 尝试取消指定请求；取消是尽力而为，不保证任务一定停止

    3.2.5 Client 内部如何分发 JSON-RPC 消息¶

    def handle_message(message: dict):
    if "method" in message and "id" in message:
        # 对端发来的 Request：按 method 路由，执行后返回相同 id
        return dispatch_request(message)

    if "method" in message:
        # 没有 id：Notification，只更新本地状态，不返回内容
        handle_notification(message)
        return None

    if "id" in message:
        # Response：通过 id 找到等待中的请求（Future/Promise）
        pending.pop(message["id"]).set_result(message)
        return None

    raise ValueError("Invalid JSON-RPC message")

    因此一个完整 Client 通常维护四类状态：协商后的版本与能力、递增请求 ID、id → Future 的等待表、工具/资源元数据缓存。同步 Client 可以一次只等待一个请求；支持并发时必须用 id 将乱序返回的响应匹配给正确调用。

    3.3 创建 MCP Server¶

    # pip install mcp
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("MyTools")

@mcp.tool()
def search_documents(query: str) -> str:
    """Search internal documentation."""
    return f"Search results for '{query}'"

@mcp.tool()
def get_file_content(path: str) -> str:
    """Read a file's content."""
    with open(path, 'r') as f:
        return f.read()

@mcp.resource("file://{path}")
def read_file_resource(path: str) -> str:
    """Read file as a resource."""
    with open(path, 'r') as f:
        return f.read()

# 本地子进程通常使用 stdio；远程服务推荐 Streamable HTTP。
# 具体 host/port 配置方式可能随 Python SDK 版本变化。
if __name__ == "__main__":
    mcp.run(transport="stdio")
    # mcp.run(transport="streamable-http")

    3.4 LangChain MCP Client¶

    ⚠️ API 版本提示：langchain-mcp-adapters 已被 LangChain 内置的 langchain.mcp.MCPAdapter 替代（langchain[mcp]>=1.4），get_tools() → list_tools()。当前 API 用法见 langchain/tutorial/02-tools/03-mcp-tools.md。以下代码保留为旧版演示。

from langchain_openai import ChatOpenAI

async def run_with_mcp():

            "command": "npx",

    3.5 从零手搓 MCP Client（面试高频）¶

    面试官常考：不用 SDK 从零实现 MCP Client。对于 stdio，核心是 JSON-RPC 2.0 + 一行一条消息 + 请求 ID 配对。下面是教学用同步版本；生产实现还需要并发请求表、超时、取消、Server→Client 请求及更完整的错误恢复。

    import json
import subprocess
import threading


class MCPClient:
    """教学版 MCP Client：单请求同步等待，使用 stdio 传输。"""

    SUPPORTED_VERSIONS = {"2025-11-25", "2025-06-18", "2025-03-26", "2024-11-05"}

    def __init__(self, command: str, args: list[str] | None = None):
        self.command = command
        self.args = args or []
        self.process = None
        self.request_id = 0
        self.protocol_version = None
        self.server_capabilities = {}
        self.tools_cache = None
        self.resources_cache = None

    def start(self):
        """Client 启动 Server 子进程，并通过三条标准流通信。"""
        self.process = subprocess.Popen(
            [self.command, *self.args],
            stdin=subprocess.PIPE,
            stdout=subprocess.PIPE,
            stderr=subprocess.PIPE,
            text=True,
            encoding="utf-8",
            bufsize=1,
        )
        # stderr 只承载日志；持续消费，避免管道写满后阻塞 Server。
        threading.Thread(target=self._drain_stderr, daemon=True).start()

    def stop(self):
        """先关闭 stdin 请求优雅退出，超时后再终止进程。"""
        if not self.process or self.process.poll() is not None:
            return
        self.process.stdin.close()
        try:
            self.process.wait(timeout=5)
        except subprocess.TimeoutExpired:
            self.process.terminate()
            self.process.wait(timeout=5)

    # ==================== 生命周期 ====================

    def initialize(self) -> dict:
        result = self._request("initialize", {
            "protocolVersion": "2025-11-25",
            "capabilities": {},  # 本教学 Client 不暴露 roots/sampling 等能力
            "clientInfo": {"name": "my-mcp-client", "version": "1.0.0"},
        })

        version = result.get("protocolVersion")
        if version not in self.SUPPORTED_VERSIONS:
            raise RuntimeError(f"Unsupported MCP protocol version: {version}")

        self.protocol_version = version
        self.server_capabilities = result.get("capabilities", {})
        self._notify("notifications/initialized")  # Notification 没有 id，不等待响应
        return result

    # ==================== Tools ====================

    def list_tools(self) -> list[dict]:
        self._require_capability("tools")
        tools, cursor = [], None
        while True:  # MCP list 方法使用 cursor 分页
            params = {"cursor": cursor} if cursor else {}
            page = self._request("tools/list", params)
            tools.extend(page.get("tools", []))
            cursor = page.get("nextCursor")
            if not cursor:
                break
        self.tools_cache = tools
        return tools

    def call_tool(self, name: str, arguments: dict) -> dict:
        self._require_capability("tools")
        # 保留完整结果，不能只提取 text；结果还可能包含图片、资源或 structuredContent。
        return self._request("tools/call", {"name": name, "arguments": arguments})

    # ==================== Resources ====================

    def list_resources(self) -> list[dict]:
        self._require_capability("resources")
        resources, cursor = [], None
        while True:
            params = {"cursor": cursor} if cursor else {}
            page = self._request("resources/list", params)
            resources.extend(page.get("resources", []))
            cursor = page.get("nextCursor")
            if not cursor:
                break
        self.resources_cache = resources
        return resources

    def read_resource(self, uri: str) -> list[dict]:
        self._require_capability("resources")
        return self._request("resources/read", {"uri": uri}).get("contents", [])

    # ==================== JSON-RPC 底层 ====================

    def _send(self, message: dict):
        # JSON 字符串内部的换行会被转义，因此每个物理行恰好是一条 MCP 消息。
        line = json.dumps(message, ensure_ascii=False, separators=(",", ":"))
        self.process.stdin.write(line + "\n")
        self.process.stdin.flush()

    def _read_message(self) -> dict:
        line = self.process.stdout.readline()
        if line == "":
            raise EOFError("MCP Server closed stdout")
        return json.loads(line)

    def _request(self, method: str, params: dict | None = None) -> dict:
        self.request_id += 1
        current_id = self.request_id
        self._send({
            "jsonrpc": "2.0",
            "id": current_id,
            "method": method,
            "params": params or {},
        })

        while True:
            message = self._read_message()
            if message.get("id") == current_id and ("result" in message or "error" in message):
                if "error" in message:
                    raise RuntimeError(f"MCP Error: {message['error'].get('message')}")
                return message.get("result", {})

            # 等待 Response 时仍可能收到通知，或者收到 Server→Client Request。
            self._handle_incoming(message)

    def _notify(self, method: str, params: dict | None = None):
        self._send({"jsonrpc": "2.0", "method": method, "params": params or {}})

    def _handle_incoming(self, message: dict):
        method = message.get("method")
        if not method:
            raise RuntimeError(f"Unexpected JSON-RPC response: {message}")

        if "id" in message:  # Server→Client Request
            if method == "ping":
                self._send({"jsonrpc": "2.0", "id": message["id"], "result": {}})
            else:
                self._send({
                    "jsonrpc": "2.0",
                    "id": message["id"],
                    "error": {"code": -32601, "message": f"Method not supported: {method}"},
                })
            return

        # Server→Client Notification：更新本地缓存，不发送响应。
        if method == "notifications/tools/list_changed":
            self.tools_cache = None
        elif method == "notifications/resources/list_changed":
            self.resources_cache = None

    def _require_capability(self, name: str):
        if name not in self.server_capabilities:
            raise RuntimeError(f"Server did not declare capability: {name}")

    def _drain_stderr(self):
        for _ in iter(self.process.stderr.readline, ""):
            pass

    def __enter__(self):
        self.start()
        return self

    def __exit__(self, *args):
        self.stop()


# 使用
with MCPClient("python", ["my_mcp_server.py"]) as client:
    client.initialize()
    tools = client.list_tools()
    result = client.call_tool("search_documents", {"query": "AI Agent"})

    这段代码体现了五个底层原则：

    1. 消息边界：stdio 通过换行分隔 JSON-RPC 消息，不使用 Content-Length。
    2. 请求配对：Request 带唯一 id，Response 必须用相同 id。
    3. 能力门控：调用方法前检查 Server 是否在初始化阶段声明对应能力。
    4. 发现与调用分离：先 list 获取元数据，再 call/read 执行实际操作。
    5. 通知驱动缓存失效：收到 list_changed 后清除缓存，下次使用时重新发现。

    4. CLI 工具与 CLI Agent¶

    4.1 CLI 作为工具¶

    CLI 作为工具 = Agent 通过执行 shell 命令来完成任务。这是最古老、最直接的工具形式。

    与 MCP 的核心区别：

    维度 CLI 工具 MCP 工具
    执行方式 直接执行 shell 命令 JSON-RPC 协议调用 Server
    配置 零配置，开箱即用 需要启动 Server、配置连接
    安全性 风险高（可执行任意命令） 好（Server 控制暴露的能力）
    上下文开销 渐进式引入（按需 ls → cat → grep） 重（握手 + 全量工具定义占窗口）
    适用场景 本地文件/代码/自动化 外部服务/数据库/跨语言

    CLI 最核心的优势是渐进式引入上下文：Agent 执行 ls 只引入文件列表，执行 cat 只引入文件内容，每一步按需引入。而 MCP 需要加载所有工具定义（JSON Schema），持续占用上下文窗口。对于复杂多步任务，CLI 能最大化利用有限的上下文。

    实现示例：

    from langchain_core.tools import tool
import subprocess

@tool
def terminal(command: str) -> str:
    """Execute shell command and return output.

    Use for file operations, git, running tests, system commands.
    NOT for: database queries, API calls (use dedicated tools instead).
    """
    # 危险命令拦截
    dangerous = ["rm -rf /", "sudo", "DROP TABLE", ":(){ :|:& };:"]
    if any(d in command for d in dangerous):
        return f"Error: Dangerous command blocked"

    result = subprocess.run(command, shell=True, capture_output=True, text=True, timeout=30)
    return f"stdout:\n{result.stdout}\nstderr:\n{result.stderr}"

    4.2 CLI Agent（命令行智能体）¶

    注意区分：CLI 工具 = Agent 用 shell 命令当工具；CLI Agent = 以终端为界面的 Agent 产品。

    典型产品：Claude Code、OpenAI Codex CLI、GitHub Copilot CLI、Aider、Cursor CLI

    架构：

    CLI 入口 (typer/click)
  ↓
用户输入（自然语言）
  ↓
上下文收集（文件、git、环境、历史）
  ↓
LLM 推理 + Tool Calling
  ↓
执行工具（terminal、file I/O、MCP）
  ↓
输出结果（终端打印、文件修改）

    最小实现：

    import typer
from langchain_openai import ChatOpenAI
from langgraph.prebuilt import create_react_agent

app = typer.Typer()

llm = ChatOpenAI(model="gpt-4o")

@app.command()
def main(task: str = typer.Argument(..., help="Task to accomplish")):
    typer.echo(f"🤖 Working on: {task}")
    result = agent.invoke({"messages": [{"role": "user", "content": task}]})
    typer.echo(f"\n✅ Result:\n{result['messages'][-1].content}")

if __name__ == "__main__":

    为什么 CLI Agent 在开发者中更火？ 1. 开发者每天在终端工作，CLI Agent 无缝融入工作流 2. 零配置，安装即用 3. Unix 工具生态丰富，不需要等 MCP Server 生态成熟 4. 可脚本化：python agent.py "fix tests" && git commit

    4.3 决策树：CLI vs MCP¶

    任务需求
  ├─ 本地文件/代码操作？      → CLI（渐进式上下文，零配置）
  ├─ 自动化脚本/CI/CD？       → CLI（可脚本化）
  ├─ 集成外部服务/API/DB？    → MCP（标准化协议，安全性好）
  ├─ 跨语言调用？             → MCP（语言无关）
  └─ 混合场景？               → CLI（本地）+ MCP（外部服务）

    5. Skills（领域技能包）¶

    5.1 概念¶

    一句话：Skill 不是运行时组件，它是一种结构化的知识注入 — 把"怎么做某件事"的经验打包好，喂给 LLM。

    类比： - Tool = 锤子、螺丝刀（原子能力） - Skill = "如何组装一个柜子"的说明书（包含用哪些工具、按什么顺序、注意什么）

    Skill = Tools + Prompts + Workflow + Context

"code_review" Skill:
├── Tools: read_file, terminal (pylint, pytest)
├── Prompts: 审查步骤说明、输出格式要求
├── Workflow: read → lint → test → report
└── Context: 项目用 pytest 不是 unittest，lint 配置在 pyproject.toml

    5.2 实现原理¶

    Skill 的实现有两种模式：

    模式一：静态编排（Workflow-driven）

    用户请求 → 匹配 Skill → 按预定义 workflow 逐步执行
                          step1: tool_A → step2: LLM_prompt → step3: tool_B → ...

    workflow 是硬编码的步骤序列，每一步要么是工具调用，要么是 LLM 推理。流程可控但不灵活。

    模式二：知识注入（Prompt-driven）— 实际主流

    用户请求 → 匹配 Skill → Skill 内容注入 System Prompt → LLM 自主决策执行

    这才是现实中 Skill 的主流实现（Hermes、Claude Code、Cursor 等都用这种）。原理很简单：Skill 本质上就是一段精心编写的 Prompt，被注入到 System Prompt 里，LLM 读了这段"说明书"后自己决定怎么调用工具、按什么顺序执行。

    ┌─────────────────────────────────────────────────────┐
│                  System Prompt                       │
│  ┌───────────────────────────────────────────────┐  │
│  │  Base Instructions (Agent 基础人设)             │  │
│  ├───────────────────────────────────────────────┤  │
│  │  Skill: "code-review"                         │  │
│  │  ─────────────────────────────────────────    │  │
│  │  你是一个代码审查专家。                         │  │
│  │  审查步骤：                                    │  │
│  │  1. 先读代码（read_file）                      │  │
│  │  2. 跑 lint（terminal: pylint）                │  │
│  │  3. 跑测试（terminal: pytest）                 │  │
│  │  4. 给出结构化审查报告                          │  │
│  │  注意事项：                                    │  │
│  │  - 关注安全漏洞                                │  │
│  │  - 检查边界条件                                │  │
│  │  - 项目用 pytest，不用 unittest                │  │
│  └───────────────────────────────────────────────┘  │
│  ┌───────────────────────────────────────────────┐  │
│  │  Available Tools: [read_file, terminal, ...]   │  │
│  └───────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────┘

    两种模式对比：

    维度 静态编排 知识注入（主流）
    谁决定执行步骤 代码（硬编码 workflow） LLM（自主规划）
    灵活性 低（固定流程） 高（按需调整）
    可控性 高（可预测） 低（LLM 可能跳步）
    实现复杂度 高（要写执行引擎） 低（就是写 Prompt）
    实际使用 早期 Agent 框架 Hermes、Claude Code、Cursor 等

    5.3 核心流程（知识注入模式）¶

    1. 用户: "帮我审查 src/main.py"
                    │

2. SkillMatcher:    │  匹配 → "code-review" Skill
                    ▼

3. Skill Loader:    读取 SKILL.md 内容
                    │

4. Prompt Builder:  基础 prompt + Skill 内容 + 工具定义
                    │  → 组装成完整的 System Prompt
                    ▼

5. LLM:             读了 Skill "说明书"，自主规划：
                    │  Thought: 先读代码
                    │  → 调用 read_file("src/main.py")
                    │  Thought: 跑一下 lint
                    │  → 调用 terminal("pylint src/main.py")
                    │  Thought: 跑测试
                    │  → 调用 terminal("pytest")
                    │  Thought: 信息够了，输出审查报告
                    ▼

6. 输出:            结构化审查报告

    5.4 Skill 的核心价值¶

    Skill 的核心价值不是"自动化执行"，而是经验复用：

    1. 领域知识封装 — 把"这个项目用 pytest 不是 unittest"这种经验写下来，LLM 不会犯错
    2. 避免重复踩坑 — 把踩过的坑写成 pitfalls，下次自动避开
    3. 跨会话复用 — 写一次，每次相关任务自动加载
    4. 降低 Prompt 工程门槛 — 非技术人员也能写 Skill（就是写 markdown）

    用 C++ 类比：Skill 就像头文件 — 把声明（接口/知识）写好，用的时候 #include 进来，实现（LLM 推理）由编译器（LLM）自己完成。

    5.5 定义与执行（代码示例）¶

    静态编排模式（适合流程固定的场景）：

    from dataclasses import dataclass

@dataclass
class Skill:
    name: str
    description: str
    tools: list           # 需要的工具
    prompts: dict         # Prompt 模板
    workflow: list        # 执行步骤 [{"step": "read", "tool": "read_file"}, ...]

class SkillEngine:
    """静态编排执行引擎：按 workflow 逐步执行"""

    def __init__(self, llm, tools: dict):
        self.llm = llm
        self.tools = tools
        self.skills = {}

    def register(self, skill: Skill):
        self.skills[skill.name] = skill

    def execute(self, skill_name: str, input_data: dict) -> dict:
        skill = self.skills[skill_name]
        state = {"input": input_data, "results": {}}

        for step in skill.workflow:
            if "tool" in step:
                result = self.tools[step["tool"]].func(**self._resolve_args(step, state))
            elif "prompt" in step:
                prompt = skill.prompts[step["prompt"]].format(**state["results"], **state["input"])
                result = self.llm.invoke(prompt).content
            state["results"][step["step"]] = result

        return state["results"]

    def _resolve_args(self, step, state):
        return {k: v for k, v in state["results"].items() if isinstance(v, str)}

    知识注入模式（主流，实际只需要 Skill 匹配 + Prompt 拼接）：

    class SkillInjector:
    """知识注入模式：将 Skill 内容拼入 System Prompt，由 LLM 自主执行"""

    def __init__(self, base_prompt: str, skills: dict[str, str]):
        self.base_prompt = base_prompt
        self.skills = skills  # name → markdown content

    def build_prompt(self, matched_skill: str | None = None) -> str:
        prompt = self.base_prompt
        if matched_skill and matched_skill in self.skills:
            prompt += f"\n\n---\n\n{self.skills[matched_skill]}"
        return prompt

    5.6 自动匹配¶

    class SkillMatcher:
    """根据用户意图自动匹配最合适的 Skill"""

    def __init__(self, llm, skills: dict[str, str]):
        self.llm = llm
        self.skills = skills  # name → description

    def match(self, user_input: str) -> str | None:
        descriptions = "\n".join(f"- {name}: {desc}" for name, desc in self.skills.items())
        result = json.loads(self.llm.invoke(
            f"Select the best skill for: {user_input}\n\nSkills:\n{descriptions}\n"
            f'Return {{"skill": "name"}} or {{"skill": null}}',
            response_format={"type": "json_object"}
        ).content)
        return result.get("skill")

    6. 工具管理最佳实践¶

    6.1 提高 Tool Calling 准确率¶

    1. 工具描述要精确 — 包含使用场景、参数说明、示例
    2. 减少工具数量 — 相关性筛选，只传相关工具给 LLM
    3. Few-shot 示例 — 在 prompt 中给出正确调用的例子
    4. 参数校验 — 白名单校验工具名，JSON Schema 验证参数

    6.2 工具失败处理¶

    def robust_tool_call(tool_func, tool_input, max_retries=2):
    """工具失败不应让 Agent 崩溃——错误信息返回给 LLM 让它调整策略"""
    for attempt in range(max_retries + 1):
        try:
            return tool_func(**tool_input)
        except Exception as e:
            if attempt < max_retries:
                return f"Error: {e}. Please check your input and try again."
            return f"Error: {e}. Max retries reached."

    6.3 并行工具调用¶

    import asyncio

async def execute_parallel(tools: dict, calls: list[dict]) -> list[dict]:
    """并行执行多个无依赖关系的工具调用"""
    async def run_one(call):
        try:
            func = tools[call["tool"]]
            if asyncio.iscoroutinefunction(func):
                result = await func(**call["args"])
            else:
                loop = asyncio.get_event_loop()
                result = await loop.run_in_executor(None, lambda: func(**call["args"]))
            return {"tool": call["tool"], "status": "success", "result": result}
        except Exception as e:
            return {"tool": call["tool"], "status": "error", "result": str(e)}

    return await asyncio.gather(*[run_one(c) for c in calls])

    OpenAI 的 parallel_tool_calls=True 原生支持并行；同步工具用 run_in_executor 包装。

    6.4 大量工具的处理（>50 个）¶

    工具数量超过 50 时，LLM 选择准确率显著下降。解决方案：两阶段检索。

    import json
import numpy as np

class TwoStageToolSelector:
    """第一阶段 RAG 召回 top-k → 第二阶段 LLM 精选"""

    def __init__(self, all_tools, embed_model, llm):
        self.all_tools = all_tools
        self.embed_model = embed_model
        self.llm = llm
        # 预计算工具描述的 embedding，归一化
        embeddings = np.array(embed_model.embed(
            [f"{t['name']}: {t['description']}" for t in all_tools]
        ))
        self.tool_embeddings = embeddings / np.linalg.norm(embeddings, axis=1, keepdims=True)

    def select(self, query: str, top_k: int = 10) -> list[dict]:
        # 阶段一：向量检索召回（余弦相似度）
        query_emb = np.array(self.embed_model.embed([query])[0])
        query_emb = query_emb / np.linalg.norm(query_emb)
        similarities = self.tool_embeddings @ query_emb  # 已归一化，直接点积
        top_indices = np.argsort(similarities)[-top_k:][::-1]
        candidates = [self.all_tools[i] for i in top_indices]

        # 阶段二：LLM 精选
        result = json.loads(self.llm.invoke(
            f"Query: {query}\nCandidates:\n"
            + "\n".join(f"- {t['name']}: {t['description']}" for t in candidates)
            + '\nReturn {"selected": ["tool1", ...]}',
            response_format={"type": "json_object"}
        ).content)
        return [t for t in candidates if t["name"] in result["selected"]]

    6.5 安全与权限¶

    权限控制：按 READ/WRITE/EXECUTE/ADMIN 分级，危险操作需用户确认。

    沙箱执行：代码在隔离环境运行，禁止 import os/subprocess 等危险操作，设置超时和内存限制。

    Prompt Injection 防御： - 直接注入：用户输入含恶意指令 → 输入过滤 - 间接注入：工具返回内容含恶意指令 → 输出隔离，工具结果和系统指令分开 - 通用手段：工具白名单 + 参数校验 + 权限最小化

    6.6 重试与熔断¶

    import time
import random

class RetryWithBackoff:
    """指数退避重试 + 随机抖动"""
    def __init__(self, max_retries=3, base_delay=1.0, max_delay=60.0):
        self.max_retries = max_retries
        self.base_delay = base_delay
        self.max_delay = max_delay

    def execute(self, func, *args, **kwargs):
        for attempt in range(self.max_retries + 1):
            try:
                return func(*args, **kwargs)
            except Exception as e:
                if attempt == self.max_retries:
                    raise
                delay = min(self.base_delay * (2 ** attempt), self.max_delay)
                delay *= (0.5 + random.random())  # 随机抖动，避免雪崩
                time.sleep(delay)

class CircuitBreaker:
    """熔断器：连续失败 N 次后熔断，保护系统"""
    def __init__(self, threshold=5, recovery_timeout=60):
        self.threshold = threshold
        self.recovery_timeout = recovery_timeout
        self.failure_count = 0
        self.state = "closed"  # closed → open → half-open → closed
        self.last_failure = 0

    def call(self, func, *args, **kwargs):
        if self.state == "open":
            if time.time() - self.last_failure > self.recovery_timeout:
                self.state = "half-open"  # 尝试恢复
            else:
                raise Exception("Circuit breaker is open")
        try:
            result = func(*args, **kwargs)
            self.failure_count, self.state = 0, "closed"
            return result
        except Exception as e:
            self.failure_count += 1
            self.last_failure = time.time()
            if self.failure_count >= self.threshold:
                self.state = "open"
            raise

    7. 面试速记¶

    Q1: Tool Calling 原理？¶

    工具 schema 随 prompt 发给 LLM → LLM 输出结构化 JSON（工具名+参数）→ 框架执行 → 结果送回 LLM → 生成最终回答。

    Q2: Tool Calling vs ReAct？¶

    Tool Calling 输出结构化 JSON（精确），ReAct 输出文本 Thought→Action→Observation（灵活）。现代框架优先 Tool Calling。

    Q3: MCP vs Function Calling？¶

    Function Calling = 单次电话（模型内部调用）；MCP = USB 基础设施（跨进程/跨语言，动态发现工具）。Function Calling 是模型能力（训练出来的），MCP 是外部协议（开发者搭建的）。

    Q4: 如何提高 Tool Calling 准确率？¶

    精确描述（含示例）+ 减少工具数量（筛选）+ Few-shot + 参数校验。

    Q5: 100+ 工具怎么处理？¶

    两阶段检索：RAG 向量召回 top-k → LLM 精选。或按领域分组，先选组再选工具。

    Q6: 手写 MCP Client 要点？¶

    JSON-RPC 2.0 over stdio：每条 JSON 消息占一行并以换行符分隔，不使用 Content-Length。用唯一 id 配对请求和响应，按 initialize → notifications/initialized → tools/list → tools/call 完成握手、发现和调用；生产实现还要支持超时、取消、并发等待表及双向请求。

    Q7: 工具调用的安全性？¶

    权限分级（READ/WRITE/EXECUTE/ADMIN）+ 沙箱隔离 + 危险操作 Human-in-the-Loop + Prompt Injection 防御（输入过滤 + 输出隔离 + 白名单）。

    Q8: CLI Agent 为什么比 MCP Agent 更火？¶

    零配置 + 即时反馈 + Unix 生态丰富 + 可脚本化 + 渐进式上下文（不浪费窗口）。MCP 优势在标准化、安全、跨语言。最佳实践：本地用 CLI，外部服务用 MCP。

    8. Checklist¶

    • Tool Definition：清晰的描述、参数类型、返回值
    • Tool Selection：智能预判是否需要工具调用
    • MCP Integration：标准化协议接入外部工具
    • CLI Tools：shell 命令作为工具（渐进式上下文）
    • Skill System：领域技能包封装
    • Permission Control：权限分级 + Human-in-the-Loop
    • Sandbox：危险操作隔离执行
    • Error Handling：失败重试 + 熔断保护 + 优雅降级
    • Parallel Calls：独立工具调用并行执行
    • Large Tool Set：两阶段检索（RAG + LLM）
