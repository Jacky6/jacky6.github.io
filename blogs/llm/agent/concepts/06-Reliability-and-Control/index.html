    06 可靠性与控制¶

    类型：canonical | 最后核对：2026-10-29 合并自：旧 07-Control_Loop（循环防御）+ 08-Self_Reflection（执行后验证）

    1. 可靠性的三个层面¶

    Agent 不可靠的来源分三层，对策各不相同：

    层面 失败来源 对策
    执行层 工具超时、网络错误、限流 重试、超时、幂等
    行为层 循环、不终止、重复动作 循环防御、终止兜底
    决策层 计划错误、结果错误 执行后验证、外部校验

    核心原则：每层的防御放在运行时，不依赖模型自觉。提示词是建议，代码是保证。

    2. 执行层：重试、超时、幂等¶

    2.1 错误分类决定策略¶

    不是所有错误都该重试：

    错误类型 例子 策略
    瞬时 网络抖动、限流 指数退避重试
    永久 参数错误、权限拒绝 不重试，返回结构化错误给模型
    不确定 下游超时 有限重试 + 熔断

    重试的代价：非幂等操作重试会造成重复副作用（邮件发两次、订单下两笔）。重试前先判断幂等性。

    2.2 幂等设计¶

    # 非幂等 → 加幂等键
def send_email(to, subject, body, idempotency_key: str):
    if already_sent(idempotency_key):      # 查重
        return previous_result(to)
    return mail_api.send(to, subject, body, key=idempotency_key)

    工具设计时给非幂等操作加幂等键（调用方生成、服务端查重），是让"重试"安全的前提。

    2.3 超时与熔断¶

    • 每个工具调用有独立超时（不能共享全局超时，快工具不该被慢工具拖死）；
    • 连续失败达到阈值后熔断该工具（一段时间内直接返回"工具不可用"），让模型换路径而不是反复撞墙。

    3. 行为层：循环防御¶

    五层防御，从基础到高级：

    class LoopGuard:
    max_iterations: int = 15        # 1. 迭代上限
    token_budget: int = 100_000     # 2. Token 预算
    timeout_seconds: int = 300      # 3. 墙钟超时
    repeat_window: int = 3          # 4. 重复检测窗口

    def check(self, iteration, tokens, elapsed, action_sig) -> Stop | None:
        if iteration >= self.max_iterations: return Stop("max_iterations")
        if tokens >= self.token_budget:      return Stop("token_budget")
        if elapsed >= self.timeout_seconds:  return Stop("timeout")
        # 重复动作检测：连续 N 次相同 (工具, 参数)
        self.history.append(action_sig)
        if len(self.history) >= self.repeat_window \
           and len(set(self.history[-self.repeat_window:])) == 1:
            return Stop("repeated_action")
        return None
    层 防什么 实现要点
    迭代上限 无限轮次 运行时计数器
    Token 预算 成本失控 累计统计（含工具结果）
    超时 挂死 墙钟时间
    重复检测 同工具同参数反复调用 签名 = (tool_name, canonical_args)
    收敛检测 状态不再变化 状态哈希对比（高级，可选）

    关键：check() 的结果必须真正影响路由——返回 Stop 就中断，不是只打日志。防御结果被忽略等于没有防御。

    3.1 从循环中恢复¶

    中断不是终点。恢复策略：

    情况 恢复方式
    重复动作 把"你已重复调用 X 三次"作为观察返回，让模型换策略
    预算耗尽 汇总已有中间产物，输出部分结果
    超时 从最近 Checkpoint 恢复（见 03），换更快的工具/模型重试

    4. 决策层：执行后验证¶

    旧教程的"Self-Reflection（自我反思）"高估了模型自评的能力：同一个模型审查自己的输出，可能重复甚至强化原有错误。可靠的验证来自外部：

    验证方式 可信度 例子
    执行验证 最高 跑测试、跑代码、调 API 验证事实
    规则检查 高 Schema 校验、断言、格式检查
    检索证据 中高 引用来源比对
    独立 Judge 中 用另一个模型（不同模型/不同提示）评审
    自我审查 低 同模型自查——只能作为兜底，不能作为主要手段

    设计原则：优先用可机械验证的手段（测试、规则、执行），模型审查只在没有机械手段时使用，且 Judge 要与被审者独立（不同模型或至少不同提示），并经过人工校准（见 08）。

    4.1 Critique-Revise 循环¶

    输出 ──▶ 验证（外部手段）──通过──▶ 完成
              │失败
              ▼
        结构化反馈（哪里错、怎么改）
              │
              ▼
           修订 ──▶ 再验证（有次数上限）

    要点：反馈必须结构化且具体（"第 3 步的 URL 返回 404"），不是"再检查一遍"；修订次数有上限，否则验证-修订本身成为循环。

    5. 降级策略¶

    所有手段失败时的出路：

    降级 做法
    部分结果 输出已完成部分 + 明确说明未完成部分
    换模型 大模型失败时降级到小模型重试简单部分
    人工升级 高价值任务转人工，附完整 Trace

    禁止：静默吞错后输出看似正常的编造结果。宁可说"失败了"，不可假装成功。

    6. 常见失败模式¶

    失败 症状 对策
    防御不生效 检测到循环但继续跑 防御结果接入路由
    重试风暴 限流下越重试越失败 指数退避 + 熔断
    重复副作用 邮件发两次 幂等键
    自评假阳性 模型说"检查过了没问题" 外部验证优先
    静默失败 输出编造结果 降级必须显式声明

    8. 本章要点¶

    1. 可靠性分三层：执行（重试/超时/幂等）、行为（循环防御）、决策（外部验证）。
    2. 防御放运行时，结果必须接入路由；提示词是建议，代码是保证。
    3. 重试前判断幂等性；非幂等操作加幂等键。
    4. 自我审查可信度最低：执行验证 > 规则检查 > 检索证据 > 独立 Judge > 自评。
    5. 降级必须显式：部分结果、换模型、转人工，禁止静默编造。
