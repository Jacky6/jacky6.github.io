    05 多 Agent 模式¶

    类型：canonical | 最后核对：2026-10-29

    1. 什么时候需要多 Agent¶

    先泼冷水：多 Agent 不是升级，是拆分。引入多 Agent 的合理理由只有三个：

    1. 上下文隔离——子任务各自需要大量专属上下文（如研究 + 写作），塞进一个窗口会互相干扰；
    2. 专业分工——不同子任务需要不同的系统提示、工具集甚至模型；
    3. 并行——无依赖的子任务同时执行。

    不合理的理由："多 Agent 更强大""更流行"。多 Agent 的代价：通信开销、结果合并、调试复杂度、成本翻倍。

    判断标准：单 Agent 的上下文没爆、专业提示没冲突、不需要并行 → 不要拆。

    2. 五种模式¶

    2.1 Subagents（子代理）¶

    主 Agent 把子 Agent 包装成工具调用：

    Main Agent ──tool_call──▶ Sub Agent A（独立上下文）
         └──tool_call──▶ Sub Agent B（独立上下文）
    • 子 Agent 有自己的循环、上下文、工具集；
    • 对主 Agent 来说就是一个"执行复杂任务的工具"；
    • 适合：研究、深度分析等需要独立长上下文的子任务。

    2.2 Handoffs（移交）¶

    一个 Agent 判断任务不属于自己，整体移交给另一个 Agent：

    Triage Agent ──handoff──▶ Specialist Agent（接管对话）
    • 与 Subagent 的区别：移交后原 Agent 退出，不是调用返回；
    • 适合：客服分流、前端/后端专家路由。

    2.3 Router（路由）¶

    轻量决策层，只做分发不做执行：

    Router ──▶ Agent A / Agent B / Agent C
    • Router 可以是规则、小模型或 LLM；
    • 适合：入口分流（见 02 的意图路由）。

    2.4 Supervisor（监督者）¶

    Supervisor 动态分配任务给 Worker，汇总结果，决定下一步：

    Supervisor ──▶ Worker A ──▶ 结果 ──▶ Supervisor
          ──▶ Worker B ──▶ 结果 ──▶ Supervisor（决定：继续/合并/结束）
    • 与 Router 的区别：Supervisor 多轮调度（看结果再决定），Router 只分发一次；
    • 适合：需要迭代协作的复杂任务。

    2.5 Custom Workflow（自定义工作流）¶

    开发者写死协作图，节点是 Agent：

    Researcher ──▶ Writer ──▶ Reviewer ──▶（不通过）──▶ Writer
    • 控制流确定，Agent 只在节点内自主；
    • 适合：流程稳定但每步需要智能的管线（如"研究→写作→审查"）。

    模式选择¶

    需求 模式
    子任务需要独立大上下文 Subagents
    任务整体属于另一个专家 Handoffs
    入口分流 Router
    多轮迭代协作 Supervisor
    流程固定、每步智能 Custom Workflow

    3. 本地协作 vs A2A：适用边界¶

    一个常见误区：把"多 Agent"直接等同于 A2A 协议。实际边界：

    维度 本地多 Agent（框架内） A2A（跨服务）
    部署 同一进程/同一所有者 独立服务、不同所有者
    信任 内部可信 需要认证、授权
    通信 进程内函数调用/状态传递 HTTP + 协议消息
    状态 共享 State 显式 Task 生命周期
    例子 LangGraph 子图、handoff 供应商 Agent 互调

    结论：同一 Harness 内的短生命周期子 Agent，用框架的原生机制（子图、handoff、包装成工具）完全合理；跨组织、远程、独立身份、长任务的 Agent 互操作才需要 A2A。两者不是竞争关系，是不同边界的方案。

    A2A 协议细节（Agent Card、Task、Message、Artifact）见 protocols/a2a/。

    4. 结果合并¶

    多 Agent 的隐藏难点：结果怎么合并。

    合并方式 适用 风险
    直接拼接 结果天然独立（各查各的） 冗余、冲突
    LLM 综合 需要消解冲突、生成统一结论 综合本身可能引入幻觉
    结构化聚合 结果是同构数据（投票、求和） 需要统一输出 Schema

    设计要点：子 Agent 的输出用结构化 Schema 约束，合并逻辑可预测；不要让子 Agent 输出自由文本再让另一个 LLM"看着办"。

    5. 常见失败模式¶

    失败 症状 对策
    为拆而拆 单 Agent 能做但拆成三个 回到第 1 节的判断标准
    责任稀释 多个 Agent 互相推诿 每个 Agent 有明确职责边界
    合并冲突 子结果矛盾无法消解 结构化输出 + 显式冲突处理
    成本爆炸 并行子 Agent 各自多轮 子 Agent 也要预算和迭代上限
    调试地狱 不知道哪个 Agent 出错 全链路 Trace（见 08）

    7. 本章要点¶

    1. 多 Agent 是拆分不是升级：上下文隔离、专业分工、并行是仅有的三个合理理由。
    2. 五种模式：Subagents、Handoffs、Router、Supervisor、Custom Workflow，按需求选。
    3. 本地协作用框架原生机制，跨服务互操作才用 A2A——不同边界的方案。
    4. 结果合并是隐藏难点：子 Agent 输出结构化，合并逻辑可预测。
    5. 子 Agent 同样需要预算和迭代上限，多 Agent 不豁免可靠性要求。
