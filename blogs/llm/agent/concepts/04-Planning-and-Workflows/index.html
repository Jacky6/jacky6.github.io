    04 规划与工作流¶

    类型：canonical | 最后核对：2026-10-29

    1. 是什么¶

    规划（Planning）解决"多步任务怎么拆、怎么排、怎么推进"。先明确一个前提：

    不是所有多步任务都需要模型规划。 步骤固定的话，用确定性 Workflow；步骤需要动态决定，才需要模型规划。

    任务复杂度光谱：

固定流程 ────────▶ 半动态 ────────▶ 全动态
Workflow          带分支 Workflow      Agent 规划
（写死步骤）      （固定步骤+条件跳转）  （模型生成计划）
    方案 控制流 可预测性 适用
    Workflow 开发者写死 高 步骤已知且稳定
    带分支 Workflow 写死 + 条件路由 高 少数已知变体
    Plan-and-Execute 模型先生成计划，再逐步执行 中 步骤未知但可枚举
    纯 Agent Loop 每轮即兴决定 低 环境反馈驱动、无法预先计划

    选型原则：能预测的都交给 Workflow，不能预测的才交给模型。混合方案（外层 Workflow + 局部 Agent）是生产系统最常见的形态。

    2. Plan-and-Execute¶

    与纯 Agent Loop（每轮即兴）相对，Plan-and-Execute 先生成完整计划再执行：

    ┌────────┐    ┌──────────┐    ┌──────────┐
│ Planner │───▶│ Executor │───▶│ Replan?  │
│ 生成计划 │    │ 逐步执行  │    │ 失败时重规划│
└────────┘    └──────────┘    └──────────┘
    维度 纯 Agent Loop Plan-and-Execute
    每轮成本 低（只看当前状态） 计划阶段一次性高
    全局性 弱（容易短视） 强（先看全局）
    出错恢复 自然（下轮修正） 需要显式重规划
    适用 探索型、反馈驱动 步骤可枚举的长任务

    2.1 计划的数据结构¶

    计划应该是可执行、可校验的结构化数据，不是一段自然语言：

    @dataclass
class Task:
    id: str
    description: str
    depends_on: list[str]      # 依赖的任务 id
    expected_output: str       # 完成标准

plan: list[Task] = planner(task)   # DAG

    要点：

    1. 每个任务有完成标准（expected_output）——否则无法判断是否完成；
    2. 依赖显式声明——支持并行执行无依赖的任务；
    3. 计划存入 State——执行中可对照，失败可重规划。

    2.2 依赖图与并行¶

    # 拓扑排序 + 分层并行
ready = [t for t in plan if all(d in done for d in t.depends_on)]
results = parallel_execute(ready)   # 同层任务并行
done |= {t.id for t in ready}

    同层无依赖任务并行执行是 Plan-and-Execute 相对串行 Loop 的主要收益。

    2.3 重规划¶

    执行失败时的三种策略：

    策略 做法 适用
    重试 原计划重执行该步 瞬时错误
    局部重规划 只替换失败任务及其下游 计划大体正确
    全局重规划 重新生成计划 前提理解错误

    重规划要有次数上限，否则"规划-失败-重规划"本身成为循环（见 06-Reliability-and-Control）。

    3. 计划审批（Plan Approval）¶

    高风险场景中，计划生成后先给人工确认再执行：

    Planner → 计划 → [人工审批] → Executor
                    │
                    └─ 修改/拒绝 → 重规划

    这是成本最低的安全干预点：在执行前拦截，而不是在每步执行时拦截（对比 07-Safety-and-HITL 的逐步审批）。

    4. 关于推理策略的定位¶

    旧教程把 CoT / ToT / Self-Consistency 作为独立"推理模块"讲解。现代定位：

    策略 现状
    CoT 已内化为模型能力；生产中不要求模型输出完整推理链，改为要求结构化计划 + 简短理由 + 可验证中间产物
    ToT / Self-Consistency 采样/搜索策略，用于离线优化或高价值决策，不是运行时默认

    关键转变：不要依赖模型的原始推理文本作为可信依据。可验证的东西放外部——计划结构、执行结果、证据引用。模型"想得对不对"由执行验证判断，不由它自己的陈述判断（见 06 的执行后验证）。

    5. 常见失败模式¶

    失败 症状 对策
    计划粒度失衡 一步太大无法执行 / 太碎浪费轮次 计划模板约束粒度
    计划脱离现实 步骤依赖不存在的工具/数据 计划校验：工具可用性检查
    只执行第一步 生成了计划但循环只跑第一步 计划存入 State，逐步推进并对照
    重规划风暴 反复推倒重来 重规划次数上限
    过度规划 简单任务也生成冗长计划 路由判断：简单任务直接执行

    7. 本章要点¶

    1. 能预测的步骤交给 Workflow，不能预测的才交给模型规划；混合方案最常见。
    2. 计划是结构化 DAG：显式依赖、完成标准、存入 State。
    3. 无依赖任务并行执行是 Plan-and-Execute 的主要收益。
    4. 重规划要有上限；计划审批是成本最低的安全干预点。
    5. 不依赖模型推理文本作为可信依据，可验证的放外部。
