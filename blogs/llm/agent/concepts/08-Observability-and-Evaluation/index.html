    08 可观测性与评估¶

    类型：canonical | 最后核对：2026-10-29

    1. 为什么 Agent 评估比普通 LLM 应用难¶

    单次调用只需评估"输出对不对"；Agent 要评估整条轨迹：

    评估对象 问题
    最终结果 任务完成了吗？
    轨迹 走的路径对吗？有没有绕路、死循环、错误工具？
    工具使用 选对工具了吗？参数对吗？
    成本/延迟 花了多少 Token、多少时间？

    只看最终结果会漏掉"结果对但过程错"（碰巧对了）和"结果错但过程对"（差一步）的情况。

    2. 可观测性：Trace¶

    Trace 是评估的数据基础。每次运行记录完整轨迹：

    Run
 ├─ 轮次 1
 │   ├─ 模型调用（输入消息、输出、token 用量、延迟）
 │   └─ 工具调用（名称、参数、结果、耗时、错误）
 ├─ 轮次 2
 │   └─ ...
 └─ 最终输出 + 终止原因

    必须记录的字段：

    字段 用途
    每轮的完整消息 回放调试
    工具调用的参数和结果 轨迹评估
    Token 用量和延迟 成本/性能分析
    终止原因（自然/上限/超时/取消） 可靠性统计
    错误与重试 失败模式分析

    注意：Trace 里的工具结果和错误信息要脱敏（见 07-Safety-and-HITL）。

    工具选择：LangSmith、OpenTelemetry 或自建 JSONL——重点不是工具，是字段完整。

    3. 评估体系¶

    3.1 Golden Set（黄金测试集）¶

    回归测试的基石：

    - id: ts-001
  task: "查询北京明天的天气并给出穿衣建议"
  expected_tools: ["get_weather"]          # 期望调用的工具
  expected_outcome: "包含温度数据和建议"     # 完成标准
- id: ts-002
  task: "总结 ./docs 下的所有 markdown 文件"
  expected_tools: ["read_file", "list_dir"]
  expected_outcome: "覆盖所有文件的关键点"

    设计要点：

    1. 覆盖典型场景 + 已知失败案例（每个线上 bug 变成一个测试用例）；
    2. 期望工具序列是轨迹评估的锚点；
    3. 完成标准可判定（能写出断言或清晰 rubric），"回答得好"不可判定。

    3.2 三层评估¶

    层 评估什么 方法
    轨迹正确性 工具选择和顺序 期望序列比对（精确/子序列/集合）
    工具参数准确率 参数填对没有 参数级比对
    端到端结果 任务完成质量 断言、LLM Judge、人工

    3.3 LLM-as-Judge 的正确用法¶

    Judge 可扩展但有偏差，使用前必须校准：

    偏差 症状 缓解
    位置偏差 偏爱先出现的答案 交换顺序评两次
    长度偏差 偏爱长回答 rubric 明确"简洁不扣分"
    自我偏好 偏爱同模型输出 Judge 与被评模型不同
    慷慨偏差 一律打高分 用已知答案的锚定用例校准

    校准方法：抽 50-100 条人工标注，与 Judge 结果对比，一致率达标（如 >85%）才可用于回归；不达标就修 rubric 或换 Judge。

    3.4 非确定性的处理¶

    Agent 评估天然有随机性，单次运行说明不了问题：

    • 每个用例跑 N 次（如 3-5 次），报告通过率而不是通过/失败；
    • 对比两个版本时用统计检验，不看单次差异；
    • 记录方差——方差大的系统即使均值高也不可信。

    4. 持续评估（生产）¶

    离线回归（每次改动跑 Golden Set）
        │
        ▼
在线采样评估（生产流量抽样 + Judge/人工）
        │
        ▼
监控指标（成本、延迟、终止原因分布、工具错误率）
        │
        ▼
失败案例 → 新增 Golden Set 用例（闭环）

    关键闭环：线上发现的每个失败模式都沉淀为测试用例，否则同样的错误会反复出现。

    监控指标¶

    指标 健康信号
    平均轮次 突增 = 循环或规划退化
    终止原因分布 上限/超时占比突增 = 可靠性问题
    工具错误率 突增 = 下游故障或参数退化
    每任务成本 突增 = 上下文管理退化
    HITL 拒绝率 突增 = 行为漂移

    5. 测试策略¶

    层 测什么 工具
    单元 单个工具、组装逻辑 常规测试框架 + Mock 模型
    集成 循环 + 工具 + 状态 脚本化模型响应（确定性回放）
    端到端 真实模型跑 Golden Set 评估框架

    Mock 模型的正确姿势：不要用关键词匹配模拟"智能"，要脚本化——按调用顺序返回预设响应，这样可以断言"第 2 轮应该请求工具 X"。

    6. 常见失败模式¶

    失败 症状 对策
    只看结果 过程错误没被发现 轨迹评估
    Judge 未校准 回归"全绿"但质量下降 人工标注对比校准
    单次运行下结论 被随机性误导 多次运行 + 统计检验
    无失败闭环 同样的 bug 反复出现 线上失败 → 测试用例
    Trace 不完整 无法回放定位 字段清单核查

    8. 本章要点¶

    1. Agent 评估看轨迹不只看结果：轨迹正确性、参数准确率、端到端三层。
    2. Trace 字段要完整（消息、工具、成本、终止原因），这是回放和评估的基础。
    3. Golden Set 覆盖典型场景和已知失败；完成标准必须可判定。
    4. Judge 必须校准（人工标注对比）且与被评模型独立。
    5. 非确定性要求多次运行 + 统计检验；线上失败沉淀为测试用例形成闭环。
