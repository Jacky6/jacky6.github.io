    读 Anthropic《The Components of Agent Memory》：Dreaming 与四层记忆架构¶

    类型：derived（外部文章研读笔记，不独立定义事实） | 最后核对：2026-11-09 事实源：Anthropic Research, The components of agent memory（2026-11 上旬），https://www.anthropic.com/research/components-of-agent-memory 关联章节：../03-State-Context-Memory.md——本文是其 §4「Store 跨会话记忆」与 §5「记忆污染/巩固」的产业界实证与扩展 日报出处：../../../../news/2026-11-09.md §5.1

    1. 一句话与核心隐喻¶

    Agent 记忆不应在会话进行中一次性定稿，而应分两层：会话内快速"标记" + 会话间离线整理（dreaming）。

    隐喻来自神经科学：海马体即时编码经历；睡眠/静息时海马体回放（replay），逐步蒸馏整合进新皮层（长期知识）。工程对应物：Letta/UC Berkeley 的 sleep-time compute；Google 的 Sleep 框架。Anthropic 的贡献是把它做成可评估的工程系统并公开全部实验数据。

    2. 「记忆」的定义边界¶

    概念 算不算 Agent 记忆
    权重更新 ❌（训练时固化）
    In-context learning ❌（不跨会话）
    Compaction 摘要 ❌（遗忘管理，非知识沉淀）
    从经验获得、跨会话保留、之后能读回上下文的知识（落盘为文件/库） ✅

    3. 四层记忆层级¶

    ┌─────────────────────────────────────────┐
│ ④ Injected Context（每会话开头预载）      │ ← 最小、最贵
│ ③ Memory Representations（wiki 等表征）   │ ← dreaming 构建/维护
│ ② Memory Notes（会话内写的显著性笔记）     │ ← 会话内写入
│ ① Transcripts（可搜索的原始日志）          │ ← 底座、ground truth
└─────────────────────────────────────────┘
       dreaming 在 ①→②③④ 之间双向流动

    关键设计：transcripts 是 ground truth，上三层都是从它蒸馏的"缓存"，都可被 dreaming 拿原始日志校验和重写。

    4. 写入侧：显著性判断是模型能力，且代际进化明显¶

    记忆本质是一种预测：写下一条规则 = 预测"未来还会用到"。所以记忆质量 ≈ 模型的显著性判断质量。

    4.1 CL-Bench 数据库问答任务（无记忆 → 有记忆）¶

    模型 无记忆 有记忆 行为特征
    Sonnet 4.6 0.330 0.364 只写下一堆没验证的猜测
    Opus 4.7 0.383 0.700 合并成单一参考文档，标注"已验证/未确认"
    Opus 5 0.564 0.828 首个闭环：规则 + 证据 + 历史答案 + 陷阱警告
    Opus 5.5 / Sonnet 5.5 0.655 / 0.644 0.838 / 0.833 均闭环

    4.2 Pokémon 对照实验（约 1 万步时对比记忆目录）¶

    Sonnet 3.7 Fable 5
    规模 413 文件 / 225 目录 / 97.8 万字符 9 文件 + global.md / 4.3 万字符
    进度 1 枚徽章 4 枚徽章
    败因 每场战斗/道具/NPC 都存档——冗余且迅速过期；曾连续 17 步只在维护记忆、一步游戏没玩 只记"游戏不直接告诉它的"：策略、计划、已验证规则

    Fable 5 的 global.md 是仪表板（当前目标 + 预案 + 记忆使用规则）。Opus 5.5 用同款小目录策略通关了游戏。

    4.3 Steering 教训：告诉"为什么"，别规定"怎么做"¶

    • 强模型给死规则反而有害：强制"只记录失败"后，Opus 5 的记忆收益 −0.234、Opus 4.7 −0.150。
    • 老模型需要 steering：指示 Sonnet 4.6"答题前先读记忆 + 显式验证理论"后，0.364 → 0.641（近翻倍）。Sonnet 5 则 10 次中 9 次主动先读记忆，无需提示。

    5. Dreaming 的五项功能¶

    5.1 纠错（拿 transcripts 当 ground truth 校验笔记）¶

    Pokémon 月见山案例：Claude 错记"PokéCenter 在山东侧"→ 宣布"月见山 DONE"→ 从单向悬崖掉回出发点却浑然不觉。未纠错的 run 掉了三次后"放弃"；跑过 dreaming 的 run 对照 transcript 发现并改写了错误笔记，第 1,935 个动作到达华蓝市。

    5.2 构建新表征（wiki 实验）¶

    语料：Stainless 内部文档（35 万文件 / 4.2 亿 token），25 个问题，Opus 5 经 2→128 个 dreaming 会话增量建 wiki：

    配置 得分
    仅 wiki 13% → 48%
    仅搜索工具 53%（不随 wiki 变化）
    wiki + 搜索 54% → 61%，每题省约 2 万 token

    wiki 何时有用：Harvey LAB 法律基准中需跨多文档 + 判断/计算的 24 题，wiki 87% vs 纯搜索 73%。何时没用：答案可在单文档搜到的任务无增益；极端反例是 wiki 长得比语料还大（1.77 倍）——作者引博尔赫斯"地图与帝国一样大"自嘲：抽象为零的表征没有价值。

    5.3 上浮（injected context 保持小）¶

    顶层每会话预载、无需搜索，但 token 宝贵、错误笔记会带进每个会话、加载≠遵守（指令越长遵守率越低）。dreaming 的工作之一是保持顶层小：细节下沉、留下链接。Claude Code auto memory 同款设计：MEMORY.md 只加载前 200 行 / 25KB 作索引。

    5.4 定向（按目标塑造记忆 + 指令自改进循环）¶

    合同摘要任务：多 agent 并发写共享条款表、互相覆盖 → 57 个评分要点只保住 41 个（72%）。随后跑"反思失败 → 改指令 → 重建 wiki"循环，Claude 自己改为"每合同单独一页、条款逐字引用、单 agent 单页"→ 57/57（100%）。

    工程启示：harness 指令本身也可被 agent 迭代优化。

    5.5 补缺（跨会话发现单会话看不见的洞）¶

    单会话只见当前上下文；dreaming 跨会话搜索共性模式。案例：wiki 中 9 个链接指向不存在的页面，第二轮 dreaming 全部重指向正确页面，并补建 3 个新页面（含索引页）。

    6. 文章自陈的开放问题¶

    1. 何时写：会话内即时写分散注意力；dreaming 后台写则不能即时可用。
    2. 如何保鲜：全量校验不现实——聚焦易变信息，或按访问频率调节 dreaming 节奏。
    3. transcript 搜索作底座：表征 + 搜索组合最有效，但维护表征要花算力、防累积幻觉。
