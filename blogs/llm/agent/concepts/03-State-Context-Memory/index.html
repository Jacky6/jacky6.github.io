    03 状态、上下文与记忆¶

    类型：canonical | 最后核对：2026-10-29

    1. 四个容易混淆的概念¶

    旧教程把 Memory 讲成"短期/会话/长期"三层，但不同框架用词不一致，先统一术语：

    概念 定义 生命周期 例子
    Context（上下文） 本次模型调用实际看到的全部信息 单次调用 system + 历史 + 检索结果 + 工具结果
    State（状态） Agent 运行中的可变数据结构 一次运行/会话 消息列表、任务清单、中间产物
    Checkpoint（检查点） State 的持久化快照，用于恢复 跨进程重启 thread 对应的历史快照
    Store（长期存储） 跨会话共享的结构化数据 跨会话/跨用户 用户偏好、知识条目

    关系：Memory 不是独立机制，而是"State 怎么持久化（Checkpoint）+ 什么信息跨会话保留（Store）+ 每次调用放什么进 Context（组装策略）"的组合。

    State ──持久化──▶ Checkpoint（恢复用）
Store ──检索──▶ ┐
RAG  ──检索──▶ ├─组装──▶ Context ──▶ 模型调用
历史 ──压缩──▶ ┘

    2. Context 组装¶

    每次模型调用前，运行时组装 Context。这是上下文工程的核心（跨框架设计见 engineering/context-engineering/）。

    2.1 组成部分与优先级¶

    ┌─────────────────────────────────┐
│ System Prompt（角色、规则）       │  最高优先级
├─────────────────────────────────┤
│ 检索结果（RAG）                   │
│ 长期记忆（Store 检索）            │  按相关性
│ 工具结果（本轮）                   │
├─────────────────────────────────┤
│ 对话历史（压缩后）                 │  可被摘要替代
├─────────────────────────────────┤
│ 当前用户输入                      │  必须完整
└─────────────────────────────────┘

    2.2 Token 预算管理¶

    class ContextBudget:
    total: int = 128_000
    allocation = {
        "system":    2_000,   # ~2%
        "retrieval": 40_000,  # ~31%
        "memory":    10_000,  # ~8%
        "tools":     20_000,  # ~16%
        "history":   50_000,  # ~39%
        "reserve":    6_000,  # 输出预留
    }

    原则：每类信息有预算上限，超限先压缩再截断，不能让单一来源挤占全部窗口。

    2.3 历史压缩策略¶

    策略 做法 适用
    滑动窗口 只保留最近 N 轮 简单场景
    摘要压缩 旧消息 LLM 摘要后替换 长会话
    选择性保留 按相关性过滤历史消息 检索型任务
    工具结果清理 旧轮的大结果替换为占位符 工具密集型

    工具结果清理常被忽略但收益最大：几轮前的网页全文对当前决策几乎无用。

    3. Checkpoint：恢复与时间旅行¶

    Checkpoint 保存 State 快照，提供三个能力：

    1. 断点恢复——进程崩溃后从最近快照继续；
    2. 人机协作——循环暂停等人工审批，之后从暂停点恢复（见 07-Safety-and-HITL）；
    3. 回放调试——从任意历史点重放，对比不同策略。

    设计要点：

    • 以 thread（会话） 为单位组织，快照按步递增；
    • 快照要包含完整 State（消息、工具结果、中间产物），否则恢复后行为不一致；
    • 生产用数据库持久化（SQLite/Postgres），内存实现只用于测试。

    ⚠️ 不要自研 Checkpointer 兼容层——框架的 Checkpoint 接口与运行时深度耦合，自制实现极易不兼容。使用框架官方实现。

    4. Store：跨会话记忆¶

    Store 解决"什么信息值得跨会话保留"：

    子问题 做法
    写什么 显式写入（工具/流程触发），不是所有消息都存
    怎么组织 namespace 分区（如 ("user", user_id, "preferences")）
    怎么检索 语义检索（embedding）+ 元数据过滤
    怎么维护 记忆巩固：定期合并、去重、衰减过时条目

    常见错误：把所有对话消息晋升为长期记忆。正确做法是选择性提取——只存稳定事实（用户偏好、已确认的结论），不存过程性内容。

    注意区分：Store 与 RAG 的边界在用途——Store 存 Agent 自己产生的记忆，RAG 检索外部知识库。实现上可能都用向量库，但写入策略完全不同。

    5. 常见失败模式¶

    失败 症状 对策
    上下文爆炸 轮数越多回答越差 预算 + 压缩 + 工具结果清理
    记忆污染 错误信息被长期记住 写入前校验；巩固时清理
    检索不准 相关记忆召回不了 元数据过滤 + 重排序
    恢复不一致 恢复后行为突变 快照包含完整 State
    记忆幻觉 检索为空时模型编造记忆 空结果显式告知"无相关记忆"

    7. 本章要点¶

    1. 四概念：Context（单次调用）、State（运行中）、Checkpoint（恢复）、Store（跨会话）。
    2. Memory = 持久化策略 + 跨会话保留 + 组装策略的组合，不是独立机制。
    3. Context 组装有预算，工具结果清理是性价比最高的压缩。
    4. Checkpoint 用官方实现，Store 写入要选择性提取。
