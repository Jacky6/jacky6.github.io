    MCP 概念与架构¶

    本教程以当前正式协议版本 2026-07-28 为主线，并在需要时标注 2025-11-25 及更早版本的差异。资料核对日期：2026-10-28。

    1. MCP 解决什么问题¶

    MCP（Model Context Protocol）是 AI 应用与外部能力之间的标准协议。它定义的是：

    • AI 应用怎样发现服务端提供的工具、资源和提示模板；
    • Client 与 Server 怎样交换 JSON-RPC 消息；
    • 本地子进程和远程 HTTP 服务怎样承载这些消息；
    • 版本、能力、缓存、通知、错误和授权怎样表达。

    MCP 不负责：

    • 决定使用哪一个 LLM；
    • 实现 Agent 的规划循环；
    • 替模型执行 Function Calling；
    • 规定工具结果一定怎样进入模型上下文；
    • 自动提供沙箱、权限或安全边界。

    可以把它理解为 AI 集成层的标准接口，而不是一个 Agent 框架。

    用户请求
   │
   ▼
AI 应用 / Agent Runtime
   │  选择工具、请求确认、组织模型上下文
   ▼
MCP Client
   │  JSON-RPC 2.0
   ▼
MCP Server
   │
   ├── 本地文件 / Git / CLI
   ├── 数据库
   └── SaaS / 内部 API

    2. 三个参与者¶

    2.1 Host¶

    Host 是承载模型、UI 和 Agent Runtime 的 AI 应用，例如 IDE、桌面客户端或自研 Agent 平台。

    Host 负责：

    • 创建和管理多个 MCP Client；
    • 决定连接哪些 Server；
    • 汇总多个 Server 的工具和上下文；
    • 把工具定义交给 LLM；
    • 审批工具调用和敏感操作；
    • 保持不同 Server 之间的安全边界；
    • 管理用户身份、模型上下文和会话。

    Host 才是复杂编排的中心。Server 应尽量聚焦于一个明确领域。

    2.2 Client¶

    Client 是 Host 内部的协议组件。通常一个 Client 只连接一个 Server：

    graph LR
    H[MCP Host] --> C1[MCP Client A]
    H --> C2[MCP Client B]
    C1 --> S1[Filesystem Server]
    C2 --> S2[Database Server]

    Client 负责：

    • 为每个请求附加协议版本和 Client 能力；
    • 调用 server/discover、tools/list 等方法；
    • 使用请求 ID 匹配响应；
    • 处理分页、缓存、通知、取消和超时；
    • 将 MCP Tool 转换成模型厂商的 Tool Schema；
    • 将模型生成的 Tool Call 路由到正确的 MCP Server。

    2.3 Server¶

    Server 是提供上下文和操作能力的程序，可以是：

    • Host 启动的本地 stdio 子进程；
    • 独立部署的 Streamable HTTP 服务（普通请求可返回非流式 JSON）；
    • 任意语言实现的服务，只要遵循协议。

    这里的 Streamable 表示传输支持按需使用 SSE，并不要求每个请求都流式返回。普通 Tool 调用完全可以直接返回一次性的 application/json 响应；只有进度通知、长期订阅等场景才需要 SSE。

    Server 负责：

    • 实现 server/discover；
    • 声明自己的协议版本和能力；
    • 暴露 Tools、Resources、Prompts；
    • 校验参数、权限和 URI；
    • 返回协议错误或可恢复的业务错误；
    • 遵守无状态、缓存和安全规则。

    Server 默认看不到完整对话，也不应看到其他 Server 的数据。Host 只应向它发送完成当前请求所必需的信息。

    3. 两层协议结构¶

    MCP 可分为数据层与传输层。

    3.1 数据层¶

    数据层基于 JSON-RPC 2.0，定义：

    • Request、Response、Notification；
    • server/discover；
    • Tools、Resources、Prompts；
    • MRTR（Multi Round-Trip Requests）；
    • 订阅、进度、取消、分页、缓存；
    • 协议版本和能力元数据。

    3.2 传输层¶

    当前标准传输有两种：

    传输 典型场景 消息承载
    stdio 本地 Server stdin/stdout，每行一条 JSON-RPC 消息
    Streamable HTTP 远程 Server 每条请求一个 HTTP POST，响应为 JSON 或 SSE

    同一个数据层方法，例如 tools/call，可以运行在任一传输之上。

    4. 核心原语¶

    4.1 Tools：模型控制¶

    Tool 表示可执行动作，例如：

    • 查询数据库；
    • 创建工单；
    • 写入文件；
    • 调用业务 API。

    典型流程：

    Client ── tools/list ──▶ Server
Client ◀─ Tool Schema ── Server
   │
   ├─ 把 Schema 交给 LLM
   │
LLM 生成 name + arguments
   │
Client ── tools/call ──▶ Server
Client ◀─ Tool Result ── Server

    Tools 被称为 model-controlled，意思是模型通常可以根据工具描述选择调用它们；不代表模型绕过 Host 直接连接 Server。真正发送 tools/call 的仍然是 Client。

    4.2 Resources：应用控制¶

    Resource 是由 URI 标识的上下文数据，例如：

    • file:///project/README.md；
    • git://repo/commit/abc123；
    • 数据库 Schema；
    • 业务记录或报告。

    Resource 被称为 application-driven：通常由 Host 的资源选择器、规则或用户决定怎样放入上下文，而不是等价于有副作用的工具调用。

    4.3 Prompts：用户控制¶

    Prompt 是 Server 提供的可参数化消息模板，例如代码审查、故障排查模板。它通常以命令或 UI 菜单呈现，由用户显式选择，因此称为 user-controlled。

    原语 主要语义 常见控制方 核心方法
    Tools 执行动作 模型，经 Host 审批 tools/list、tools/call
    Resources 读取上下文 应用或用户 resources/list、resources/read
    Prompts 获取消息模板 用户 prompts/list、prompts/get

    这些是交互模型，不是协议强制的 UI。Host 可以采用其他展示方式。

    5. 一次完整 Tool 调用¶

    sequenceDiagram
    actor U as User
    participant H as Host
    participant L as LLM
    participant C as MCP Client
    participant S as MCP Server

    opt 能力发现
        C->>S: server/discover
        S-->>C: versions + capabilities
    end
    C->>S: tools/list
    S-->>C: tools + inputSchema
    H->>L: 用户消息 + Tool Schemas
    L-->>H: tool_call(name, arguments)
    H->>U: 敏感操作确认（可选）
    U-->>H: 允许
    H->>C: 执行工具
    C->>S: tools/call
    S-->>C: content / structuredContent
    C-->>H: Tool Result
    H->>L: Tool Result
    L-->>H: 最终回答
    H-->>U: 展示结果

    关键点：

    1. LLM 不直接讲 MCP；它看到的是 Host 转换后的工具定义。
    2. MCP 不取代模型的 Tool Calling；MCP 负责 Client 与 Server 之间的发现和调用。
    3. Host 是权限、确认、工具聚合和上下文管理的责任方。
    4. Server 返回的工具描述和结果都是不可信输入，不能当系统指令处理。

    6. 2026-07-28 的无状态协议¶

    这里的“无状态”专指没有协议级 Session 状态，不是说 Server 不能保存数据库数据，也不是说 HTTP、SSE 或 stdio 连接必须立即关闭。

    6.1 到底移除了什么状态¶

    2025-11-25 及以前，Client 和 Server 先通过 initialize 建立一段协议 Session。后续请求会隐式依赖初始化阶段保存的信息：

    • 协商后的协议版本；
    • Client 和 Server Capabilities；
    • Client/Server 身份信息；
    • HTTP Server 可选分配的 Mcp-Session-Id；
    • Server→Client Request 使用的反向通道；
    • Resource Subscription 等连接级状态。

    从 2026-07-28 开始，这些信息不能再依赖“之前在同一连接上发生过什么”。每个 Request 都必须包含处理它所需的版本和 Client Capabilities。

    状态类型 Legacy：2025-11-25 及以前 Modern：2026-07-28
    协议版本 initialize 时协商并保存在 Session 每个 Request 在 _meta 中声明
    Client Capabilities initialize 时声明一次 每个 Request 都携带相关能力
    Server Capabilities Initialize Result 返回 server/discover 返回
    HTTP Session Server 可返回 Mcp-Session-Id 已移除
    Server→Client Request 可通过 stdio/SSE 反向发送 已移除，改用 MRTR
    变化通知 独立 GET SSE、resources/subscribe 等 subscriptions/listen 长请求
    SSE 恢复 可使用 Event ID、Last-Event-ID 已移除
    跨请求业务状态 经常被实现为连接/Session 状态 必须使用显式 Handle 或外部存储

    6.2 Legacy 初始化流程¶

    以 2025-11-25 为例，连接后的第一件事必须是初始化：

    sequenceDiagram
    participant C as Legacy Client
    participant S as Legacy Server

    C->>S: initialize(protocolVersion, capabilities, clientInfo)
    S-->>C: protocolVersion + capabilities + serverInfo
    C--)S: notifications/initialized
    Note over C,S: 协议 Session 建立
    C->>S: tools/list
    S-->>C: tools
    C->>S: tools/call
    S-->>C: Tool Result

    初始化请求类似：

    {
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-11-25",
    "capabilities": {
      "roots": {},
      "sampling": {}
    },
    "clientInfo": {
      "name": "example-client",
      "version": "1.0.0"
    }
  }
}

    初始化完成后，普通 tools/list、tools/call 不再重复发送版本和能力，因为 Server 从 Session 中读取。

    在 Legacy Streamable HTTP 中，Server 还可以在 Initialize Response 中返回：

    Mcp-Session-Id: 1868a90c...

    Client 随后的 HTTP 请求必须带回这个 ID。Server 可能把 Session 数据只放在创建它的进程内存中，因此多实例部署通常需要 Sticky Session；请求落到另一个实例时可能得到 Session not found。

    stdio 没有 HTTP Header，但 Server 进程仍会把初始化结果和连接绑定，同样属于隐式协议状态。

    6.3 Modern 每请求流程¶

    现代协议不需要初始化，也不要求 Client 先调用 server/discover。规范要求 Server 必须实现 Discover，但 Client 可以不调用：

    • Client 已知要使用的协议版本时，可以直接发送携带完整 _meta 的 tools/list、tools/call 等业务请求；
    • Client 想预先查询 Server 支持的版本和能力时，可以先调用一次 server/discover；
    • 直接调用遇到 UnsupportedProtocolVersion 时，也可以根据 Server 返回的版本列表选择共同版本并重试。

    因此，若 Client 选择预发现，从报文数量看确实是把 Legacy 的 initialize 加 notifications/initialized 两条设置消息变成一条 server/discover Request；但本质区别不是“少一次调用”，而是 Discover 只是普通的无状态查询，既不建立 Session，也不让后续请求省略 _meta。Client 也可以完全跳过它，实现零前置握手。

    sequenceDiagram
    participant C as Modern Client
    participant S as Modern Server

    opt 可选预发现
        C->>S: server/discover + _meta
        S-->>C: supportedVersions + capabilities
    end
    C->>S: tools/list + _meta
    S-->>C: resultType=complete + tools
    C->>S: tools/call + _meta
    S-->>C: resultType=complete + Tool Result

    每个请求都包含：

    {
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/list",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": {
        "name": "example-client",
        "version": "1.0.0"
      },
      "io.modelcontextprotocol/clientCapabilities": {
        "elicitation": {
          "form": {}
        }
      }
    }
  }
}

    其中：

    • protocolVersion 必填；
    • clientCapabilities 必填；
    • clientInfo 建议携带，但不能用于安全决策；
    • HTTP 还必须在 MCP-Protocol-Version Header 中发送相同版本。

    Server 不支持该版本时返回 -32022 UnsupportedProtocolVersion 和支持列表，Client 选择双方共同版本后以新请求重试。

    6.4 server/discover 的角色变化¶

    现代 Server 必须实现 server/discover，但 Client 不一定要先调用：

    策略 A：server/discover → 选择版本/能力 → tools/list
策略 B：直接 tools/list → 遇到版本错误再选择共同版本

    Discover Response 返回：

    • supportedVersions；
    • Server Capabilities；
    • Server Info；
    • 可选 Instructions；
    • ttlMs 和 cacheScope。

    因此它是“预发现”方法，不是新的初始化握手。调用过 Discover 后，后续 Request 仍然必须重复携带自己的 _meta，Server 不能依赖 Discover 保存状态。

    6.5 Server 需要 Client 输入时的流程变化¶

    Legacy 允许 Server 在处理 tools/call 时反向发送独立 Request：

    sequenceDiagram
    participant C as Legacy Client
    participant S as Legacy Server

    C->>S: tools/call (id=10)
    S->>C: elicitation/create (id=90)
    C-->>S: ElicitResult (id=90)
    S-->>C: Tool Result (id=10)

    这要求连接上存在 Server→Client 反向通道。

    Modern 删除了这种反向 Request，改用 MRTR（Multi Round-Trip Requests）：

    sequenceDiagram
    participant C as Modern Client
    participant S as Modern Server

    C->>S: tools/call (id=10)
    S-->>C: resultType=input_required + inputRequests + requestState
    Note over C,S: 第一次 Request 已结束
    Note over C: 收集用户输入
    C->>S: 重试 tools/call (id=11) + inputResponses + requestState
    S-->>C: resultType=complete + Tool Result

    关键差异：

    1. 第一次 tools/call 已经结束，不是在原请求里“暂停等待”；
    2. Retry 必须使用新的 JSON-RPC ID；
    3. Client 原样回传 Server 给出的 requestState；
    4. Retry 必须带上完成处理所需的全部输入；
    5. Server 不能假设 Retry 会到达同一进程；
    6. 多实例 Server 必须共享 requestState 加密密钥，或使用共享状态存储。

    MRTR 使负载均衡不再依赖连接粘性，同时保留用户确认、Elicitation 等多轮交互。

    6.6 变化通知的流程变化¶

    Legacy 通常依赖连接级订阅或独立通知流：

    resources/subscribe(uri)
GET SSE notification stream
notifications/resources/updated

    Modern 使用一个显式的长期 Request：

    sequenceDiagram
    participant C as Client
    participant S as Server

    C->>S: subscriptions/listen (id=50, filters)
    S--)C: notifications/subscriptions/acknowledged
    S--)C: notifications/tools/list_changed
    S--)C: notifications/resources/updated
    Note over C,S: Response Stream 保持打开

    订阅状态只属于这个 subscriptions/listen Request：

    • 每条通知都带 subscriptionId=50；
    • HTTP 用该 POST 的 SSE Response Stream；
    • stdio 仍共享 stdout，但通过 Subscription ID 分流；
    • 断线后没有重放保证，Client 必须重新 Listen 并重新获取数据；
    • 关闭该请求就结束订阅，不存在协议 Session 级订阅状态。

    6.7 无状态不等于没有任何状态¶

    需要区分四种状态：

    状态 是否存在 生命周期
    协议 Session 状态 Modern 中不存在 Legacy 连接/Session
    Transport 状态 存在 stdio 进程、HTTP/SSE 连接
    In-flight Request 状态 存在 单个 Request 完成或取消前
    业务状态 可以存在 数据库、Redis、工作流系统或显式 Handle

    Transport 状态是为了让字节和消息能够继续传输而维护的临时运行状态。例如：

    • stdio：子进程是否存活、stdin/stdout 管道是否打开、尚未组成完整 JSON 行的读取缓冲区；
    • HTTP：TCP/TLS 或 HTTP/2 连接是否可用、Keep-Alive、流量控制和写入队列；
    • SSE：Response Stream 是否仍然打开、是否发生背压或断线。

    它回答的是“当前通信通道还能不能继续收发消息”，而不是“Client 之前协商了什么”或“用户正在处理哪个业务对象”。Transport 断开会导致依赖它的在途请求或订阅流结束，但不应让数据库中的购物车、任务等业务对象消失。

    例如，HTTP Client 的两次 tools/call 可以复用同一个 TCP 连接，也可以使用不同连接，两种情况下的 MCP 语义必须相同；stdio 虽然长期复用同一个子进程和管道，每个 Modern Request 仍然必须携带完整 _meta。Server 不能因为“连接还活着”就省略版本、能力或身份校验。

    In-flight Request 状态是单个 JSON-RPC Request 已被接收、但尚未返回结果或错误时的临时执行上下文，通常包括：

    • Request ID 与正在执行的 Handler、协程或 Future 的映射；
    • 已解析的方法、参数以及本次请求的身份和授权上下文；
    • 超时、取消信号、进度状态和当前 Response Stream；
    • 执行期间临时占用的数据库事务、文件句柄或计算资源。

    它的生命周期严格受单个 Request 限制：返回结果、返回错误、被取消或连接异常终止后，就应释放。stdio 可以在同一管道上并发承载多个在途请求，Server 通过不同的 JSON-RPC ID 区分它们；一个 HTTP POST 返回 SSE 时，该 Request 在流结束前一直处于 in-flight 状态。

    MRTR 尤其能体现这个边界：当 id=10 返回 resultType: "input_required" 时，第一次 Request 已结束，其执行上下文不能继续隐藏在内存中等待；Client 收集输入后使用新 ID 发起的 Retry 是另一个 Request。跨越两次 Request 所需的信息必须放进 requestState，或由它引用外部共享状态。

    长连接仍然可以存在，例如：

    • stdio Server 进程持续运行；
    • subscriptions/listen SSE 长时间打开；
    • 一个 Tool 的 SSE Response 持续报告进度。

    但连接只是承载消息的通道，不能被当作用户会话、购物车或工作流身份。

    6.8 跨请求业务状态必须显式化¶

    如果业务需要状态，应显式返回 Handle：

    create_cart() → { cart_id: "cart_8f13" }
add_item(cart_id="cart_8f13", sku="...")
checkout(cart_id="cart_8f13")

    典型实现：

    Request 1 → 任意 Server 实例 → 创建 cart_8f13 → 写入数据库/Redis
Request 2 → 另一 Server 实例 → 根据 cart_id 读取状态 → 添加商品
Request 3 → 又一 Server 实例 → 根据 cart_id 结算

    Server 每次都必须：

    • 验证调用者身份；
    • 验证 Handle 是否属于该用户和租户；
    • 验证权限和 Scope；
    • 检查有效期和业务状态；
    • 对写操作应用幂等策略。

    不能把“知道 Handle”当作身份认证。未认证服务中的 Handle 本质上是 Bearer Token，必须高熵、不可猜测并设置短 TTL。

    6.9 对部署架构的直接影响¶

    Modern 无状态协议带来以下变化：

    场景 Legacy Modern
    HTTP 负载均衡 Session 通常要求 Sticky Routing 普通请求可发往任意实例
    Server 重启 Session 和反向通道丢失 在途请求丢失，后续请求可直接发往新实例
    横向扩容 需要考虑 Session 复制/粘性 业务状态外置即可
    鉴权 仍应每请求校验，但实现容易误依赖 Session 明确要求每请求携带并校验凭据
    多轮交互 原连接上反向请求 Client 用新 ID 重试，状态显式携带
    订阅 连接/Session 级 独立长请求，断开后重建

    不过“可发往任意实例”仍有两个前提：

    1. 业务状态不能只存在某个进程内存中；
    2. MRTR 的 requestState 必须能被所有实例验证和解密。

    6.10 Dual-era 兼容¶

    Dual-era Client 不是 MCP 定义的新角色，而是教程使用的工程术语，指同时实现两套协议状态机的兼容 Client：

    • Legacy 状态机：支持 2025-11-25 及以前的 initialize、notifications/initialized、Session ID 和 Server→Client Request；
    • Modern 状态机：支持 2026-07-28 及以后的每请求 _meta、server/discover、MRTR 和 subscriptions/listen。

    它的用途是让同一个 Host 在迁移期间既能连接尚未升级的旧 Server，也能连接 Modern Server。它不是在一次交互中同时使用两套协议，而是先判断对端属于哪个 Era，再为该连接或 Server 固定使用相应状态机。

    已知 Server 版本时应直接使用对应模式；未知时可以进行受控探测：

    server/discover + Modern _meta
├─ DiscoverResult                     → 锁定 Modern 模式
├─ UnsupportedProtocolVersion         → 仍是 Modern，选择共同版本后重试
├─ 明确的 MethodNotFound/Legacy 响应   → 重建 Transport，尝试 Legacy initialize
└─ 401/403、TLS、网络超时或 5xx         → 连接失败，不作为 Legacy 证据

    不能因为认证失败、网络故障或任意 Server Error 就自动降级，否则既可能掩盖真实故障，也可能造成降级攻击。对于 stdio，严格的 Legacy Server 可能会在收到非 initialize 的第一条消息后退出，因此回退前通常要重启子进程，而不是直接复用已受污染的 Transport。

    Dual-era Server 则根据 Client 的开场方式选择语义：

    • 收到带现代 _meta 的 Request：按无状态 Modern 处理；
    • 收到 initialize：建立 Legacy Session。

    模式一旦确定就不能混用，例如不能先 initialize，随后又省略 Legacy Session 状态并发送 Modern subscriptions/listen。实现中通常还会缓存某个 Server 已验证的 Era，并提供强制指定模式的配置，以避免每次连接都试探。

    更完整的线上报文和兼容矩阵见：通信过程与版本协商 与 协议版本演进与兼容。

    7. MCP 与相近概念¶

    7.1 MCP vs Function Calling¶

    维度 Function Calling MCP
    所在层 模型 API / Agent Runtime 外部集成协议
    解决问题 模型怎样输出工具名和参数 Client 怎样发现并调用 Server 能力
    执行主体 Host / Agent Runtime MCP Server
    发现机制 通常由应用静态传入 tools/list 动态发现
    传输 模型厂商 API 格式 JSON-RPC over stdio / HTTP

    二者通常串联使用，而不是二选一。

    7.2 MCP vs REST API¶

    REST API 是通用服务接口；MCP 在其上增加了适合 AI Host 的统一语义：

    • 工具 Schema 发现；
    • 资源和提示模板；
    • 版本与能力元数据；
    • 多轮补充输入；
    • 统一 Tool Result 内容块。

    MCP Server 内部完全可以继续调用 REST API。

    7.3 MCP vs 插件¶

    插件通常与某个 Host SDK、语言和进程模型绑定。MCP Server 是协议边界，可以跨进程、跨语言并被多个 Host 复用。

    7.4 MCP vs A2A¶

    MCP 重点是 Host/Agent 与工具和上下文服务的集成；A2A 重点是 Agent 之间的任务协作。一个远端 Agent 可以通过 A2A 接收任务，再通过 MCP 使用工具。

    8. 信任边界¶

    graph TD
    U[User] --> H[Host: 身份/审批/策略]
    H --> L[LLM: 不可信生成]
    H --> C[MCP Client]
    C --> S[MCP Server: 不可信外部组件]
    S --> D[外部数据: 可能含提示注入]

    必须明确：

    • Tool 描述可能包含 Tool Poisoning；
    • Resource 和 Tool Result 可能包含间接 Prompt Injection；
    • 本地 stdio Server 是普通本机进程，不是沙箱；
    • 远程 HTTP Server 需要认证、授权和 Origin 校验；
    • 高风险 Tool 应保留 Human-in-the-Loop；
    • 每个 Server 只获得完成任务所需的最小权限。
