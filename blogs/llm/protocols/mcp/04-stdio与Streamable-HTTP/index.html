    stdio 与 Streamable HTTP¶

    MCP 的数据层消息相同，传输层负责消息边界、进程/连接生命周期、流式响应和授权。本章以 2026-07-28 为准。

    1. 传输选择¶

    维度 stdio Streamable HTTP
    典型部署 本地子进程 远程独立服务
    Client→Server stdin 每条消息一个 HTTP POST
    Server→Client stdout JSON Response 或当前请求的 SSE Response
    日志 stderr 服务端日志系统 / OpenTelemetry
    认证 环境变量或本机机制 OAuth 2.1 / Bearer Token
    多 Client 通常 1:1 通常多租户、多 Client
    安全边界 与本机进程同一信任域 网络、身份、Origin、授权边界

    本地文件和开发工具优先 stdio；远程 SaaS、团队共享服务和生产服务优先 Streamable HTTP。

    2. stdio 传输¶

    2.1 进程模型¶

    sequenceDiagram
    participant C as MCP Client
    participant P as MCP Server Process
    C->>P: 启动子进程
    C->>P: stdin: JSON-RPC + newline
    P-->>C: stdout: JSON-RPC + newline
    P--)C: stderr: 日志
    C->>P: 关闭 stdin
    P-->>C: 退出

    Client 启动 Server 子进程：

    • Client 写 Server 的 stdin；
    • Client 读 Server 的 stdout；
    • Server 可把任意 UTF-8 日志写入 stderr；
    • stderr 有输出不等价于协议错误。

    2.2 消息分帧¶

    stdio 使用 newline-delimited JSON-RPC：

    {"jsonrpc":"2.0","id":1,"method":"tools/list","params":{...}}\n
{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{...}}\n

    规则：

    • 一条消息占一个物理行；
    • 消息之间用换行符分隔；
    • JSON 字符串中的换行必须编码为 \n，不能写成真实物理换行；
    • 所有消息使用 UTF-8；
    • 不使用 Content-Length；
    • stdout 不能输出 Banner、调试文本、print() 或普通日志。

    Content-Length 分帧常见于 LSP，但不是 MCP stdio 标准格式。

    2.3 为什么 stdout 污染会断协议¶

    错误示例：

    Server started!
{"jsonrpc":"2.0",...}

    Client 会尝试把 Server started! 解析为 JSON，连接立即失败。Python 应使用写入 stderr 的 logging，Node.js 应使用 console.error()。

    2.4 请求并发¶

    stdout 是共享通道，Server 可乱序完成并发请求：

    Client → id=1 slow_tool
Client → id=2 fast_tool
Server → id=2 result
Server → id=1 result

    Client 必须使用 id → Future 表匹配，不得按行顺序假设归属。

    订阅通知也共享 stdout，需要通过 _meta.io.modelcontextprotocol/subscriptionId 分流。

    2.5 stdio 取消¶

    stdio 没有独立的每请求流，Client 发送：

    {
  "jsonrpc": "2.0",
  "method": "notifications/cancelled",
  "params": {
    "requestId": 42,
    "reason": "用户取消"
  }
}

    Server 应尽快停止工作并释放资源，但取消是竞态、best effort：操作可能已完成。Client 应忽略取消后迟到的响应。

    2.6 关闭与重启¶

    Client 应：

    1. 关闭 Server stdin；
    2. 等待 Server 退出；
    3. 超时后发送系统终止信号；
    4. 再超时才强制杀死。

    Server 应在 stdin EOF 后尽快退出。

    现代协议无状态，Server 意外退出后 Client 可以重启进程；在途请求和订阅会丢失，需要根据幂等性重试并重新订阅。

    2.7 stdio 安全现实¶

    stdio 不是沙箱。Server 是与 Host 同权限运行的普通进程，可能读取：

    • 环境变量；
    • 用户可读文件；
    • SSH、云平台和浏览器凭据；
    • 本地网络和互联网。

    真正的隔离需要容器、VM、独立用户、文件只读挂载和网络出口控制。

    3. Streamable HTTP¶

    3.1 单一端点¶

    现代 Server 提供一个支持 POST 的 MCP Endpoint，例如：

    https://mcp.example.com/mcp

    每一条 Client 消息都是新的 HTTP POST。现代 2026-07-28：

    • 没有独立 GET 通知流；
    • 没有 Mcp-Session-Id；
    • 没有 DELETE Session；
    • 没有 Last-Event-ID 恢复；
    • Server 不能在 SSE 中发送独立 JSON-RPC Request。

    3.2 请求 Headers¶

    基础请求：

    POST /mcp HTTP/1.1
Host: mcp.example.com
Content-Type: application/json
Accept: application/json, text/event-stream
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: get_weather
Authorization: Bearer <token>

    Body：

    {
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": {"city": "上海"},
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}

    现代合规要求：

    Header 来源 要求
    MCP-Protocol-Version _meta 中协议版本 所有 POST 必须存在且与 Body 相同
    Mcp-Method JSON-RPC method 所有 Request 必须存在
    Mcp-Name params.name 或 params.uri tools/call、prompts/get、resources/read 必须存在

    Header 名称大小写不敏感，Header 值大小写敏感。

    如果 Header 与 Body 不匹配，Server 返回 HTTP 400 与 -32020 HeaderMismatch。这样网关按 Header 路由时不会与后端按 Body 执行产生语义分裂。

    3.3 普通 JSON 响应¶

    Server 可以直接返回：

    HTTP/1.1 200 OK
Content-Type: application/json

    {
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "resultType": "complete",
    "content": [{"type": "text", "text": "上海：晴"}]
  }
}

    3.4 SSE 流式响应¶

    长操作可返回：

    HTTP/1.1 200 OK
Content-Type: text/event-stream
X-Accel-Buffering: no

    流中先发送与该请求相关的通知，最后发送 JSON-RPC Response：

    data: {"jsonrpc":"2.0","method":"notifications/progress",...}

data: {"jsonrpc":"2.0","method":"notifications/progress",...}

data: {"jsonrpc":"2.0","id":1,"result":{"resultType":"complete",...}}

    规则：

    • 通知必须与发起该 POST 的请求相关；
    • 最终 Response 发送后通常结束流；
    • Server 不能在这里发送独立 JSON-RPC Request；
    • 断开不支持 Last-Event-ID 恢复；
    • 断线导致在途请求丢失，Client 用新 ID 重新发起；
    • 代理层应关闭响应缓冲；
    • 长订阅流可发送 SSE Comment :\r\n 保活。

    3.5 HTTP 取消¶

    现代 HTTP 每个 Request 有自己的响应流，因此关闭该 SSE Response Stream 就是取消信号：

    • 不需要额外 POST notifications/cancelled；
    • Server 必须把断开视为该请求取消；
    • Server 应停止工作，不能继续向该流发送消息。

    这与 Legacy 不同，也与 stdio 不同。

    4. 长期通知：subscriptions/listen¶

    现代 HTTP 没有独立 GET 通知通道。Client 发送一个长时间不结束的 POST：

    {
  "jsonrpc": "2.0",
  "id": 50,
  "method": "subscriptions/listen",
  "params": {
    "notifications": {
      "toolsListChanged": true,
      "resourcesListChanged": true,
      "resourceSubscriptions": ["file:///project/config.json"]
    },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}

    Server 用 SSE 保持 Response 打开：

    1. 第一条属于该订阅的消息必须是 notifications/subscriptions/acknowledged；
    2. 之后发送匹配过滤器的通知；
    3. 每条通知都带 subscriptionId = 50；
    4. Client 关闭该 SSE 流即可取消；
    5. 断线后重新发起 subscriptions/listen。

    请求级 Progress 不进入此流，它仍留在原业务 Request 的 Response Stream 中。

    5. x-mcp-header¶

    Tool 可以要求 HTTP Client 把某个普通参数镜像到 Header，供网关路由或限流：

    {
  "type": "object",
  "properties": {
    "region": {
      "type": "string",
      "x-mcp-header": "Region"
    },
    "query": {"type": "string"}
  },
  "required": ["region", "query"]
}

    调用时添加：

    Mcp-Param-Region: us-west1

    限制包括：

    • 只能用于 string、integer、boolean；
    • Header 名必须符合 RFC 9110 token；
    • 不能用于敏感信息；
    • Header 与 Body 必须一致；
    • 非 ASCII 或危险值使用规范定义的 Base64 Sentinel 编码；
    • HTTP Client 必须排除带非法 x-mcp-header 的 Tool；
    • stdio Client 可以忽略这个扩展。

    6. HTTP 授权¶

    HTTP Authorization 是可选的；启用时应遵循 MCP OAuth 2.1 规范：

    Authorization: Bearer <access-token>

    Token 必须出现在每个 HTTP 请求中，不能放在 Query String。Server 必须验证：

    • 签名和有效期；
    • Issuer；
    • Audience 是当前 MCP Server；
    • Scope 足以执行当前方法；
    • 不能把 MCP Token 透传给下游 API。

    stdio 不使用这套 OAuth 传输授权；本地凭据通常由环境变量、操作系统 Secret Store 或 Host 注入。

    7. HTTP 安全要求¶

    7.1 Origin 校验¶

    Server 必须验证 Origin，防止 DNS Rebinding。存在但不合法时返回 403。

    7.2 本地监听¶

    本地 HTTP Server 应绑定 127.0.0.1，而不是 0.0.0.0。但 localhost 也不是认证边界，仍应使用授权和 Origin 校验。

    7.3 代理和缓冲¶

    • 对 SSE 设置 X-Accel-Buffering: no；
    • 配置反向代理的 idle timeout；
    • 禁止压缩/缓冲导致事件延迟；
    • 限制请求体和 SSE 事件大小；
    • 记录 Request ID、Trace Context 和延迟。

    8. HTTP 状态码与 JSON-RPC 错误¶

    场景 HTTP JSON-RPC
    正常结果 200 result
    Client Notification 被接受 202 空 Body
    Header 不一致 400 -32020
    缺少 Client Capability 400 -32021
    不支持协议版本 400 -32022
    方法不存在 404 -32601
    未认证/Token 无效 401 OAuth Challenge
    Scope 不足 403 WWW-Authenticate: insufficient_scope
    Origin 非法 403 可选 JSON-RPC Error

    Client 必须同时检查 HTTP 状态和 JSON-RPC Body，不能把所有 400 都当成同一种错误。

    9. Legacy HTTP 差异¶

    9.1 2025-03-26 到 2025-11-25¶

    旧 Streamable HTTP 可能包含：

    • initialize 握手；
    • Mcp-Session-Id；
    • GET 打开 Server→Client SSE；
    • DELETE 结束 Session；
    • Server 在 SSE 中发送独立 Request；
    • SSE Event ID 与 Last-Event-ID 恢复。

    这些机制都不属于现代 2026-07-28。

    9.2 2024-11-05 HTTP+SSE¶

    更早版本使用两个端点：GET SSE + POST Message。它已经 Deprecated，新实现不应采用。

    10. 选择建议¶

    选择 stdio¶

    适合：

    • 本地文件、Git、编译器、IDE 集成；
    • 单用户桌面工具；
    • 希望由 Host 负责进程生命周期；
    • 不需要网络授权和多租户。

    必须处理：stdout 纯净、绝对路径、受限环境变量、子进程退出、沙箱。

    选择 Streamable HTTP¶

    适合：

    • SaaS 和内部平台；
    • 多用户共享；
    • 中央部署和统一升级；
    • OAuth、审计、限流、网关和高可用。

    必须处理：OAuth、Origin、SSE 代理、无状态扩缩容、Header 校验和幂等性。
