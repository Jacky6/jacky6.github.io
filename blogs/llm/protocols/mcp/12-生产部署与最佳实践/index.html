    MCP 生产部署与最佳实践¶

    能在 Inspector 中调用 Tool 只是起点。生产系统还需要无状态扩缩容、授权、幂等、缓存、可观测性、沙箱和版本治理。

    1. 部署模式¶

    1.1 本地 stdio¶

    graph LR
    H[Desktop / IDE Host] -->|spawn + stdio| S[Local MCP Server]
    S --> F[Local Files / Tools]

    适合：

    • 文件和代码；
    • Git、编译器、IDE；
    • 硬件和本地应用；
    • 单用户环境。

    风险集中在本机代码执行和供应链。

    1.2 远程 Streamable HTTP¶

    graph LR
    C[MCP Clients] --> G[Gateway / WAF]
    G --> S1[MCP Server]
    G --> S2[MCP Server]
    S1 --> D[(Database / API)]
    S2 --> D
    A[Authorization Server] --> C

    适合：

    • SaaS；
    • 团队共享内部服务；
    • 统一升级、审计和权限；
    • 多租户和高可用。

    风险集中在身份、授权、网络、租户隔离和远程内容。

    2. 现代无状态架构¶

    2026-07-28 要求请求自包含：

    • Version 和 Client Capabilities 每请求携带；
    • 不使用 Mcp-Session-Id；
    • Server 不能依赖同一连接之前发生的请求；
    • 同一连接可交错不同用户任务；
    • 横向扩容不需要协议 Session Sticky Routing。

    2.1 业务状态¶

    需要跨请求状态时使用显式 Handle：

    create_workflow → workflow_id
workflow_step(workflow_id, input)
workflow_status(workflow_id)

    存储选择：

    • 数据库；
    • Redis；
    • Durable Workflow Engine；
    • 对短小状态使用完整性保护的 requestState。

    不要把关键状态只放进单个 Server 进程内存，否则负载均衡或重启后丢失。

    2.2 Handle 安全¶

    • 高熵；
    • 不透明；
    • 每请求校验主体；
    • TTL；
    • 用途限制；
    • 不能替代认证；
    • 不在日志和模型输出中暴露敏感内部结构。

    3. API 和 Tool 设计¶

    3.1 小而明确¶

    好 Tool：

    orders.get(order_id)
orders.cancel(order_id, reason, idempotency_key)

    差 Tool：

    do_everything(action, payload)

    过于通用的 Tool：

    • Schema 难理解；
    • 权限粒度粗；
    • 审计困难；
    • 模型易选错；
    • 安全审批无法展示真实副作用。

    3.2 Schema 优先¶

    • 使用 JSON Schema 2020-12；
    • additionalProperties: false；
    • 枚举代替自由字符串；
    • 限制长度、范围、数组数量；
    • 写 Tool 提供 idempotency_key；
    • 结构化返回提供 outputSchema；
    • Client 和 Server 双重校验。

    3.3 Tool 描述¶

    描述是模型路由信息，应说明：

    • 做什么；
    • 何时用；
    • 何时不要用；
    • 副作用；
    • 前置 Tool/Resource；
    • 参数单位和格式；
    • 结果上限；
    • 错误恢复方式。

    同时把描述当作不可信输入。Host 不应允许 Server 描述修改系统权限策略。

    4. 权限模型¶

    建议将能力映射为细粒度 Scope：

    orders:read
orders:create
orders:cancel
admin:refund

    每次 Tool Call 都重新验证：

    Token 有效
∧ Audience 是当前 Server
∧ Scope 足够
∧ Tenant 匹配
∧ Resource 属于该 Principal
∧ 业务状态允许

    不要只在 tools/list 过滤一次后信任后续 Call。Tool 列表过滤改善体验，不替代执行时授权。

    高风险操作：

    • Human-in-the-Loop；
    • 展示 Server、Tool、关键参数和影响；
    • 支持拒绝；
    • 记录批准人和时间；
    • 对金额、生产环境、删除等设置策略阈值。

    5. 幂等与重试¶

    5.1 分类¶

    操作 示例 重试策略
    安全读取 List/Get 指数退避 + Jitter
    幂等写 Put/Set with key 可重试
    非幂等写 Create/Charge 必须提供幂等键
    长流程 Deploy/Import 返回 Handle，查询状态

    5.2 断线不等于未执行¶

    HTTP Response 断开可能发生在 Server 已完成写入之后。Client 再次 Call 会重复副作用。

    写 Tool 推荐参数：

    {
  "idempotency_key": "client-generated-uuid",
  "order": {...}
}

    Server 保存 Key 与结果，并对重复 Key 返回同一业务结果。

    5.3 Circuit Breaker¶

    对下游 API：

    • 只重试瞬时错误；
    • 指数退避和 Jitter；
    • 429 尊重 Retry-After；
    • 设置最大尝试次数和总时长；
    • 熔断并提供清晰 Tool Execution Error；
    • 不在模型循环和 SDK 层重复叠加无限重试。

    6. Timeout 与资源限制¶

    分层设置：

    层 示例
    Transport Connect/Process Start Timeout
    Protocol Request Timeout
    Tool Execution Timeout
    Downstream HTTP/DB Timeout
    MRTR Round Limit + Total Timeout
    SSE Idle + Absolute Timeout

    还应限制：

    • Request/Response 字节数；
    • Tool Result Content 数量；
    • 图片/音频大小；
    • Schema 深度与分支；
    • 并发 Tool 数；
    • 每用户/每 Tool QPS；
    • stdio 子进程 CPU、内存和进程数。

    7. 缓存¶

    7.1 遵循协议提示¶

    ttlMs       → 新鲜度
cacheScope  → public/private
    • Public 只能用于非用户特定结果；
    • Private 按 Authorization Context 分区；
    • List Changed / Resource Updated 立即失效；
    • MRTR Retry Result 不缓存；
    • 每个分页独立缓存；
    • Cursor 失效时丢弃所有页并从头拉取。

    7.2 Tool 列表稳定性¶

    Server：

    • Tool 集合没变时保持确定性顺序；
    • Tool Name 稳定；
    • Schema Breaking Change 使用新 Tool 名或 Server 版本策略；
    • 权限过滤后正确设置 Private Cache。

    Host：

    • 缓存定义；
    • 收到变化通知后刷新索引；
    • 不在每轮模型请求中无意义重新排序 Tools，以保护 Provider Prompt Cache。

    8. 大规模 Tool 管理¶

    8.1 渐进式发现¶

    当 Tool Schema 占据 Context Window 较大比例时：

    Catalog → Search → Inspect → Execute
    1. Host 拉取并索引全部 Tool，但不全部注入模型；
    2. 暴露轻量 search_tools Meta Tool；
    3. 模型搜索相关 Tool；
    4. 只加载候选完整 Schema；
    5. 执行。

    检索方式：

    • BM25/关键词；
    • Embedding；
    • 小模型/Subagent；
    • Hybrid。

    Server 动态管理也可渐进：只在任务需要时连接相关 Server。

    8.2 Code Mode¶

    多步数据处理可让模型写受限脚本，Host 在 Sandbox 中拦截函数并路由到 MCP：

    graph LR
    L[LLM] -->|生成代码| X[Sandbox]
    X -->|Typed Stub| H[Host Broker]
    H --> S1[MCP Server A]
    H --> S2[MCP Server B]
    X -->|仅最终摘要| L

    要求：

    • Sandbox 无直接网络；
    • 不暴露 Token；
    • Host 对每次 Tool Call 仍做授权；
    • 设置 CPU/内存/时间限制；
    • 跨 Server 数据流继续审查；
    • 输出限长和校验。

    9. 可观测性¶

    9.1 指标¶

    按 Server/Tool/Result 统计：

    • Request Count；
    • Success / Protocol Error / Tool Error；
    • P50/P95/P99 Latency；
    • Cancellation / Timeout；
    • MRTR Rounds；
    • Cache Hit；
    • Tool List Size 和 Schema Tokens；
    • SSE Active Streams / Disconnect；
    • OAuth 401/403 和 Step-up；
    • Downstream Error Rate。

    9.2 Trace¶

    使用 _meta 中的：

    traceparent
tracestate
baggage

    Span 建议：

    Host model turn
└── MCP tools/call
    └── authorization
    └── business operation
        └── downstream HTTP/DB

    不要把 Tool 参数全文默认放进 Trace Attribute，避免 PII 和高基数。

    9.3 日志¶

    记录：

    • Protocol Era/Version；
    • SDK/Server Version；
    • Request ID；
    • Method/Tool；
    • Principal/Tenant 的不可逆标识；
    • Scope Decision；
    • 耗时、结果类型、错误码；
    • 幂等键摘要；
    • 取消和重试。

    不记录：Token、Authorization Code、Cookie、密码、完整用户文档和敏感 Tool Result。

    10. stdio 生产安全¶

    • Pin Package Version，容器镜像最好 Pin Digest；
    • 审查 Publisher、SBOM、Signature；
    • Server 在容器/沙箱/VM 中运行；
    • 仅挂载目标项目，优先 Read-only；
    • 独立 Environment，不继承全局 Secret；
    • 无需网络则关闭 Egress；
    • 需要网络则 Allowlist；
    • stdout 只允许协议；
    • stderr 限流，防止磁盘/管道耗尽；
    • Host 能随时终止进程；
    • 记录启动命令但脱敏环境变量。

    本地 Server 与 Host 同一信任域；Transport 不提供隔离。

    11. HTTP 生产安全¶

    • HTTPS；
    • Origin Allowlist；
    • OAuth 2.1；
    • Audience、Issuer、Scope；
    • 禁止 Token Passthrough；
    • Protected Resource Metadata；
    • PKCE、State、iss；
    • Header/Body 一致性；
    • SSRF Egress Controls；
    • WAF、Body Limit、Rate Limit；
    • SSE 禁止代理缓冲；
    • 多租户行级授权；
    • Secrets 使用 KMS/Vault；
    • Key Rotation 和 Revocation；
    • Admin Tool 单独 Scope 和审批。

    12. Prompt Injection 防御¶

    安全决策不能交给 LLM。采用确定性策略层：

    Model proposes tool call
        ↓
Policy Engine
  ├─ server allowlist
  ├─ tool allowlist
  ├─ parameter constraints
  ├─ data classification
  ├─ user confirmation
  └─ tenant/resource authorization
        ↓
MCP Client executes

    Tool Result：

    • 标记来源；
    • 与系统指令隔离；
    • 限长；
    • 过滤不支持 Content Type；
    • 跨 Server 转发前重新审查；
    • 不因为结果里写了“已获用户授权”就跳过审批。

    13. 版本与发布¶

    13.1 支持矩阵¶

    维护：

    Server version → SDK version → Protocol versions → Target Hosts

    每次发布自动测试：

    • Inspector Modern；
    • Inspector Legacy（如宣称支持）；
    • 至少一个目标 Host；
    • OAuth / stdio；
    • Schema Snapshot；
    • Migration Test。

    13.2 Tool Schema 变更¶

    兼容变更：

    • 增加非必填字段；
    • 扩展描述；
    • 增加可选输出字段。

    可能 Breaking：

    • 重命名 Tool；
    • 新增必填参数；
    • 缩小枚举；
    • 改变单位；
    • 改变副作用；
    • 改变 structuredContent 类型。

    即使 MCP Protocol Version 不变，你自己的 Tool Contract 也需要版本治理。

    13.3 灰度¶

    • 新 Tool 先仅对测试 Scope 开放；
    • 比较旧/新 Schema 调用成功率；
    • 监控模型选 Tool 准确率；
    • 支持快速隐藏 Tool；
    • 高风险写 Tool 使用 Feature Flag；
    • 保留回滚和凭据吊销路径。

    14. 容量与 SLO¶

    示例 SLO：

    Availability: 99.9%
P95 tools/list: < 300 ms
P95 read-only tools/call: < 2 s
Protocol error rate: < 0.1%
Subscription reconnect success: > 99%

    容量规划考虑：

    • Tool Schema 大小；
    • 并发 SSE；
    • MRTR 等待用户时不要占工作线程；
    • 二进制内容内存峰值；
    • 下游连接池；
    • Per-tenant 限流；
    • 缓存命中；
    • 模型重试放大流量。

    15. 故障恢复¶

    Server 重启¶

    • Modern Request 无 Session 恢复；
    • 在途请求按幂等性处理；
    • Subscription 重建；
    • Handle 状态放外部 Durable Store。

    下游失败¶

    • 返回可行动 Tool Execution Error；
    • 不暴露内部 Stack/Token；
    • 降级到缓存需标注陈旧；
    • 写操作不确定时返回状态查询方法。

    Authorization Server 故障¶

    • 已签发短期 Token 可按策略继续验证；
    • 不绕过认证；
    • Metadata 和 JWKS 缓存有明确 TTL；
    • Key Rotation 支持多 Key 验证窗口。

    16. 代码审查问题¶

    协议¶

    • 是否真的支持声明的 Protocol Version？
    • 是否混用了 Initialize 与 Modern _meta？
    • 是否正确处理 resultType？
    • 是否把 Notification 当 Request？
    • Cursor 空字符串是否被错误判结束？

    状态¶

    • 是否依赖连接内隐式状态？
    • Handle 是否绑定用户？
    • requestState 是否可篡改/重放？

    安全¶

    • 每次 Call 是否重新鉴权？
    • Token Audience 是否校验？
    • 是否存在 Token Passthrough？
    • Tool 描述/结果是否被当成可信指令？
    • 本地 Server 是否拥有过宽权限？

    可靠性¶

    • 写操作是否幂等？
    • Timeout 是否分层？
    • Retry 是否叠加？
    • Cancellation 后副作用是否清楚？
    • stderr 是否持续消费？

    17. 上线清单¶

    Server¶

    • server/discover、Capabilities、版本正确
    • Tool/Resource/Prompt Contract 有测试
    • 无连接级隐式状态
    • 输入输出 Schema 双向校验
    • 幂等、Timeout、Rate Limit、Circuit Breaker
    • Authorization 和租户隔离
    • Log/Metric/Trace 脱敏

    Transport¶

    • stdio stdout 纯净、进程可终止、运行隔离
    • HTTP TLS、Origin、Headers、OAuth、SSE 代理配置
    • 断线和订阅重建测试

    Host¶

    • Server/Tool Allowlist
    • Tool 名冲突处理
    • Human-in-the-Loop
    • Prompt Injection 隔离
    • 渐进式 Tool 发现
    • Cache/Notification 一致性
    • MRTR/取消循环上限

    运维¶

    • 依赖和镜像 Pin
    • SBOM/漏洞扫描
    • Secret Rotation
    • SLO 和告警
    • 灰度、回滚、禁用 Tool
    • Incident Runbook

    18. 结论¶

    生产 MCP 的核心不是“把函数加一个装饰器”，而是建立稳定边界：

    清晰 Contract
+ 每请求版本/能力/授权
+ 显式状态句柄
+ 幂等与取消
+ 缓存与通知
+ 沙箱与最小权限
+ 可观测和版本治理
