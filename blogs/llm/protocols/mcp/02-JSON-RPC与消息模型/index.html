    JSON-RPC 与消息模型¶

    本章讨论 2026-07-28 现代协议的线上消息。为了便于阅读，官方很多原语示例会省略 _meta；真实现代请求不能省略必填元数据。

    1. MCP 使用 JSON-RPC 2.0¶

    MCP 数据层使用 JSON-RPC 2.0，并在其上定义方法、参数和结果 Schema。

    线上有三类消息：

    类型 识别方式 是否响应
    Request 有 method 和 id 必须返回相同 id 的 Response
    Response 有 id，并包含 result 或 error 不再响应
    Notification 有 method，没有 id 禁止响应

    2. Request¶

    {
  "jsonrpc": "2.0",
  "id": 17,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": {"city": "上海"},
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": {
        "name": "example-client",
        "version": "1.0.0"
      },
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}

    规则：

    • jsonrpc 必须是 "2.0"；
    • id 必须是字符串或整数，MCP 不允许 null；
    • 未完成请求的 id 必须唯一；
    • method 是协议方法名；
    • params 按方法 Schema 解释；
    • 现代 MCP 的协议元数据位于 params._meta。

    3. Response¶

    3.1 成功结果¶

    {
  "jsonrpc": "2.0",
  "id": 17,
  "result": {
    "resultType": "complete",
    "content": [
      {"type": "text", "text": "上海：晴，25°C"}
    ],
    "isError": false
  }
}

    id 必须与 Request 一致。当前协议要求 Result 包含 resultType：

    值 含义
    complete 请求已完成，结果是最终结果
    input_required 请求尚未完成，需要 Client 补充输入并重试
    扩展定义值 只有双方声明支持相应扩展时才可使用

    为了兼容旧 Server，Client 收到缺少 resultType 的旧版结果时，必须按 complete 处理。

    3.2 错误结果¶

    {
  "jsonrpc": "2.0",
  "id": 17,
  "error": {
    "code": -32602,
    "message": "Unknown tool: get_wether",
    "data": {"name": "get_wether"}
  }
}

    标准 JSON-RPC 错误：

    Code 含义
    -32700 Parse error
    -32600 Invalid Request
    -32601 Method not found
    -32602 Invalid params
    -32603 Internal error

    现代 MCP 预留错误：

    Code 名称 典型原因
    -32020 HeaderMismatch HTTP Header 与 JSON Body 不一致
    -32021 MissingRequiredClientCapability 请求缺少 Server 所需 Client 能力
    -32022 UnsupportedProtocolVersion Server 不支持请求版本

    -32000 到 -32019 是历史实现使用区，新实现不应分配新含义；-32020 到 -32099 由 MCP 规范保留。

    4. Notification¶

    {
  "jsonrpc": "2.0",
  "method": "notifications/progress",
  "params": {
    "progressToken": "import-42",
    "progress": 60,
    "total": 100,
    "message": "正在导入"
  }
}

    Notification 没有 id，接收方不能返回 Response。发送者也无法知道它是否被处理，因此通知通常是 best effort。

    当前 Server→Client 通知包括：

    • 请求作用域的 notifications/progress；
    • 已订阅的 notifications/tools/list_changed；
    • 已订阅的 notifications/resources/updated；
    • notifications/subscriptions/acknowledged。

    5. 每个现代请求的 _meta¶

    现代协议不依赖初始化 Session。每个 Request 必须包含：

    {
  "_meta": {
    "io.modelcontextprotocol/protocolVersion": "2026-07-28",
    "io.modelcontextprotocol/clientCapabilities": {}
  }
}

    建议同时包含：

    {
  "io.modelcontextprotocol/clientInfo": {
    "name": "my-host",
    "version": "2.3.0"
  }
}

    5.1 字段语义¶

    Key 必填 含义
    io.modelcontextprotocol/protocolVersion 是 当前请求采用的协议版本
    io.modelcontextprotocol/clientCapabilities 是 当前请求可使用的 Client 能力
    io.modelcontextprotocol/clientInfo 建议 Client 名称和版本，仅用于展示、日志、调试
    io.modelcontextprotocol/logLevel 否 请求级协议日志阈值，Logging 已 Deprecated
    progressToken 否 请求选择接收进度通知
    traceparent / tracestate / baggage 否 OpenTelemetry/W3C Trace Context

    缺少必填字段时，Server 必须返回 -32602；HTTP 传输同时返回 400。

    clientInfo 和 serverInfo 是自报信息，不能用于鉴权、安全决策或行为分支。

    6. Server 能力怎样返回¶

    server/discover 返回版本、能力和身份：

    {
  "jsonrpc": "2.0",
  "id": "discover-1",
  "result": {
    "resultType": "complete",
    "supportedVersions": ["2026-07-28", "2025-11-25"],
    "capabilities": {
      "tools": {"listChanged": true},
      "resources": {"subscribe": true},
      "prompts": {},
      "completions": {},
      "extensions": {}
    },
    "_meta": {
      "io.modelcontextprotocol/serverInfo": {
        "name": "demo-server",
        "version": "1.0.0"
      }
    },
    "ttlMs": 3600000,
    "cacheScope": "public"
  }
}

    Server 不能使用 Client 没有声明的能力。如果一次操作必须依赖 elicitation，但请求的 Client capabilities 没有它，应返回 -32021，而不是盲目发送交互请求。

    7. 并发与乱序响应¶

    stdio 的所有消息共享 stdout，HTTP 也可能有多个并发 POST。响应顺序不保证与请求顺序相同：

    send id=10 ─┐
send id=11 ─┼─▶ 并行处理
             │
recv id=11 ◀─┤
recv id=10 ◀─┘

    生产级 Client 通常维护：

    pending: Map<RequestId, Future/Promise>

    收到 Response 后通过 id 找到等待者。不能假设“下一条 Response 就属于上一条 Request”。

    现代协议不再允许 Server 在通道上发送独立 JSON-RPC Request。Server 需要用户输入、模型补全或 Roots 时，通过 InputRequiredResult 表达，详见 MRTR。

    8. Tool 的两类错误¶

    这是最容易混淆的地方。

    8.1 协议错误¶

    未知工具、请求结构不符合 Schema 等使用 JSON-RPC error：

    {
  "jsonrpc": "2.0",
  "id": 3,
  "error": {
    "code": -32602,
    "message": "Unknown tool: invalid_tool"
  }
}

    8.2 工具执行错误¶

    参数值不合法、上游 API 失败、业务规则拒绝等，使用正常 JSON-RPC result，但设置 isError: true：

    {
  "jsonrpc": "2.0",
  "id": 4,
  "result": {
    "resultType": "complete",
    "content": [
      {"type": "text", "text": "日期必须晚于今天，请修改后重试"}
    ],
    "isError": true
  }
}

    这样 Host 可以把可行动的错误交给 LLM，让模型修正参数。Client 不应只依靠异常判断工具是否失败。

    9. JSON Schema¶

    MCP 使用 JSON Schema 描述 Tool 输入输出等结构。

    • 未声明 $schema 时，默认使用 JSON Schema 2020-12；
    • Client 和 Server 必须至少支持 2020-12；
    • Tool inputSchema 必须是有效对象；
    • outputSchema 可描述结构化输出；
    • 遇到不支持的方言应返回明确错误，而不是静默放宽校验。

    无参数 Tool 推荐：

    {
  "type": "object",
  "additionalProperties": false
}

    9.1 $ref 安全¶

    实现不能默认联网解析指向远程地址的 $ref，否则会产生 SSRF 和资源消耗风险。若提供显式开启：

    • 使用 Host allowlist；
    • 拒绝 loopback、link-local 和私网地址；
    • 设置超时、大小和递归深度限制；
    • 验证失败时拒绝 Schema。

    对 oneOf、anyOf、allOf 和深层 $defs 也应设置复杂度限制，避免 Schema DoS。

    10. 分页¶

    以下方法支持 cursor 分页：

    • tools/list；
    • resources/list；
    • resources/templates/list；
    • prompts/list。
    {
  "resultType": "complete",
  "tools": [],
  "nextCursor": "opaque-token",
  "ttlMs": 300000,
  "cacheScope": "public"
}

    Client 必须把 Cursor 当作不透明字符串：

    • 不解析；
    • 不修改；
    • 不假设页大小；
    • 即使 nextCursor 是空字符串，只要字段存在且非 null，也不能当成结束。

    11. 缓存字段¶

    当前以下完整结果必须带 ttlMs 和 cacheScope：

    • server/discover；
    • tools/list；
    • prompts/list；
    • resources/list；
    • resources/templates/list；
    • resources/read。
    {
  "ttlMs": 300000,
  "cacheScope": "private"
}
    • ttlMs 是新鲜度提示，不是后台轮询周期；
    • public 可跨用户共享，Server 必须确认结果不含用户数据；
    • private 只能在同一授权上下文中复用；
    • 收到对应 list_changed 或 resources/updated 时立即失效；
    • MRTR 中携带 inputResponses 或 requestState 的结果禁止缓存。

    12. Client 分发伪代码¶

    def handle_message(message):
    if "method" in message and "id" not in message:
        handle_notification(message)
        return

    if "id" in message and ("result" in message or "error" in message):
        waiter = pending.pop(message["id"], None)
        if waiter is not None:
            waiter.resolve(message)
        return

    raise ProtocolError("Unsupported message shape")

    当前 Server 不能发送独立 Request，因此比旧版分发器少一个 Server→Client Request 分支。需要向 Client 请求输入时，处理 resultType: "input_required"。

    13. 常见错误¶

    • 把 Notification 当 Request 并返回 Response；
    • 请求 ID 重复，导致响应配错；
    • 忽略 resultType；
    • 只处理 TextContent，丢失图片、音频、Resource 或 structuredContent；
    • 把 isError: true 当成网络异常；
    • 在现代请求中省略 _meta；
    • 默认联网解析远程 $ref；
    • 把 Cursor 当页码解析；
    • 把 cacheScope: public 用在用户私有数据上。
