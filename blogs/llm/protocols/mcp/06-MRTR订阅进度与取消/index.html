    MRTR、订阅、进度与取消¶

    一次请求从发出到结束，中间可能发生四件事：Server 缺信息、执行很慢、用户想停、数据会变。本章讲这四种情况的标准做法，它们全部建立在无状态 Request/Response 之上。

    1. 先建立一个心智模型¶

    普通 RPC 是一问一答：

    Client ── Request ──▶ Server
Client ◀─ Response ── Server

    但真实的一次"办事"往往不是一问一答。想象去政务大厅办护照：

    • 窗口说"缺一张照片，补齐再来"——办事被打断，需要再跑一趟；
    • 叫号屏显示"还剩 3 人"——办事在进行，你想看进度；
    • 你等不及走了——办事被中止；
    • 公告栏的政策会更新——你关心的信息会变。

    MCP 把这四种情况标准化为四个模式，全部挂在"请求"这个基本单位上：

    现实场景 MCP 模式 一句话概括 核心机制
    材料不全，补齐再来 MRTR Server 缺信息，先结束本次请求，Client 补齐后重新发 input_required + 新 ID 重试
    叫号屏显示进度 Progress 长任务执行中，Server 主动汇报进展 progressToken + 通知
    你等不及走了 Cancellation Client 中止在途请求 关流 / notifications/cancelled
    公告栏更新 Subscriptions Client 长期监听 Server 变化 subscriptions/listen 长请求

    为什么必须显式设计这些模式？因为现代协议有两条硬约束：

    1. 没有隐式 Session：每个请求自包含，Server 不能"记住上一个请求聊到哪了"；
    2. 禁止 Server 反向发请求：旧版 Server 可以在处理中途反过来向 Client 发独立 JSON-RPC Request，现代协议删除了这条通道。

    旧版靠这两样东西实现的交互（中途问用户、连接级订阅），新版必须换一种做法。这就是本章四个模式的由来。

    2. MRTR：Server 缺信息时怎么办¶

    MRTR（Multi Round-Trip Requests，多轮往返请求）是 2026-07-28 引入的 Breaking Change，替代旧版的 Server→Client 反向请求。

    2.1 旧版怎么做，新版改成了什么¶

    设想一个"部署到生产环境"的工具，Server 执行前需要用户确认。

    旧版：Server 处理到一半，反过来向 Client 发一个独立请求：

    Client ── tools/call (id=10) ──▶ Server
Client ◀── elicitation/create (id=90) ── Server   （Server 中途反问）
Client ── ElicitResult (id=90) ──▶ Server         （Client 回答）
Client ◀── Tool Result (id=10) ── Server          （原请求这时才完成）

    这像客服处理工单时中途打电话问你问题。它要求连接上存在 Server→Client 反向通道，而且原请求 id=10 一直悬着等答案——这些都是连接级状态。

    新版：Server 不反问，而是直接结束本次请求，把"缺什么"写进结果：

    Client ── tools/call (id=10) ──▶ Server
Client ◀── resultType=input_required ── Server    （本次请求已结束）
           （Client 收集用户输入）
Client ── tools/call (id=11) ──▶ Server            （全新的请求）
Client ◀── resultType=complete ── Server

    这像窗口工作人员说："材料不全办不了，这是缺件清单，补齐了重新取号。"原请求彻底结束，第二次是全新请求。

    一次业务操作由多个独立请求接力完成，这就是 MRTR。

    2.2 支持范围¶

    只有三个方法允许返回 input_required：

    • tools/call；
    • resources/read；
    • prompts/get。

    其他方法不能使用 MRTR。

    2.3 基本流程¶

    sequenceDiagram
    actor U as User
    participant C as Client
    participant S as Server

    C->>S: tools/call (id=1)
    S-->>C: resultType=input_required
    Note over C: 处理 inputRequests
    C->>U: 表单/确认/打开 URL
    U-->>C: 输入结果
    C->>S: 重试 tools/call (id=2)
    S-->>C: resultType=complete

    第一次 Request 已经结束。第二次是新的独立 Request，因此必须使用不同 ID。

    2.4 inputRequests：Server 的"缺件清单"¶

    Server 把需要的每项输入打包成一个 Map，Key 由 Server 自己分配：

    {
  "inputRequests": {
    "confirm_publish": {
      "method": "elicitation/create",
      "params": {
        "mode": "form",
        "message": "确认发布版本 2.0.0？",
        "requestedSchema": {
          "type": "object",
          "properties": {
            "confirmed": {"type": "boolean"}
          },
          "required": ["confirmed"]
        }
      }
    }
  }
}

    允许的请求类型：

    • elicitation/create；
    • sampling/createMessage（已 Deprecated，新实现不应采用）；
    • roots/list（已 Deprecated，新实现不应采用）。

    Server 不能请求 Client 未声明支持的能力。

    2.5 inputResponses：Client 按清单补交¶

    Client 收集完输入后，按同名 Key 逐项交回：

    {
  "inputResponses": {
    "confirm_publish": {
      "action": "accept",
      "content": {
        "confirmed": true
      }
    }
  }
}

    Elicitation 的动作有：

    Action 含义
    accept 用户提交/同意
    decline 用户明确拒绝
    cancel 用户关闭或未作选择

    Server 必须区分这三种状态，不能把 cancel 当成 decline 或成功。

    2.6 requestState：Server 给的"回执"¶

    重试是全新请求，Server 怎么知道"你上次来过、办到哪一步"？靠 requestState：Server 把恢复所需的状态编码成不透明字符串，Client 下次原样带回：

    {
  "resultType": "input_required",
  "inputRequests": {...},
  "requestState": "opaque-state"
}

    Client 的规则：

    • 原样回传；
    • 不解析；
    • 不修改；
    • 不跨请求复用；
    • Server 没返回时不要自行添加。

    Server 必须把它当攻击者可控输入。如果影响权限、资源或业务逻辑，应使用 HMAC 或 AEAD 保护完整性，并验证：

    • 认证主体；
    • 短 TTL；
    • 原始方法和关键参数摘要；
    • 必要时单次使用标记。

    仅 Base64 JSON 不提供完整性保护。

    2.7 完整示例¶

    第一次调用：

    {
  "jsonrpc": "2.0",
  "id": 100,
  "method": "tools/call",
  "params": {
    "name": "deploy",
    "arguments": {"environment": "production", "version": "2.0.0"},
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {
        "elicitation": {"form": {}}
      }
    }
  }
}

    中间结果：

    {
  "jsonrpc": "2.0",
  "id": 100,
  "result": {
    "resultType": "input_required",
    "inputRequests": {
      "deploy_confirm": {
        "method": "elicitation/create",
        "params": {
          "mode": "form",
          "message": "这是生产环境发布，请确认。",
          "requestedSchema": {
            "type": "object",
            "properties": {
              "confirmed": {"type": "boolean"}
            },
            "required": ["confirmed"]
          }
        }
      }
    },
    "requestState": "signed-state"
  }
}

    重试：

    {
  "jsonrpc": "2.0",
  "id": 101,
  "method": "tools/call",
  "params": {
    "name": "deploy",
    "arguments": {"environment": "production", "version": "2.0.0"},
    "inputResponses": {
      "deploy_confirm": {
        "action": "accept",
        "content": {"confirmed": true}
      }
    },
    "requestState": "signed-state",
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {
        "elicitation": {"form": {}}
      }
    }
  }
}

    2.8 多轮与循环保护¶

    Server 可以连续多次返回 input_required。Client 应设置：

    • 最大轮数；
    • 总超时；
    • 用户取消入口；
    • 相同请求重复检测；
    • requestState 大小限制。

    否则恶意或有 Bug 的 Server 可以制造无限交互循环。

    3. Elicitation：MRTR 里"问什么"¶

    MRTR 是机制（请求怎么往返），Elicitation 是内容（Server 问用户什么）。它是 MRTR 最主要的用途：Server 借助 Client 的 UI 向用户要确认、要表单输入，或引导用户完成一次外部授权。

    3.1 Client 能力¶

    {
  "elicitation": {
    "form": {},
    "url": {}
  }
}

    空对象的 Legacy 兼容语义等价于仅 Form。现代实现应明确声明支持的模式。

    3.2 Form 模式¶

    适合普通结构化输入：

    {
  "method": "elicitation/create",
  "params": {
    "mode": "form",
    "message": "请输入通知邮箱",
    "requestedSchema": {
      "type": "object",
      "properties": {
        "email": {
          "type": "string",
          "format": "email"
        }
      },
      "required": ["email"]
    }
  }
}

    Form Schema 被限制为扁平对象和基础类型，以便 Client 生成 UI。

    禁止通过 Form 请求：密码、API Key、Access Token、支付凭据。

    3.3 URL 模式¶

    敏感交互应在 Server 控制的 HTTPS 页面中完成：

    {
  "method": "elicitation/create",
  "params": {
    "mode": "url",
    "url": "https://mcp.example.com/connect",
    "message": "请连接第三方账号后继续"
  }
}

    Client 必须：

    • 显示完整 URL 和来源 Server；
    • 获得用户明确同意；
    • 不预抓取 URL；
    • 不让 LLM 看到页面输入；
    • 使用安全浏览器容器打开；
    • 拒绝危险 Scheme。

    URL Elicitation 用于 Server 与第三方服务的授权或敏感输入，不能代替 MCP Client 访问 MCP Server 本身的 OAuth 授权。

    4. Subscriptions：监听"公告栏"¶

    subscriptions/listen 是一个长请求：Client 发出"这些变化我要听"，这个请求的 Response Stream 就一直开着，有变化 Server 就往里推通知。订阅状态只属于这个请求本身，不属于任何连接或 Session。

    4.1 过滤器¶

    {
  "notifications": {
    "toolsListChanged": true,
    "promptsListChanged": true,
    "resourcesListChanged": true,
    "resourceSubscriptions": [
      "file:///project/config.yaml"
    ]
  }
}

    所有字段可选。Server 不能发送 Client 没订阅的通知类型。

    4.2 确认¶

    Server 的第一条该订阅消息必须是：

    {
  "jsonrpc": "2.0",
  "method": "notifications/subscriptions/acknowledged",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/subscriptionId": 500
    },
    "notifications": {
      "toolsListChanged": true,
      "resourceSubscriptions": ["file:///project/config.yaml"]
    }
  }
}

    确认中的过滤器是 Server 实际接受的子集，Client 应检查哪些能力未被接受。

    4.3 通知关联¶

    订阅 ID 就是 subscriptions/listen 的 JSON-RPC Request ID。每条通知都必须携带它：

    {
  "jsonrpc": "2.0",
  "method": "notifications/tools/list_changed",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/subscriptionId": 500
    }
  }
}

    Client 可以并发打开多个订阅，并用此 ID 分流。

    4.4 订阅终止¶

    Client 终止：

    • HTTP：关闭 SSE Response Stream；
    • stdio：发送 notifications/cancelled，requestId 指向 Listen Request。

    Server 主动正常终止时，应发送原 Listen Request 的最终成功 Response，然后关闭流：

    {
  "jsonrpc": "2.0",
  "id": 500,
  "result": {
    "resultType": "complete",
    "_meta": {
      "io.modelcontextprotocol/subscriptionId": 500
    }
  }
}

    断线没有重放保证，Client 需要重建订阅并重新读取列表/资源。

    4.5 长请求靠什么维持¶

    先澄清两个常见误解：

    它不是回调。Client 不需要暴露任何 HTTP 端点，Server 也不会反向发起请求。整个机制是：Client 发一次 POST，Server 返回 text/event-stream 响应，并且故意不结束这个响应——有变化就往响应体里写一条事件。数据始终沿着 Client 自己发起的那条响应流下行。

    它也不是永不断开的连接。协议明确假设流会断：没有重放保证，断线后必须重新 Listen。断开的常见原因：

    • 网络抖动或客户端切换网络；
    • Server 重启、发布、扩缩容；
    • 反向代理/负载均衡器的空闲超时（如 nginx 默认 proxy_read_timeout 是 60 秒）；
    • 中间设备对 SSE 响应做缓冲，导致事件积压或连接被回收。

    维持这条流，依赖三层各自做对事：

    层 要做什么
    Server Handler 不返回、持有响应流；定期发送 SSE 心跳（注释行 : keepalive），让流不"空闲"
    中间设施 代理不缓冲 text/event-stream；读超时大于心跳间隔；LB 允许长响应
    Client 设置 SSE 空闲超时（连续 N 秒无任何事件即判定断开）；断开后重新 Listen

    服务端设了超时，流不就被杀了吗？ 会——这是 SSE 部署最常见的坑。但要区分两类超时，应对完全不同：

    超时类型 判定条件 心跳能否化解 应对
    空闲超时 距上次收到字节的时长 ✅ 能：心跳让流永不空闲 心跳间隔 < 最小空闲超时
    绝对超时 请求总时长，无论是否活跃 ❌ 不能 对该路由禁用或调大

    常见来源：nginx proxy_read_timeout（空闲型，默认 60s）、云 LB 空闲超时（ALB 默认 60s）、gunicorn --timeout（绝对型，超时直接杀 worker）、Go http.Server.WriteTimeout（绝对型）、ASP.NET RequestTimeout 中间件（绝对型）。

    正确做法不是全局去掉超时，而是：

    1. 对 MCP 路由单独配置：proxy_buffering off、proxy_read_timeout 调大（如 24h）；
    2. 心跳间隔小于链路上最小的空闲超时（如 15s 心跳 vs 60s 超时）；
    3. 绝对型超时对该路由禁用——注意 gunicorn 这类杀 worker 的超时无法按路由豁免，长流场景应换异步 worker 或独立部署；
    4. 即使仍偶发断开，协议本身已兜底：Client 重连并重新拉数据，正确性不受影响，只损失效率。

    传输层细节：HTTP/1.1 下这条流独占一个 TCP 连接，并发订阅数受连接数限制；HTTP/2 下它是多路复用的一条 stream，不独占连接；stdio 没有这些设施问题——"流"就是子进程的 stdout，进程活着它就在。

    无论哪层导致断开，恢复动作都一样：重新发送 subscriptions/listen，再重新拉取关心的列表或资源。不要试图"续传"——Modern MCP 已移除 Last-Event-ID 重放。

    4.6 订阅是可选功能¶

    Server 不必须提供订阅。规范只要求实现能正确处理 subscriptions/listen 这类消息，不要求每个 Server 都实际维护通知流。不想提供订阅的 Server 有两种合规做法：

    做法 表现 Client 看到
    直接拒绝 对 subscriptions/listen 返回 JSON-RPC 错误（如 -32601 Method not found） 该 Server 无订阅，退化为 TTL 模式
    接受但确认空子集 接受 Listen 请求，但在 acknowledged 的 notifications 中省略所有不支持的通知类型 acknowledged 与请求的差集即未接受部分

    第二种正是 acknowledged 设计成"Server 实际接受的子集"的原因：Client 请求了四类通知，Server 可以只接受其中两类，甚至一类都不接受。

    Client 必须优雅处理这两种情况：检查 acknowledged 与请求的差集，对未接受的通知类型退化为 TTL 驱动的新鲜度管理。

    没有订阅不影响正确性，只影响时效：

    • 有订阅：变化时缓存立即失效，TTL 只是兜底；
    • 无订阅：完全依赖 ttlMs，过期后重新拉取，最坏延迟一个 TTL 周期。

    Server 还可以在 Capabilities 中提前表态：tools: {"listChanged": true} 表示"工具列表变化时我会发通知"。未声明 listChanged 的 Server，Client 本来就不应期待对应通知。静态工具列表的 Server（工具在编译期固定）天然不需要订阅——这也是大多数简单 Server 的实际情况。

    5. Progress：执行中的"叫号屏"¶

    进度通知是 Server 在请求执行期间主动推送的汇报。Client 想接收进度，就在请求 _meta 中放一个唯一 Token：

    {
  "_meta": {
    "progressToken": "deploy-2026-42",
    "io.modelcontextprotocol/protocolVersion": "2026-07-28",
    "io.modelcontextprotocol/clientCapabilities": {}
  }
}

    Server 可发送：

    {
  "jsonrpc": "2.0",
  "method": "notifications/progress",
  "params": {
    "progressToken": "deploy-2026-42",
    "progress": 45,
    "total": 100,
    "message": "正在发布第 9/20 个实例"
  }
}

    规则：

    • Token 是字符串或整数；
    • 所有活动请求中唯一；
    • progress 必须单调增加；
    • total 可以省略，也可以是浮点；
    • Server 可以选择不发；
    • 完成后必须停止；
    • 应限流，避免高频通知淹没通道。

    Progress 可以延长软超时，但 Client 仍应设置绝对最大超时。

    6. Cancellation：用户"不等了"¶

    取消的对象是在途请求，做法按传输分两种：

    6.1 stdio¶

    {
  "jsonrpc": "2.0",
  "method": "notifications/cancelled",
  "params": {
    "requestId": 100,
    "reason": "用户停止发布"
  }
}

    Server 应：

    • 停止可停止的工作；
    • 释放资源；
    • 不再返回该 Request 的 Response。

    Server 可以忽略未知、已完成或不可取消请求。Client 应忽略取消后迟到的结果。

    6.2 Streamable HTTP¶

    关闭该请求的 SSE Response Stream。因为每个 Request 有独立流，不需要额外取消 Notification。

    6.3 取消不是回滚¶

    取消只表示停止继续处理，不保证撤销已发生副作用：

    已创建云实例 3 个
→ 用户取消
→ Server 停止创建后续实例
→ 已创建的 3 个实例不会自动消失

    Tool 应明确描述部分完成语义，并提供补偿 Tool 或状态查询 Tool。

    7. Timeout¶

    超时是 Client 的自保措施：不能无限等一个请求。每个请求都应配置：

    • 连接/启动超时；
    • 首字节超时；
    • 请求软超时；
    • 绝对最大超时；
    • MRTR 总轮数和总时长；
    • SSE 空闲超时和保活策略。

    超时后：

    1. 按传输发起取消；
    2. 停止等待；
    3. 根据 Tool 幂等性决定是否重试；
    4. 记录 Request ID、Tool 名、阶段和耗时。

    8. 缓存、通知与分页的组合¶

    这些模式不是孤立的，它们与缓存、分页互相影响：

    8.1 缓存¶

    fresh = now < received_at + ttlMs

    ttlMs 是按需访问时的新鲜度判断，不应直接成为固定轮询周期。

    8.2 通知失效¶

    收到：

    notifications/tools/list_changed

    应立即把 tools/list 缓存标记为 stale，即使 TTL 尚未到期。

    8.3 分页¶

    每一页独立缓存；底层列表变化时可能出现重复或遗漏。要求一致快照时，从无 Cursor 的第一页重新拉取。

    8.4 断线¶

    通知不会重放，所以恢复连接后：

    1. 重新 subscriptions/listen；
    2. 重新 Discover 或使用未过期缓存；
    3. 关键列表最好重新从第一页拉取；
    4. 关键资源重新 Read。

    9. Tasks 扩展：比"一次请求"更长的工作¶

    MRTR 和 Progress 都活在"一次请求"内。如果工作要跑几分钟到几小时、Client 断开后仍要继续，就需要 Tasks。实验性 Tasks 曾在 2025-11-25 Core 中出现，2026-07-28 已移出 Core，成为官方扩展 io.modelcontextprotocol/tasks。

    适用场景：

    • 几分钟到几小时的 durable 工作；
    • Client 断开后任务仍运行；
    • 需要任务句柄、轮询和后续输入。

    现代 Server 在 Capabilities Extensions 中声明：

    {
  "extensions": {
    "io.modelcontextprotocol/tasks": {}
  }
}

    不要把普通的数秒级 Tool Call 都建模为 Task。短操作使用 Progress + Cancellation；持久异步工作再使用 Tasks 扩展。

    10. Deprecated Client 能力¶

    2026-07-28 中以下能力仍存在，但已 Deprecated，新实现不应采用：

    • Roots：改为 Tool 参数、Resource URI 或 Server 配置；
    • Sampling：Server 直接接入模型 Provider API；
    • Logging：stdio 写 stderr，远程使用 OpenTelemetry。

    教程仍会解释它们，是为了阅读旧实现和处理兼容，不代表推荐用于新项目。

    11. 实现检查表¶

    Client¶

    • input_required 使用新 Request ID 重试
    • 原样回传 requestState
    • MRTR 有最大轮数和总超时
    • Elicitation 提供 accept/decline/cancel
    • URL 模式不预抓取且显示完整域名
    • 订阅先等待 acknowledged
    • 断线后重建订阅
    • Progress Token 在活动请求中唯一
    • 取消后忽略迟到结果

    Server¶

    • 只在允许方法上返回 input_required
    • 不请求 Client 未声明的能力
    • requestState 有完整性、主体、TTL 和请求绑定
    • 不假设 Client 一定重试
    • 不向订阅发送未请求通知
    • Progress 单调、限频且完成后停止
    • 取消时尽快释放资源
    • 部分副作用可查询或补偿
