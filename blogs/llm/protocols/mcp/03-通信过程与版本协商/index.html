    MCP 通信过程与版本协商¶

    MCP 在 2026-07-28 发生了协议时代切换。本章同时讲清 现代无状态流程 与 旧版初始化流程，避免把两者混用。

    1. 两个协议时代¶

    时代 版本 核心特征
    Legacy 2025-11-25 及以前 initialize 握手建立协议 Session
    Modern 2026-07-28 及以后 每个请求携带版本和能力，无初始化 Session

    现代与旧版不是简单增加字段，而是通信模型的 Breaking Change。

    2. 现代协议总流程¶

    sequenceDiagram
    participant C as Client
    participant S as Server

    opt 可选的预发现
        C->>S: server/discover + 每请求 _meta
        S-->>C: supportedVersions + capabilities
    end

    C->>S: tools/list + 每请求 _meta
    S-->>C: tools + ttlMs + cacheScope

    C->>S: tools/call + 每请求 _meta
    alt 直接完成
        S-->>C: resultType=complete
    else 需要额外输入
        S-->>C: resultType=input_required
        Note over C: 获取用户输入/其他输入
        C->>S: 用新 id 重试原方法 + inputResponses
        S-->>C: resultType=complete
    end

    opt 监听变化
        C->>S: subscriptions/listen
        S--)C: subscriptions/acknowledged
        S--)C: notifications/*
    end

    每个 Request 都是自包含的。Server 不能假设前面已经调用过 server/discover。

    3. server/discover¶

    现代 Server 必须实现 server/discover，但 Client 可以不调用。Client 有两种策略：

    1. 先 Discover，提前知道版本和能力；
    2. 直接发送业务请求，遇到版本错误后重试。

    3.1 Discover 请求¶

    {
  "jsonrpc": "2.0",
  "id": "discover-1",
  "method": "server/discover",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": {
        "name": "demo-client",
        "version": "1.0.0"
      },
      "io.modelcontextprotocol/clientCapabilities": {
        "elicitation": {"form": {}, "url": {}}
      }
    }
  }
}

    3.2 Discover 响应¶

    {
  "jsonrpc": "2.0",
  "id": "discover-1",
  "result": {
    "resultType": "complete",
    "supportedVersions": ["2026-07-28"],
    "capabilities": {
      "tools": {"listChanged": true},
      "resources": {"subscribe": true},
      "prompts": {}
    },
    "instructions": "本服务提供天气与报告能力。",
    "_meta": {
      "io.modelcontextprotocol/serverInfo": {
        "name": "weather-server",
        "version": "1.2.0"
      }
    },
    "ttlMs": 3600000,
    "cacheScope": "public"
  }
}

    Discover 适合：

    • 展示 Server 名称和功能；
    • 一次获得 Server 能力；
    • 选择共同版本；
    • stdio 中探测 Server 属于 Modern 还是 Legacy；
    • 缓存 Server 元数据。

    4. 现代版本协商¶

    版本采用 YYYY-MM-DD，表示最后一次发生不兼容变更的日期。兼容性更新不会自动改变版本号。

    每个请求声明版本：

    {
  "io.modelcontextprotocol/protocolVersion": "2026-07-28"
}

    HTTP 还必须发送相同值：

    MCP-Protocol-Version: 2026-07-28

    如果 Server 不支持：

    {
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32022,
    "message": "Unsupported protocol version",
    "data": {
      "supported": ["2026-07-28", "2025-11-25"],
      "requested": "2099-01-01"
    }
  }
}

    Client 应从 supported 中选择自己也支持的版本，使用新请求重新发送；没有交集时向用户报告不兼容。

    注意：版本是按请求声明的，不是连接建立后永久保存的连接状态。一个实现可以同时支持多个协议版本。

    5. 能力协商¶

    Client 在每个请求中声明与该请求相关的能力：

    {
  "io.modelcontextprotocol/clientCapabilities": {
    "elicitation": {
      "form": {},
      "url": {}
    },
    "extensions": {
      "io.modelcontextprotocol/ui": {
        "mimeTypes": ["text/html;profile=mcp-app"]
      }
    }
  }
}

    Server 在 Discover 中声明能力：

    {
  "tools": {"listChanged": true},
  "resources": {"listChanged": true, "subscribe": true},
  "prompts": {"listChanged": true},
  "completions": {},
  "extensions": {}
}

    能力是功能门控：

    • Server 未声明 tools，Client 不应调用 tools/list；
    • Client 未声明 elicitation，Server 不能在 MRTR 中请求 elicitation；
    • 一方不支持扩展时，另一方必须回退到 Core 行为或明确拒绝。

    6. 从发现到 Tool 调用¶

    6.1 发现工具¶

    {
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/list",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}

    Server 返回成功响应：

    {
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "resultType": "complete",
    "tools": [
      {
        "name": "get_weather",
        "title": "查询天气",
        "description": "查询指定城市的实时天气。",
        "inputSchema": {
          "type": "object",
          "properties": {
            "city": {
              "type": "string",
              "description": "城市名称，例如北京"
            }
          },
          "required": ["city"],
          "additionalProperties": false
        },
        "outputSchema": {
          "type": "object",
          "properties": {
            "city": {"type": "string"},
            "condition": {"type": "string"},
            "temperature": {"type": "number"}
          },
          "required": ["city", "condition", "temperature"]
        }
      }
    ],
    "ttlMs": 300000,
    "cacheScope": "public"
  }
}

    响应中的 id 必须与请求一致。resultType: "complete" 表示本轮请求已经完成；tools 提供输入、输出 Schema；ttlMs 表示结果建议缓存 5 分钟；cacheScope: "public" 表示该列表不包含用户私有信息，可以跨用户共享缓存。如果不同用户看到的 Tool 不同，则必须使用 private。

    Client 可以缓存 Tool 列表，再把相关定义转换成模型厂商的 Tool Schema。

    6.2 模型选择工具¶

    这一步发生在 Host 与 LLM 之间，不是 MCP 消息：

    {
  "name": "get_weather",
  "arguments": {"city": "北京"}
}

    6.3 调用工具¶

    {
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": {"city": "北京"},
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}

    Server 校验：

    1. 方法和消息结构；
    2. Tool 是否存在；
    3. 参数是否符合 JSON Schema；
    4. 身份和权限；
    5. 业务规则；
    6. 限流和超时。

    6.4 返回工具结果¶

    {
  "jsonrpc": "2.0",
  "id": 3,
  "result": {
    "resultType": "complete",
    "content": [
      {"type": "text", "text": "北京：晴，18°C"}
    ],
    "structuredContent": {
      "city": "北京",
      "condition": "晴",
      "temperature": 18
    },
    "isError": false
  }
}

    Host 再把结果作为 Tool Message/Observation 交给模型。

    7. MRTR：Server 需要额外输入¶

    现代协议禁止 Server 在通道上突然发送独立 JSON-RPC Request。Server 需要用户输入时，返回中间结果：

    {
  "jsonrpc": "2.0",
  "id": 10,
  "result": {
    "resultType": "input_required",
    "inputRequests": {
      "confirm_delete": {
        "method": "elicitation/create",
        "params": {
          "mode": "form",
          "message": "确认删除报告？",
          "requestedSchema": {
            "type": "object",
            "properties": {
              "confirmed": {"type": "boolean"}
            },
            "required": ["confirmed"]
          }
        }
      }
    },
    "requestState": "opaque-integrity-protected-state"
  }
}

    Client 收集输入后，以新 JSON-RPC ID 重试原方法：

    {
  "jsonrpc": "2.0",
  "id": 11,
  "method": "tools/call",
  "params": {
    "name": "delete_report",
    "arguments": {"report_id": "r-42"},
    "inputResponses": {
      "confirm_delete": {
        "action": "accept",
        "content": {"confirmed": true}
      }
    },
    "requestState": "opaque-integrity-protected-state",
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {
        "elicitation": {"form": {}}
      }
    }
  }
}

    这仍是无状态流程：重试请求包含完成处理所需的全部上下文。

    8. 变化通知¶

    现代协议通过 subscriptions/listen 打开长响应流：

    sequenceDiagram
    participant C as Client
    participant S as Server
    C->>S: subscriptions/listen (id=50)
    S--)C: notifications/subscriptions/acknowledged
    S--)C: notifications/tools/list_changed
    C->>S: tools/list
    S-->>C: 新 Tool 列表

    每条订阅通知都带：

    {
  "_meta": {
    "io.modelcontextprotocol/subscriptionId": 50
  }
}

    通知不是可靠队列；断线后需要重建订阅，Client 仍应结合 TTL 保持数据新鲜。

    9. Legacy 初始化流程¶

    2025-11-25 及以前版本使用握手：

    sequenceDiagram
    participant C as Legacy Client
    participant S as Legacy Server
    C->>S: initialize
    S-->>C: protocolVersion + capabilities + serverInfo
    C--)S: notifications/initialized
    C->>S: tools/list
    S-->>C: tools
    C->>S: tools/call
    S-->>C: result

    9.1 初始化请求¶

    {
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-11-25",
    "capabilities": {},
    "clientInfo": {
      "name": "legacy-client",
      "version": "1.0.0"
    }
  }
}

    Server 选择版本并返回能力；Client 不支持返回版本时应断开。随后 Client 发送没有 ID 的 notifications/initialized。

    Legacy 流程中版本和能力是 Session 状态，普通请求不需要重复携带现代 _meta。

    10. Dual-era 兼容¶

    10.1 stdio 探测¶

    同时支持 Modern 与 Legacy 的 Client 应：

    1. 先发送带现代 _meta 的 server/discover；
    2. 收到 DiscoverResult：使用 Modern；
    3. 收到 UnsupportedProtocolVersion：仍是 Modern，选共同版本重试；
    4. 收到其他错误或合理超时：判定为 Legacy，回退到 initialize。

    不能只根据一个固定错误码回退，因为旧 Server 对初始化前未知请求的行为不统一。

    10.2 HTTP 探测¶

    Dual-era Client 先发送 Modern POST：

    • 成功或收到可识别的现代错误：继续 Modern；
    • 收到 400 且 Body 不是现代错误：回退 initialize；
    • 如还要兼容 2024-11-05，可进一步探测已 Deprecated 的 HTTP+SSE。

    10.3 兼容矩阵¶

    Client Server 结果
    Modern Modern 正常
    Modern Legacy 失败；Modern-only Client 不会初始化回退
    Dual-era Modern 正常，保持 Modern
    Dual-era Legacy 探测后回退初始化
    Legacy Modern 失败；Legacy Client 没有向前协商机制
    Legacy Dual-era Server 以 Legacy 模式服务

    11. 关闭与恢复¶

    现代协议没有 shutdown RPC。

    • stdio：Client 关闭子进程 stdin，等待退出，必要时终止进程；
    • HTTP：关闭请求响应流；
    • Server 崩溃：无状态请求的在途结果丢失，Client 可按幂等性策略重试；
    • 订阅流断开：重新发送 subscriptions/listen；
    • 非幂等 Tool 不可盲目重试，必须使用业务幂等键或先查询操作状态。

    12. 常见误区¶

    1. “MCP 建连第一步一定是 initialize”：只对 Legacy 成立。
    2. “server/discover 是所有请求的前置条件”：Server 必须实现，但 Client 调用是可选的。
    3. “无状态意味着不能保持长连接”：无状态指请求处理不依赖隐式 Session。
    4. “LLM 直接调用 MCP Server”：Host/Client 才是协议调用方。
    5. “版本在 TCP/stdio 连接上协商一次”：现代版本按请求声明。
    6. “收到 input_required 后继续使用原 id”：重试必须使用新 ID。
    7. “通知可替代缓存 TTL”：通知是 best effort，两者互补。
