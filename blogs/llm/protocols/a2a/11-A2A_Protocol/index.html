    A2A (Agent2Agent) Protocol 学习指南¶

    A2A = Agent-to-Agent 通信协议，Google 开源并捐赠给 Linux Foundation 的开放标准。 目标：让不同框架、不同厂商构建的 AI Agent 能够无缝互操作和协作。

    1. 为什么需要 A2A？¶

    1.1 核心理念：Agents Are Not Tools¶

    Agent ≠ Tool——这是 A2A 存在的根本理由。

    维度 Tool Agent
    本质 原语（Primitive） 自治系统（Autonomous System）
    状态 通常无状态 有状态（维护对话上下文）
    交互 一次调用，返回结果 多轮对话、协商、反问
    能力 执行特定函数 推理、规划、使用多个工具
    类比 计算器、数据库查询 同事、合作伙伴

    把 Agent 包装成 Tool 来调用是降维使用——把有自主推理能力的智能体退化为无状态函数。 A2A 让 Agent 作为平等的智能体协作，保持其推理、规划、多轮对话的完整能力。

    1.2 问题背景¶

    假设你要一个 AI 助手规划一次出国旅行，需要协调多个专业 Agent：

                        🧑 用户
                      │
            ┌─────────┴─────────┐
            ▼                   ▼
        ✈️ 航班预订 Agent    🏨 酒店预订 Agent

        💱 货币兑换 Agent    🚌 当地旅游 Agent

    没有 A2A 时的困境： - 🔧 每个 Agent 都得"包装成 Tool"才能被调用——但 Agent 不是 Tool！ - 🔗 需要为每一对 Agent 写点对点集成代码 - 🐌 每新增一个 Agent 都要重新做集成，创新慢 - 📐 系统无法横向扩展，Agent 越多越乱 - 🔒 临时通信缺乏统一的安全标准

    1.3 A2A 的解决方案¶

    A2A 提供了一套标准化的 Agent 间通信协议：

    🧑 用户 → 🤖 主协调 Agent ↔ A2A协议 ↔ ✈️ 航班 Agent
                               ↔ A2A协议 ↔ 🏨 酒店 Agent
                               ↔ A2A协议 ↔ 💱 货币 Agent
                               ↔ A2A协议 ↔ 🚌 旅游 Agent

    所有 Agent 通过同一个协议对话，不需要知道对方的内部实现。

    1.4 Agent Stack 全景图¶

    A2A 在整个 AI 技术栈中的位置：

    ┌─────────────────────────────────────────────────────────────┐
│                      User / Human                           │
│                          ↕                                  │
├─────────────────────────────────────────────────────────────┤
│  Layer 4: Inter-Agent Communication                         │
│  **A2A Protocol** — Agent ↔ Agent 协作                      │
├─────────────────────────────────────────────────────────────┤
│  Layer 3: Agent Frameworks                                  │
│  ADK (Google) / LangGraph / CrewAI / Semantic Kernel / 自研   │
├─────────────────────────────────────────────────────────────┤
│  Layer 2: Tool & Resource Access                            │
│  **MCP** — Agent ↔ Tool/数据                                │
├─────────────────────────────────────────────────────────────┤
│  Layer 1: Foundation Models                                 │
│  Gemini / GPT / Claude / Qwen / Llama / ...                 │
└─────────────────────────────────────────────────────────────┘

    一句话理解： A2A 不是替代 MCP 或 LangGraph，而是在更高层次上让它们协同工作。

    官方推荐公式：用 ADK 构建 Agent + 用 MCP 接入工具 + 用 A2A 与其他 Agent/人类通信 = 完整的 Agentic 应用

    1.5 生态集成¶

    项目 与 A2A 的关系
    IBM ACP Agent Communication Protocol 已并入 A2A 规范
    Cisco agntcy 提供 Agent 基础设施（发现、群组通信、身份），使用 A2A 作为通信协议
    Google ADK Agent 开发框架，与 A2A 无缝集成
    LangGraph/CrewAI 任何框架构建的 Agent 都可以通过 A2A 互操作

    2. 核心概念¶

    概念 一句话解释 类比
    Agent Card Agent 的"名片"——JSON 格式描述身份、能力、端点、认证 营业执照 + 服务目录
    Task 有状态的工作单元，有唯一 ID 和完整生命周期 一个工单
    Message 单次通信回合，包含角色和 Part 内容 一条消息
    Part 最小内容单元——文本、文件引用、结构化数据 消息里的一段内容
    Artifact 任务产出的具体结果（文档、图片、结构化数据） 交付物
    contextId 关联多个 Task 的上下文标识符 会话 ID
    Streaming SSE 实时推送任务进度 直播弹幕
    Push Notification Webhook 异步通知（适合超长任务） 短信通知

    2.1 核心角色¶

    🧑 用户 (User)
  │
  ▼
🤖 A2A 客户端 / 协调 Agent (Client Agent)
  │  发起请求，代表用户
  │
  ▼
🌐 A2A 服务端 / 远程 Agent (Remote Agent)
     接收请求，处理任务，返回结果
     ── 对客户端来说是个黑盒 ──

    3. A2A 三层架构¶

    A2A 规范分为三层，每层职责清晰：

    ┌─────────────────────────────────────────────┐
│  Layer 1: 数据模型 (Data Model)              │
│  Task | Message | AgentCard | Part |         │
│  Artifact | Extension                        │
├─────────────────────────────────────────────┤
│  Layer 2: 抽象操作 (Abstract Operations)     │
│  SendMessage | SendStreamingMessage |         │
│  GetTask | ListTasks | CancelTask |           │
│  GetAgentCard                                 │
├─────────────────────────────────────────────┤
│  Layer 3: 协议绑定 (Protocol Bindings)       │
│  JSON-RPC 2.0 | gRPC | HTTP/REST | 自定义    │
└─────────────────────────────────────────────┘
    • Layer 1：所有实现必须理解的核心数据结构（用 Protocol Buffers 定义）
    • Layer 2：Agent 必须支持的基本能力（与具体协议无关）
    • Layer 3：将抽象操作映射到具体传输协议

    好处：核心语义在所有协议绑定中保持一致，新增协议绑定不用改数据模型。

    4. A2A 请求生命周期¶

    完整的交互流程分 4 步：

    Step 1: Agent 发现
  Client ──GET──> /.well-known/agent-card.json
  Client <──200── Agent Card (JSON)

Step 2: 认证
  Client ──OAuth2 / JWT──> Auth Server
  Client <──JWT Token── Auth Server

Step 3: 发送消息 (同步)
  Client ──POST /sendMessage + JWT──> A2A Server
  Client <──Task (submitted)── A2A Server

Step 4: 流式接收结果
  Client ──POST /sendMessageStream + JWT──> A2A Server
  A2A Server ──SSE──> Stream:
    ├─ Task (submitted)
    ├─ TaskStatusUpdateEvent (working)
    ├─ TaskArtifactUpdateEvent (artifact A)
    ├─ TaskArtifactUpdateEvent (artifact B)
    └─ TaskStatusUpdateEvent (completed)

    5. Agent Card — 核心结构¶

    Agent Card 是 A2A 的发现机制，一个 JSON 文档：

    {
  "name": "Flight Booking Agent",
  "description": "Agent for searching and booking flights",
  "url": "https://flights.example.com/a2a",
  "version": "1.0.0",
  "capabilities": {
    "streaming": true,
    "pushNotifications": true
  },
  "skills": [
    {
      "id": "search_flights",
      "name": "Search Flights",
      "description": "Search for available flights between two airports",
      "inputModes": ["text", "application/json"],
      "outputModes": ["text", "application/json"],
      "examples": ["Find flights from PEK to JFK on 2025-06-01"]
    },
    {
      "id": "book_flight",
      "name": "Book Flight",
      "description": "Book a specific flight",
      "inputModes": ["application/json"],
      "outputModes": ["application/json"]
    }
  ],
  "securitySchemes": {
    "bearerAuth": {
      "type": "http",
      "scheme": "bearer",
      "bearerFormat": "JWT"
    }
  }
}

    关键字段： - name / description：Agent 身份 - url：A2A 服务端点 - capabilities：支持的功能（流式、推送通知等） - skills[]：具体技能列表，每个技能有输入/输出模式 - securitySchemes：认证要求

    6. Task 生命周期¶

    Task 是 A2A 的核心工作单元，有明确的状态机：

                        ┌──────────────┐
                    │   SUBMITTED  │  任务已接收
                    └──────┬───────┘
                           │
                    ┌──────▼───────┐
                    │   WORKING    │  处理中
                    └──────┬───────┘
                           │
          ┌────────────────┼────────────────┐
          │                │                │
   ┌──────▼──────┐ ┌──────▼──────┐ ┌───────▼───────┐
   │  COMPLETED  │ │   FAILED    │ │  CANCELED     │
   │  ✅ 完成    │ │  ❌ 失败    │ │  ⛔ 已取消    │
   └─────────────┘ └─────────────┘ └───────────────┘
          │
   ┌──────▼──────┐
   │  REJECTED   │  被拒绝（权限不足等）
   └─────────────┘

  中断状态（非终态）：
   ├─ INPUT_REQUIRED   需要用户输入
   └─ AUTH_REQUIRED    需要认证

    6.1 Task vs Message 的区别¶

    场景 用 Message 用 Task
    简单问答 ✅ 即时返回
    需要状态跟踪 ✅ 长时间处理
    需要多轮对话 ✅ 有上下文
    需要产出具体结果 ✅ 有 Artifact
    需要流式进度 ✅ SSE 推送

    6.2 混合 Agent (Hybrid Agent)¶

    实际中最常见的模式： 1. 先用 Message 协商能力和范围 2. 确认后用 Task 跟踪执行 3. Task 完成后不能再发消息，需要新 Task（Task 不可变）

    7. A2A vs MCP — 互补协议¶

    这是面试必考点！

    ┌─────────────────────────────────────────────────────────┐
│                    完整 Agent 应用                        │
│                                                         │
│  ┌───────────┐     A2A     ┌───────────┐                │
│  │ Agent A   │◄──────────►│ Agent B   │  ← Agent 间    │
│  └─────┬─────┘             └─────┬─────┘    协作        │
│        │ MCP                     │ MCP                  │
│        ▼                         ▼                      │
│  ┌───────────┐             ┌───────────┐                │
│  │ Tool 1,2  │             │ Tool 3,4  │  ← Agent 内    │
│  │ (DB, API) │             │ (搜索,计算) │    工具调用    │
│  └───────────┘             └───────────┘                │
└─────────────────────────────────────────────────────────┘
    维度 MCP (Model Context Protocol) A2A (Agent2Agent Protocol)
    通信对象 Agent ↔ Tool Agent ↔ Agent
    本质 调用函数/工具 对话协商/任务委派
    状态 通常无状态 有状态（Task 生命周期）
    交互方式 一次调用，返回结果 多轮对话、流式、异步
    透明度 Tool 的 Schema 对 Agent 透明 Agent 内部对协作方不透明
    典型场景 查询数据库、调用 API 旅行规划、客服转派
    一句话 "我用工具" "我和同事合作"

    MCP = USB 接口（插工具）
    A2A = 电话会议（Agent 之间打电话）

    面试加分话术¶

    "MCP 解决的是Agent 怎么用工具的问题，定义了工具描述、调用、返回的标准方式。
    A2A 解决的是Agent 怎么和其他 Agent 协作的问题，定义了发现、认证、任务管理、流式推送的标准流程。
    一个完整的 Agentic 应用中，内部用 MCP 连工具，外部用 A2A 和其他 Agent 通信。"

    8. 流式与异步操作¶

    8.1 SSE 流式（适合客户端在线）¶

    Client ──POST /sendMessageStream──> Server
Server ──text/event-stream──> Client (连接保持打开)

事件流:
  event: message
  data: {"jsonrpc":"2.0", "result":{"task":{"id":"t1","status":{"state":"WORKING"}}}}

  event: message
  data: {"jsonrpc":"2.0", "result":{"type":"statusUpdate", ...}}

  event: message
  data: {"jsonrpc":"2.0", "result":{"type":"artifactUpdate", "artifact":{"name":"report.md",...}}}

  event: message
  data: {"jsonrpc":"2.0", "result":{"task":{"status":{"state":"COMPLETED"}}}}
  ← 流关闭

    适用场景： - 实时监控长任务进度 - 大文件分块接收（Artifact 流式传输） - 需要即时反馈的交互式对话

    8.2 Push Notification（适合客户端断开）¶

    Client 在请求中提供 webhook URL:
  {"pushNotificationConfig": {"url": "https://client.example.com/webhook"}}

Server 处理...
  处理中...（客户端可以断开连接）

Server ──POST──> https://client.example.com/webhook
  Payload: {"taskId":"t1", "status":{"state":"COMPLETED"}, "artifacts":[...]}

Client 收到通知后 ──GET /getTask──> Server 获取完整结果

    适用场景： - 超长任务（分钟/小时/天级别） - 移动端/Serverless 等无法保持持久连接 - 只需关注关键状态变更

    9. 企业级特性¶

    9.1 安全体系¶

    ┌─────────────────────────────────────────┐
│           A2A 安全纵深防御                │
├─────────────────────────────────────────┤
│ 传输层:  HTTPS (TLS 1.2+)               │
│ 认证层:  OAuth2 / OpenID Connect / API  │
│          Key (Agent Card 声明认证方案)   │
│ 授权层:  基于 Skill 粒度授权              │
│          最小权限原则                    │
│ 数据层:  不携带身份在 Payload 中          │
│          身份在 HTTP Header 传递         │
└─────────────────────────────────────────┘

    9.2 可观测性¶

    • 分布式追踪: 通过 W3C Trace Context 传递 trace ID，实现端到端可观测
    • 日志: 记录 taskId、contextId、correlation ID
    • 指标: 请求率、错误率、任务处理延迟
    • 审计: 记录任务创建、关键状态变更

    9.3 API 治理¶

    推荐通过 API Gateway 管理 A2A 端点： - 集中式策略执行（认证、限流、配额） - 流量管理（负载均衡、路由） - 分析报表 - 开发者门户

    10. Agent 发现策略¶

    有三种方式发现其他 Agent 的能力：

    策略 适用场景 机制
    Well-Known URI 公开 Agent GET https://domain/.well-known/agent-card.json
    注册中心 企业/市场 查询中心化注册表（按技能/标签筛选）
    直接配置 私有/开发 硬编码 URL 或配置文件

    11. A2A 在我们的 Agent 架构中的位置¶

    回顾我们之前构建的 Agent 教程（00-10 章），A2A 是新增的关键拼图：

    ┌─────────────────────────────────────────────────┐
│              Task Level (任务层)                  │
│         Planning + Multi-Agent + A2A             │
│   "怎么拆分任务、怎么委派给远程 Agent"             │
├─────────────────────────────────────────────────┤
│              Action Level (行动层)                │
│         ReAct + Tool Use (MCP) + Reflection      │
│   "当前怎么做、用什么工具"                          │
├─────────────────────────────────────────────────┤
│              Thought Level (思维层)               │
│         CoT + Memory + Perception                │
│   "怎么想清楚这个问题"                             │
└─────────────────────────────────────────────────┘

    与现有教程的关系：

    教程章节 与 A2A 的关系
    05 Tool Use (MCP) 互补：MCP 连工具，A2A 连 Agent
    06 Agent Architecture 扩展：A2A 让 Supervisor 可以委派给远程 Worker
    07 Control Loop 配合：A2A Task 生命周期 = 远程 Control Loop 的延伸

    之前的 Supervisor 模式只能调用本地 Worker，有了 A2A，Supervisor 可以把任务委派给任何 A2A 兼容的远程 Agent——不管对方用 LangGraph、CrewAI 还是自研框架。

    12. LangGraph 集成思路（概念性）¶

    虽然 A2A 官方 SDK 主要支持 Python FastAPI 实现，但我们可以把 A2A Client 封装为 LangGraph 的一个节点：

    from langgraph.graph import StateGraph, END
from typing import TypedDict
import httpx

class A2AState(TypedDict):
    user_query: str
    remote_agent_url: str
    agent_card: dict
    task_id: str
    result: str

# ── 节点 1：发现 Agent ──
async def discover_agent(state: A2AState) -> dict:
    async with httpx.AsyncClient() as client:
        resp = await client.get(f"{state['remote_agent_url']}/.well-known/agent-card.json")
        return {"agent_card": resp.json()}

# ── 节点 2：发送任务 ──
async def send_task(state: A2AState) -> dict:
    payload = {
        "jsonrpc": "2.0",
        "id": "1",
        "method": "SendMessage",
        "params": {
            "message": {
                "role": "user",
                "parts": [{"text": state["user_query"]}]
            }
        }
    }
    async with httpx.AsyncClient() as client:
        resp = await client.post(
            f"{state['agent_card']['url']}/",
            json=payload,
            headers={"Authorization": "Bearer YOUR_TOKEN"}
        )
    result = resp.json()["result"]
    task_id = result.get("taskId", "")
    return {"task_id": task_id}

# ── 节点 3：查询结果 ──
async def poll_task(state: A2AState) -> dict:
    payload = {
        "jsonrpc": "2.0",
        "id": "2",
        "method": "GetTask",
        "params": {"id": state["task_id"]}
    }
    async with httpx.AsyncClient() as client:
        resp = await client.post(state["agent_card"]["url"], json=payload)
    task = resp.json()["result"]
    status = task["status"]["state"]

    if status in ("COMPLETED", "FAILED", "CANCELED"):
        artifacts = task.get("artifacts", [])
        result_text = ""
        for art in artifacts:
            for part in art.get("parts", []):
                result_text += part.get("text", "")
        return {"result": result_text, "route": "end"}

    return {"route": "poll_task"}  # 继续轮询

# ── 构建图 ──
builder = StateGraph(A2AState)
builder.add_node("discover", discover_agent)
builder.add_node("send", send_task)
builder.add_node("poll_task", poll_task)

builder.set_entry_point("discover")
builder.add_edge("discover", "send")
builder.add_edge("send", "poll_task")
builder.add_conditional_edges("poll_task", 
    lambda s: s.get("route", "poll_task"),
    {"poll_task": "poll_task", "end": END}
)

graph = builder.compile()

    13. 关键设计原则速记¶

    原则 说明
    Simple 复用 HTTP、JSON-RPC 2.0、SSE 等已有标准
    Enterprise Ready 对齐企业安全/认证/追踪实践
    Async First 原生支持长任务和人工介入
    Modality Agnostic 支持文本、文件、结构化数据
    Opaque Execution Agent 协作不需要暴露内部逻辑

    14. 面试速记¶

    Q: 为什么说 "Agents Are Not Tools"？¶

    把 Agent 包装成 Tool 是降维使用——丧失了自主推理、多轮对话、协商反问等核心能力。 A2A 让 Agent 作为平等智能体协作，保持完整的推理和规划能力。 Tool 是"我用工具"，Agent 是"我和同事合作"。

    Q: A2A 和 MCP 什么区别？¶

    MCP 是 Agent → Tool（用工具），A2A 是 Agent → Agent（Agent 间协作）。
    MCP 处理无状态函数调用，A2A 处理有状态多轮任务。两者互补，一个完整系统可以同时使用。

    Q: A2A 的核心数据结构有哪些？¶

    Agent Card（发现）、Task（有状态工作单元）、Message（单次通信）、Part（内容单元）、Artifact（产出物）。

    Q: A2A 支持哪些通信模式？¶

    同步请求/响应、SSE 流式推送、Webhook 异步推送、轮询查询。

    Q: Task 完成后能继续发消息吗？¶

    不能。Task 进入终态（COMPLETED/FAILED/CANCELED/REJECTED）后不可变。后续交互需要创建新 Task（同一个 contextId 下）。

    Q: Agent 怎么发现其他 Agent？¶

    三种方式：Well-Known URI（公开）、注册中心（企业/市场）、直接配置（私有）。

    Q: A2A 怎么保证安全？¶

    HTTPS 传输、Agent Card 声明认证方案（OAuth2/JWT）、身份通过 HTTP Header 传递（不在 Payload）、基于 Skill 的授权。
