    A2A 进阶补充 — Agent Stack、生态集成与核心理念¶

    基于官网最新更新补充：Agent Stack 全景、ADK 集成、IBM ACP / Cisco agntcy 生态，以及 "Agents Are Not Tools" 核心理念。 配合 11-A2A_Protocol.md 和 A2A_Learning.md 构成完整的 A2A 学习路径。

    1. Agent Stack 全景图¶

    官网更新后明确定位了 A2A 在整个 AI Agent 技术栈中的位置：

    ┌─────────────────────────────────────────────────────────────┐
│                      User / Human                           │
│                          ↕                                  │
├─────────────────────────────────────────────────────────────┤
│  Layer 4: Inter-Agent Communication                         │
│  A2A Protocol                                                │
│  "Agent ↔ Agent 协作"                                        │
│  ↳ 跨组织、跨框架、跨供应商                                    │
├─────────────────────────────────────────────────────────────┤
│  Layer 3: Agent Frameworks                                   │
│  ADK (Google) / LangGraph / CrewAI / Semantic Kernel / 自研   │
│  "怎么构建 Agent"                                             │
├─────────────────────────────────────────────────────────────┤
│  Layer 2: Tool & Resource Access                            │
│  MCP (Model Context Protocol)                                │
│  "Agent ↔ Tool/数据"                                        │
│  ↳ 数据库、API、文件系统、搜索...                              │
├─────────────────────────────────────────────────────────────┤
│  Layer 1: Foundation Models                                  │
│  Gemini / GPT / Claude / Qwen / Llama / ...                 │
│  "推理引擎"                                                   │
└─────────────────────────────────────────────────────────────┘

    一句话理解每层：

    层 协议/工具 类比 解决什么
    L4 互 Agent A2A 电话会议 Agent 之间怎么对话协作
    L3 框架构建 ADK/LangGraph 工具箱 怎么搭建一个 Agent
    L2 工具接入 MCP USB 接口 Agent 怎么调用外部工具
    L1 推理引擎 LLM 大脑 怎么思考和生成内容

    关键洞察：A2A 不是替代 MCP，也不是替代 LangGraph，而是在更高层次上让它们协同工作。

    2. ADK (Agent Development Kit) 与 A2A¶

    2.1 什么是 ADK？¶

    ADK 是 Google 开源的 Agent 开发套件，类似 LangGraph/CrewAI 的 Agent 构建框架。

    特点：

    • 为 Gemini AI 和 Google 生态做了优化
    • 模型无关：可以接任意 LLM
    • 部署无关：不绑定特定云平台
    • 兼容其他框架：可以与 LangGraph、CrewAI 等混合使用

    2.2 ADK + A2A 集成模式¶

    官方推荐的 Agent 构建公式：

    用 ADK (或任意框架) 构建 Agent
    +
用 MCP (或任意工具集) 接入工具
    +
用 A2A 与远程 Agent、本地 Agent、人类通信
    =
完整的 Agentic 应用

    2.3 ADK Agent 暴露为 A2A 端点¶

    3. A2A 生态集成¶

    官网首页新增了与以下项目的集成说明：

    3.1 IBM ACP (Agent Communication Protocol)¶

    • 已并入 A2A 协议
    • IBM 的 beehive 项目（i-am-bee）中的 Agent 通信协议已合并到 A2A 规范中
    • 这意味着 A2A 现在吸收了 IBM 在 Agent 互操作方面的实践经验
    • GitHub 讨论：https://github.com/orgs/i-am-bee/discussions/5

    3.2 Cisco agntcy (Internet of Agents)¶

    Cisco 提供的 Agent 基础设施组件：

    组件 作用
    Discovery Agent 发现与注册
    Group Communication 群组通信（多对多）
    Identity Agent 身份管理
    Observability 监控与追踪

    与 A2A 的关系：

    • agntcy 使用 A2A 作为 Agent 间通信协议
    • 使用 MCP 作为工具调用协议
    • agntcy 提供的是基础设施层，A2A/MCP 是应用层协议

    4. "Agents Are Not Tools" — 核心理念展开¶

    这是 A2A 存在的根本理由，官网专门有一篇讨论文章： https://discuss.google.dev/t/agents-are-not-tools/192812

    4.1 为什么把 Agent 包装成 Tool 是错误的？¶

    ❌ 错误做法：把 Agent 包装成 MCP Tool
┌──────────┐     MCP      ┌──────────────┐
│  Agent A │────────────→│  Agent B      │
│          │  tool_call   │ (被包装成 Tool)│
│          │←────────────│              │
│          │  result      │              │
└──────────┘              └──────────────┘

问题：
  - Agent B 变成了无状态函数，丧失了自主推理能力
  - 无法进行多轮对话（比如确认细节、协商方案）
  - Agent B 无法主动反问或要求补充信息
  - 一次调用只能返回一次结果

    ✅ 正确做法：A2A Agent-to-Agent 通信
┌──────────┐     A2A      ┌──────────────┐
│  Agent A │────────────→│  Agent B      │
│          │  Task/Sub   │ (保持 Agent)  │
│          │←────────────│              │
│          │  Stream/    │  自主推理     │
│          │  Artifact   │  多轮交互     │
└──────────┘              │  协商/反问    │
                          └──────────────┘

优势：
  - Agent B 保持完整的自主推理能力
  - 支持多轮对话（确认、协商、补充信息）
  - 支持流式输出和异步长任务
  - Agent B 可以产出多个 Artifact（文档、数据、建议）

    4.2 Tool vs Agent 对比¶

    维度 Tool Agent
    本质 原语（Primitive） 自治系统（Autonomous System）
    状态 通常无状态 有状态（维护对话上下文）
    交互 一次调用，返回结果 多轮对话、协商、反问
    能力 执行特定函数 推理、规划、使用多个工具
    输入/输出 结构化 schema 灵活（文本、文件、结构化数据）
    透明度 对调用方完全透明 不透明执行（Opaque）
    类比 计算器、数据库查询 同事、合作伙伴

    4.3 面试加分话术¶

    "很多项目把 Agent 包装成 Tool 来调用，这本质上是降维使用——把有自主推理能力的智能体退化为无状态函数。 A2A 的核心理念就是 Agent ≠ Tool：Agent 应该作为平等的智能体协作，保持其推理、规划、多轮对话的完整能力。 MCP 解决 'Agent 用什么工具'，A2A 解决 'Agent 怎么和其他 Agent 合作'。两者缺一不可。"

    5. 更丰富的实战场景¶

    5.1 汽车修理店案例（官网精选）¶

    这个案例比旅行规划更能体现 A2A 的多层次协作：

    🧑 顾客 (Customer)
  │
  │ A2A: "我的车有异响"
  ▼
🤖 店长 Agent (Shop Manager)
  │
  │ A2A: "能发段异响视频吗？漏油多久了？"
  │ (多轮对话诊断)
  ▼
🤖 技师 Agent (Mechanic)
  │
  ├── MCP → 车辆诊断扫描仪: scan_vehicle_for_error_codes(vehicle_id='XYZ123')
  ├── MCP → 维修手册数据库: get_repair_procedure(error_code='P0300', make='Toyota')
  ├── MCP → 举升机工具: raise_platform(height_meters=2)
  │
  │ A2A: "需要零件 #12345，2018 Camry 有货吗？"
  ▼
🤖 零件供应商 Agent (Parts Supplier)
  │
  │ A2A: "有货，下单确认"
  │
  └── (订单处理)

    这个案例的亮点：

    交互层 协议 说明
    顾客 ↔ 店长 A2A 多轮对话，确认问题
    店长 ↔ 技师 A2A 任务委派，进度跟踪
    技师 ↔ 工具 MCP 调用诊断设备、查询数据库
    技师 ↔ 供应商 A2A Agent 间协商下单

    一句话总结：A2A 处理高层次的对话式、任务式协作；MCP 处理 Agent 内部的工具调用。

    6. A2A Skill 的 MCP 资源映射¶

    官网提到一个有趣的能力：A2A Server 可以把部分 Skill 暴露为 MCP 兼容资源。

    ┌────────────────────────────────────────────┐
│              A2A Server                     │
│                                            │
│  Skill A: 复杂多轮任务 ───→ A2A Task       │
│    (需要协商、多轮交互)                       │
│                                            │
│  Skill B: 简单查询 ───────→ MCP Resource   │
│    (无状态、可工具化)                        │
│                                            │
│  Skill C: 混合模式                          │
│    A2A 主通道 + MCP 辅助资源                │
└────────────────────────────────────────────┘

    适用场景：

    • 当 Agent 的某些技能确实适合无状态工具调用时
    • 其他 Agent 可以通过 MCP-style 方式发现并调用这些技能
    • 但这不是 A2A 的主要场景，只是一种兼容能力
