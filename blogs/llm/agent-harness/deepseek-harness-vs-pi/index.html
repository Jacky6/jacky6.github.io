    一、DeepSeek Harness：Everything is a Plugin¶

    底层是 Cordis 框架（配套论文《A Programming Paradigm for Spatiotemporal Composability》）。一句话：没有特权核心，产品的每一部分都是插件。

    1.1 一切皆插件，连 agent loop 也是¶

    模型适配器、工具注册表、会话日志、agent loop 本身都是插件，都能从配置替换。扩展方式不是在核心打补丁，而是"在旁边挂一个插件"；注册本身是可回滚的 effect，插件卸载时自动撤销。

    1.2 Profile + Bundle：配置即架构¶

    一次运行 = 启动时按序组装的插件树：

    层叠顺序（后者覆盖前者）：
profile 里的 bundles（按声明顺序）
  → profile 级 cordis.patch.yml
  → home 级 cordis.patch.yml
  → --patch 命令行覆盖
    • profile：命名的组合（web、headless 两个模板），存在 Harness home 里
    • bundle：Cordis 配置行 + 代码的发行格式，在 package.json 的 dsh 字段声明
    • dsh-base 是所有 profile 的第一层（模型适配器/工具/持久化/沙箱与审批策略/设置/凭证/遥测）；dsh-web-app 加浏览器应用；dsh-headless 加无服务器一次性 runner
    • dsh --profile web --dump-config 打印当前机器真实启动的树——任何一行配置都能被你的 patch 替换，且可审计

    1.3 Capability Seams（能力接缝）¶

    每个能力三角色：Service Definition（接口声明）、Service Provider（实现）、Consumer（通常是面向模型的工具）。单独一个角色不构成 seam。

    "Seams are why one provider swap changes the whole product."

    例：文件系统和子进程的 provider 共享一个执行世界，把它们指向远程沙箱，Bash、PTY、LSP 就整体跟着搬家，消费方零改动。Subagent provider 同样在一个接口后面变化巨大（从新建子 agent 到委托给另一个产品的一个 turn）。

    1.4 会话日志 = 唯一事实源 + 运行时不变式¶

    • append-only 的 SessionEvent 日志；模型看到的历史由 deriveMessages() 从日志投影出来
    • fork、resume、转写、遥测、持久化全部从这条流派生；原始 assistant/chunk 事件保留重放与 UI 保真度
    • 最硬的设计原则："Model-visible means logged"——凡是到达模型请求的东西必须能从日志重建，运行时断言强制检查。所以新的模型可见输入 = 新的 session event 类型（扩展 SessionEventMap）

    1.5 事件系统分域，拦截点推到"模型看见之前"¶

    域 语义 例子
    Session events 持久事实，写进日志并广播 turn/*、step/*、user/message、assistant/*、tool/*
    Agent events 观察/拦截在途工作 agent/pre-step、agent/request、inbox、status、continuation
    Capability events 给接缝挂策略/适配器 fs/*、tools/*、telemetry/*

    agent/pre-step、agent/request、llm/stream、tools/* 是 waterfall 事件（监听者必须调 next() 委托）——可以改写甚至拒绝模型将要看到的消息。被拒绝的 claim 仍会留下一个"没花 step 的 turn"记录，日志不丢事实。

    1.6 Turn/Step 模型¶

    一个 step = 一次模型请求 + 它调的工具；一个 turn = 零或多个 step。流程：turn/start → claim 输入 → 组装 prompt sections + tool schemas → agent/pre-step（可拒绝）→ step/start → agent/request → llm/stream → assistant/chunk* → tool/call* → tools/pre-execute → tools/execute → tools/post-execute → tool/result* → step/end → 还有欠的请求就下一个 step → agent/turn-stopping → turn/end。

    1.7 短板¶

    • 概念门槛高：要先学 Cordis（有 primer 和 tutorial，但毕竟是额外负担）
    • developer preview 阶段，官方明说会破坏兼容
    • 全插件化 → 调试前得先搞清当前这棵树怎么组装出来的

    二、Pi：激进的极简主义 + 自扩展¶

    一句话：核心只做最少的事，缺的都长在外面。"Adapt pi to your workflows, not the other way around, without having to fork."

    2.1 包结构（5 个可独立发布的 npm 包）¶

    包 职责
    pi-ai 统一多 provider LLM API（OpenAI/Anthropic/Google/...），本身就是独立产品
    pi-agent-core agent 运行时：工具调用 + 状态管理
    pi-coding-agent 交互式编码 CLI
    pi-tui 差分渲染的终端 UI 库（可单独复用）
    pi-telemetry 厂商中立遥测契约 + 参考适配器 + 一致性测试 + 类型化 schema

    2.2 哲学：明确列出"不做什么"¶

    默认只给模型 4 个工具：read / write / edit / bash。然后 README 里明说：

    • No MCP——写带 README 的 CLI 工具当 skill，或写 extension 加 MCP 支持（作者专文论证：《What if you don't need MCP?》）
    • No sub-agents——实现方式太多：tmux 起 pi 实例、extension 自建、装第三方包
    • No permission popups——跑容器里，或 extension 自建确认流
    • No plan mode——把计划写文件里，或自建

    四种运行形态：interactive / print+JSON / RPC（进程集成）/ SDK（嵌入应用）。

    2.3 TypeScript Extensions：真正的逃生舱¶

    export default function (pi: ExtensionAPI) {
  pi.registerTool({ name: "deploy", ... });
  pi.registerCommand("stats", { ... });
  pi.on("tool_call", async (event, ctx) => { ... });
}

    能做：自定义工具（或整体替换内置工具）、sub-agents、plan mode、自定义 compaction、权限门与路径保护、自定义编辑器/UI 组件、状态栏。extension 工厂可以是 async（启动前等初始化完成，比如先拉远程模型列表）。

    扩展分发的单位是 Pi Package（npm 或 git），skills（遵循 agentskills.io 标准）、prompt templates、themes 都走同一渠道。

    2.4 会话：JSONL 树，一个 parentId 解决分叉¶

    每条记录带 id + parentId，原地分叉不产生新文件：

    • pi -c 续最近会话；pi -r 浏览选择；--fork <path|id> 从历史点开叉
    • /tree 树内导航（折叠/跳转/过滤模式/书签标签），/fork 从任意历史用户消息开新分支，/clone 复制当前分支
    • Compaction：自动触发（接近上限时主动、溢出时恢复重试），有损但完整历史留在 JSONL 可回看；行为可被 extension 自定义
    • footer 常驻显示 token/cache 用量（↑输入 ↓输出 R 缓存读 W 缓存写 CH 命中率）+ 花费 + 上下文占用

    2.5 Provider 覆盖（同类最全）¶

    30+ provider：Anthropic / OpenAI / Azure / DeepSeek / Google+Vertex / Bedrock / Mistral / Groq / Cerebras / xAI / OpenRouter / ZAI / Kimi / MiniMax / 小米 MiMo / HuggingFace 等。支持订阅登录（/login：Claude Pro/Max、ChatGPT Plus/Pro、GitHub Copilot），也支持 llama.cpp 本地路由。模型目录自动刷新（pi update --models 强制）。

    2.6 供应链安全（多数 agent 项目完全不管的领域）¶

    • 直接依赖精确钉版（save-exact=true）；内部 workspace 包才用版本区间
    • min-release-age=2：npm 解析时排除发布不足 2 天的版本（防当天投毒）
    • package-lock.json 是唯一事实来源，pre-commit 拦截意外 lockfile 提交
    • 发布的 CLI 带 npm-shrinkwrap.json 钉住传递依赖；生命周期脚本有显式白名单，新 lifecycle-script 依赖不通过检查
    • CI npm ci --ignore-scripts + 定期 npm audit --omit=dev + npm audit signatures
    • release 冒烟测试在仓库外做隔离安装

    2.7 安全立场：诚实¶

    README 明说没有内置权限系统（不限制文件/进程/网络/凭证），默认以启动用户的权限运行。要更强边界就容器化，文档给三种模式：

    1. Gondolin extension：pi 和 provider 认证留在宿主，内置工具与 ! 命令路由进本地 Linux micro-VM
    2. 纯 Docker：整个 pi 进容器
    3. OpenShell：策略控制的沙箱

    2.8 数据飞轮¶

    公开号召用户把 OSS 工作会话发布到 HuggingFace（配 pi-share-hf 工具）；维护者自己定期发布 pi-mono 会话数据集。理由：真实开发流数据（工具使用、失败、修复）比玩具 benchmark 更有价值。

    2.9 短板¶

    • 无内置权限 = 裸跑安全性全靠自己
    • 功能靠 extension 拼 = 体验取决于生态成熟度
    • 新贡献者 issue/PR 默认自动关闭（维护者每日复审）——刻意的高参与门槛

    三、对照总结¶

    维度 DeepSeek Harness Pi
    赌注 最大化可组合：一切皆插件，配置即架构 最小化核心：4 工具 + 逃生舱
    Agent loop 是插件，可被整个替换 是核心包（pi-agent-core），稳定不动
    会话 事件溯源日志 + 投影 + 运行时不变式（重，白送 fork/replay/审计） JSONL 树，parentId 原地分叉（轻）
    拦截/审批 waterfall 事件，agent/pre-step 能改模型看到的内容 extension 事件钩子；权限外推给容器
    扩展分发 bundle + profile（配置层叠） pi package（npm/git，代码分发）
    配置系统 层叠 patch 代数，--dump-config 可审计 全局/项目两级 settings.json + extension
    可观测 telemetry 是 capability seam 之一 pi-telemetry 独立包，厂商中立契约
    成熟度 developer preview，破坏性变更 v0.84，核心稳定高频发布
    安全 沙箱/审批策略是内置 bundle 的一部分 明说不做，给容器化路径

    殊途同归：两者都把 agent loop 做成了可替换/可编程的部件（插件 vs 独立包+SDK/RPC），都把会话做成了可分叉的结构（事件溯源 vs 树形 JSONL），都认真做了遥测。分歧只在"复杂度放在核心还是放在生态"。

    四、与 TinyCoder 教程（build-your-own-coder）的映射¶

    TinyCoder 手写 dsh pi
    P2 while 循环 + MAX_ITERATIONS loop 是插件，可替换 pi-agent-core 独立包
    P5 PermissionEngine 三模式 + fail-closed 沙箱与审批策略是 dsh-base 的内置行 不做，外推容器（立场诚实）
    P7 session.py 快照持久化 事件溯源 + "model-visible means logged" 不变式 JSONL 树 + parentId 分叉
    P9 MCP 客户端 模型适配器/工具走 seam "No MCP"，CLI+README 或 extension
    P10 hooks（pre/post_tool_use） waterfall 事件，拦截点提前到模型可见前 pi.on("tool_call") 事件钩子
    P10 四层配置合并 profile/bundle/patch 层叠（同思想的重装备版） 全局/项目两级 JSON
    P10 JsonLogger telemetry capability seam pi-telemetry 契约包
    P10 --print headless dsh-headless bundle print/JSON/RPC/SDK 四形态
    P11 checkpointer/SqliteSaver 会话日志派生一切 session-backends 包（可换后端）

    结论：手写一遍再看这两个项目，每个设计决策都能对号入座——dsh 回答的是"如何把 agent 做成可组合的平台"，pi 回答的是"如何把 agent 做成不会过时的内核"。
