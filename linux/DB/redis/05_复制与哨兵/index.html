05_复制与哨兵

详解 Redis 主从复制、哨兵模式，实现高可用架构

1. 主从复制

1.1 概述

主从复制是 Redis 高可用的基础，支持一主多从、链式复制。

架构示例：
         ┌─────────────┐
         │   Master    │
         │ 192.168.1.10│
         │   :6379     │
         └──────┬──────┘
                │
       ┌────────┼────────┐
       │        │        │
       ▼        ▼        ▼
┌──────────┐ ┌──────────┐ ┌──────────┐
│  Slave1  │ │  Slave2  │ │  Slave3  │
│192.168.1.11│ │192.168.1.12│ │192.168.1.13│
│  :6379   │ │  :6379   │ │  :6379   │
└──────────┘ └──────────┘ └──────────┘

1.2 复制特点

特性 说明
异步复制 主库写入后异步同步到从库
一主多从 一个主库可以有多个从库
链式复制 从库可以有从库（A→B→C）
读写分离 主库写，从库读
故障恢复 从库可提升为主库

1.3 配置主从

（1）从库配置

# redis-slave.conf

# 指定主库地址
replicaof 192.168.1.10 6379

# 主库密码（如果设置了）
masterauth your-master-password

# 从库只读（默认 yes）
replica-read-only yes

# 从库优先级（用于哨兵选举）
replica-priority 100

# 从库端口（如果和主库同机）
port 6380

（2）动态配置

# 在从库上执行
127.0.0.1:6380> SLAVEOF 192.168.1.10 6379
OK

# 断开复制（变为独立主库）
127.0.0.1:6380> SLAVEOF NO ONE
OK

1.4 复制过程

1. 从库连接主库
      ↓
2. 从库发送 PSYNC 命令
      ↓
3. 主库执行 BGSAVE 生成 RDB
      ↓
4. 主库发送 RDB 给从库
      ↓
5. 从库加载 RDB
      ↓
6. 主库发送缓冲区写命令
      ↓
7. 从库执行命令，数据一致
      ↓
8. 持续同步（命令流）

1.6 全量复制 vs 增量复制

类型 触发条件 命令
全量复制 首次复制、断开重连、ID 不匹配 PSYNC ? -1
增量复制 网络闪断、ID 匹配 PSYNC

1.7 读写分离

# Python 示例：读写分离
import redis

# 主库（写）
master = redis.Redis(host='192.168.1.10', port=6379, db=0)

# 从库（读）
slave1 = redis.Redis(host='192.168.1.11', port=6379, db=0)
slave2 = redis.Redis(host='192.168.1.12', port=6379, db=0)

# 写操作
master.set('user:1001:name', '张三')

# 读操作（从从库）
name = slave1.get('user:1001:name')

# 注意：主从复制有延迟，可能读到旧数据
# 关键数据建议读主库

# 检查从库延迟

# 从库查看同步状态

master_link_status:down  # 断开

2. 哨兵模式（Sentinel）

2.1 概述

哨兵是 Redis 高可用解决方案，提供：

  • 监控：监控主从库状态
  • 通知：故障时通知管理员
  • 自动故障转移：主库故障时选举新主库
  • 配置中心：提供当前主库地址
架构示例：
         ┌─────────────┐
         │   Master    │
         │ 192.168.1.10│
         └──────┬──────┘
                │
       ┌────────┼────────┐
       ▼        ▼        ▼
┌──────────┐ ┌──────────┐ ┌──────────┐
│  Slave1  │ │  Slave2  │ │  Slave3  │
└──────────┘ └──────────┘ └──────────┘
       ▲        ▲        ▲
       │        │        │
       └────────┼────────┘
                │
       ┌────────┼────────┐
       ▼        ▼        ▼
┌──────────┐ ┌──────────┐ ┌──────────┐
│ Sentinel1│ │ Sentinel2│ │ Sentinel3│
│192.168.1.20│ │192.168.1.21│ │192.168.1.22│
└──────────┘ └──────────┘ └──────────┘

2.2 哨兵配置

# sentinel.conf

# 哨兵端口
port 26379

# 守护进程
daemonize yes

# 日志文件
logfile "/var/log/redis/sentinel.log"

# 工作目录
dir /var/lib/redis/sentinel

# 监控主库
# sentinel monitor <master-name> <ip> <port> <quorum>
sentinel monitor mymaster 192.168.1.10 6379 2

# 主库密码
sentinel auth-pass mymaster your-password

# 故障判定时间（毫秒）
# 超过此时间认为主库下线
sentinel down-after-milliseconds mymaster 5000

# 故障转移超时（毫秒）
sentinel failover-timeout mymaster 60000

# 并行同步的从库数量
sentinel parallel-syncs mymaster 1

# 通知脚本（故障时执行）
# sentinel notification-script mymaster /var/redis/notify.sh

# 客户端重定向脚本
# sentinel client-reconfig-script mymaster /var/redis/reconfig.sh

2.3 启动哨兵

# 启动哨兵
redis-sentinel /etc/redis/sentinel.conf

# 或
redis-server /etc/redis/sentinel.conf --sentinel

# 后台运行
redis-sentinel /etc/redis/sentinel.conf --daemonize yes

2.5 故障转移过程

1. 哨兵监控到主库故障
      ↓
2. 主观下线（单个哨兵判定）
      ↓
3. 客观下线（quorum 个哨兵确认）
      ↓
4. 选举领头哨兵（Raft 算法）
      ↓
5. 领头哨兵选择新主库
   - 优先级高（replica-priority）
   - 复制偏移量大（数据新）
   - 运行 ID 小
      ↓
6. 领头哨兵发送 SLAVEOF NO ONE 给新主库
      ↓
7. 其他从库复制新主库
      ↓
8. 更新配置，故障转移完成

2.6 客户端连接哨兵

# Python 示例：通过哨兵连接
from redis.sentinel import Sentinel

# 哨兵列表
sentinel = Sentinel(
    [('192.168.1.20', 26379),
     ('192.168.1.21', 26379),
     ('192.168.1.22', 26379)],
    socket_timeout=0.1
)

# 获取主库（写）
master = sentinel.master_for('mymaster', socket_timeout=0.1)

# 获取从库（读）
slave = sentinel.slave_for('mymaster', socket_timeout=0.1)

# 写操作
master.set('user:1001:name', '张三')

# 读操作（自动从从库）
name = slave.get('user:1001:name')

# 故障转移后自动重连
# 哨兵客户端会自动获取新主库地址

// Java 示例（Jedis）
import redis.clients.jedis.JedisSentinelPool;
import redis.clients.jedis.Jedis;

import java.util.HashSet;
import java.util.Set;

Set<String> sentinels = new HashSet<>();
sentinels.add("192.168.1.20:26379");
sentinels.add("192.168.1.21:26379");
sentinels.add("192.168.1.22:26379");

JedisSentinelPool pool = new JedisSentinelPool(
    "mymaster",
    sentinels,
    null,  // 连接池配置
    "password"  // 密码
);

try (Jedis jedis = pool.getResource()) {
    jedis.set("key", "value");
    String val = jedis.get("key");
}

3. 高可用架构

3.1 架构对比

架构 节点数 可用性 复杂度 适用场景
单机 1 低 低 开发测试
主从 2+ 中 低 读写分离
哨兵 3+ 高 中 高可用
集群 6+ 高 高 大规模

3.2 推荐配置

小型应用（主从 + 哨兵）

3 个哨兵 + 1 主 2 从 = 6 个节点

Sentinel1 (26379) ─┐
Sentinel2 (26379) ─┼── 监控 ── Master (6379)
Sentinel3 (26379) ─┘              │
                           ┌──────┴──────┐
                           ▼             ▼
                       Slave1(6380)  Slave2(6381)

中型应用（多主从 + 哨兵）

3 个哨兵 + 2 主 4 从 = 9 个节点

                    Master1 (6379) ── Slave1 (6380)
                    │
3 个哨兵 ── 监控 ──┤
                    │
                    Master2 (6381) ── Slave2 (6382)

3.3 部署脚本

#!/bin/bash
# deploy-redis-ha.sh - 部署 Redis 高可用架构

# 主库配置
MASTER_HOST="192.168.1.10"
MASTER_PORT="6379"

# 从库配置
SLAVE1_HOST="192.168.1.11"
SLAVE2_HOST="192.168.1.12"

# 哨兵配置
SENTINEL1_HOST="192.168.1.20"
SENTINEL2_HOST="192.168.1.21"
SENTINEL3_HOST="192.168.1.22"
SENTINEL_PORT="26379"
QUORUM=2

# 部署主库
echo "Deploying Master..."
ssh $MASTER_HOST "redis-server /etc/redis/redis.conf"

# 部署从库
echo "Deploying Slaves..."
ssh $SLAVE1_HOST "redis-server /etc/redis/redis-slave.conf"
ssh $SLAVE2_HOST "redis-server /etc/redis/redis-slave.conf"

# 部署哨兵
echo "Deploying Sentinels..."
for host in $SENTINEL1_HOST $SENTINEL2_HOST $SENTINEL3_HOST; do
    cat > /tmp/sentinel.conf <<EOF
port $SENTINEL_PORT
daemonize yes
logfile "/var/log/redis/sentinel.log"
dir /var/lib/redis/sentinel
sentinel monitor mymaster $MASTER_HOST $MASTER_PORT $QUORUM
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 60000
sentinel parallel-syncs mymaster 1
EOF
    scp /tmp/sentinel.conf $host:/etc/redis/sentinel.conf
    ssh $host "redis-sentinel /etc/redis/sentinel.conf"
done

echo "Deployment complete!"

4. 常见问题

Q1: 哨兵为什么至少需要 3 个？

A: 哨兵需要 quorum（法定人数）判定主库下线。如果只有 2 个哨兵： - quorum=1：容易误判 - quorum=2：一个哨兵故障就无法故障转移

3 个哨兵可以容忍 1 个故障，推荐奇数个哨兵。

Q2: 主从复制延迟怎么解决？

A: 1. 检查网络带宽 2. 减少主库写压力 3. 增加从库数量分散读压力 4. 使用更强大的硬件 5. 监控 lag 指标

Q3: 脑裂问题如何解决？

A: 脑裂（Split-Brain）发生在网络分区时：

配置参数：
min-slaves-to-write 1      # 至少 1 个从库才接受写
min-slaves-max-lag 10      # 从库延迟不超过 10 秒

Q4: 如何平滑扩容从库？

A:

# 1. 启动新从库
redis-server /etc/redis/redis-slave.conf

# 2. 动态添加为主库的从库
127.0.0.1:6380> SLAVEOF 192.168.1.10 6379

# 3. 哨兵会自动发现新从库

Q5: 哨兵配置文件中的 quorum 是什么？

A: quorum 是判定主库下线所需的最少哨兵数量。

3 个哨兵，quorum=2：至少 2 个哨兵认为主库下线，才触发故障转移
5 个哨兵，quorum=3：至少 3 个哨兵认为主库下线，才触发故障转移
