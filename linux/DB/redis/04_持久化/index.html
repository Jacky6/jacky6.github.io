04_持久化

Redis 是内存数据库，持久化用于防止数据丢失。详解 RDB 和 AOF 两种持久化方式。

1. 持久化概述

1.1 为什么需要持久化？

Redis 数据存储在内存中 → 断电/重启会导致数据丢失
          ↓
    持久化到磁盘
          ↓
    重启时恢复数据

1.2 两种持久化方式

特性 RDB AOF
全称 Redis Database Backup Append Only File
原理 数据快照 记录写命令
文件 dump.rdb appendonly.aof
密度 紧凑、二进制 较大、文本
恢复速度 快 慢
数据完整性 可能丢失最后一次快照后的数据 可配置丢失秒数
适用场景 备份、快速恢复 高数据安全性

2. RDB（快照）

2.1 工作原理

触发 RDB 快照
      ↓
fork() 子进程
      ↓
子进程写入临时文件
      ↓
写入完成，替换旧 RDB 文件
      ↓
主进程继续服务（无阻塞）

2.2 触发方式

（1）自动触发（配置文件）

# redis.conf

# 900 秒内至少 1 个 key 变化
save 900 1

# 300 秒内至少 10 个 key 变化
save 300 10

# 60 秒内至少 10000 个 key 变化
save 60 10000

# RDB 文件名
dbfilename dump.rdb

# 工作目录
dir /var/lib/redis

# 压缩 RDB 文件
rdbcompression yes

# RDB 校验和
rdbchecksum yes

# 停止保存（禁用 RDB）
# save ""

（2）手动触发

# 阻塞式保存（生产环境慎用）
127.0.0.1:6379> SAVE
OK

# 非阻塞式保存（推荐）
127.0.0.1:6379> BGSAVE
Background saving started

# 查看保存进度
127.0.0.1:6379> LASTSAVE
(integer) 1711353600  # Unix 时间戳

# 查看持久化状态
127.0.0.1:6379> INFO persistence
# Persistence
loading:0
current_cow_size:0
rdb_changes_since_last_save:15
rdb_bgsave_in_progress:0
rdb_last_save_time:1711353600
rdb_last_bgsave_status:ok

2.4 优缺点

优点 缺点
文件紧凑，适合备份 可能丢失最后一次快照后的数据
恢复速度快 fork() 时可能阻塞（大数据集）
性能最大化（子进程处理） 无法实时持久化

3. AOF（追加日志）

3.1 工作原理

写命令执行
      ↓
追加到 AOF 缓冲区
      ↓
根据策略刷盘
      ↓
重启时重放 AOF 恢复数据

3.2 配置选项

# redis.conf

# 启用 AOF
appendonly yes

# AOF 文件名
appendfilename "appendonly.aof"

# 同步策略
# always: 每次写入都同步（最安全，性能最差）
# everysec: 每秒同步一次（推荐，丢失最多 1 秒数据）
# no: 由操作系统决定何时同步（性能最好，可能丢失较多）
appendfsync everysec

# AOF 重写时是否禁用同步
no-appendfsync-on-rewrite no

# 自动重写触发条件
# 当前 AOF 文件大小比上次重写后增长 100%
# 且 AOF 文件至少 64MB
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb

# 加载损坏的 AOF 文件
aof-load-truncated yes

# 使用 RDB 前缀加速加载
aof-use-rdb-preamble yes

3.3 AOF 重写

问题：AOF 文件会越来越大（如 INCR 命令记录 100 次）

解决：AOF 重写，将多次操作合并为一条

# 手动触发重写
127.0.0.1:6379> BGREWRITEAOF
Background append only file rewriting started

# 查看重写状态
127.0.0.1:6379> INFO persistence
# Persistence
aof_enabled:1
aof_rewrite_in_progress:0
aof_last_rewrite_time_sec:5
aof_current_rewrite_time_sec:-1
aof_last_bgrewrite_status:ok
aof_last_write_status:ok

重写过程：

原始 AOF：
SET count 0
INCR count  → 1
INCR count  → 2
INCR count  → 3
...
INCR count  → 100

重写后 AOF：
SET count 100

3.5 优缺点

优点 缺点
数据安全性高 文件较大
可配置丢失秒数 恢复速度慢于 RDB
追加写，不易损坏 性能略低于 RDB

4. 混合持久化（Redis 4.0+）

4.1 原理

结合 RDB 和 AOF 的优点：

AOF 重写时：
┌─────────────────────────────────────┐
│ RDB 格式（现有数据快照）             │
├─────────────────────────────────────┤
│ AOF 格式（增量写命令）               │
└─────────────────────────────────────┘

4.2 配置

# 启用混合持久化
aof-use-rdb-preamble yes

4.3 优势

特性 传统 AOF 混合持久化
文件大小 大 小
加载速度 慢 快
数据完整性 高 高
兼容性 所有版本 Redis 4.0+

5. 持久化策略选择

5.1 场景推荐

场景 推荐方案 配置建议
缓存（可丢失） 禁用持久化 save "", appendonly no
一般业务 RDB + AOF 默认配置
高数据安全 AOF everysec appendfsync always
高性能 RDB 为主 延长 save 间隔
大数据集 混合持久化 aof-use-rdb-preamble yes

5.2 生产环境配置示例

# ==================== 持久化配置 ====================

# RDB 快照（适度频率）
save 900 1
save 300 10
save 60 10000

# RDB 文件
dbfilename dump.rdb
dir /data/redis

# AOF 持久化
appendonly yes
appendfilename "appendonly.aof"
appendfsync everysec

# AOF 重写
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb

# 混合持久化（加速加载）
aof-use-rdb-preamble yes

# 安全选项
no-appendfsync-on-rewrite no
aof-load-truncated yes

6. 备份与恢复

6.1 备份策略

#!/bin/bash
# backup-redis.sh - Redis 备份脚本

BACKUP_DIR="/backup/redis"
DATE=$(date +%Y%m%d_%H%M%S)
REDIS_DIR="/var/lib/redis"

# 创建备份目录
mkdir -p $BACKUP_DIR

# 触发 BGSAVE
redis-cli BGSAVE

# 等待保存完成
sleep 5

# 复制 RDB 文件
cp $REDIS_DIR/dump.rdb $BACKUP_DIR/dump_$DATE.rdb

# 复制 AOF 文件（如果启用）
if [ -f "$REDIS_DIR/appendonly.aof" ]; then
    cp $REDIS_DIR/appendonly.aof $BACKUP_DIR/appendonly_$DATE.aof
fi

# 压缩备份
cd $BACKUP_DIR
tar -czf redis_backup_$DATE.tar.gz dump_$DATE.rdb appendonly_$DATE.aof 2>/dev/null

# 删除旧备份（保留 7 天）
find $BACKUP_DIR -name "redis_backup_*.tar.gz" -mtime +7 -delete

echo "Backup completed: redis_backup_$DATE.tar.gz"

6.2 恢复数据

# 方式 1：恢复 RDB
# 1. 停止 Redis
sudo systemctl stop redis

# 2. 替换 RDB 文件
cp /backup/redis/dump_20240325_100000.rdb /var/lib/redis/dump.rdb

# 3. 启动 Redis
sudo systemctl start redis

# 方式 2：恢复 AOF
# 1. 停止 Redis
sudo systemctl stop redis

# 2. 替换 AOF 文件
cp /backup/redis/appendonly_20240325_100000.aof /var/lib/redis/appendonly.aof

# 3. 启动 Redis
sudo systemctl start redis

# 方式 3：从 RDB+AOF 混合恢复
# 同时替换两个文件，Redis 会优先加载 AOF

6.3 故障恢复流程

1. 检查持久化文件状态
   $ redis-check-rdb dump.rdb
   $ redis-check-aof --fix appendonly.aof

2. 查看 Redis 日志
   $ tail -100 /var/log/redis/redis-server.log

3. 尝试启动 Redis
   $ redis-server /etc/redis/redis.conf

4. 检查数据完整性
   $ redis-cli
   > DBSIZE
   > KEYS *
   > INFO persistence

7. 性能影响

7.1 RDB 性能

fork() 时的影响：
- 小数据集（<1GB）：几乎无感知
- 大数据集（>10GB）：可能短暂阻塞（毫秒级）

写入磁盘：
- 子进程完成，主进程无阻塞
- 磁盘 I/O 不影响 Redis 性能

7.2 AOF 性能

appendfsync always:
- 每次写入都 fsync
- 延迟：~1ms/写
- 吞吐量：~1000 写/秒

appendfsync everysec（推荐）:
- 每秒 fsync 一次
- 延迟：正常 <1ms，fsync 时可能 2ms
- 吞吐量：~10000 写/秒

appendfsync no:
- 由 OS 决定
- 延迟：最低
- 风险：可能丢失较多数据

7.3 监控指标

# 查看持久化相关指标
127.0.0.1:6379> INFO persistence

# 关键指标
rdb_changes_since_last_save  # 自上次保存后的变化数
rdb_last_bgsave_time_sec     # 上次保存耗时
aof_current_size             # 当前 AOF 大小
aof_last_rewrite_time_sec    # 上次重写耗时

8. 常见问题

Q1: RDB 和 AOF 同时启用，恢复时用哪个？

A: Redis 启动时优先加载 AOF，因为 AOF 数据更完整。

Q2: AOF 文件太大怎么办？

A: 1. 触发 BGREWRITEAOF 重写 2. 调整 auto-aof-rewrite-percentage 3. 启用混合持久化

Q3: 如何禁用持久化？

A:

save ""
appendonly no

Q4: 持久化导致性能下降？

A: 1. 使用 SSD 磁盘 2. 调整 save 频率 3. AOF 使用 everysec 而非 always 4. 避免大数据集频繁 fork()

Q5: 如何迁移 Redis 数据？

A:

# 方式 1：复制持久化文件
scp dump.rdb appendonly.aof new-server:/var/lib/redis/

# 方式 2：使用 redis-cli --rdb
redis-cli --rdb /tmp/dump.rdb

# 方式 3：在线同步（使用主从复制）
